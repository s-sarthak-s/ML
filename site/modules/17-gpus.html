Module 17 · Inference eng. I

GPUs and accelerators: the machine under the model

An H100 can do close to 1015 bf16 operations per second, yet a chatbot answering one user on it keeps the arithmetic units busy well under 1% of the time. The rest of the time it waits for memory. This module opens the box: what is on the chip, how code gets mapped onto it, why bytes matter more than FLOPs for LLM decode, and how to choose hardware by doing the arithmetic yourself instead of trusting the spec sheet's headline number.

~4 hoursprereqs: 01, 08, 09hands-on: PyTorch, CUDA C, MLX, nvidia-smi

By the end you can

  1. Sketch an H100 from memory (SMs, tensor cores, register file, shared memory, L2, HBM) and give each level's rough capacity and bandwidth.
  2. Explain grids, blocks, warps and SIMT, compute a global thread index, and predict when a memory access pattern wastes bandwidth.
  3. Work out occupancy from registers and shared memory, and use Little's law to say how much data must be in flight to saturate HBM.
  4. Place any matmul on a roofline from its shapes and dtype, and say whether it's compute-bound or memory-bound on a given chip.
  5. Compare PCIe, NVLink and InfiniBand transfer times, and size a deployment: memory, GPU count, a tokens/s ceiling and a rough cost per million tokens.

Why GPUs

A CPU core is built to finish one instruction stream as fast as possible. Most of its transistors go to features that cut latency: deep out-of-order pipelines, branch predictors, prefetchers, and megabytes of cache per core so that a load rarely has to wait for DRAM. A modern server CPU has a few dozen to a couple of hundred such cores.

A GPU makes the opposite bet. It spends its transistors on arithmetic lanes and very little on cleverness per lane. An H100 has 16,896 FP32 lanes and 528 tensor cores spread over 132 streaming multiprocessors. Instead of avoiding memory stalls, it hides them: each SM keeps dozens of thread groups resident and switches to another group on every cycle that one is waiting. That only works if you have tens of thousands of independent pieces of work, and a matrix multiply has millions.

LLM inference fits the GPU's bet unusually well. For every generated token, every layer does the same few things: matmuls for the Q/K/V and output projections, three matmuls in the MLP, attention over the KV cache, and some cheap elementwise work (norms, RoPE, activations). The matmuls account for almost all of the FLOPs: about \(2N\) per token for an \(N\)-parameter dense model, so roughly 16 GFLOP per token for an 8B model (Module 07 derives this). The other half of the bill is memory traffic: weights and KV cache have to stream from memory to the arithmetic units. Every chip has two speed limits, and a kernel runs into one of them first.

$$\htmlClass{t1}{t_{\text{kernel}}} \;\approx\; \max\!\left(\frac{\htmlClass{t2}{F}}{\htmlClass{t3}{P_{\text{peak}}}},\; \frac{\htmlClass{t4}{Q}}{\htmlClass{t5}{BW}}\right)$$
\(t_{\text{kernel}}\)
lower bound on how long the kernel takes
\(F\)
floating-point operations it performs (a multiply-add counts as 2)
\(P_{\text{peak}}\)
peak compute, FLOP/s (H100 SXM bf16 dense ≈ 989 TFLOP/s)
\(Q\)
bytes it must move to or from main memory
\(BW\)
main-memory bandwidth (H100 SXM ≈ 3.35 TB/s)

In wordsCompute and memory transfers overlap, so the slower one sets the pace. A kernel is memory-bound when the second term is bigger and compute-bound when the first is.

Why it mattersThis one line explains most of inference performance. The rest of the module is about the two denominators (what sets them) and about how close real code gets to them.

Think first: Llama-3-8B decoding one token at batch 1 on an H100. Which term wins, and by how much?
Weights: about 15 GB in bf16 (the matmuls touch ≈ 7.5B parameters). Memory time = 15 GB ÷ 3.35 TB/s ≈ 4.5 ms. Compute: ≈ 15 GFLOP ÷ 989 TFLOP/s ≈ 15 µs. Memory wins by a factor of about 300, which is the ridge point you'll compute in the roofline section. The tensor cores sit idle 99.7% of the step.

Anatomy of an H100

NVIDIA's Hopper die (GH100) is organised as a hierarchy. The chip contains GPCs (graphics processing clusters); each GPC contains TPCs, each with two SMs; each SM has four sub-partitions that each issue one warp instruction per clock. The full die has 144 SMs. The H100 SXM product enables 132 of them, so dies with a few defects can still ship. The specs below are approximate and specific to the SXM5 80 GB part; the PCIe card has 114 SMs and about 2 TB/s of HBM2e.

Definition · CUDA core vs tensor core

A "CUDA core" is NVIDIA's name for one FP32 lane: it does one fused multiply-add on one pair of numbers per clock. A tensor core does a small matrix multiply-accumulate per instruction, \(D = AB + C\) on tiles of several hundred elements. Per clock, one H100 tensor core does about 512 bf16 multiply-adds, while one FP32 lane does one. That's why NVIDIA's dense bf16 tensor throughput is about fifteen times its FP32 throughput.

In wordsCount the units, multiply by work per unit per tick, multiply by ticks per second. 132 × 4,096 × ~1.83 GHz ≈ 989 TFLOP/s for bf16 tensor math; 132 × 256 × ~1.98 GHz ≈ 67 TFLOP/s on the FP32 lanes.

Why it mattersThe headline number assumes every tensor core on every SM finishes an MMA every cycle at full clock. Any idle SM, stalled warp, or power-throttled clock comes straight off it, so real GEMMs land below spec and small or oddly shaped ones land far below.

Hopper added three features that matter for the kernels in Module 18. The Tensor Memory Accelerator (TMA) copies whole tiles from HBM into shared memory asynchronously, so a warp can issue one instruction and go back to math. Thread block clusters let neighbouring blocks on different SMs read each other's shared memory. And warpgroup MMA (wgmma) lets four warps (128 threads) drive the tensor cores together, reading operands straight from shared memory.

Spec sheets are per SKU and approximate

"H100" covers SXM5 (132 SMs, HBM3, 700 W), PCIe (114 SMs, HBM2e, 350 W), and the H100 NVL variant, plus export variants with cut interconnects. Peak numbers are at boost clock; sustained clocks under a heavy GEMM are often lower. Quote the exact part when you compare.

The memory hierarchy

Data that the tensor cores consume travels through a ladder of memories. Each step down gives you roughly ten to a thousand times more capacity, several times less bandwidth, and about ten times more latency. Fast kernels are mostly about keeping data on the upper rungs and reusing it there as many times as possible before it's evicted.

Intuition

Registers are the workbench under your hands. Shared memory is the shelf above the bench. L2 is the storeroom down the hall, HBM is the warehouse across the street, and host RAM is a depot across town reached by one narrow road (PCIe). A good kernel makes one trip to the warehouse per crate and then does as much work as possible at the bench.

Pitfall · CPU offload looks like it works

When a model doesn't fit, frameworks will happily keep some layers in host RAM and stream them over PCIe for every forward pass. It runs, but at 64 GB/s, 16 GB of offloaded weights costs about 0.25 s per decode step: about four tokens per second, no matter how fast the GPU is. If decode suddenly drops to single digits, check whether something got offloaded.

The CUDA programming model

A GPU program is a kernel: a function that the CPU launches over a grid of threads. The programmer chooses two numbers: how many threads go in a block (up to 1,024) and how many blocks make up the grid (effectively unlimited). Every thread runs the same function and uses its built-in coordinates (blockIdx, threadIdx) to decide which data to touch.


__global__ void vadd(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // my element
    if (i < n) c[i] = a[i] + b[i];                  // guard the ragged last block
}

int threads = 256;
int blocks  = (n + threads - 1) / threads;           // ceil(n / threads)
vadd<<<blocks, threads>>>(a, b, c, n);              // asynchronous: returns immediately
$$\htmlClass{t1}{i} = \htmlClass{t2}{\texttt{blockIdx.x}} \cdot \htmlClass{t3}{\texttt{blockDim.x}} + \htmlClass{t4}{\texttt{threadIdx.x}}, \qquad \htmlClass{t5}{\texttt{gridDim.x}} = \left\lceil \frac{\htmlClass{t6}{n}}{\htmlClass{t3}{\texttt{blockDim.x}}} \right\rceil$$
\(i\)
this thread's position in the whole problem (which array element it owns)
blockIdx.x
which block this thread belongs to: 0 … gridDim.x − 1
blockDim.x
threads per block, chosen at launch (commonly 128–512)
threadIdx.x
this thread's index inside its block: 0 … blockDim.x − 1
gridDim.x
number of blocks launched
\(n\)
problem size, e.g. elements in the vector

In wordsSkip past all the earlier blocks, then add your offset within your block. Round the block count up so every element gets a thread, and guard with if (i < n) so the extra threads in the last block do nothing.

Why it mattersWith \(n = 10^6\) and 256 threads per block, you launch 3,907 blocks. The last one has 64 threads with work and 192 that exit at the guard. Forget the guard and those threads write past the end of the array.

Warps and SIMT

The hardware doesn't schedule single threads. It groups each block into warps of 32 consecutive threads, and a warp issues one instruction at a time for all 32 lanes. NVIDIA calls this SIMT (single instruction, multiple threads). It looks like 32 independent threads in your code, since each has its own registers and can take its own branch, but the hardware runs it like a 32-wide vector unit.

The cost shows up at branches. If some lanes of a warp take the if and others take the else, the warp runs both paths one after the other with the inactive lanes masked off. That's warp divergence. if (threadIdx.x % 2) splits every warp in half and doubles the time of the branchy section. if ((threadIdx.x / 32) % 2) gives the same 50/50 split of threads but no divergence, because the condition is uniform within each warp.

Launching, and the tail effect

A kernel launch is asynchronous: the CPU enqueues it on a stream and returns, and the GPU runs launches from one stream in order. Each launch costs a few microseconds of CPU and driver time. That's negligible for a 5 ms matmul but dominant for the hundreds of tiny kernels in one decode step of a small model, which is why engines capture decode steps as CUDA graphs (Module 18).

Blocks run in waves. If each SM can hold one block of your kernel, the first 132 blocks start together and the 133rd waits for a free SM.

$$\htmlClass{t1}{\text{waves}} = \left\lceil \frac{\htmlClass{t2}{\text{blocks}}}{\htmlClass{t3}{n_{\text{SM}}} \cdot \htmlClass{t4}{b_{\text{SM}}}} \right\rceil, \qquad \htmlClass{t5}{\text{utilization}} = \frac{\htmlClass{t2}{\text{blocks}}}{\htmlClass{t1}{\text{waves}} \cdot \htmlClass{t3}{n_{\text{SM}}} \cdot \htmlClass{t4}{b_{\text{SM}}}}$$
waves
rounds of blocks the GPU needs to run them all
blocks
blocks in the grid
\(n_{\text{SM}}\)
SMs on the chip (132)
\(b_{\text{SM}}\)
blocks that fit on one SM at once (the occupancy section computes this)
utilization
fraction of SM-slots doing work, averaged over all waves

In wordsA partial last wave leaves SMs idle. 264 equal blocks at one per SM is two full waves; 133 blocks is also two waves, but the second runs on 1 SM while 131 sit idle, so utilization is about 50%.

Why it mattersGEMM libraries pick tile sizes partly to avoid bad tails, and "persistent" kernels launch exactly one block per SM and loop over tiles to sidestep the problem. A matmul whose speed jumps oddly as you change one dimension by a few rows is often hitting a wave boundary.

Coalescing and bank conflicts

HBM doesn't deliver single floats. The memory system moves data in 32-byte sectors (grouped into 128-byte cache lines), and when a warp issues a load, the hardware works out which sectors its 32 addresses touch and fetches each one once. If the 32 threads read 32 consecutive 4-byte floats, that's 128 bytes in exactly four sectors: a coalesced access with no waste. If they read every fourth float, the same 128 useful bytes are spread across sixteen sectors, and 75% of the bytes fetched are thrown away.

$$\htmlClass{t1}{BW_{\text{eff}}} = \frac{\htmlClass{t2}{\text{useful bytes}}}{\htmlClass{t3}{\text{transferred bytes}}} \times \htmlClass{t4}{BW_{\text{peak}}}$$
\(BW_{\text{eff}}\)
rate at which data your code actually uses arrives
useful bytes
bytes the threads asked for (32 threads × 4 B = 128 B per warp load)
transferred bytes
sectors touched × 32 B
\(BW_{\text{peak}}\)
what the memory system can deliver (3.35 TB/s HBM3)

In wordsEvery wasted byte in a sector still costs bandwidth. A stride of 2 floats halves effective bandwidth; a stride of 8 or more leaves one useful float per 32-byte sector, 12.5%.

Why it mattersFor a memory-bound kernel (most non-matmul ops), effective bandwidth is speed. Layouts are chosen so the innermost, fastest-varying index maps to consecutive threads: structure-of-arrays rather than array-of-structures, and KV caches laid out so a warp reads a contiguous head dimension.

Shared memory banks

Shared memory has its own rule. It's split into 32 banks, each 4 bytes wide, and successive 4-byte words go to successive banks. A warp's 32 accesses complete in one pass if they hit 32 different banks (or the same word, which is broadcast). If several threads hit different words in the same bank, those accesses are serialized: a \(k\)-way bank conflict takes \(k\) passes.

$$\htmlClass{t1}{\text{bank}} = \left\lfloor \frac{\htmlClass{t2}{\text{addr}}}{\htmlClass{t3}{4}} \right\rfloor \bmod \htmlClass{t4}{32}$$
bank
which of the 32 banks serves this address
addr
byte address within shared memory
4
bank width in bytes
32
number of banks, matching the warp size

In wordsWord \(w\) lives in bank \(w \bmod 32\). If thread \(t\) reads word \(s\cdot t\), the conflict degree is \(\gcd(s, 32)\): stride 1 or any odd stride is conflict-free, while stride 32 sends every thread to bank 0, a 32-way conflict.

Why it mattersReading a column of a 32×32 float tile is exactly stride 32. The classic fix is to declare the tile as float tile[32][33]: one padding column shifts each row by one bank, and the column read becomes stride 33, which is odd and conflict-free.

Pitfall · transposes and permutes aren't free

In PyTorch, x.transpose(1, 2) only changes strides. The next kernel that reads it may get a strided, uncoalesced pattern, or PyTorch may insert a .contiguous() copy that costs a full read and write of the tensor. In a profiler, unexpected copy_ or elementwise_kernel entries right after a reshape are usually this.

Occupancy and latency hiding

An HBM load takes on the order of 500 ns, roughly a thousand clock cycles. A warp that needs the result stalls for that long. The SM's answer is to keep many warps resident and, on every cycle, let each scheduler issue from any warp that isn't stalled. If there are enough warps with independent work, the arithmetic units never notice the latency. How many warps an SM can keep resident is limited by its fixed pools of registers, shared memory and thread slots.

$$\htmlClass{t1}{\text{occupancy}} = \frac{\htmlClass{t2}{\text{active warps per SM}}}{\htmlClass{t3}{\text{max warps per SM}}}$$
occupancy
how full the SM's warp slots are, 0 to 100%
active warps
resident blocks × warps per block
max warps
64 on H100 (2,048 threads ÷ 32)

In wordsThe share of the SM's thread capacity your kernel actually fills. More resident warps means more candidates to switch to when one stalls.

$$\htmlClass{t1}{b_{\text{SM}}} = \min\!\left( \left\lfloor \frac{2048}{\htmlClass{t2}{T}} \right\rfloor,\; 32,\; \left\lfloor \frac{65{,}536}{\htmlClass{t3}{R}\cdot \htmlClass{t2}{T}} \right\rfloor,\; \left\lfloor \frac{228\ \text{KB}}{\htmlClass{t4}{S}} \right\rfloor \right)$$
\(b_{\text{SM}}\)
blocks of this kernel that fit on one SM at once
\(T\)

\(R\)

\(S\)

In wordsFour resources, four ceilings, and the tightest one wins. With 256 threads and 128 registers each, one block needs 32,768 registers, so only 2 blocks fit: 16 warps, 25% occupancy, even though thread slots would allow 8 blocks.

Why it mattersTo fill all 2,048 thread slots you need at most 32 registers per thread. Compilers trade registers against occupancy; __launch_bounds__ and Triton's num_warps/num_stages are the knobs.

Why do warps matter so much? Because to keep a memory pipe full, you need enough requests in flight to cover its latency. This is Little's law from queueing theory (Little, 1961), applied to bytes.

$$\htmlClass{t1}{\text{bytes in flight}} = \htmlClass{t2}{BW} \times \htmlClass{t3}{\text{latency}}$$
bytes in flight
outstanding requested-but-not-yet-arrived data needed to saturate the link
\(BW\)
bandwidth to sustain (3.35 TB/s)
latency
round-trip time of one request (~500–600 ns for HBM, approximate)

In words3.35 TB/s × 600 ns ≈ 2 MB must be requested and not yet delivered at every instant. Spread across 132 SMs, that's about 15 KB per SM, or about 30 warps per SM each waiting on a 16-byte-per-thread load (512 B per warp).

Why it mattersOccupancy is one way to get bytes in flight; issuing several independent loads per thread (instruction-level parallelism) and asynchronous copies (cp.async, TMA) are the others. A kernel with few warps and one blocking load each cannot reach peak bandwidth, however clean its access pattern.

Higher occupancy isn't always faster

Volkov (2010) showed matmul kernels beating vendor libraries at lower occupancy by giving each thread more registers and more independent work. Modern GEMMs and FlashAttention routinely run one or two large blocks per SM: they need big register and shared-memory tiles for reuse, and they get their bytes in flight from asynchronous, pipelined copies rather than from many warps. Treat occupancy as a diagnostic, not a target.

Tensor cores and number formats

A tensor core takes a small tile of \(A\), a small tile of \(B\), multiplies them, and adds the result to an accumulator tile \(C\), all in one instruction. Input precision varies; the accumulator is usually FP32 (FP16 accumulation is an option on some parts). The same silicon runs several input formats, and the narrower the format, the more multiply-adds it completes per clock.

Definition · "With sparsity"

Since Ampere, tensor cores can skip work when a weight matrix has 2:4 structured sparsity: in every group of four consecutive weights, at least two are zero. The hardware stores only the non-zeros plus a small index and does half the multiplies, so spec sheets print a number twice the dense one. Real LLM weights aren't 2:4 sparse. Pruning them that way costs accuracy and usually needs retraining, so production LLM inference almost always runs dense. When a spec sheet has an asterisk, halve the number.

Why lower precision is faster

Two separate effects. The first is about compute: the area and energy of a multiplier grow roughly with the square of the number of significand bits it has to handle, so a chip of fixed size and power fits many more narrow multipliers than wide ones. The second is about memory: half the bytes per number means half the HBM traffic, twice as many numbers per register and per shared-memory byte, and twice the arithmetic intensity for the same matmul.

$$\htmlClass{t1}{A_{\text{mult}}} \;\propto\; \htmlClass{t2}{p}^{\,2}$$
\(A_{\text{mult}}\)
silicon area (and roughly energy) of one multiplier
\(p\)
significand width in bits, counting the implicit leading 1: FP32 24, TF32 11, BF16 8, FP8 E4M3 4

In wordsAn array multiplier is a grid of \(p \times p\) partial products. FP32 → 576 units of area, BF16 → 64, FP8 E4M3 → 16. Exponent handling and the wide FP32 accumulator add a cost that doesn't shrink, which is one reason FP8 gets 2× BF16's throughput on H100 rather than 4×.

Why it mattersThis is the physics behind every new format: FP8 on Hopper, FP4 on Blackwell. It's also why bf16 (8-bit significand) and not fp16 (11-bit) is roughly as cheap as it gets for training-grade 16-bit math. Module 09 covers the bit layouts and the accuracy side (number formats, weight-only vs W8A8).

FP8 accumulation isn't full FP32

The DeepSeek-V3 report (DeepSeek-AI, 2024) found that FP8 GEMM accumulation on Hopper tensor cores keeps fewer bits than true FP32, enough to hurt very long reductions. Their fix was to periodically move partial sums to FP32 registers on the CUDA cores. Libraries now handle this, but it explains why "FP8 matmul" in practice means FP8 inputs, careful scaling, and a higher-precision accumulator somewhere.

Roofline deep dive

The two-speed-limit formula becomes a picture once you divide everything by bytes. The roofline model (Williams, Waterman and Patterson, 2009) plots attainable FLOP/s against a kernel's arithmetic intensity on log-log axes. Module 08 introduced it for inference (08 · roofline); here we build it from hardware numbers and apply it to arbitrary matmul shapes.

$$\htmlClass{t1}{AI} = \frac{\htmlClass{t2}{F}}{\htmlClass{t3}{Q}}$$
\(AI\)
arithmetic intensity, FLOP per byte
\(F\)
FLOPs the kernel performs
\(Q\)
bytes moved between HBM and the chip (cache hits don't count)

In wordsHow much work you get out of each byte fetched. It's a property of the algorithm and its data layout, independent of the hardware.

$$\htmlClass{t1}{P_{\text{att}}} = \min\!\big(\htmlClass{t2}{P_{\text{peak}}},\; \htmlClass{t3}{AI} \cdot \htmlClass{t4}{BW}\big), \qquad \htmlClass{t5}{AI^{*}} = \frac{\htmlClass{t2}{P_{\text{peak}}}}{\htmlClass{t4}{BW}}$$
\(P_{\text{att}}\)
best FLOP/s this kernel can reach on this chip
\(P_{\text{peak}}\)
peak compute for the format in use (bf16, fp8 …)
\(AI\)
the kernel's arithmetic intensity
\(BW\)
HBM bandwidth
\(AI^{*}\)

In wordsLeft of the ridge, throughput rises linearly with intensity (memory-bound). Right of it, throughput is flat at peak (compute-bound). H100 bf16: 989 ÷ 3.35 ≈ 295 FLOP/B. FP8 doubles the peak without changing the bandwidth, so its ridge is ≈ 590.

Why it mattersThe ridge point is the single most useful number on a spec sheet. Faster compute without faster memory moves the ridge right and makes more workloads memory-bound, which is what has happened with every GPU generation.

For a matmul \(C_{M\times N} = A_{M\times K}\,B_{K\times N}\), the FLOPs are \(2MNK\), and a well-tiled kernel reads each input once and writes the output once. In an LLM linear layer, \(M\) is the number of tokens in the batch, \(K\) is the input width and \(N\) the output width, so \(B\) is the weight matrix (Module 01 covers the shapes in why GPUs love matmuls).

$$\htmlClass{t1}{AI_{\text{mm}}} = \frac{2\,\htmlClass{t2}{M}\,\htmlClass{t3}{N}\,\htmlClass{t4}{K}}{\htmlClass{t5}{b}\,\big(\htmlClass{t2}{M}\htmlClass{t4}{K} + \htmlClass{t4}{K}\htmlClass{t3}{N} + \htmlClass{t2}{M}\htmlClass{t3}{N}\big)}$$

\(b\)

In wordsWhen \(M\) is small, the weight term \(KN\) dominates the bytes and \(AI \approx 2M/b\): one FLOP per byte per token in bf16. When all three dimensions are large, AI grows like the smallest of them.

Why it mattersLlama-3-8B's MLP up-projection (\(K = 4096\), \(N = 14{,}336\)) at \(M = 1\) has AI ≈ 1.0 and takes about 35 µs on an H100, all of it reading 117 MB of weights. At \(M = 4096\) the AI is ≈ 1,800, and the same weights feed 4,096 tokens in about 0.5 ms of pure compute.

Think first: a square 4096³ bf16 matmul is compute-bound on an H100. Is it compute-bound on an M4 Max too? And a 256³ one?
4096³ in bf16 has AI = 2·4096³ / (2·3·4096²) ≈ 1,365, well past both ridges (295 and ~30), so it's compute-bound on both, at very different absolute speeds. 256³ has AI ≈ 85: memory-bound on the H100 (below 295) but compute-bound on the Mac (above ~30). The same kernel can sit on different sides of the ridge on different chips. In practice a 256³ matmul is also too small to fill 132 SMs and is dominated by launch overhead.
The roofline is a ceiling, not a prediction

Real kernels sit below their roof: imperfect tiling re-reads data, small grids leave SMs idle, clocks throttle, and the epilogue (bias, activation, write-back) takes time. Good large GEMMs commonly reach 60–80% of the dense peak; memory-bound kernels commonly reach 70–90% of HBM bandwidth. The model also has more roofs than one: separate L2 and shared-memory rooflines exist, and a kernel can be bound by L2 bandwidth even when its HBM intensity looks fine.

Prefill and decode on the roofline

Module 08 explained why decode is memory-bound and how batching helps (roofline, batching). With the matmul intensity formula, you can now see exactly where each phase of LLM inference lands, and how much batching it takes to reach the ridge.

$$\htmlClass{t1}{B^{*}} \;\approx\; \frac{\htmlClass{t2}{AI^{*}} \cdot \htmlClass{t3}{b_w}}{2}$$
\(B^{*}\)
decode batch at which the weight matmuls reach the ridge
\(AI^{*}\)
ridge point for the format the math runs in
\(b_w\)
bytes per weight as stored in HBM

In wordsDecode intensity is about \(2B/b_w\); set it equal to the ridge and solve. H100 bf16: \(B^{*} \approx 295\). W4A16 (4-bit weights, bf16 math): \(B^{*} \approx 295 \times 0.5 / 2 \approx 74\). FP8 W8A8: ridge 590, \(b_w = 1\), \(B^{*} \approx 295\) again.

Why it mattersBelow \(B^{*}\), adding sequences to the batch is almost free for the weight matmuls, so throughput rises nearly linearly. Above it you pay compute for every extra sequence. Weight-only quantization reaches the compute roof at a smaller batch, which is why it helps low-batch latency more than high-batch throughput.

MLE angle · What the roofline says about serving design

Three engine features follow directly from this picture. Large decode batches amortize each weight read (Module 19's continuous batching keeps the batch full). Chunked prefill mixes a compute-bound prefill chunk into memory-bound decode steps so both roofs are used in the same step. Disaggregated serving (Module 20) goes further and runs prefill and decode on different GPUs, each sized for its own side of the ridge. And because KV-cache reads don't batch, long contexts drag decode back to the left: at 32K tokens the KV bytes per step can exceed the weight bytes.

Other accelerators

The same two numbers, compute and bandwidth, plus a third, memory capacity, describe every inference chip. Different designs pick different points in that space.

Apple Silicon: unified memory

M-series chips put CPU, GPU and Neural Engine on one die sharing one pool of LPDDR memory. There's no PCIe copy: a tensor the CPU wrote is already visible to the GPU. Bandwidth scales with the chip tier, roughly 100–120 GB/s for base chips, around 150–270 GB/s for Pro, 400–550 GB/s for Max, and about 800 GB/s for Ultra parts (approximate; varies by generation). Capacity goes up to 128 GB on a Max and higher on Ultra configurations. That makes a Mac good at holding large quantized models and decoding at batch 1, since a 4-bit 70B model fits and decodes at a speed set by bandwidth. GPU compute is modest, tens of TFLOP/s at most, so prefill of long prompts is slow: the ridge sits near 30 FLOP/B, and a 4,000-token prompt is firmly compute-bound.

AMD MI300X

The MI300X pairs eight compute chiplets with 192 GB of HBM3 at about 5.3 TB/s and a 256 MB on-package Infinity Cache, with bf16 dense peak around 1.3 PFLOP/s (approximate). Its main inference selling point is capacity: Llama-3-70B in bf16 (about 141 GB) fits on one GPU, so no tensor parallelism is needed, and there's more room for KV cache. The programming model is ROCm/HIP, closely modelled on CUDA. One difference that matters for kernel writers: AMD's CDNA GPUs schedule wavefronts of 64 threads, not warps of 32.

Google TPUs: systolic arrays

A TPU's matrix unit (MXU) is a systolic array (Kung, 1982; Jouppi et al., 2017): a grid of multiply-accumulate cells, each wired only to its neighbours. Weights are loaded into the cells once; activations flow in from one edge and partial sums flow out the other. Each operand fetched from memory gets used by a whole row or column of cells without going back through a register file or cache.

TPUs are programmed through the XLA compiler (from JAX, or PyTorch/XLA), which plans data movement statically, and chips connect directly to each other through an inter-chip interconnect arranged as a torus. As one data point, a TPU v5e is listed at about 197 TFLOP/s bf16 with 16 GB of HBM at about 819 GB/s (Google's published figures; check current docs, since generations change quickly).

SRAM-heavy inference chips

If decode is bound by memory bandwidth, one radical answer is to drop HBM and keep weights in on-chip SRAM, whose bandwidth is orders of magnitude higher. Groq's LPU has a few hundred MB of SRAM per chip and a compiler that schedules every data movement ahead of time, so execution is deterministic. Cerebras builds one processor from an entire wafer with tens of GB of on-wafer SRAM. Both companies report very high single-user tokens/s.

What SRAM buys

Bandwidth per byte stored

On-chip SRAM delivers far more bandwidth than HBM, so batch-1 decode can run far above a GPU's memory roof. Latency is low and predictable.

What it costs

Capacity per dollar

SRAM is much less dense than DRAM. A 70B model at 8 bits needs about 70 GB, so it's spread over many chips (hundreds, at a few hundred MB each) with every chip-to-chip link in the critical path. KV cache for long contexts competes for the same scarce memory.

Figures for these chips are vendor-stated and architectures change between generations; treat this as the conceptual trade-off rather than a benchmark.

When a model doesn't fit on one GPU, or you need more bandwidth than one GPU has, chips have to talk. The links between them are slower than HBM by one to two orders of magnitude, and that gap shapes every parallelism strategy in Module 20.

A link's speed for a given message is well described by two parameters.

$$\htmlClass{t1}{t} = \htmlClass{t2}{\alpha} + \frac{\htmlClass{t3}{n}}{\htmlClass{t4}{\beta}}$$

$$\htmlClass{t1}{n_{1/2}} = \htmlClass{t2}{\alpha} \cdot \htmlClass{t3}{\beta}$$
\(n_{1/2}\)
message size at which you achieve half the link's bandwidth
\(\alpha\)
per-message latency
\(\beta\)
link bandwidth

In wordsBelow \(n_{1/2}\) you're paying mostly latency. With α ≈ 3 µs and β ≈ 450 GB/s, \(n_{1/2}\) ≈ 1.35 MB. A tensor-parallel all-reduce of one decode token's hidden state (8,192 × 2 bytes = 16 KB) is far below it, so it's latency-bound, not bandwidth-bound.

Why it mattersThis is why tensor parallelism across nodes hurts decode so much (dozens of tiny latency-bound all-reduces per token), and why engines keep TP inside the NVLink domain.

Pitfall · Gb/s, GB/s, and "total"

Network links are quoted in gigabits per second (400 Gb/s = 50 GB/s). NVLink is quoted as a bidirectional total (900 GB/s = 450 each way). PCIe is usually quoted per direction. Before you compare, convert everything to gigabytes per second in the direction your data moves.

Power is the cost people forget. An 8×H100 node can draw over 10 kW once CPUs, networking and cooling are included, and many datacenters are now limited by power delivery rather than by floor space. Energy per token falls with batch size for the same reason cost does: the board draws similar power whether it serves 1 user or 64.

MLE angle · A sizing procedure

(1) Compute weight bytes at the precision you'll serve. (2) Add KV cache for your p95 concurrency × context, not the average. (3) Pick the smallest power-of-two GPU count that fits, inside one NVLink domain if you can. (4) Check the per-user decode ceiling (aggregate bandwidth ÷ bytes per step) against your latency target, and expect to reach 60–80% of it. (5) Only then compare $/M tokens, and measure: the widget's numbers are ceilings, and real engines spend time on scheduling, sampling and communication.

Hands-on

1. Measure matmul TFLOP/s across sizes (CUDA or Apple MPS)

This runs square matmuls of growing size and decode-shaped ones (\(M\) small, \(K = N = 8192\)). Watch TFLOP/s climb with size until it plateaus below the spec-sheet peak, and watch the decode shapes report GB/s close to your memory bandwidth instead.


import time, torch

dev = "cuda" if torch.cuda.is_available() else "mps" if torch.backends.mps.is_available() else "cpu"
dtype = torch.bfloat16 if dev == "cuda" else torch.float16 if dev == "mps" else torch.float32
# torch.backends.cuda.matmul.allow_tf32 = True   # only matters for fp32 inputs on CUDA

def sync():
    if dev == "cuda":
        torch.cuda.synchronize()
    elif dev == "mps":
        torch.mps.synchronize()

def bench(m, k, n, iters=50):
    a = torch.randn(m, k, device=dev, dtype=dtype)
    b = torch.randn(k, n, device=dev, dtype=dtype)
    for _ in range(5):                      # warm-up: kernel selection, clocks ramp up
        a @ b
    sync()
    t0 = time.perf_counter()
    for _ in range(iters):
        c = a @ b
    sync()                                  # kernels are async: wait before stopping the clock
    dt = (time.perf_counter() - t0) / iters
    flops = 2 * m * k * n
    nbytes = a.element_size() * (m * k + k * n + m * n)
    return dt, flops / dt / 1e12, nbytes / dt / 1e9, flops / nbytes

print(f"device={dev} dtype={dtype}")
print(f"{'M x K x N':>18} {'time':>10} {'TFLOP/s':>8} {'GB/s':>7} {'AI':>6}")
for s in (256, 512, 1024, 2048, 4096, 8192):
    dt, tf, gbs, ai = bench(s, s, s)
    print(f"{f'{s}x{s}x{s}':>18} {dt*1e6:8.1f}us {tf:8.1f} {gbs:7.0f} {ai:6.0f}")
for m in (1, 8, 32, 128, 512, 2048):         # decode-shaped: M = batch of tokens
    dt, tf, gbs, ai = bench(m, 8192, 8192)
    print(f"{f'{m}x8192x8192':>18} {dt*1e6:8.1f}us {tf:8.1f} {gbs:7.0f} {ai:6.0f}")

3. A complete CUDA C kernel

Vector add is the "hello world" of CUDA and is purely memory-bound: 12 bytes moved per FLOP. Its achieved GB/s is a good estimate of your practical HBM bandwidth.


#include <cstdio>
#include <cuda_runtime.h>

__global__ void vadd(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];
}

__global__ void fill(float* x, float v, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) x[i] = v;
}

int main() {
    const int n = 1 << 26;                         // 67M floats = 256 MiB per array
    const size_t bytes = size_t(n) * sizeof(float);
    float *a, *b, *c;
    cudaMalloc(&a, bytes); cudaMalloc(&b, bytes); cudaMalloc(&c, bytes);

    const int threads = 256;
    const int blocks = (n + threads - 1) / threads;   // 262,144 blocks
    fill<<<blocks, threads>>>(a, 1.0f, n);
    fill<<<blocks, threads>>>(b, 2.0f, n);
    vadd<<<blocks, threads>>>(a, b, c, n);          // warm-up

    cudaEvent_t t0, t1;
    cudaEventCreate(&t0); cudaEventCreate(&t1);
    cudaEventRecord(t0);
    for (int r = 0; r < 20; ++r) vadd<<<blocks, threads>>>(a, b, c, n);
    cudaEventRecord(t1);
    cudaEventSynchronize(t1);
    float ms = 0.f;
    cudaEventElapsedTime(&ms, t0, t1);
    ms /= 20;

    float host_c = 0.f;
    cudaMemcpy(&host_c, c, sizeof(float), cudaMemcpyDeviceToHost);
    printf("c[0] = %.1f, %.3f ms, %.0f GB/s\n", host_c, ms, 3.0 * bytes / (ms * 1e6));
    cudaFree(a); cudaFree(b); cudaFree(c);
    return 0;
}

Use -arch=sm_80 for A100 and sm_89 for RTX 4090 / L40S. Try changing threads to 32 and 1024, and try making thread \(i\) read a[(i * 32) % n]: the coalescing widget predicts what happens to GB/s.

An H100 SXM does about 1,979 TFLOP/s of dense FP8 tensor math with 3.35 TB/s of HBM bandwidth. What is its FP8 ridge point?

  1. ≈ 295 FLOP/byte
  2. ≈ 590 FLOP/byte
  3. ≈ 1,180 FLOP/byte
  4. ≈ 59 FLOP/byte
1,979 × 10¹² ÷ 3.35 × 10¹² ≈ 590. FP8 doubles peak compute but bandwidth is unchanged, so the ridge doubles from bf16's ≈ 295 and FP8 kernels need twice the intensity to be compute-bound.

Decode at batch 1 runs a bf16 matmul with \(M = 1\), \(K = 8192\), \(N = 8192\). What's its arithmetic intensity?

  1. ≈ 1 FLOP/byte
  2. ≈ 64 FLOP/byte
  3. ≈ 2,730 FLOP/byte
  4. ≈ 295 FLOP/byte
FLOPs = 2·1·8192·8192 ≈ 134M. Bytes = 2·(8192 + 67.1M + 8192) ≈ 134M. Ratio ≈ 1. Every weight is read once and used once. 2,730 is the square 8192³ case; 295 is the H100's ridge, not this kernel's intensity.

On an H100-like SM (65,536 registers, 2,048 threads, 32 blocks, 228 KB shared memory), a kernel uses 256 threads per block, 128 registers per thread and 16 KB of shared memory per block. What limits occupancy, and what is it?

  1. Thread slots; 100%
  2. Shared memory; 50%
  3. The 32-blocks-per-SM cap; 25%
  4. Registers; 25%
Registers: 128 × 256 = 32,768 per block, so 2 blocks fit. Threads would allow 8 blocks, shared memory about 13, the block cap 32. Registers win: 2 blocks × 8 warps = 16 of 64 warps = 25%.

You copy 16 GB of weights from one H100 to another in the same HGX node. Roughly how long over NVLink 4 (~450 GB/s per direction) versus over PCIe Gen5 x16 (~64 GB/s per direction)?

  1. ~3.5 ms vs ~25 ms
  2. ~36 ms on both, since HBM is the bottleneck
  3. ~36 ms vs ~250 ms
  4. ~0.36 s vs ~2.5 s
16 GB ÷ 450 GB/s ≈ 36 ms; 16 GB ÷ 64 GB/s = 250 ms. Latency (microseconds) is negligible at this size. HBM at 3.35 TB/s isn't the bottleneck for either link. The ~7× gap is why tensor parallelism lives on NVLink.

Why does an H100 deliver about twice as many dense FP8 tensor-core FLOP/s as BF16?

  1. An FP8 multiplier handles far fewer significand bits, so it's much smaller and cheaper in energy; the same silicon and power do about twice the multiply-adds per clock, and each operand is half the bytes
  2. FP8 instructions run at a higher clock frequency
  3. FP8 automatically uses 2:4 structured sparsity
  4. FP8 matmuls skip the accumulation step
Multiplier area grows roughly with the square of significand width (4 bits for E4M3 vs 8 for bf16). Clocks are the same, the 2× is dense (sparsity would double it again), and accumulation still happens at higher precision.

Each thread \(t\) of a warp reads a 4-byte float at index \(2t\). If this pattern dominates a memory-bound kernel on a 3.35 TB/s GPU, roughly what effective bandwidth do you get for useful data?

  1. 3.35 TB/s: the hardware coalesces any pattern
  2. ~0.42 TB/s
  3. ~0.1 TB/s
  4. ~1.7 TB/s
32 threads span 64 floats = 256 bytes = 8 sectors of 32 bytes, but only 128 bytes are used. Efficiency 50%, so about 1.7 TB/s. 0.42 TB/s (12.5%) is what you'd get at stride 8 or more.

HBM latency is about 600 ns and bandwidth 3.35 TB/s. How many bytes must be in flight across the whole GPU to keep HBM saturated?

  1. ~2 KB
  2. ~200 KB
  3. ~2 MB
  4. ~2 GB
Little's law: 3.35 × 10¹² B/s × 600 × 10⁻⁹ s ≈ 2 × 10⁶ B. Spread over 132 SMs that's about 15 KB per SM, which is why kernels need many warps or asynchronous copies to reach peak bandwidth.
