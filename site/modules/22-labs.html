How to use the labs

Every lab runs the same four-step loop. You write down what you expect before touching the keyboard. You build the smallest thing that can test that expectation. You measure carefully. Then you explain the gap between the two numbers. The explanation is the part that sticks. A lab you "ran" without a prediction teaches you a command; a lab where you predicted 90 tok/s, measured 31, and found out why teaches you how the machine works.

Exit criteria are numbers

"Trained a LoRA" isn't an exit criterion. "LoRA scores 0.86 exact-match on 200 held-out examples against 0.71 for the best few-shot prompt, and the paired bootstrap interval for the difference excludes zero" is. Every lab card ends with two or three criteria of that shape. They stop you from quitting at the first plausible output, and they force you to build the measurement harness, which is most of the real engineering. The table you're left with gets reused the next time someone asks "how fast would this run on our hardware?"

Most criteria compare a measurement against a ceiling you computed first. One ratio captures that:

$$\htmlClass{t1}{\eta} = \frac{\htmlClass{t2}{x_{\text{measured}}}}{\htmlClass{t3}{x_{\text{ceiling}}}}$$
\(\eta\)
efficiency: the fraction of the theoretical limit you actually got
\(x_{\text{measured}}\)
what you timed: tok/s, TFLOP/s, GB/s
\(x_{\text{ceiling}}\)
what the formula allows: bandwidth ÷ bytes per token, datasheet peak FLOP/s, link bandwidth

In wordsDivide what you got by what physics allows. The ratio tells you where to look next.

Why it mattersRule of thumb, not a law: large well-tuned kernels and engines land around 0.6–0.85. Between 0.3 and 0.6, look for overhead such as Python, kernel launches, small batches or the wrong dtype. Below 0.3, a different resource is the bottleneck, and your model of the system is missing something.

Make the measurement trustworthy

GPU timing goes wrong in quiet ways. On CUDA and on MPS, kernel launches return before the work finishes, so a naive timer measures the launch. MLX is lazy: a @ b builds a graph and nothing runs until mx.eval. The first few calls pay for compilation, memory allocation and cache warmup. A fanless MacBook Air throttles after a minute or two of sustained load, and Low Power Mode caps the clocks. The figure shows what a raw timing trace looks like.


import statistics, time
import torch

def _sync(device):
    if device == "cuda":
        torch.cuda.synchronize()
    elif device == "mps":
        torch.mps.synchronize()

def bench(fn, device, warmup=10, iters=50):
    """Time fn() on a GPU correctly: warm up, synchronize, report median and p95 in ms."""
    for _ in range(warmup):
        fn()
    _sync(device)
    times = []
    for _ in range(iters):
        t0 = time.perf_counter()
        fn()
        _sync(device)                      # wait for the GPU before reading the clock
        times.append((time.perf_counter() - t0) * 1e3)
    times.sort()
    return {"median_ms": statistics.median(times), "p95_ms": times[int(0.95 * (len(times) - 1))]}

# MLX equivalent: wrap the work so it ends in mx.eval(result); MLX is lazy and nothing runs before that.
Pitfall · measuring the wrong thing

Before trusting any speed number, check four things. Is the tensor actually on the GPU (x.device)? Is the dtype what you think, and not silently fp32? Did the machine swap? Watch Activity Monitor's memory pressure, because a model that spills out of unified memory runs 10–100× slower. And is anything else hammering the GPU, such as a browser tab playing video or a second notebook you forgot about?

Quality metrics have their own noise: a score measured on a finite eval set is an estimate. Before you claim one configuration beats another, check how wide the error bars are.

$$\htmlClass{t1}{\text{SE}} = \sqrt{\frac{\htmlClass{t2}{p}\,(1-\htmlClass{t2}{p})}{\htmlClass{t3}{n}}}, \qquad \text{95\% CI} \approx \htmlClass{t2}{p} \pm 1.96\,\htmlClass{t1}{\text{SE}}$$
SE
standard error of the measured rate
\(p\)
measured accuracy, pass rate, recall or win rate
\(n\)
number of independent eval items

In wordsWith 200 items at 70% accuracy, SE ≈ 0.032, so the 95% interval is about ±6.4 points. Two systems 3 points apart on that set are indistinguishable.

Why it mattersThis sets the size of your eval sets. Comparing two systems on the same items (a paired test, Module 13) is tighter than comparing two independent intervals, so always keep per-item results.

Think first: you predicted 60 tok/s for a 3B model at 4-bit on your Mac and measured 18. What do you check, in order?
First the cheap, embarrassing causes: is it running on the GPU, and is the model really 4-bit (file size ≈ N × 4.5 / 8 bytes)? Next, memory: if the Mac is swapping, everything else is noise. Then overhead: at batch 1 on a small model, per-token Python and launch costs can dominate. Compare llama-bench (C++, no Python) with your script. Finally, context: at long prompts, KV-cache reads add to the bytes per token (Module 08). Write down which one it was. Next time your prediction will include it.

Environment setup

All thirteen core labs run on an Apple Silicon Mac, and so do L16 and L19 if you use small models. L14 needs a cloud GPU for half of its measurements. L15, L17 and L18 need NVIDIA hardware outright, because CUDA, Triton, vLLM and NCCL don't run on Apple GPUs. Rent that hardware by the hour rather than buying it.

On the Mac

Use uv for Python. It creates environments and installs packages fast enough that keeping a separate environment per lab costs nothing. PyTorch's standard macOS wheels include the MPS backend. MLX is Apple's array framework and is usually the fastest way to run and fine-tune models on a Mac. llama.cpp gives you the C++ inference engine and its benchmarking tools.

L1

micrograd: autograd from scratch

~4 h · Mac CPU · 02, 04
Goal

Build a scalar automatic-differentiation engine and a tiny neural net on top of it, so backpropagation stops being a black box.

Steps
  1. Write a Value class that stores data, grad, its parents and a local _backward closure for +, *, **, tanh, exp and relu.
  2. Implement backward() with a topological sort. Accumulate with +=, because a node used twice must receive both gradients.
  3. Build Neuron, Layer and MLP, then train on 100 two-moons points with SGD and a hinge or cross-entropy loss.
  4. Write a gradient check that rebuilds the same expressions in PyTorch float64 and compares every leaf's gradient.
Deliverable

engine.py, nn.py, a test file and a decision-boundary plot. The reference is Karpathy's micrograd; write yours before reading it.

Exit criteria
  • Max |your grad − PyTorch grad| ≤ 1e-6 on the test expression below and on 50 random expressions of 20+ nodes, each reusing at least one node.
  • The MLP reaches ≥ 95% training accuracy on two-moons.
  • You can explain what breaks if gradients are assigned with = instead of +=, and why the topological order matters.

import torch
from engine import Value                      # your implementation

a, b = Value(-4.0), Value(2.0)
c = a + b; d = a * b + b**3
c += c + 1; c += 1 + c + (-a)
d += d * 2 + (b + a).relu(); d += 3 * d + (b - a).relu()
e = c - d; f = e**2; g = f / 2.0; g += 10.0 / f
g.backward()

A = torch.tensor(-4.0, dtype=torch.float64, requires_grad=True)
B = torch.tensor(2.0, dtype=torch.float64, requires_grad=True)
C = A + B; D = A * B + B**3
C = C + C + 1; C = C + 1 + C + (-A)
D = D + D * 2 + (B + A).relu(); D = D + 3 * D + (B - A).relu()
E = C - D; F = E**2; G = F / 2.0; G = G + 10.0 / F
G.backward()

assert abs(g.data - G.item()) < 1e-6
assert abs(a.grad - A.grad.item()) < 1e-6 and abs(b.grad - B.grad.item()) < 1e-6
print("forward and gradients match")
L2

Bigram → MLP character model

~3 h · Mac · 03, 04
Goal

Train character-level language models of increasing capacity and read every improvement in nats.

Steps
  1. Use the ~32k-name list from Karpathy's makemore; split 80/10/10 with a fixed seed.
  2. Count bigrams, add-one smooth, and compute the dev-set negative log-likelihood per character.
  3. Train the same bigram as a 27×27 weight matrix with softmax and cross-entropy. It should converge to the counting solution.
  4. Replace it with an MLP over a 3-character context (embedding → tanh hidden layer → logits), in the style of Bengio et al. (2003), and sweep embedding size and width.
Deliverable

A table of train and dev NLL for counted bigram, neural bigram and 2–3 MLP sizes, plus 20 samples from each.

Exit criteria
  • Neural-bigram dev NLL within 0.01 nats of the counted bigram.
  • Best MLP beats the bigram by ≥ 0.2 nats on the dev split. As a rough guide, the bigram sits near 2.45 on this dataset and a small MLP reaches about 2.1–2.2.
  • You report the train–dev gap for each model and say whether it's over- or underfitting.

A byte-level BPE trainer

Implement BPE training, encoding and decoding over raw bytes, then compare compression with production tokenizers.

L5

Add a KV cache, then benchmark it

~3 h · Mac · 08
Goal

Give your L3 model (or a GPT-2 implementation) a KV cache and measure exactly what it buys.

Steps
  1. Store K and V per layer. On each decode step, feed only the newest token, offset its position, and attend over the cache.
  2. Check that greedy outputs match the no-cache path.
  3. Time per-token latency at positions 1 to 1024, with and without the cache, using bench.py.
  4. Compute the cache size from the formula and compare it with the bytes your tensors actually hold.
Deliverable

A latency-vs-position plot (two lines) and a memory table.

Exit criteria
  • Token-identical greedy output for 256 tokens in fp32, with and without the cache.
  • Per-token latency with the cache grows ≤ 2× from position 64 to 1024, while the no-cache version grows roughly linearly.
  • Measured cache bytes match \(2 \cdot L \cdot H_{kv} \cdot d_h \cdot T \cdot b\) within 1%.

LoRA with mlx-lm that beats prompting

~3.5 h · Mac · 10
Goal

Fine-tune a small instruct model on a narrow task and show, with error bars, that it beats the best prompt you can write.

Steps
  1. Pick a task with an automatic metric, such as JSON field extraction, classification or a fixed output format. Build train/valid/test.jsonl with at least 500 / 100 / 200 examples, deduplicated across splits.

L8

DPO, judged fairly

~3.5 h · Mac (0.5B) or cloud GPU · 10, 13
Goal

Preference-tune an SFT model with DPO and measure the win rate with a judge that can't be gamed by answer order.

Steps
  1. Start from an instruct model or your own SFT checkpoint. Use a few thousand preference pairs, for example from trl-lib/ultrafeedback_binarized.
  2. Train with TRL's DPOTrainer (β = 0.1 to start).
  3. Generate answers from SFT and DPO for 200 held-out prompts.
  4. Have a judge compare each pair twice, once in each order. A verdict that flips with the order counts as a tie.
Deliverable

Win/tie/loss counts, judge consistency, and average response length for both models.

Exit criteria
  • DPO win rate vs SFT ≥ 55% on 200 prompts, with ties counted as half a win, judged in both orders.
  • Judge position-consistency (same verdict in both orders) reported as a percentage.
  • If DPO answers average more than 1.3× the SFT length, you also report a length-controlled win rate.

from datasets import load_dataset

Roofline benchmark: MPS, MLX and a cloud GPU

~3 h (≈1 GPU-h) · 17
Goal

Measure achieved TFLOP/s against matrix size on three backends and explain the curve's shape with the roofline.

Steps
  1. Time square matmuls for \(n = 128 \ldots 8192\) in fp16/bf16 with warmup and synchronization (script below), on PyTorch MPS, on MLX, and on one cloud GPU.
  2. Compute FLOP/s \(= 2n^3 / t\) and the ideal arithmetic intensity \(2n^3 / (3 n^2 b)\).
  3. Measure achievable bandwidth with a large copy (\(\geq\) 1 GB), counting bytes read plus bytes written.
  4. Plot achieved FLOP/s against intensity, with the datasheet peak and your measured bandwidth as the roof.
Deliverable

One roofline plot with three backends, and a table of n, intensity, TFLOP/s and % of peak.

Exit criteria
  • On the cloud GPU, the largest sizes reach ≥ 60% of the dense datasheet peak for that dtype.
  • Measured copy bandwidth ≥ 70% of the datasheet memory bandwidth on the cloud GPU.
  • You locate the knee for each backend and explain why it sits to the right of the ideal ridge point (launch overhead, tile quantization, too few tiles to fill the SMs). Apple doesn't publish a matmul peak for every chip, so use your best measured value as the Mac ceiling and say so.

import time, torch

dev = "cuda" if torch.cuda.is_available() else "mps"
dtype = torch.bfloat16 if dev == "cuda" else torch.float16
sync = torch.cuda.synchronize if dev == "cuda" else torch.mps.synchronize

for n in [128, 256, 512, 1024, 2048, 4096, 8192]:
    a = torch.randn(n, n, device=dev, dtype=dtype)
    b = torch.randn(n, n, device=dev, dtype=dtype)
    for _ in range(5):
        a @ b
    sync()
    iters = min(5000, max(10, int(2e11 / (2 * n**3))))   # more repeats for tiny sizes
    t0 = time.perf_counter()
    for _ in range(iters):
        c = a @ b
    sync()
    dt = (time.perf_counter() - t0) / iters
    ai = 2 * n**3 / (3 * n * n * a.element_size())        # FLOPs per byte with perfect reuse
    print(f"n={n:5d}  AI={ai:7.1f} FLOP/B  {2 * n**3 / dt / 1e12:8.2f} TFLOP/s")

A serving platform: replicas, a router, open-loop load

~5 h (≈4 h on 2 GPUs, or a Mac) · 21
Goal

Find the knee of a throughput–latency curve, and measure what prefix-aware routing buys over round-robin.

Steps
  1. Run two replicas: vLLM on two GPUs, or two llama-server processes with a small model on a Mac.
  2. Write a router of about 100 lines that proxies streaming requests. Policy A is round-robin. Policy B is prefix affinity: hash the conversation ID or the first few hundred prompt characters to a replica, and fall back to the less-loaded one when the in-flight imbalance exceeds a threshold.
  3. Drive it with an open-loop Poisson load generator (below), using a multi-turn workload whose turns share prefixes.
  4. Step the request rate up until p95 TTFT passes your SLO, for each policy.
Deliverable

Two throughput-vs-p95-TTFT curves on one plot, plus per-replica cache hit rates.

Exit criteria
  • At least 6 offered-load points per policy, with the knee identified.
  • At the same sub-saturation load, prefix affinity shows lower p95 TTFT and a higher cache hit rate than round-robin, with both numbers reported.
  • The generator is verifiably open-loop: the achieved arrival rate stays within 5% of the target even past saturation.

import asyncio, random, time
import httpx

URL, MODEL = "http://localhost:9000/v1/completions", "served-model-name"

async def one(client, prompt, out):
    t0, first, last, gaps = time.perf_counter(), None, None, []
    body = {"model": MODEL, "prompt": prompt, "max_tokens": 128, "stream": True}
    async with client.stream("POST", URL, json=body) as r:
        async for line in r.aiter_lines():
            if not line.startswith("data: ") or line.strip() == "data: [DONE]":
                continue
            now = time.perf_counter()
            if first is None:
                first = now
            else:
                gaps.append(now - last)               # chunk gaps approximate ITL
            last = now
    if first is not None:
        out.append({"ttft": first - t0, "itl": gaps, "e2e": last - t0})

async def run(rate, n, prompts):
    out, tasks = [], []
    async with httpx.AsyncClient(timeout=None, limits=httpx.Limits(max_connections=None)) as client:
        start = next_t = time.perf_counter()
        for _ in range(n):
            next_t += random.expovariate(rate)        # schedule arrivals on an absolute clock
            await asyncio.sleep(max(0.0, next_t - time.perf_counter()))
            tasks.append(asyncio.create_task(one(client, random.choice(prompts), out)))
        sent_rate = n / (time.perf_counter() - start) # must stay near `rate`, even when the server is slow
        await asyncio.gather(*tasks)
    ttft = sorted(o["ttft"] for o in out)
    p95 = ttft[int(0.95 * (len(ttft) - 1))]
    print(f"target {rate:.1f}/s  sent {sent_rate:.2f}/s  p95 TTFT {p95 * 1e3:.0f} ms  completed {len(out)}")

Formula cheat sheet

These twelve formulas answer most sizing questions you'll get: will it fit, how fast can it go, what will it cost, and is the result real? Each links to the module that derives it. Example numbers are worked from the formulas, not measured.

$$\mathrm{Attn}(\htmlClass{t1}{Q},\htmlClass{t2}{K},\htmlClass{t3}{V}) = \mathrm{softmax}\!\left(\frac{\htmlClass{t1}{Q}\htmlClass{t2}{K}^{\top}}{\sqrt{\htmlClass{t4}{d_k}}} + \htmlClass{t5}{M}\right)\htmlClass{t3}{V}$$

\(K\)

\(V\)

In wordsScore every key against every query, turn scores into weights, average the values.

\(T\)

\(p_\theta\)

\(x_t\)

\(x_{\lt t}\)
everything before it

In wordsAverage surprise at the true next token. Uniform over 27 characters gives ln 27 ≈ 3.30.

Habits of strong MLEs and inference engineers

Talent matters less here than routine. The people who get very good at this work tend to repeat a small set of behaviours until they're automatic. Most of them are the lab loop applied to everyday work.

HabitWhat it looks like on a normal Tuesday
Predict before you runA comment above the benchmark call: # expect ~85 tok/s (bandwidth-bound). The gap gets investigated, not ignored.
Know the datasheet by heartMemory bandwidth, peak FLOP/s per dtype, memory size and link bandwidth for the two or three chips you use most, so sizing questions get answered in a meeting rather than after one.
Eval first, model secondThe test set and its scorer exist before the first fine-tuning run, and per-item results are kept so paired comparisons are possible.
One change at a timeA sweep script and a results table instead of a notebook edited in place. Every row records the git commit and library versions.
Profile, then optimizeA trace (Nsight Systems, the PyTorch profiler, Instruments on a Mac) before touching code. Time goes to the kernel the trace points at, not the one that looks slow.
Reproduce, then extendA paper's headline number at small scale before your own variant. If you can't reproduce the baseline, your improvement means nothing yet.
Read the engine's sourceWhen vLLM or llama.cpp does something surprising, the answer is in the scheduler or the kernel dispatch code, and reading it is faster than guessing.
Watch the unitsGB vs GiB, tokens vs characters, per-GPU vs aggregate throughput, p50 vs p95. Most "impossible" results are unit mistakes.
Cost is a metricEvery serving result carries a $/1M-token figure next to its latency, and cloud instances shut themselves down when idle.
Write it down shortA half-page note per experiment: question, prediction, result, explanation. These notes become the design docs and interview stories later.
A caution about pace

The 18-week plan assumes steady weeks. Real weeks aren't steady. When one slips, finish the current lab's exit criteria before starting the next module. Momentum comes from closed loops, not from pages read.

You wrap c = a @ b (two 4096×4096 fp16 tensors on MPS) in time.perf_counter() calls and get 0.02 ms. That works out to about 6,900 TFLOP/s. What happened?

  1. MPS used a sparse kernel that skipped zeros
  2. The result was cached from an earlier identical call
  3. The GPU runs asynchronously, so you timed the launch, not the work. Synchronize before reading the clock
  4. perf_counter only has millisecond resolution on macOS
2 × 4096³ ≈ 1.37 × 10¹¹ FLOPs in 2 × 10⁻⁵ s is about 6.9 × 10¹⁵ FLOP/s, about seven times an H100's dense bf16 peak and hundreds of times what a laptop GPU can do. The call returned as soon as the kernel was queued. Call torch.mps.synchronize() (or torch.cuda.synchronize(), or mx.eval in MLX) before stopping the timer, and discard warmup iterations.

Your load generator runs 32 workers, each sending its next request only after the previous one finishes. As you push the server toward saturation, p95 TTFT barely moves. Why is this curve misleading?

  1. A closed loop slows its own arrival rate when the server slows down, so queues never build the way real, independent traffic would build them
  2. 32 workers is too few samples to estimate a p95
  3. TTFT has to be measured on the server, not the client
  4. Streaming responses hide when the first token arrives
Real users don't wait for each other. In a closed loop, a slow server automatically receives fewer requests, which hides the queueing delay you're trying to measure (often called coordinated omission). L19 requires an open-loop generator whose achieved arrival rate stays on target past saturation.

In L14, a 4096×4096 bf16 matmul takes 0.25 ms on an H100 SXM (dense bf16 peak ≈ 989 TFLOP/s). What fraction of peak is that?

  1. About 28%
  2. About 56%
  3. About 111%
  4. About 14%
2 × 4096³ = 1.374 × 10¹¹ FLOPs; ÷ 0.25 × 10⁻³ s = 550 TFLOP/s; ÷ 989 ≈ 0.56. Forgetting the factor of 2 gives 28%. A result over 100% means a timing bug, like the one in the first question. This run would miss L14's 60% exit criterion, so try larger n or check clocks and power limits.

In L8 a judge compares DPO and SFT answers on 200 prompts, once in each order. DPO wins consistently 120 times, SFT wins consistently 50 times, and 30 verdicts flip with the order. Counting flipped verdicts as ties (half a win each), what is DPO's win rate?

  1. 60.0%
  2. 70.6%
  3. 85.0%
  4. 67.5%
(120 + 0.5 × 30) / 200 = 135 / 200 = 67.5%. 60% ignores the ties entirely, 70.6% drops them from the denominator (which hides the judge's indecision), and 85% is the judge's position-consistency rate, (120 + 50) / 200.

Your L7 LoRA scores 0.78 accuracy and the prompted baseline 0.74, both on the same 100 test examples. Have you met the exit criterion?

  1. Yes: a 4-point gain is a clear win
  2. No: a LoRA has to beat prompting by at least 10 points
  3. Not shown yet. Each score's 95% interval is about ±8 points, so run a paired test on per-item results or grow the test set
  4. Yes, provided the training loss went down
SE ≈ √(0.76 × 0.24 / 100) ≈ 0.043, so ±1.96 SE ≈ ±8.4 points per system. A paired comparison over the same items (bootstrap or McNemar) is tighter because both systems face identical questions, but 4 points on 100 items rarely clears it. That's why the lab asks for 200+ test items and a paired interval that excludes zero.
