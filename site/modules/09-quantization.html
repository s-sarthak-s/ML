Quantization: trading bits for speed

An 8B-parameter model takes 16 GB in bf16. At 4 bits it fits in about 4.5 GB and generates roughly three times faster on the same laptop, with output you'd struggle to tell apart. This module explains the bookkeeping behind that and where it breaks.

~2.5 hoursprereqs: 01, 08hands-on: llama.cpp, MLX

By the end you can

  1. Work out a model's memory footprint and decode speed ceiling from its parameter count and bit width.
  2. Read a floating-point bit layout and say why bf16 beat fp16 for training.
  3. Quantize a vector by hand with absmax and zero-point schemes, and predict how an outlier ruins it.
  4. Explain group-wise scales, NF4, GPTQ, AWQ, and what "Q4_K_M" actually means.
  5. Pick a quantization for a given device and task, then measure whether it hurt.

Why quantize at all

A language model's weights are a few billion numbers. Every time the model generates one token, the hardware has to read essentially all of them from memory (Module 08 covers why). So two numbers decide whether a model is usable on a machine:

  1. Does it fit? Weight memory has to fit in GPU memory or unified RAM.
  2. How fast is it? At batch size 1, generation speed is capped by how quickly those bytes can be streamed.

Both scale with bytes per parameter, and quantization is the practice of making that number smaller.

$$\htmlClass{t1}{M_{\text{weights}}} = \htmlClass{t2}{N} \times \frac{\htmlClass{t3}{b}}{8}$$
\(M\)
bytes needed to hold the weights
\(N\)
number of parameters (8B model → \(8\times10^9\))
\(b\)
bits per weight, including any per-group scale overhead

In wordsCount the numbers, multiply by how many bits each one takes, divide by 8 to get bytes.

Why it matters8B × 16 bits = 16 GB. 8B × 4.5 bits = 4.5 GB. That's the difference between needing a server GPU and running on a laptop.

$$\htmlClass{t1}{\text{tokens/s}} \;\lesssim\; \frac{\htmlClass{t2}{B_{\text{mem}}}}{\htmlClass{t3}{M_{\text{weights}}} + \htmlClass{t4}{M_{\text{KV}}}}$$
tokens/s
upper bound on generation speed for one sequence
\(B_{\text{mem}}\)
memory bandwidth, bytes per second (M3 Max ≈ 400 GB/s, H100 ≈ 3.35 TB/s)
\(M_{\text{weights}}\)
bytes of weights read per token
\(M_{\text{KV}}\)
bytes of KV cache read per token (grows with context, Module 08)

In wordsEach token requires streaming every weight once. Halve the bytes and you roughly double the ceiling.

Why it mattersThat's why quantization speeds up generation even though the arithmetic is the same: the bottleneck is moving bytes, not doing multiplies.

Intuition

Picture the weights as a library the model has to read cover to cover for every word it writes. Quantization is printing the same library in a smaller font. Read too small and you start misreading letters.

How computers store numbers

Before compressing numbers, you need to know how they're stored. A floating-point number has three fields, like scientific notation in base 2:

$$x = (-1)^{\htmlClass{t2}{s}} \times 2^{\,\htmlClass{t3}{e} - \htmlClass{t4}{\text{bias}}} \times \left(1 + \frac{\htmlClass{t1}{m}}{2^{\htmlClass{t5}{M}}}\right)$$
\(s\)
sign bit: 0 for positive, 1 for negative
\(e\)
exponent field (unsigned int). More exponent bits = wider range
bias
\(2^{E-1}-1\), so the exponent can be negative (fp32: 127)
\(m\)
mantissa field. More mantissa bits = finer precision
\(M\)
number of mantissa bits (fp32: 23, bf16: 7)

In wordsThe exponent picks which power-of-two "bucket" you're in. The mantissa picks a point inside that bucket, using \(2^M\) evenly spaced slots.

Why it mattersPrecision is relative: gaps between neighbouring values grow with the magnitude. Integers are the opposite, with equal gaps everywhere, so you need a scale factor to use them.

Think first: why does 0.1 look slightly wrong in every format?
0.1 in binary is 0.0001100110011… repeating forever, the same way 1/3 repeats in decimal. Every format cuts it off somewhere, and fewer mantissa bits means an earlier cut. In bf16, 0.1 is stored as 0.10009765625. Your model weights carry rounding like that all the time, and it's mostly harmless because networks tolerate noise.

Integer quantization: scale and zero point

Integers are cheap to store and fast to multiply, but they have a fixed grid: int8 can only say −128…127. To represent a weight like −0.0371, we choose a scale \(s\) and store \(q = \text{round}(x/s)\). To read it back we compute \(\hat{x} = s\cdot q\). The whole game is choosing \(s\) well.

Symmetric (absmax) quantization

$$\htmlClass{t1}{s} = \frac{\max_i |\htmlClass{t2}{x_i}|}{2^{\htmlClass{t3}{b}-1}-1}, \qquad \htmlClass{t4}{q_i} = \text{clamp}\!\left(\text{round}\!\left(\frac{\htmlClass{t2}{x_i}}{\htmlClass{t1}{s}}\right),\, -2^{\htmlClass{t3}{b}-1}+1,\; 2^{\htmlClass{t3}{b}-1}-1\right), \qquad \htmlClass{t5}{\hat{x}_i} = \htmlClass{t1}{s}\cdot \htmlClass{t4}{q_i}$$
\(s\)
scale: real-number size of one integer step. Stored in fp16 alongside the ints
\(x_i\)
original weights in this block
\(b\)
bit width. 8-bit: \(2^7-1=127\) levels each side. 4-bit: 7
\(q_i\)
the stored integer
\(\hat{x}_i\)
dequantized value used at compute time. Error is \(x_i-\hat{x}_i\)

In wordsStretch the integer grid so its end lands exactly on the largest weight, then snap every weight to the nearest grid point.

Why it mattersThe biggest value sets the step size for everyone. One huge outlier makes the steps coarse, and all the small weights round to 0.

Asymmetric (zero-point / affine) quantization

$$\htmlClass{t1}{s} = \frac{\max(\htmlClass{t2}{x}) - \min(\htmlClass{t2}{x})}{2^{\htmlClass{t3}{b}}-1}, \qquad \htmlClass{t6}{z} = \text{round}\!\left(-\frac{\min(\htmlClass{t2}{x})}{\htmlClass{t1}{s}}\right), \qquad \htmlClass{t4}{q_i}=\text{clamp}\!\left(\text{round}\!\left(\tfrac{\htmlClass{t2}{x_i}}{\htmlClass{t1}{s}}\right)+\htmlClass{t6}{z},\,0,\,2^{\htmlClass{t3}{b}}-1\right), \qquad \hat{x}_i = \htmlClass{t1}{s}\,(\htmlClass{t4}{q_i}-\htmlClass{t6}{z})$$
\(s\)
scale: the [min, max] range divided into \(2^b-1\) steps
\(z\)
zero point: which integer represents real 0, which shifts the grid
\(x\)
values in the block
\(b\)
bit width. Uses all \(2^b\) levels, unsigned
\(q_i\)
unsigned stored integer

In wordsInstead of centring the grid on zero, slide it to cover exactly the range the data occupies.

Why it mattersFor lopsided data (activations after ReLU/GELU are mostly positive), absmax wastes half its levels on values that never occur. A zero point recovers them, at the cost of storing \(z\) and doing a subtraction.

Definition · SNR

Signal-to-noise ratio in decibels: \(\text{SNR} = 10\log_{10}\frac{\sum x_i^2}{\sum (x_i-\hat x_i)^2}\). Every extra bit adds about 6 dB, because it halves the step size, and the error power then drops by 4×. Use it as a quick sanity check when you write your own quantizer.

Outliers and granularity

The widget above shows the central problem: one outlier sets the scale for its whole block. Real LLM weights and activations have exactly this problem. A few channels carry values 10–100× larger than the rest. The standard fix is to give smaller blocks their own scales.

Per-tensor

One scale per matrix

Cheapest. A single outlier anywhere ruins precision everywhere. Fine for int8 on well-behaved tensors, bad for 4-bit.

Per-channel

One scale per row

Each output channel gets its own range. The standard for int8 weights. The overhead is negligible: one fp16 per row of thousands.

Per-group

One scale per 32–128 weights

Required for good 4-bit. Outliers only damage their own small group. Costs extra bits: a 16-bit scale per 32 weights is +0.5 bits/weight.

$$\htmlClass{t1}{b_{\text{eff}}} = \htmlClass{t2}{b} + \frac{\htmlClass{t3}{b_s} + \htmlClass{t4}{b_z}}{\htmlClass{t5}{g}}$$
\(b_{\text{eff}}\)
real storage cost per weight
\(b\)
bits for the integer itself (e.g. 4)
\(b_s\)
bits for each group's scale (fp16 → 16)
\(b_z\)
bits for each group's zero point or min (0 if symmetric)
\(g\)
group size: how many weights share one scale

In wordsSmaller groups give better accuracy but more metadata. 4-bit with an fp16 scale and bias per 64 weights (MLX's default) costs 4 + 32/64 = 4.5 bits.

Activation outliers: LLM.int8() and SmoothQuant

Weights are easy because they're fixed, so you can inspect them offline. Activations change with every input, and in models above a few billion parameters, a handful of hidden dimensions systematically produce huge values (Dettmers et al., 2022). Two classic responses:

  • LLM.int8() splits the matmul. The few outlier columns run in fp16 and the remaining 99.9% run in int8. Accurate, but the split slows it down.
  • SmoothQuant moves the difficulty from activations to weights with an exact rescaling. Divide each activation channel by \(s_j\) and multiply the matching weight row by \(s_j\), and the product is unchanged.
$$\mathbf{Y} = \big(\htmlClass{t1}{\mathbf{X}}\,\mathrm{diag}(\htmlClass{t2}{\mathbf{s}})^{-1}\big)\big(\mathrm{diag}(\htmlClass{t2}{\mathbf{s}})\,\htmlClass{t3}{\mathbf{W}}\big), \qquad \htmlClass{t2}{s_j} = \frac{\max|\htmlClass{t1}{\mathbf{X}_j}|^{\htmlClass{t4}{\alpha}}}{\max|\htmlClass{t3}{\mathbf{W}_j}|^{1-\htmlClass{t4}{\alpha}}}$$
\(\mathbf{X}\)
activations; column \(j\) may be an outlier channel
\(s_j\)
per-channel smoothing factor
\(\mathbf{W}\)
weights; row \(j\) absorbs the scale
\(\alpha\)
migration strength, typically 0.5: split the difficulty evenly

In wordsMathematically a no-op, but it flattens the spiky activations so both sides quantize cleanly to int8.

Smarter quantizers: NF4, GPTQ, AWQ

Rounding each weight to its nearest grid point ("round-to-nearest", RTN) is the baseline. Everything in this section tries to beat it at the same bit budget, either with a smarter grid or by choosing roundings that cancel each other's error.

NF4: put the levels where the weights are

Trained weights are roughly normally distributed: lots near zero, few in the tails. A uniform int4 grid spends as many levels on the empty tails as on the crowded centre. NormalFloat-4 (from the QLoRA paper) places its 16 levels at quantiles of a normal distribution, so each level gets about the same share of weights.

GPTQ: let later columns fix earlier mistakes

RTN treats every weight independently. But what matters isn't the error in the weights, it's the error in the layer's output on real inputs. GPTQ (Frantar et al., 2022) solves that problem, one layer at a time:

$$\htmlClass{t1}{\widehat{\mathbf{W}}} = \arg\min_{\widehat{\mathbf{W}} \in \text{grid}} \big\lVert \htmlClass{t2}{\mathbf{W}}\htmlClass{t3}{\mathbf{X}} - \htmlClass{t1}{\widehat{\mathbf{W}}}\htmlClass{t3}{\mathbf{X}} \big\rVert_F^2, \qquad \htmlClass{t4}{\mathbf{H}} = 2\,\htmlClass{t3}{\mathbf{X}}\htmlClass{t3}{\mathbf{X}}^{\top}$$
\(\widehat{\mathbf{W}}\)
quantized weights, restricted to representable values
\(\mathbf{W}\)
original full-precision layer weights
\(\mathbf{X}\)
layer inputs collected from a few hundred calibration samples
\(\mathbf{H}\)
Hessian of that loss: which input directions the output is sensitive to

In wordsMake the quantized layer produce the same outputs as the original on realistic inputs, even if individual weights end up farther from their originals.

AWQ: protect the weights that matter

Activation-aware Weight Quantization (Lin et al., 2023) observes that roughly 1% of weight channels matter far more than the rest: the ones multiplied by large activations. Instead of keeping them in fp16 (awkward for kernels), AWQ scales those channels up before quantizing and scales the matching activations down, the same trick as SmoothQuant. The salient weights then get relatively finer steps. AWQ needs no backprop and only a small calibration set, which makes it fast and robust.

Calibration caveat

GPTQ and AWQ fit to calibration data. If you calibrate on generic English web text and then deploy on code or another language, you may lose more quality than RTN would have. Calibrate on data that looks like your workload.

Weight-only vs weights + activations

W4A16 · weight-only

Shrink storage, compute in 16-bit

Weights are dequantized on the fly inside the kernel, then multiplied in bf16/fp16. Big win for decode, which is bandwidth-bound. Little or no win for prefill, which is compute-bound, and the dequant overhead can even slow it down.

W8A8 · weights + activations

Do the math in low precision too

Both operands in int8/fp8, using low-precision tensor cores at roughly 2× the bf16 throughput. Helps compute-bound workloads such as prefill and large-batch serving. Needs activation-outlier handling (SmoothQuant, per-token scales).

MLE angle · KV cache quantization

At long contexts the KV cache can outgrow the weights (Module 08: about 128 KB/token for Llama-3-8B in fp16, so 1 GB per 8K tokens). Quantizing the cache to 8-bit halves that, and engines expose it as a flag (vLLM --kv-cache-dtype fp8, llama.cpp --cache-type-k q8_0). Keys tend to have channel outliers, so they're more sensitive than values.

Measuring the damage

Never trust "4-bit is fine" blindly. Measure it on your model and task. Three levels of evidence, from cheapest to most meaningful:

  1. Perplexity on held-out text (Module 03). Cheap and sensitive, but small perplexity changes don't map cleanly to task quality.
  2. KL divergence to the full-precision model: run both on the same text and measure how far the quantized next-token distribution drifts. llama-perplexity --kl-divergence does exactly this. It's better than perplexity because it catches changes that average out.
  3. Task evals: your real prompts, scored the same way you score production (Module 13). Reasoning, math, code, and long context usually degrade first.
The rule that surprises people

At a fixed memory budget, a larger model at 4-bit usually beats a smaller model at 16-bit. A 14B model at Q4 (~8.5 GB) generally outperforms a 4B model in bf16 (~8 GB). Parameters carry more capability than the last few bits of precision.

Post-training vs quantization-aware training

Everything so far has been post-training quantization (PTQ): train in high precision, compress afterwards. Quantization-aware training (QAT) simulates quantization during training (or a short fine-tune), so the weights settle into spots that survive rounding. Google's QAT releases of Gemma and the MXFP4-native gpt-oss models work this way.

$$\text{forward: } \htmlClass{t1}{\hat{w}} = s\cdot\text{round}(\htmlClass{t2}{w}/s) \qquad\quad \text{backward: } \frac{\partial \mathcal{L}}{\partial \htmlClass{t2}{w}} \approx \frac{\partial \mathcal{L}}{\partial \htmlClass{t1}{\hat{w}}}$$
\(\hat{w}\)
"fake-quantized" weight used in the forward pass
\(w\)
latent full-precision weight that the optimizer actually updates

In wordsRounding has zero gradient almost everywhere, which would stop learning cold. So we pretend it's the identity function on the way back and pass the gradient straight through.

Why it mattersThis hack is how every QAT method and every binary or ternary network (e.g. BitNet) trains at all.

Choosing a quantization

Hands-on

1. Write your own group-wise quantizer (do this first)

Thirty lines of NumPy will teach you more than any paper. Then try group sizes 32/64/128/full row and bit widths 8/4/3/2 on a real weight matrix, and check that the SNR changes match what the widgets above predict.


import numpy as np

def quantize_groupwise(w, bits=4, group=64):
    """Symmetric absmax quantization with one fp16 scale per group."""
    rows, cols = w.shape
    assert cols % group == 0
    g = w.reshape(rows, cols // group, group)            # (rows, n_groups, group)
    qmax = 2 ** (bits - 1) - 1                            # 7 for int4
    scale = np.abs(g).max(axis=-1, keepdims=True) / qmax  # one scale per group
    scale = np.where(scale == 0, 1e-8, scale).astype(np.float16)
    q = np.clip(np.round(g / scale), -qmax, qmax).astype(np.int8)
    return q, scale

def dequantize(q, scale, shape):
    return (q.astype(np.float32) * scale.astype(np.float32)).reshape(shape)

def snr_db(w, w_hat):
    return 10 * np.log10((w ** 2).sum() / ((w - w_hat) ** 2).sum())

rng = np.random.default_rng(0)
w = rng.normal(0, 0.02, size=(4096, 4096)).astype(np.float32)
w[:, 7] *= 40                                             # inject an outlier channel

for group in (32, 64, 128, 4096):
    q, s = quantize_groupwise(w, bits=4, group=group)
    eff_bits = 4 + 16 / group
    print(f"group={group:5d}  bits/wt={eff_bits:.3f}  SNR={snr_db(w, dequantize(q, s, w.shape)):.1f} dB")

A 70B model in Q4_K_M (~4.8 bits/weight). Roughly how much memory do the weights need?

  1. ~17.5 GB
  2. ~35 GB
  3. ~42 GB
  4. ~140 GB
70×10⁹ × 4.8 / 8 ≈ 42×10⁹ bytes ≈ 39 GiB. 35 GB would be exactly 4.0 bits with no scale overhead. 140 GB is bf16.

Why did bf16 replace fp16 as the default training format?

  1. It has more mantissa bits, so it's more precise
  2. It has fp32's exponent range, so gradients don't overflow or underflow
  3. It uses less memory than fp16
  4. GPUs can't multiply fp16
bf16 has 8 exponent bits like fp32 but only 7 mantissa bits, so it's less precise than fp16 (10). Range turned out to matter more for training stability, and it removes the need for loss scaling.

You absmax-quantize a block of 64 weights to int4. One weight is 30× larger than the others. What happens?

  1. The outlier gets clipped and everything else is fine
  2. Nothing, int4 has enough levels
  3. The outlier is stored with high error
  4. The scale becomes huge, so most small weights round to 0
Absmax sets the scale from the largest value, so the outlier is represented almost exactly and everyone else loses resolution. That's why group size and outlier handling matter so much at 4 bits.

Weight-only int4 quantization makes token generation (decode) much faster but barely changes prompt processing (prefill). Why?

  1. Decode is memory-bandwidth-bound; prefill is compute-bound and still multiplies in 16-bit
  2. Prefill doesn't use the weights
  3. Prefill weights are cached in fp32
  4. int4 is only supported during decode
Decode reads every weight for one token, so fewer bytes means faster. Prefill processes thousands of tokens per weight read, so arithmetic dominates, and W4A16 kernels still do that arithmetic in bf16, plus dequant overhead.

What does GPTQ optimize that plain round-to-nearest ignores?

  1. The number of bits per weight
  2. The size of the calibration set
  3. The error in the layer's outputs on real inputs, letting later weights compensate for earlier rounding
  4. The training loss on the full dataset
GPTQ minimizes ‖WX − ŴX‖² using second-order (Hessian) information from calibration activations. When one column is rounded, the remaining columns are adjusted to cancel the error.
