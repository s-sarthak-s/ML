A live formula card

Here's the first one. Move your pointer over the coloured symbols.

$$\htmlClass{t4}{s} = \htmlClass{t1}{\mathbf{a}} \cdot \htmlClass{t2}{\mathbf{b}} = \sum_{i=1}^{\htmlClass{t3}{d}} \htmlClass{t1}{a_i}\,\htmlClass{t2}{b_i}$$
\(s\)
the result: a single number (a scalar)
\(\mathbf{a}, a_i\)
first vector (bold), and its \(i\)-th entry (plain, with a subscript)
\(\mathbf{b}, b_i\)
second vector, same length as \(\mathbf{a}\)
\(d\)
length of each vector. Llama-3-8B's hidden vectors have \(d = 4096\)

In wordsMultiply the two lists entry by entry and add up the products. The \(\Sigma\) is just a for-loop that sums.

Why it mattersAttention scores, embedding similarity, and every matrix multiplication are dot products. A matmul of an \([m, k]\) matrix by a \([k, n]\) matrix is \(m \cdot n\) dot products of length \(k\), which is where most of a model's compute goes.

Think first: how many arithmetic operations is one dot product of two 4096-long vectors?
4096 multiplies and 4095 additions, so about \(2d = 8192\) floating-point operations (FLOPs). Hold on to that factor of 2: one multiply and one add per pair. Section 3 turns it into the rule that a forward pass costs about 2 FLOPs per parameter per token.

The one mental model: bytes and FLOPs per token

When a model generates text, it produces one token at a time. For each token the hardware does two kinds of work. It moves bytes: every weight has to travel from memory to the compute units, along with the cached keys and values of every earlier token. And it does arithmetic: roughly one multiply and one add per weight. Whichever of the two takes longer sets the speed.

Four formulas cover most of the sizing questions you'll be asked: will it fit, how fast will it go, and what happens when the context gets long or the batch gets big. Learn these by heart. The rest of the course explains where each one comes from and when it bends.

$$\htmlClass{t1}{M_{\text{w}}} = \htmlClass{t2}{N} \times \frac{\htmlClass{t3}{b}}{8}$$
\(M_{\text{w}}\)
bytes needed to hold the weights
\(N\)
number of parameters (Llama-3-8B: \(8.03 \times 10^9\))
\(b\)
bits per weight: 16 for bf16, about 4.5 to 4.9 for common 4-bit formats once scales are counted (Module 09)

In wordsCount the numbers, multiply by bits per number, divide by 8 bits per byte.

Why it mattersThis is the first question for any model on any device: do the weights fit at all? An 8B model is 16 GB in bf16 and under 5 GB at 4 bits.

$$\htmlClass{t1}{C_{\text{fwd}}} \approx 2\,\htmlClass{t2}{N} \;+\; 4\,\htmlClass{t3}{L}\,\htmlClass{t4}{T}\,\htmlClass{t5}{d}$$
\(C_{\text{fwd}}\)
floating-point operations to push one token through the model
\(N\)
parameters used in matrix multiplies: one multiply and one add each, hence the 2
\(L\)
number of transformer layers (Llama-3-8B: 32)
\(T\)
how many tokens are already in the context
\(d\)
attention width, the number of query heads × head size (4096 for Llama-3-8B)

In wordsAbout two FLOPs per parameter, plus an attention term for comparing the new token against every earlier one. The attention term only catches up with \(2N\) once \(T \approx N/(2Ld)\): about 30,000 tokens for Llama-3-8B.

Why it mattersTraining costs about three times the forward pass (forward plus a backward pass that is roughly twice as expensive), which gives the famous \(6ND\) of Module 07. This form comes from Kaplan et al. (2020).

$$\htmlClass{t1}{m_{\text{KV}}} = \htmlClass{t6}{2} \cdot \htmlClass{t2}{L} \cdot \htmlClass{t3}{n_{\text{kv}}} \cdot \htmlClass{t4}{d_{\text{head}}} \cdot \htmlClass{t5}{\beta}$$
\(m_{\text{KV}}\)
bytes of cache added for each token in the context
\(2\)
one key vector and one value vector
\(L\)
layers: every layer keeps its own cache
\(n_{\text{kv}}\)
number of key/value heads. With grouped-query attention this is smaller than the query-head count (Llama-3-8B: 8 KV heads serve 32 query heads)
\(d_{\text{head}}\)
size of each head (usually 128)
\(\beta\)
bytes per number in the cache: 2 for bf16, 1 for 8-bit

In wordsFor each token, every layer stores a key and a value for every KV head. Multiply by context length \(T\) and batch size \(B\) to get the whole cache: \(M_{\text{KV}} = m_{\text{KV}}\, T\, B\).

Why it mattersWeights are a fixed cost. The cache grows with every token and every concurrent user, and at long context or high batch it becomes the larger of the two.

$$\htmlClass{t1}{\text{tok/s}} \;\lesssim\; \frac{\htmlClass{t2}{\text{BW}}}{\htmlClass{t3}{M_{\text{w}}} + \htmlClass{t4}{T}\cdot\htmlClass{t5}{m_{\text{KV}}}}$$
tok/s
upper bound on generation speed for a single sequence
\(\text{BW}\)
memory bandwidth in bytes per second (M4 Max: 546 GB/s; H100 SXM: 3.35 TB/s)
\(M_{\text{w}}\)
weight bytes, all read once per generated token
\(T\)
current context length in tokens
\(m_{\text{KV}}\)
cache bytes per token, also read in full every step

In wordsEach new token requires streaming every weight and the whole cache through the chip once. You can't go faster than the memory can deliver them.

Why it mattersIt explains three things people find surprising: why 4-bit models generate faster even though the arithmetic isn't cheaper, why a Mac with lots of bandwidth keeps up with some GPUs, and why batching is nearly free at first (the weights read for one step serve every sequence in the batch).

Worked example: Llama-3-8B

Config: 32 layers, 32 query heads, 8 KV heads, head size 128, hidden size 4096, \(8.03\times10^9\) parameters. Here is the whole napkin.

Weights, Q4_K_M (~4.85 bits)\(8.03\times10^9 \times 4.85/8\)4.9 GB

At batch 1 in bf16, decoding does about 2 FLOPs for every 2 bytes it reads: one FLOP per byte. An H100 can do roughly 295 FLOPs in the time it takes to read one byte. So single-stream decode leaves more than 99% of the arithmetic idle, and the whole speed question turns into a memory question. Prefill, where hundreds of prompt tokens share each weight read, is the opposite: it's limited by compute. Module 08 draws this as a roofline.

Think first: Llama-2-7B has the same 32 layers and head size 128, but 32 KV heads (no grouped-query attention). How much KV cache per token?
\(2 \times 32 \times 32 \times 128 \times 2 = 524{,}288\) bytes, which is 512 KiB per token, four times Llama-3-8B. At 8K context that's 4 GiB for a single conversation, a quarter of the weights. Grouped-query attention (Ainslie et al., 2023), covered in Modules 06 and 08, was adopted largely to shrink this number. Select Llama-2-7B in the calculator and watch the KV bar.
Caveats you'll meet later

Mixture-of-experts models break the "one N" assumption. Mixtral 8x7B stores about 47B parameters but each token only passes through about 13B of them. Use the total for memory and the active count for FLOPs and for bytes read per token. Units: this course writes GB for \(10^9\) bytes and GiB for \(2^{30}\). The 7% difference stops being a rounding error at 70B scale. Ceilings are ceilings: as a rule of thumb, well-tuned engines reach roughly 60–85% of the bandwidth bound at batch 1, never all of it.

Intuition

Think of the weights as a long book the model must read cover to cover for every word it writes, with the KV cache as its notes on the conversation so far. Generation speed is reading speed. Quantization prints the book in a smaller font (Module 09). Batching lets one reading serve many writers at once (Module 08). Long context makes the notes thicker than the book.

Life of a request

Here's what happens between pressing enter and seeing the first word, with the module that explains each stage. Every later module zooms into one box.

  1. Tokenize (05). The text becomes a list of integer ids, using a vocabulary learned with byte-pair encoding. "The capital of France is" is about five tokens. Llama 3's vocabulary has 128,256 entries.
  2. Embed (05). Each id selects one row of an embedding matrix, giving a vector of size \(d\). The prompt is now a \([T, d]\) array: the start of the residual stream.
  3. Transform, \(L\) times (06). Each block normalizes the stream, runs attention (which lets positions read from each other) and adds the result back, then does the same with an MLP that works on each position separately. The stream keeps its shape \([T, d]\) all the way up.
  4. Unembed (05, 06). A final norm and one more matrix turn the last position's vector into logits: one score for every token in the vocabulary.
  5. Softmax and sample (03, 08). Softmax turns scores into probabilities. A sampler picks one, greedily or with temperature and top-p.
  6. Detokenize and loop (05, 08). The id is turned back into text and streamed to you. It's also appended to the input, and the stack runs again for one token, reading the cache for everything before it.
Think first: why does the first token usually take noticeably longer than each one after it?
The first token has to wait for prefill: the whole prompt must pass through every layer, filling the KV cache, before the model can score anything. A 2,000-token prompt is about 2,000 times the arithmetic of one decode step, though it runs efficiently because it's one big batch of matmuls. After that, each step processes just one new token. Serving dashboards report the two separately: time to first token (TTFT) and time per output token (TPOT), Module 13.
MLE angle · where the time goes

When someone says "the model is slow", ask which half. Slow TTFT with a long prompt is a compute problem: shorter prompts, prefix caching, a faster GPU. Slow tokens after the first is a bandwidth problem: smaller weights (09), a smaller KV cache (08), better batching, or speculative decoding. They need different fixes, and mixing them up is the most common sizing mistake.

Pitfall · row vs column vectors

Papers often write \(\mathbf{y} = \mathbf{W}\mathbf{x}\) with \(\mathbf{x}\) as a column. PyTorch stores a batch as rows and computes y = x @ W.T inside nn.Linear, whose weight has shape [out, in]. Same math, transposed bookkeeping. When a shape error appears, write the shapes next to each operand before changing any code.

Shapes are the fastest way to catch bugs and the fastest way to estimate memory. The widget follows one attention layer (standard multi-head attention, every head with its own K and V) from token ids to output.

How to study to get really good

Build one habit above all others: never run an experiment without first writing down what you expect. A wrong prediction points straight at the broken piece of your mental model, and a right one tells you which formula you can trust next time.

Build it from scratch, once

Using a library and understanding it are different skills. For each core idea, write a small version yourself, in plain NumPy or PyTorch, usually under 150 lines: a BPE tokenizer (05), attention from raw matmuls checked against torch.nn.functional.scaled_dot_product_attention (06), a KV cache that makes generation faster (08), a group-wise quantizer (09), a LoRA layer (10), BM25 plus vector search with reciprocal-rank fusion (11), an agent loop with two tools (12). Then go back to the production library and read how it does the same thing. Andrej Karpathy's Zero to Hero series is the best-known model of this approach.

A weekly rhythm

Keep one page per week: what you predicted, what you measured, and the one-sentence explanation of the difference. After twelve weeks you have a notebook of real numbers from your own hardware, which beats any blog post when you need to size a deployment.

Your first predict → measure

Do this today. Look up your machine's memory bandwidth, predict the decode ceiling for a 0.5B model with the calculator above, then measure it. Expect to land well below the ceiling with plain transformers. A model this small is limited by per-step Python and kernel-launch overhead, not bandwidth. Explaining that gap is your first lab.


import time
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

name = "Qwen/Qwen2.5-0.5B-Instruct"
device = "cuda" if torch.cuda.is_available() else "mps" if torch.backends.mps.is_available() else "cpu"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name, dtype=torch.bfloat16).to(device)  # older transformers: torch_dtype=

n = sum(p.numel() for p in model.parameters())
print(f"{n / 1e9:.2f}B params -> {2 * n / 1e9:.2f} GB of bf16 weights read per token")

inputs = tok("The capital of France is", return_tensors="pt").to(device)
model.generate(**inputs, max_new_tokens=8)  # warm-up: the first call pays one-off costs

t0 = time.perf_counter()
out = model.generate(**inputs, max_new_tokens=128, min_new_tokens=128, do_sample=False)
dt = time.perf_counter() - t0
new = out.shape[1] - inputs["input_ids"].shape[1]
print(f"measured: {new / dt:.1f} tok/s")
print(tok.decode(out[0, inputs["input_ids"].shape[1]:], skip_special_tokens=True))

Llama-3-8B stores 128 KiB of KV cache per token in bf16. How much cache does one 32,768-token conversation need?

  1. ~1 GiB
  2. ~4 GiB
  3. ~16 GiB
  4. ~32 GiB
128 KiB × 32,768 = 4,194,304 KiB = 4 GiB. That's a quarter of the bf16 weights for a single user, and it scales linearly with batch size: 16 such conversations need 64 GiB of cache.

A 14B-parameter model is quantized to 4.5 bits per weight. Roughly how much memory do the weights take?

  1. ~3.5 GB
  2. ~14 GB
  3. ~7.9 GB
  4. ~28 GB
14 × 10⁹ × 4.5 / 8 = 7.9 × 10⁹ bytes. 28 GB would be bf16 and 14 GB would be 8-bit. A useful shortcut: at 16 bits it's 2 bytes per parameter, at 8 bits it's 1, at about 4.5 bits it's a little over half a byte.

A laptop with 400 GB/s of memory bandwidth runs an 8B model in bf16 at short context, batch 1. What's the decode-speed ceiling?

  1. ~250 tok/s
  2. ~50 tok/s
  3. ~2.5 tok/s
  4. ~25 tok/s
Each token reads all 16 GB of weights: 400 / 16 = 25 tok/s. The 50 tok/s option forgets that bf16 is 2 bytes per parameter. A 4-bit version (~4.9 GB) would raise the ceiling to about 80 tok/s.

Roughly how many FLOPs does one forward pass of a dense 70B model cost per token at short context?

  1. ~140 GFLOP
  2. ~70 GFLOP
  3. ~420 GFLOP
  4. ~1.4 TFLOP
2 FLOPs per parameter (one multiply, one add): 2 × 70 × 10⁹ = 1.4 × 10¹¹. 420 GFLOP is the 6N cost of a training step per token (forward plus backward).

Batch 2, 32 heads, 4,096 tokens, bf16. If one attention layer materializes the full score tensor \([B, h, T, T]\), how big is it?

  1. ~32 MiB
  2. ~256 MiB
  3. ~2 GiB
  4. ~64 GiB
2 × 32 × 4,096 × 4,096 = 2³⁰ elements × 2 bytes = 2 GiB, for one layer. This quadratic term is why FlashAttention (Dao et al., 2022) computes attention in tiles and never stores the full matrix.

On one GPU at short context, going from batch 1 to batch 16 raises total decode throughput almost 16×. Why?

  1. The GPU raises its clock speed under load
  2. Decode is bandwidth-bound, and the weights read for one step are shared by all 16 sequences, so the step takes about as long as before
  3. Batching reduces the number of FLOPs per token
  4. The KV cache is shared between the requests
At batch 1 the chip does about 1 FLOP per byte read and the arithmetic units sit idle. Sixteen sequences reuse each weight 16 times per read, so step time barely moves until the cache reads add up or compute becomes the limit. Each request still has its own KV cache; that's what eventually caps the batch.
