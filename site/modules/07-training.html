Module 07 · Running models

Training LLMs: where the FLOPs go

GPT-3 took about 3×10²³ floating-point operations to train. Llama 3 405B took about 4×10²⁵, most of it on 16,384 H100s running for roughly two months. This module shows where numbers like that come from, how a model too big for any single GPU gets split across thousands of them, and the few formulas that let you price a training run before you launch it.

By the end you can

  1. Estimate the FLOPs, GPU-hours, wall-clock time and rough cost of a training run from its parameter count and token count.
  2. Use the Chinchilla scaling law to pick a compute-optimal model size, and explain why most shipped models train far past that point.
  3. Budget per-GPU training memory (16 bytes per parameter plus activations) and choose a ZeRO/FSDP stage that fits.
  4. Explain data, tensor, pipeline and context parallelism: what each one splits, what it sends over the wire, and how big the pipeline bubble is.
  5. Write a bf16 training loop with AdamW, warmup plus cosine decay, gradient clipping and accumulation, then launch it on many GPUs with torchrun and FSDP.

The pretraining objective

Pretraining has one job: given some text, predict the next token. You take trillions of tokens of text, show the model each prefix, and nudge its weights so the token that actually came next gets a higher probability. There's no labelling step. The text supervises itself, which is why the dataset can be the size of a large fraction of the public web.

Module 03 introduced cross-entropy. Here it is applied to a whole sequence at once:

$$\htmlClass{t1}{\mathcal{L}(\theta)} = -\frac{1}{\htmlClass{t2}{T}}\sum_{t=1}^{\htmlClass{t2}{T}} \log \htmlClass{t5}{p_\theta}\big(\htmlClass{t3}{x_t} \mid \htmlClass{t4}{x_{\lt t}}\big)$$
\(\mathcal{L}(\theta)\)
average loss in nats per token for weights \(\theta\); training minimizes its average over the corpus
\(T\)
number of token positions in the sequence (e.g. 8,192)
\(x_t\)
the token that actually appears at position \(t\), the "label"
\(x_{\lt t}\)
every token before position \(t\), the context the model is allowed to see
\(p_\theta\)
the model's softmax output: a probability for every token in the vocabulary

In wordsAt every position, look up how much probability the model gave to the real next token, take the log, flip the sign, and average. A model that always assigns probability 1 to the right token scores 0.

Why it mattersCausal masking (Module 06) lets one forward pass over a sequence of length \(T\) produce \(T\) predictions at once. Every token in the corpus is a training example, and nothing is wasted on padding if sequences are packed.

Two reference points make the number readable. A model that guesses uniformly over a 128K vocabulary has loss \(\ln 128{,}000 \approx 11.8\) nats. Good open models get to roughly 1.5–2 nats on typical web text. The whole training run is the journey between those two numbers, and scaling laws (below) predict how far along it a given budget gets you.

Think first: loss falls from 11.8 to 2.0. Is the model six times better?
Not in any useful sense. Loss is a log scale: 2.0 nats means the model gives the right token an average (geometric-mean) probability of \(e^{-2}\approx 0.14\), which is a perplexity of about 7.4 (Module 03). 11.8 nats is a perplexity of 128,000. The last few tenths of a nat are where capabilities like arithmetic and instruction following tend to show up, which is why labs spend enormous compute to shave them.

The data pipeline

Before any GPU spins up, someone has to turn the raw web into training tokens. Most quality differences between open models of the same size trace back to this step. Common Crawl publishes billions of pages per monthly snapshot; most of it is boilerplate, spam, duplicates, or text in languages you don't want. The pipeline is a long funnel of filters.

Some details matter more than they look:

  • Extraction decides what counts as the page. Navigation menus, cookie banners and comment sections become training text if you don't strip them.
  • Quality filtering used to be hand-written rules (Gopher's rules: drop pages with too few words, too many symbols, lines that don't end in punctuation). Modern pipelines add a small classifier. FineWeb-Edu trained one on Llama-3-70B ratings of "educational value"; DCLM used a fastText classifier. Both gave large benchmark gains at the same token count.
  • Deduplication matters because the web repeats itself. Memorized boilerplate wastes compute and raises the risk of regurgitating training data verbatim.
  • Packing concatenates documents with an end-of-sequence token between them and cuts the stream into fixed windows (say 8,192 tokens), so no compute is spent on padding. Llama 3 also masked attention so tokens can't attend across a document boundary inside a window.
Definition · MinHash near-duplicate detection

Represent each document as its set of word 5-grams. The Jaccard similarity \(s\) of two sets is |overlap| / |union|. MinHash compresses each set into a short signature such that two signatures agree in any one position with probability exactly \(s\). Split a signature into \(b\) bands of \(r\) hashes; two documents become a duplicate candidate if any band matches completely, which happens with probability \(1-(1-s^r)^b\). With 14 bands of 8 (FineWeb's setup), a pair at \(s=0.75\) is caught about 77% of the time, at \(s=0.9\) more than 99.9%, at \(s=0.5\) only about 5%. That S-shaped curve is the point: one pass over billions of documents, no pairwise comparisons.

MLE angle · data mixtures

The final corpus isn't just web text. Labs mix web, code, math, papers, books and multilingual data in tuned proportions, and often upsample the best sources for a few epochs. Llama 3's paper reports roughly half general knowledge, a quarter math and reasoning, 17% code and 8% multilingual tokens. Choosing the mixture is usually done with small proxy models trained on candidate mixes, which is a cheap application of scaling laws.

Anatomy of a training step

One optimizer step is the same five beats repeated hundreds of thousands of times. With data parallelism, every GPU holds a copy of the model and processes a different slice of the batch, and they only talk once per step, to agree on the gradient.

  1. Forward. Run the batch through every layer, keeping the intermediate activations because backward will need them.
  2. Loss. Cross-entropy between the logits and the shifted tokens.
  3. Backward. Backprop (Module 04) produces one gradient number per weight.
  4. All-reduce. Sum gradients across replicas and divide by their count. NCCL does this over NVLink inside a node and InfiniBand or RoCE between nodes.
  5. Optimizer step. AdamW updates its moment estimates and the weights. Then zero the gradients and start again.

A ring all-reduce sends and receives \(2(G-1)/G\) times the gradient size per GPU, so the per-GPU traffic barely changes as you add GPUs. For an 8B model with bf16 gradients that's about 2 × 16 GB = 32 GB per step. At a realistic 50 GB/s per GPU across nodes that would be well over half a second if done serially, which is why PyTorch DDP and FSDP split gradients into buckets and start reducing the last layers while backward is still computing the first ones.

Training compute: C ≈ 6ND

The single most useful formula in this module. Almost all of a transformer's arithmetic is matrix multiplication, and a matmul that touches a weight once per token does one multiply and one add with it. So the forward pass costs about 2 FLOPs per parameter per token.

$$\htmlClass{t1}{C} \;\approx\; (\htmlClass{t4}{2} + \htmlClass{t5}{4})\,\htmlClass{t2}{N}\,\htmlClass{t3}{D} \;=\; 6ND$$
\(C\)
total training compute in FLOPs (floating-point operations, not per second)
\(N\)
number of parameters (non-embedding, strictly; the difference is small for big models)
\(D\)
number of training tokens processed
\(2\)
forward pass: one multiply and one add per weight per token
\(4\)
backward pass: gradients with respect to activations (2) and with respect to weights (2)

In wordsEvery token touches every weight six times' worth of arithmetic: twice going forward, four times coming back.

Why it mattersGPT-3 (175B params, 300B tokens): 6 × 1.75×10¹¹ × 3×10¹¹ ≈ 3.15×10²³ FLOPs, matching the paper. Llama 3 405B (15.6T tokens): ≈ 3.8×10²⁵, matching Meta's report. Two numbers give you the bill.

Think first: why is backward exactly twice the forward?
Take one linear layer \(y = Wx\) with \(W\) of shape \(m\times n\). Forward costs \(2mn\) FLOPs per token. Backward has to produce two things: the gradient for the previous layer, \(\partial L/\partial x = W^\top \partial L/\partial y\), which is another \(2mn\), and the gradient for the weights, \(\partial L/\partial W = (\partial L/\partial y)\,x^\top\), another \(2mn\). Two matmuls the size of the forward one, so 4N. Embedding lookups and elementwise ops are cheap enough to ignore.

6ND leaves out attention's score computation, which grows with context length. Kaplan et al. (2020) count it as an extra \(6\,n_{\text{layer}}\,n_{\text{ctx}}\,d_{\text{model}}\) FLOPs per training token. For an 8B model at 8K context that's around 13% on top of 6N before accounting for causal masking (which lets FlashAttention skip roughly half of it). It matters for long-context training; for back-of-envelope budgeting, 6ND is enough.

Model FLOPs utilization (MFU)

A GPU's spec sheet number is the peak. Real training never gets there: time goes to memory traffic, communication, non-matmul kernels, data loading and pipeline bubbles. MFU (Chowdhery et al., 2022, the PaLM paper) measures how much of the peak you actually turn into model progress.

$$\htmlClass{t1}{\text{MFU}} = \frac{6\,\htmlClass{t2}{N}\cdot \htmlClass{t3}{\tau}}{\htmlClass{t4}{n_{\text{gpu}}}\cdot \htmlClass{t5}{P_{\text{peak}}}} \qquad\Longrightarrow\qquad \text{wall-clock} = \frac{6ND}{\htmlClass{t4}{n_{\text{gpu}}}\cdot \htmlClass{t5}{P_{\text{peak}}}\cdot \htmlClass{t1}{\text{MFU}}}$$
MFU
fraction of peak spent on the 6N model FLOPs; 35–50% is good for large dense models
\(N\)
parameter count
\(\tau\)
measured training throughput, tokens per second for the whole job
\(n_{\text{gpu}}\)
number of GPUs
\(P_{\text{peak}}\)
peak dense FLOP/s per GPU at the training dtype: A100 312 T, H100 SXM ≈ 989 T (bf16)

In wordsTake the FLOPs the model strictly needed for the tokens you processed, divide by what the hardware could have done in that time.

Why it mattersRecomputing activations (see memory section) makes the GPU do 8N per token instead of 6N. That extra work counts toward hardware FLOPs utilization (HFU) but not MFU, which is why MFU is the honest number for comparing setups. PaLM reported 46% MFU; Llama 3 405B reported 38–43%.

Pitfall · quoting sparse peak numbers

NVIDIA spec sheets often lead with "with sparsity" figures (H100: ~1,979 TFLOP/s bf16), which assume 2:4 structured sparsity that dense LLM training doesn't use. Divide by two. FP8 peaks are about twice bf16 again, but only the matmuls you actually run in FP8 get that speed.

Scaling laws

Given a compute budget \(C\), you still have a choice: a big model on fewer tokens, or a small model on many. Scaling laws are empirical fits that predict the loss for each choice, made by training dozens to hundreds of small models and extrapolating.

Kaplan et al. (2020)

OpenAI's first scaling-law paper found loss falls as a smooth power law in each resource when the others aren't the bottleneck: roughly \(L \propto N^{-0.076}\) in parameters and \(L \propto D^{-0.095}\) in tokens, over seven orders of magnitude. Their compute-optimal recipe put most extra compute into parameters (\(N_{\text{opt}} \propto C^{0.73}\)) and recommended stopping well before convergence. GPT-3's 175B parameters on only 300B tokens (1.7 tokens per parameter) followed this advice.

Chinchilla (Hoffmann et al., 2022)

DeepMind trained over 400 models from 70M to 16B parameters on 5B to 500B tokens, with the learning-rate schedule matched to each run's length (Kaplan's runs used one schedule length, which made shorter runs look worse than they were). Their third fitting approach models loss as an irreducible floor plus one penalty for being too small and one for seeing too little data:

$$\htmlClass{t1}{L(N, D)} = \htmlClass{t2}{E} + \htmlClass{t3}{\frac{A}{N^{\alpha}}} + \htmlClass{t4}{\frac{B}{D^{\beta}}}, \qquad E=1.69,\; A=406.4,\; B=410.7,\; \alpha=0.34,\; \beta=0.28$$
\(L(N,D)\)
predicted pretraining loss (nats/token on their data) for \(N\) params trained on \(D\) tokens
\(E\)
irreducible loss: the entropy of text itself, which no model can beat
\(A/N^{\alpha}\)
capacity penalty: a finite model can't represent the true distribution; shrinks as \(N\) grows
\(B/D^{\beta}\)
data penalty: finite training can't fully fit even the model you have; shrinks as \(D\) grows

In wordsLoss is a floor plus two terms that decay as power laws, one in model size and one in data. Spend compute on whichever term is currently bigger.

Why it mattersGopher (280B params, 300B tokens) and Chinchilla (70B, 1.4T tokens) used about the same compute. Chinchilla, four times smaller, beat Gopher on most benchmarks. Most models of that era were too big for their data.

Substitute \(D = C/6N\) and minimize over \(N\). Setting the derivative to zero gives \(\alpha A/N^\alpha = \beta B / D^\beta\): at the optimum, the marginal loss reduction per FLOP is the same in both directions. Solving:

$$\htmlClass{t1}{N_{\text{opt}}} = \htmlClass{t4}{G}\left(\frac{\htmlClass{t3}{C}}{6}\right)^{\frac{\beta}{\alpha+\beta}}, \qquad \htmlClass{t2}{D_{\text{opt}}} = \htmlClass{t4}{G}^{-1}\left(\frac{\htmlClass{t3}{C}}{6}\right)^{\frac{\alpha}{\alpha+\beta}}, \qquad \htmlClass{t4}{G} = \left(\frac{\alpha A}{\beta B}\right)^{\frac{1}{\alpha+\beta}}$$
\(N_{\text{opt}}\)
loss-minimizing parameter count for budget \(C\)
\(D_{\text{opt}}\)
matching token count; \(6N_{\text{opt}}D_{\text{opt}} = C\)
\(C\)
compute budget in FLOPs
\(G\)
constant from the fit (≈ 1.35 with the published values)

In wordsWith the published fit the exponents are 0.45 and 0.55, both close to ½: ten times more compute should buy about 2.8× more parameters and 3.5× more tokens. Chinchilla's other two fitting methods gave almost exactly ½ and ½, which is where the famous rule of thumb comes from: about 20 tokens per parameter.

Caveat · the published fit and "20 tokens per parameter" disagree

Run the widget with the published constants and the optimum lands at 30–120 tokens per parameter depending on budget, not 20. Besiroglu et al. (2024) reconstructed the data from the paper's figures and found the published Approach-3 fit doesn't match it well; their refit (\(E=1.82, A=482, B=2085, \alpha=0.35, \beta=0.37\)) gives about 20 tokens per parameter, agreeing with Chinchilla's other two methods. Toggle the fit to compare. The practical lesson survives either way: the valley is flat. At \(10^{21}\) FLOPs, the 20N model and the fit-optimal one differ by under 0.01 nats.

Why modern small models are "overtrained"

Chinchilla answers one question: what's the lowest loss for a fixed training budget? A company shipping a model asks a different one: what's the cheapest model that's good enough, counting every token it will ever generate? Inference costs about \(2N\) FLOPs per generated token, forever. A smaller model trained on more data costs more to train than it "should" but less every time someone uses it (Sardana et al., 2023, "Beyond Chinchilla-Optimal").

Llama 3 8B was trained on about 15T tokens: roughly 1,900 tokens per parameter, almost 100× the Chinchilla ratio. Training compute: 6 × 8×10⁹ × 1.5×10¹³ ≈ 7.2×10²³ FLOPs. The 20N rule would spend that budget on a ~77B model with 1.5T tokens. Plug both into the published fit and you get predicted losses of about 1.95 for the 8B and 1.93 for the 77B. Giving up roughly 0.02–0.05 nats (depending on which fit you trust) buys a model that's nearly ten times cheaper to serve per token and fits on a single consumer GPU. Llama 3.2's 1B and 3B went further still, at up to 9T tokens.

Intuition

Chinchilla-optimal is the cheapest way to reach a loss. Overtraining is paying extra in the factory to make a product that's cheaper to run. Whenever inference volume is large, the second trade wins. Note too that these fits are extrapolated far beyond the token ratios they were measured at, so treat the exact losses as illustrative.

Training memory

Inference needs the weights (2 bytes per parameter in bf16) plus a KV cache. Training needs far more, because it also stores gradients, optimizer state and activations. The weights turn out to be the small part.

$$\htmlClass{t1}{M_{\text{state}}} = \htmlClass{t2}{N}\times\big(\htmlClass{t3}{2} + \htmlClass{t4}{2} + \htmlClass{t5}{4} + \htmlClass{t6}{4 + 4}\big) = 16N \text{ bytes}$$
\(M_{\text{state}}\)
bytes for everything that persists between steps
\(N\)
parameter count
2
bf16 copy of the weights used in forward and backward
2
bf16 gradients
4
fp32 master weights, the copy the optimizer actually updates
4 + 4
Adam's first moment \(m\) and second moment \(v\), both fp32

In wordsSixteen bytes per parameter before a single activation is stored. Twelve of them belong to the optimizer.

Why it mattersA 7B model needs 7×10⁹ × 16 = 112 GB of state. That doesn't fit on one 80 GB GPU even with zero activations, which is why full fine-tuning a 7B model needs sharding (or LoRA, Module 10). Setups that keep gradients in fp32 for accumulation use 18 bytes; FSDP with fp32 sharded parameters and bf16 compute copies works out to about 16.

Activations

Backward needs the intermediate values from forward: attention inputs, MLP hidden states, normalization inputs. Those scale with tokens in flight, not with parameters. Korthikanti et al. (2022) count them for a GPT-style block in 16-bit:

$$\htmlClass{t1}{M_{\text{act}}} \approx 34 \cdot \htmlClass{t2}{s}\cdot \htmlClass{t3}{b}\cdot \htmlClass{t4}{h}\cdot \htmlClass{t5}{L} \text{ bytes}$$
\(M_{\text{act}}\)
activation bytes held for the backward pass, per GPU, no tensor parallelism
\(s\)
sequence length in tokens
\(b\)
micro-batch size (sequences per forward pass)
\(h\)
hidden size \(d_{\text{model}}\)
\(L\)
number of layers

In wordsAbout 34 bytes per hidden unit per token per layer. The paper's full formula has an extra term that grows with \(s^2\) for the attention matrix; FlashAttention never materializes that matrix, so it drops out. Modern SwiGLU blocks differ somewhat, so treat this as an order-of-magnitude estimate.

Why it mattersLlama-3-8B shape (32 layers, \(h = 4096\)) at 4,096 tokens: 34 × 4096 × 4096 × 32 ≈ 18 GB for a single sequence. Activations easily rival model state.

Activation checkpointing (also called gradient checkpointing or rematerialization) trades compute for memory. Keep only each layer's input during forward, throw away everything inside, and recompute the layer's forward pass during backward when its internals are needed. Memory drops to about \(2sbhL\) bytes plus one layer's full working set. The price is an extra forward pass: about 8N FLOPs per token instead of 6N, so roughly 33% more compute. Selective checkpointing recomputes only the cheap-but-large parts (attention softmax, activation functions) and gets most of the saving for a few percent of compute.

Mixed precision

Module 09 covered the formats. The training recipe that uses them: do the expensive matmuls in a 16-bit format, at 2× or more the throughput and half the memory traffic of fp32, while keeping the numerically delicate parts in fp32.

Why keep an fp32 master copy at all? bf16 has only 8 bits of precision. Near 1.0, neighbouring bf16 values are \(2^{-7}\approx 0.0078\) apart. A typical update \(\eta\,\hat g\) of \(10^{-4}\) to a weight of 1.0 is less than half a step, so it rounds away to nothing. Do that for every weight on every step and training silently stalls. In fp32 the gap near 1.0 is about \(10^{-7}\), so small updates accumulate.

bf16 · the default

Same range as fp32

8 exponent bits, so gradients don't underflow. Wrap the forward pass in torch.autocast(dtype=torch.bfloat16), keep parameters and optimizer in fp32, and that's it. Supported on A100, H100, TPUs and recent consumer GPUs.

fp16 · needs loss scaling

Narrow range, extra bookkeeping

Max 65,504 and small gradients flush to zero. Multiply the loss by a scale \(S\) (PyTorch's GradScaler starts at \(2^{16}\)), so gradients are \(S\times\) larger; unscale before clipping; skip the step and halve \(S\) on inf/NaN; double \(S\) after 2,000 clean steps.

FP8 training goes one step further on H100 and newer hardware: matmul inputs in FP8 (E4M3 for weights and activations, often E5M2 for gradients) with fine-grained scaling factors, everything else in bf16/fp32. DeepSeek-V3 (DeepSeek-AI, 2024) was trained this way at scale. It's real but fiddlier; bf16 remains the safe default.

Data parallelism, ZeRO and FSDP

Plain data parallelism (PyTorch DDP) replicates everything: weights, gradients, optimizer state. It scales throughput but not model size. Every GPU still needs all 16N bytes. The ZeRO paper (Rajbhandari et al., 2020) noticed that this replication is pure waste: each GPU only needs the full optimizer state for the parameters it's responsible for updating. Shard the states across the \(G\) data-parallel GPUs and gather pieces only when needed.

$$\htmlClass{t1}{M_{\text{GPU}}} = \frac{2\htmlClass{t2}{N}}{\htmlClass{t3}{G_w}} + \frac{2\htmlClass{t2}{N}}{\htmlClass{t4}{G_g}} + \frac{12\htmlClass{t2}{N}}{\htmlClass{t5}{G_o}}$$
\(M_{\text{GPU}}\)
model-state bytes on each GPU (activations not included)
\(N\)
parameter count
\(G_w\)
\(G\) if weights are sharded (stage 3), else 1
\(G_g\)
\(G\) if gradients are sharded (stage 2+), else 1
\(G_o\)
\(G\) if optimizer state is sharded (stage 1+), else 1

In wordsEach stage divides one more term by the number of GPUs. At stage 3, a 70B model's 1.12 TB of state spread over 64 GPUs is 17.5 GB each.

Why it mattersPyTorch's FSDP is ZeRO-3 (its SHARD_GRAD_OP mode is ZeRO-2). DeepSpeed exposes all stages plus CPU/NVMe offload. In practice: try DDP if it fits, else FSDP, and add tensor or pipeline parallelism only when FSDP alone stops scaling.

ZeRO-3 / FSDP works layer by layer. Before a layer's forward, all-gather its full weights from the shards, compute, then free them. Backward does the same again, then reduce-scatters the gradients so each GPU ends up with only its shard's summed gradient, and updates only its shard. Prefetching the next layer's all-gather while the current one computes hides most of the cost, as long as layers are big enough relative to network bandwidth.

Pitfall · ZeRO doesn't shard activations

All ZeRO stages divide model state. Activations stay per-GPU because each GPU processes its own micro-batch. If activations are your problem (long sequences, big micro-batches), sharding more aggressively won't help. Activation checkpointing, smaller micro-batches with gradient accumulation, or sequence/context parallelism will.

Model parallelism: tensor, pipeline, context

FSDP shards storage, but each GPU still runs every layer on its full micro-batch. At the largest scales that hits limits: the global batch gets too big to train well, all-gathers stop hiding behind compute, and a single sequence's activations overflow memory. The next tools split the computation itself.

Tensor parallelism

Megatron-LM (Shoeybi et al., 2019) splits individual weight matrices across GPUs. The trick is pairing a column split with a row split so the two matmuls of an MLP need only one communication between them.

Tensor parallelism communicates inside every layer, twice per layer in forward and twice in backward, with activation-sized messages. That's only affordable over NVLink, so TP is almost always confined to the 8 GPUs of one node. It also splits activation memory across the TP group, which FSDP can't do.

Pipeline parallelism

Pipeline parallelism splits the model by depth: GPU 0 holds layers 1–20, GPU 1 holds 21–40, and so on. Only activations cross stage boundaries, point-to-point, which tolerates slower inter-node links. The catch is idle time. With one batch, stage 3 waits while stages 0–2 run forward, and stage 0 waits while the gradients travel back. Splitting the batch into \(m\) micro-batches lets stages work on different micro-batches at once (GPipe; Huang et al., 2019).

$$\htmlClass{t1}{\text{bubble}} = \frac{\htmlClass{t2}{p} - 1}{\htmlClass{t3}{m} + \htmlClass{t2}{p} - 1}$$
bubble
fraction of total step time a stage sits idle
\(p\)
number of pipeline stages
\(m\)
number of micro-batches per optimizer step

In wordsFilling and draining the pipeline costs \(p-1\) slots of idle time per stage, out of \(m + p - 1\) total. Keep \(m\) several times larger than \(p\).

Why it matters\(p = 8\), \(m = 8\): 47% idle. \(m = 32\): 18%. But more micro-batches means a bigger global batch. Some papers write the bubble as \((p-1)/m\), relative to useful compute rather than total time; same physics.

GPipe runs all forwards, then all backwards, so stage 0 holds activations for all \(m\) micro-batches at once. The 1F1B schedule (PipeDream-Flush; Narayanan et al., 2021) starts each micro-batch's backward as soon as possible, alternating one forward with one backward. The bubble is identical, but stage \(i\) holds at most \(p-i\) micro-batches of activations instead of \(m\). Interleaved schedules (several small stages per GPU) and zero-bubble schedules shrink the bubble further at the cost of more communication.

Sequence and context parallelism

Two different things share similar names. Sequence parallelism (Korthikanti et al., 2022) is a companion to tensor parallelism: the layer norms and dropouts that TP leaves replicated get split along the sequence dimension instead, removing the remaining duplicated activations. Context parallelism splits one long sequence across GPUs for the whole layer, including attention. Each GPU keeps its chunk of queries, and key/value blocks rotate around a ring of GPUs so every query sees every key (Ring Attention; Liu et al., 2023). It's how 128K–1M-token training fits: Llama 3 used it for its long-context stage.

Batch size, schedules and stability

Batch size

The quantity that matters is tokens per optimizer step: \(B_{\text{tokens}} = b_{\text{micro}} \times k_{\text{accum}} \times G_{\text{DP}} \times s\). For example 1 sequence × 16 accumulation steps × 128 replicas × 8,192 tokens ≈ 16.8M tokens. Gradient accumulation lets a single GPU emulate a large batch by running several micro-batches before stepping.

Bigger batches give less noisy gradients, but past a critical batch size (McCandlish et al., 2018) the extra noise reduction stops buying faster progress per token, and you're just burning compute. The critical size grows as loss falls, which is why runs often ramp the batch up: GPT-3 used 3.2M tokens per batch for 175B; Llama 3 405B started at 4M tokens and grew to 16M.

Learning-rate schedule

Nearly every LLM uses AdamW (β₁ = 0.9, β₂ = 0.95, weight decay 0.1 are common choices) with a schedule: a short linear warmup from near zero, then a decay. Warmup matters because Adam's second-moment estimate \(v\) starts at zero and is unreliable for the first few hundred steps, so large early updates can blow the model up.

$$\htmlClass{t1}{\eta_t} = \htmlClass{t3}{\eta_{\min}} + \tfrac{1}{2}\big(\htmlClass{t2}{\eta_{\max}} - \htmlClass{t3}{\eta_{\min}}\big)\left(1 + \cos\!\left(\pi\,\frac{t - \htmlClass{t4}{t_w}}{\htmlClass{t5}{T} - \htmlClass{t4}{t_w}}\right)\right), \qquad t \ge t_w$$
\(\eta_t\)
learning rate at step \(t\)
\(\eta_{\max}\)
peak learning rate, smaller for bigger models (GPT-3: 6×10⁻⁴ at 125M, 0.6×10⁻⁴ at 175B)
\(\eta_{\min}\)
floor, often 10% of peak
\(t_w\)
warmup steps (hundreds to a few thousand); before \(t_w\), \(\eta_t = \eta_{\max}\, t/t_w\)
\(T\)
total steps, fixed in advance

In wordsRamp up, then glide down along half a cosine wave to the floor exactly at the last step.

Why it mattersCosine forces you to choose \(T\) up front; stopping early leaves the model at a high learning rate and a worse loss. Warmup-stable-decay (WSD) schedules hold the peak flat and decay only in the last 10–20%, so you can branch a decay off any checkpoint. That's convenient for scaling-law sweeps and for extending a run.

Training stability

Large runs sometimes show loss spikes: the loss jumps sharply, then either recovers or diverges. Common culprits are attention logits growing until softmax saturates, output logits drifting to huge magnitudes, a bad batch, or simply a learning rate too high for the current scale. A diverged run at 10,000 GPUs costs real money, so the standard recipe stacks several defences:

  • Gradient clipping: if the global gradient norm exceeds \(c\) (usually 1.0), scale it down, \(g \leftarrow g\cdot\min(1, c/\lVert g\rVert)\). Log the pre-clip norm; a rising trend often precedes a spike.
  • QK-norm: apply RMSNorm to queries and keys per head before the dot product, which bounds attention logits (Dehghani et al., 2023; used in OLMo 2 and Gemma 3).
  • Lower β₂: 0.95 instead of Adam's default 0.999 lets the second moment react faster when gradient scale shifts.
  • Rewind and skip: PaLM's response to a spike was to restart from a checkpoint about 100 steps earlier and skip a few hundred batches around it.
$$\mathcal{L}_{z} = \htmlClass{t1}{\lambda}\,\log^2 \htmlClass{t2}{Z}, \qquad \htmlClass{t2}{Z} = \sum_{i} e^{\htmlClass{t3}{z_i}}$$
\(\lambda\)
small coefficient; PaLM used \(10^{-4}\)

In wordsSoftmax doesn't care if you add a constant to every logit, so logits can drift upward without changing the loss until bf16 runs out of precision. This auxiliary term pulls \(\log Z\) toward 0 and keeps logits anchored.

Checkpoints, evals, and what comes after

Checkpointing

At this scale hardware fails constantly. Llama 3's report counted 466 job interruptions in a 54-day window, 419 of them unexpected, mostly GPU and host failures: about one every three hours. So the job saves checkpoints regularly and restarts from the last one. A full checkpoint is model plus optimizer state: about 16 bytes per parameter, roughly 6.5 TB for 405B. Each rank writes its own shards in parallel (torch.distributed.checkpoint), often asynchronously so training continues while files flush to storage.

How often? A classic approximation (Young, 1974) sets the interval near \(\sqrt{2\,\delta\, M}\), where \(\delta\) is the time to write a checkpoint and \(M\) the mean time between failures. With \(\delta = 2\) minutes and \(M = 3\) hours, that's about 27 minutes. Checkpoint more often and you waste time writing; less often and each failure throws away more work.

Evals during training

Training loss alone can mislead: it's on data the model is currently seeing, and a data-mixture change moves it for reasons unrelated to quality. Runs track held-out loss per domain (web, code, math, each language), plus cheap downstream evals every few thousand steps, typically multiple-choice tasks scored by comparing log-probabilities, since a base model can't follow instructions yet. Sudden drops in one domain's held-out loss, or a gradient-norm spike, are what wake someone up at 3 a.m.

MLE angle · read a loss curve like a pro

A healthy curve falls fast, then follows a smooth power law on a log-log plot. Plateaus that break suddenly often mean a learning-rate or data-ordering issue. Steady upward drift in gradient norm means instability is coming. A sharp drop near the end of a cosine or WSD schedule is normal: that's the decay phase cashing in. When comparing runs, compare at equal tokens, not equal steps.

After pretraining

The pretrained base model is a superb text predictor and a poor assistant. A few more phases turn it into a product:

  1. Mid-training (annealing). Continue pretraining while the LR decays, on upsampled high-quality data: math, code, curated documents, and long documents to extend context. Llama 3 stretched its context from 8K to 128K in stages over roughly 800B tokens.
  2. Supervised fine-tuning (SFT). Train on prompt/response pairs so the model follows instructions and uses a chat template.
  3. Preference tuning and RL. RLHF, DPO, and RL with verifiable rewards (GRPO and relatives) shape helpfulness, safety and reasoning.

These phases use a tiny fraction of pretraining compute but change behaviour enormously. Module 10 covers them in depth, including LoRA, which sidesteps most of this module's memory problems.

Hands-on

1. A minimal single-GPU training loop

Everything from this module in one file: packed token windows, bf16 autocast over fp32 weights, AdamW with decoupled weight decay on matrices only, warmup plus cosine, gradient accumulation, clipping, and an MFU readout. Use a small config (e.g. Llama-3.2-1B's shape, randomly initialized) on a single 24–80 GB GPU.


import math, time
import numpy as np
import torch
import torch.nn.functional as F
from transformers import AutoConfig, AutoModelForCausalLM

torch.manual_seed(0)
device = "cuda"
torch.backends.cuda.matmul.allow_tf32 = True

# --- data: one long stream of token ids (docs joined with EOS), memory-mapped
tokens = np.memmap("train.bin", dtype=np.uint32, mode="r")   # uint32: vocab is 128K
seq_len, micro_bs, accum_steps = 2048, 4, 8                 # 64K tokens per optimizer step

def get_batch():
    ix = torch.randint(len(tokens) - seq_len - 1, (micro_bs,))
    buf = torch.stack([torch.from_numpy(tokens[i:i + seq_len + 1].astype(np.int64)) for i in ix])
    buf = buf.pin_memory().to(device, non_blocking=True)
    return buf[:, :-1], buf[:, 1:]                           # inputs, next-token targets

# --- model: architecture only, random init, fp32 master weights
config = AutoConfig.from_pretrained("meta-llama/Llama-3.2-1B")
model = AutoModelForCausalLM.from_config(config).to(device)
model.gradient_checkpointing_enable(                          # trade ~33% compute for memory
    gradient_checkpointing_kwargs={"use_reentrant": False})
n_params = sum(p.numel() for p in model.parameters())

# --- AdamW: decay matrices, not norms/biases
decay = [p for p in model.parameters() if p.dim() >= 2]
no_decay = [p for p in model.parameters() if p.dim() < 2]
opt = torch.optim.AdamW(
    [{"params": decay, "weight_decay": 0.1}, {"params": no_decay, "weight_decay": 0.0}],
    lr=3e-4, betas=(0.9, 0.95), eps=1e-8, fused=True)

# --- warmup + cosine to 10% of peak
total_steps, warmup, min_ratio = 20_000, 1_000, 0.1
def lr_lambda(step):
    if step < warmup:
        return (step + 1) / warmup
    progress = (step - warmup) / max(1, total_steps - warmup)
    return min_ratio + (1 - min_ratio) * 0.5 * (1 + math.cos(math.pi * progress))
sched = torch.optim.lr_scheduler.LambdaLR(opt, lr_lambda)

model.train()
for step in range(total_steps):
    t0 = time.time()
    for _ in range(accum_steps):
        x, y = get_batch()
        with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
            logits = model(input_ids=x).logits
        # loss in fp32; divide so accumulated grads equal the mean over the big batch
        loss = F.cross_entropy(logits.float().view(-1, logits.size(-1)), y.reshape(-1))
        (loss / accum_steps).backward()
    gnorm = torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
    opt.step()
    sched.step()
    opt.zero_grad(set_to_none=True)

    if step % 50 == 0:
        torch.cuda.synchronize()
        dt = time.time() - t0
        tok_s = micro_bs * seq_len * accum_steps / dt
        mfu = 6 * n_params * tok_s / 989e12                   # H100 bf16 dense peak; 312e12 for A100
        print(f"step {step} loss {loss.item():.3f} gnorm {gnorm:.2f} "
              f"lr {sched.get_last_lr()[0]:.2e} {tok_s:,.0f} tok/s MFU {mfu:.1%}")
Notes on the loop

The MFU printed here uses 6N, so with gradient checkpointing on it under-reports how busy the GPU is (the hardware does about 8N). logits.float() for a 128K vocabulary is about 1 GB per 2K-token sequence; fused or chunked cross-entropy kernels avoid materializing it. Add model = torch.compile(model) once everything works for a typical 10–30% speedup.

2. Many GPUs with torchrun and FSDP

The same loop, sharded with FSDP2's fully_shard (PyTorch 2.6+). Each transformer block becomes its own shard unit, so only one block's full weights are ever gathered at once. The mixed-precision policy replaces autocast: sharded parameters stay in fp32, are all-gathered in bf16 for compute, and gradients are reduced in fp32.


import os
import torch
import torch.distributed as dist
import torch.distributed.checkpoint as dcp
import torch.nn.functional as F
from torch.distributed.fsdp import fully_shard, MixedPrecisionPolicy
from torch.distributed.checkpoint.state_dict import get_state_dict
from transformers import AutoConfig, AutoModelForCausalLM
from data import get_batch                 # train.py's memmap get_batch(), moved into data.py

total_steps = 20_000
dist.init_process_group("nccl")
rank, world = dist.get_rank(), dist.get_world_size()
local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)

torch.manual_seed(0)                       # same init on every rank before sharding
config = AutoConfig.from_pretrained("meta-llama/Llama-3.1-8B")
with torch.device("cuda"):                 # 8B fp32 = 32 GB, fits before sharding on 80 GB GPUs;
    model = AutoModelForCausalLM.from_config(config)   # beyond ~13B, build on "meta" and init shards
model.gradient_checkpointing_enable(gradient_checkpointing_kwargs={"use_reentrant": False})

mp = MixedPrecisionPolicy(param_dtype=torch.bfloat16, reduce_dtype=torch.float32)
for block in model.model.layers:           # one FSDP unit per transformer block
    fully_shard(block, mp_policy=mp)
fully_shard(model, mp_policy=mp)           # root: embeddings, final norm, lm_head

opt = torch.optim.AdamW(model.parameters(), lr=3e-4, betas=(0.9, 0.95), weight_decay=0.1)
torch.manual_seed(1234 + rank)             # different data on every rank

for step in range(total_steps):
    x, y = get_batch()                     # each rank samples its own windows
    logits = model(input_ids=x).logits     # FSDP casts params to bf16; no autocast needed
    loss = F.cross_entropy(logits.float().view(-1, logits.size(-1)), y.reshape(-1))
    loss.backward()                        # grads reduce-scattered to their owning shard
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    opt.step()
    opt.zero_grad(set_to_none=True)

    if step % 1000 == 0:                   # every rank writes its own shards in parallel
        msd, osd = get_state_dict(model, opt)
        dcp.save({"model": msd, "optim": osd}, checkpoint_id=f"ckpt/step{step:07d}")

dist.destroy_process_group()

You want to fully fine-tune a 7B model with AdamW in bf16 mixed precision. How much memory does the model state alone (weights, gradients, master copy, Adam moments) need?

16 bytes/param × 7×10⁹ = 112 GB: 2 (bf16 weights) + 2 (bf16 grads) + 4 (fp32 master) + 4 + 4 (Adam m, v). 14 GB is just the bf16 weights, what inference needs. It won't fit on one 80 GB GPU before you even count activations.

  4. About 112 GB
Stage 2 shards gradients and optimizer state but keeps full bf16 weights: 2N + (2 + 12)N/8 = 14 + 12.25 ≈ 26 GB. Stage 3 would shard the weights too: 112/8 = 14 GB.

  1. 1B tokens, about 6 × 10¹⁸ FLOPs
  2. 2T tokens, about 1.2 × 10²² FLOPs

  1. About 3%
  2. About 18%

  4. About 88%
(p − 1)/(m + p − 1) = 7/39 ≈ 18%. With only 8 micro-batches it would be 7/15 ≈ 47%. Switching GPipe to 1F1B doesn't change this number; it reduces activation memory.

Why does fp16 training need loss scaling while bf16 training usually doesn't?

  1. bf16 has more mantissa bits, so it's more precise
  2. bf16 gradients are computed in fp32 automatically
  3. fp16's 5-bit exponent can't represent very small gradients, so they flush to zero unless scaled up
  4. fp16 can't be used on tensor cores
bf16 shares fp32's 8-bit exponent and covers the same range; it's actually less precise than fp16 (7 vs 10 mantissa bits). fp16's smallest normal value is about 6×10⁻⁵, and many gradients are smaller, so you multiply the loss by a large S, then unscale before the update.
