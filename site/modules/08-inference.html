Module 08 · Running models

Inference: where the context lives

When you send a prompt, the model reads all of it in one parallel pass. Then it writes the answer one token at a time, streaming its entire set of weights through the chip for every single token. Serving speed, cost, and the real limits of a "128K context window" all follow from those two phases and from one data structure most users never see: the KV cache, which is what context physically is.

Two phases: prefill and decode

Send a model a 2,000-token prompt and ask for a 500-token answer. The server handles that request in two phases that load the hardware in opposite ways. Nearly every optimization in this module targets one of them.

  1. Prefill. All 2,000 prompt tokens are known up front. The causal mask says position \(t\) may only look at positions \(\le t\), and every one of those is already available, so the model computes all positions in a single forward pass. Each weight matrix gets multiplied by a [2000 × 4096] block of activations: a matrix–matrix product, which is what GPUs are built for. The pass produces two things. The logits at the last position give the first output token. The keys and values for every prompt position in every layer get stored as the KV cache.
  2. Decode. Output token 2 depends on output token 1, which didn't exist until a moment ago. So the remaining 499 tokens come out one per forward pass. Each pass pushes a single position through the network, which turns every weight multiply into a matrix–vector product: read each weight from memory, do two FLOPs with it, move on.
Definition · Context window

The maximum number of token positions, prompt plus generated output, that one sequence can hold. Two separate things cap it: the positions the model was trained (or extended) to handle, and the memory available for its KV cache. The first is a property of the model. The second is a property of your server and of how many other requests are sharing it right now.

The autoregressive loop

A language model is a function from a token sequence to a probability distribution over the next token (Module 03). The probability of a whole sequence factorizes into those next-token predictions:

$$p(\htmlClass{t1}{x_1}, \dots, \htmlClass{t1}{x_n}) = \prod_{t=1}^{n} p_{\htmlClass{t2}{\theta}}\big(\htmlClass{t1}{x_t} \mid \htmlClass{t3}{x_{\lt t}}\big)$$
\(x_t\)
the token at position \(t\)
\(\theta\)
the model's weights, fixed during inference
\(x_{\lt t}\)
everything before position \(t\): the prompt plus every token generated so far

In wordsPredict one token from everything before it, append it, and predict again. A full answer is a chain of single-token decisions.

Why it mattersBecause each factor conditions on the previous output, generation is inherently sequential. You can't compute token 300 before token 299 exists. That one fact is why decode can't be parallelized across output positions the way prefill is across prompt positions.

The model never drafts the whole answer and then types it out. Any "plan" has to live in the tokens it has already written and in the hidden states that produced them. That's also why asking a model to think step by step before answering works at all: the reasoning tokens become context for the answer tokens.

Think first: prefill of a 2,000-token prompt takes 0.2 s. Roughly how long will 2,000 output tokens take?
Much longer, typically tens of times longer. Prefill handled all 2,000 positions in one pass and was limited by arithmetic. Decode needs 2,000 sequential passes, each limited by how fast the weights can be read. If one decode step takes 25 ms, that's 50 seconds. It's the main reason output tokens are priced higher than input tokens on API price sheets.

The KV cache: what context physically is

Recall attention from Module 06. In each layer, the newest token forms a query \(q\), scores it against the keys \(k_1, \dots, k_t\) of every earlier position, and takes a weighted average of their values \(v_1, \dots, v_t\). Past keys and values never change. Token 7's key depends only on tokens 1–7, and the causal mask guarantees nothing later can alter it. So compute each position's K and V once, per layer, and keep them.

Without that cache, every decode step would push the entire sequence back through every weight matrix just to get the one new row of K and V it actually needs.

$$\htmlClass{t1}{W_{\text{no cache}}} = \sum_{t=0}^{\htmlClass{t3}{n}-1} (\htmlClass{t2}{P} + t) = \htmlClass{t3}{n}\htmlClass{t2}{P} + \frac{\htmlClass{t3}{n}(\htmlClass{t3}{n}-1)}{2} \qquad \text{vs} \qquad \htmlClass{t4}{W_{\text{cache}}} = \htmlClass{t2}{P} + \htmlClass{t3}{n} - 1$$
\(W_{\text{no cache}}\)
token-positions pushed through the weight matmuls when every step recomputes the whole sequence
\(P\)
prompt length in tokens
\(n\)
number of tokens to generate
\(W_{\text{cache}}\)
the same count with a cache: the prompt once, then one new position per remaining step

In wordsWithout a cache, step \(t\) re-processes all \(P+t\) tokens seen so far. With one, each step processes only the token it just added.

Why it matters\(P = 1000\), \(n = 500\): 624,750 position-passes without a cache vs 1,499 with one, about 417× less matmul work. Attention still reads every cached position each step, but reading is far cheaper than recomputing.

That's all a KV cache is: in every layer, two tensors that gain one row per token. Its size is easy to compute from a model's config file, and it decides how many users fit on a GPU before memory runs out.

$$\htmlClass{t1}{M_{\text{KV}}} = 2 \cdot \htmlClass{t2}{L} \cdot \htmlClass{t3}{n_{\text{kv}}} \cdot \htmlClass{t4}{d_{\text{head}}} \cdot \htmlClass{t5}{b} \cdot \htmlClass{t6}{T} \cdot \htmlClass{t7}{B}$$
\(M_{\text{KV}}\)
bytes of KV cache. The leading 2 counts one key tensor and one value tensor
\(L\)
number of transformer layers (num_hidden_layers). Every layer keeps its own cache
\(n_{\text{kv}}\)
number of key/value heads (num_key_value_heads), often fewer than query heads (next section)
\(d_{\text{head}}\)
dimension of each head, usually 128 (head_dim, or hidden_size / num_attention_heads)
\(b\)
bytes per stored element: 2 for bf16/fp16, 1 for fp8 or int8
\(T\)
tokens held in the sequence so far: prompt plus generated
\(B\)
batch size: number of sequences resident at once. Each has its own cache

In wordsEvery token, in every layer, leaves behind one key vector and one value vector per KV head. Count them and multiply by their size.

Why it mattersWeights are a fixed cost you pay once per server. KV is paid per token, per user. At long contexts or high concurrency it becomes the larger bill.

Worked example, Llama-3-8B. \(L = 32\), \(n_{\text{kv}} = 8\), \(d_{\text{head}} = 128\), bf16 so \(b = 2\). Per token: \(2 \times 32 \times 8 \times 128 \times 2 = 131{,}072\) bytes \(= 128\) KiB. An 8,192-token conversation holds \(8192 \times 128\) KiB \(= 1\) GiB of cache. At Llama 3.1's full 128K context, that's 16 GiB for one sequence, more than the model's 15 GiB of bf16 weights.

Intuition · context is working memory, not storage

When a chat app says your conversation is "in context", this is what it means: for Llama-3-8B, about 12 GiB of tensors per 100K tokens, sitting in GPU memory and read in full on every new token. A long context isn't a filing cabinet the model glances into; it's a stack of paper the model reads cover to cover before writing each word.

Deep cut · positions are baked into the cache

Modern models apply RoPE to keys before caching them, so each cached key carries its absolute position. You can't drop a chunk from the middle of a conversation and slide the rest down without re-rotating those keys (llama.cpp's context shift does exactly that) or recomputing them. It's also why a cached prefix only helps if it really is a prefix: same tokens, at the same positions.

Pitfall · budgeting a GPU by weights alone

A 24 GB card holds Llama-3-8B's 15 GiB of bf16 weights and leaves about 8 GiB. That's at most 64K tokens of KV cache, shared by all concurrent users, before activations and framework overhead take their share. Set the server's max context and concurrency from that number, or it will refuse to start, or start preempting requests under load.

Sharing heads: MHA, MQA, GQA

The \(n_{\text{kv}}\) term in the formula is where architecture choices pay off. In the original multi-head attention (MHA), each of the \(H\) query heads has its own key and value head, so \(n_{\text{kv}} = H\). Shazeer (2019) noticed that decode spends most of its time loading K and V and proposed multi-query attention (MQA): keep \(H\) query heads, but let them all share a single K/V head. The cache shrinks by \(H\times\), with some quality loss and occasional training instability.

Grouped-query attention (GQA; Ainslie et al., 2023) sits in between: query heads are split into groups, and each group shares one K/V head. The paper reported quality close to MHA at speed close to MQA, and showed that an existing MHA checkpoint can be converted by "uptraining" with about 5% of its original pretraining compute. Llama 3, Mistral 7B, Qwen2.5, and Gemma 2 all use it.

$$\htmlClass{t1}{r} = \frac{\htmlClass{t2}{n_{\text{heads}}}}{\htmlClass{t3}{n_{\text{kv}}}}, \qquad \htmlClass{t4}{M_{\text{KV}}^{\text{GQA}}} = \frac{\htmlClass{t5}{M_{\text{KV}}^{\text{MHA}}}}{\htmlClass{t1}{r}}$$
\(r\)
group size: how many query heads share each K/V head
\(n_{\text{heads}}\)
number of query heads (num_attention_heads)
\(n_{\text{kv}}\)
number of K/V heads. MHA: \(n_{\text{kv}} = n_{\text{heads}}\). MQA: \(n_{\text{kv}} = 1\)
\(M_{\text{KV}}^{\text{GQA}}\)
KV cache size with grouped heads
\(M_{\text{KV}}^{\text{MHA}}\)
what the cache would be if every query head had its own K/V

In wordsIf \(r\) query heads read the same keys and values, you only have to store one copy for the group.

Why it mattersLlama-3-70B has 64 query heads and 8 KV heads, so \(r = 8\). Its cache is 320 KiB/token. With full MHA it would be 2.5 MiB/token, and a single 32K-token conversation would need 80 GiB, a whole H100 just for one user's cache.

GQA has a second benefit that shows up on the roofline in the next section. During decode, every K/V byte loaded from memory now serves \(r\) query heads, so attention does \(r\) times more math per byte loaded. DeepSeek-V2 (2024) goes further with multi-head latent attention (MLA): it caches one compressed latent vector per token per layer and reconstructs keys and values from it, which shrinks the cache well below what GQA achieves.

Arithmetic intensity and the roofline

Every chip has two speed limits: how many FLOPs per second it can do, and how many bytes per second it can pull from its main memory. A kernel runs into whichever limit it reaches first. To know which one, count how much math the kernel does per byte it moves.

Definition · Arithmetic intensity

The number of floating-point operations a computation performs per byte it reads from or writes to main memory (HBM on a GPU, unified RAM on a Mac). A matrix–matrix multiply reuses each loaded weight many times, so its intensity is high. A matrix–vector multiply uses each weight once, so its intensity is tiny.

$$\htmlClass{t1}{\text{AI}} = \frac{\htmlClass{t2}{\text{FLOPs}}}{\htmlClass{t3}{\text{bytes moved}}}, \qquad \htmlClass{t4}{P_{\text{attainable}}} = \min\!\big(\htmlClass{t5}{P_{\text{peak}}},\; \htmlClass{t1}{\text{AI}} \times \htmlClass{t6}{\text{BW}}\big), \qquad \htmlClass{t7}{\text{AI}^{*}} = \frac{\htmlClass{t5}{P_{\text{peak}}}}{\htmlClass{t6}{\text{BW}}}$$
AI
arithmetic intensity, FLOPs per byte
FLOPs
operations the kernel performs (a multiply-add counts as 2)
bytes moved
traffic to and from main memory: weights, KV cache, activations
\(P_{\text{attainable}}\)
the best FLOP/s this kernel can possibly reach on this chip
\(P_{\text{peak}}\)
the chip's peak compute (H100 SXM: 989 TFLOP/s dense bf16)
BW
memory bandwidth (H100 SXM: 3.35 TB/s)
\(\text{AI}^{*}\)
ridge point: the intensity where the two limits meet

In wordsIf each byte you fetch supports only a few FLOPs, you're waiting on memory and the compute units sit idle. Past the ridge point, memory keeps up and compute becomes the limit.

Why it mattersH100: 989 × 10¹² ÷ 3.35 × 10¹² ≈ 295 FLOPs per byte. A kernel has to do about 300 FLOPs for every byte it reads before the tensor cores become the bottleneck.

Why decode is memory-bound

Count it for one weight matrix with \(N\) parameters during decode with \(B\) sequences in the batch. Each sequence contributes one position, so the matmul does \(2NB\) FLOPs (one multiply and one add per weight per sequence). It has to read all \(N\) weights once, \(bN\) bytes. Activations are tiny by comparison.

$$\htmlClass{t1}{\text{AI}_{\text{decode}}} \approx \frac{2\,\htmlClass{t2}{N}\,\htmlClass{t3}{B}}{\htmlClass{t4}{b}\,\htmlClass{t2}{N}} = \frac{2\,\htmlClass{t3}{B}}{\htmlClass{t4}{b}} \;\;\xrightarrow{\;b\,=\,2\ (\text{bf16})\;}\;\; \htmlClass{t1}{\text{AI}_{\text{decode}}} \approx \htmlClass{t3}{B}$$
\(\text{AI}_{\text{decode}}\)
FLOPs per byte for the weight matmuls in one decode step
\(N\)
parameters in the matrices being multiplied (cancels out)
\(B\)
batch size: sequences decoded together, each contributing one token
\(b\)
bytes per weight: 2 in bf16, about 0.5 at 4-bit

In wordsIn bf16, decode does about one FLOP per byte per sequence in the batch. At batch 1, that's one FLOP per byte against a ridge of 295.

Why it mattersLlama-3-8B on an H100 at batch 1: the matmuls touch about 7.5B parameters, 15 GB. Reading them takes 15 GB ÷ 3.35 TB/s ≈ 4.5 ms. The math takes 15 GFLOP ÷ 989 TFLOP/s ≈ 15 µs. The tensor cores are busy for well under 1% of each step, and the ceiling is about 220 tokens/s no matter how fast the chip computes.

This is the economic engine of LLM serving. At batch 64, the same 15 GB weight read serves 64 sequences. With short contexts the step takes only modestly longer than at batch 1 (most of the extra time is reading 64 KV caches), yet it produces 64 tokens instead of one. Throughput keeps climbing with batch size, nearly linearly at first, and the cost per token falls with it. It is also why weight quantization (Module 09) speeds up decode: at \(b = 0.5\), the same batch gets four times the intensity, and each step has four times fewer bytes to read.

The KV cache doesn't batch

Weights are shared by every sequence in the batch. KV caches are not: each sequence brings its own. During decode, attention reads \(B \cdot T \cdot 128\) KiB of cache per step (Llama-3-8B), and its intensity stays near the GQA group size \(r\) (4 here) regardless of batch. At 8K context, a batch of 64 reads 64 GiB of KV per step against 15 GB of weights. Drag the context slider in the roofline widget: as context grows, every decode point slides left toward the attention intensity, and the gains from batching fade.

Batching: static vs continuous

Since a decode step costs about the same whether it serves 1 sequence or 64, every serious server batches. The naive approach, static batching, collects \(B\) requests, runs them until all have finished, and then takes the next \(B\). Three things go wrong:

  1. Requests finish at different times. A slot whose answer ended at token 40 sits idle until the longest answer in its batch ends at token 900.
  2. New arrivals wait for the entire current batch to drain, so queueing delay becomes part of TTFT.
  3. Prompts of different lengths get padded to a common length, which wastes compute.

Continuous batching, also called iteration-level scheduling (Yu et al., 2022, the Orca paper), makes the scheduling decision after every decode step instead of every batch. Finished sequences leave immediately, waiting ones are admitted (their prefill runs), and the batch keeps running. vLLM, SGLang, TensorRT-LLM, TGI, and llama.cpp's server (with multiple slots) all schedule this way.

Prefill gets in the way

Continuous batching creates a new problem. When a request with a 30K-token prompt joins, its prefill has to run in some iteration, and that iteration takes much longer than a decode step. Every user already streaming sees a stall. Two fixes are now standard:

  • Chunked prefill (Agrawal et al., 2023, Sarathi): split long prompts into chunks of a few hundred to a few thousand tokens and give each iteration a token budget shared between decode tokens and one prefill chunk. Decode steps stay short and the prefill still finishes. vLLM's V1 engine enables it by default.
  • Disaggregated serving (DistServe, Zhong et al., 2024; Splitwise, Patel et al., 2024): run prefill and decode on separate GPU pools, each tuned for its own bottleneck, and ship the KV cache from one to the other.
Pitfall · throughput and latency pull against each other

Larger batches raise total tokens/s until the step becomes compute-bound or KV reads dominate. Past that point, every extra sequence makes every user's TPOT worse. Settings like vLLM's --max-num-seqs and --max-num-batched-tokens are where you choose a point on that curve. Choose it from a latency target, not from the throughput number alone.

PagedAttention: virtual memory for the KV cache

Continuous batching needs a memory manager. Earlier systems reserved one contiguous KV region per request, sized for the longest output it might produce. A request allowed 4K tokens that stops at 300 wastes over 90% of its reservation, and regions of different sizes fragment the free space between them. Kwon et al. (2023) measured that in existing systems only about 20–40% of KV cache memory actually held token states.

PagedAttention, the core of vLLM, borrows the operating system's answer to the same problem: virtual memory. The KV cache is cut into fixed-size blocks of a few tokens each (vLLM's default is 16). Each sequence gets a block table mapping its logical blocks to physical blocks anywhere in GPU memory, and a new block is allocated only when the previous one fills.

What this buys:

  • Almost no fragmentation. Waste is at most one partly filled block per sequence, so many more sequences fit. The paper reported 2–4× higher throughput than the systems it compared against at similar latency.
  • Sharing. Blocks are reference-counted. Parallel samples of one prompt (n > 1), beam search, and requests with an identical prefix can point at the same physical blocks, copying a block only when one sequence writes to it (copy-on-write).
  • Preemption. Under memory pressure, the scheduler can evict a sequence's blocks (swap them to CPU memory, or drop them and recompute later) and resume it afterwards.

The price is that the attention kernel has to gather K and V through the block table instead of reading one contiguous tensor, which adds a small overhead that the extra batch size more than pays back.

MLE angle · reading vLLM's startup log

vLLM profiles a forward pass, subtracts weights and peak activations from --gpu-memory-utilization × GPU memory, and turns the remainder into KV blocks. It then logs the KV cache size in tokens and the maximum concurrency for requests of --max-model-len tokens. If that concurrency is lower than your expected load, your options are: shorter max length, fp8 KV cache, a smaller or more quantized model, or more GPUs.

FlashAttention: exact attention without the T×T matrix

Written naively, attention over \(T\) tokens computes the score matrix \(S = QK^\top/\sqrt{d}\) (size \(T \times T\) per head), writes it to HBM, reads it back to compute \(P = \text{softmax}(S)\), writes \(P\), and reads it again to compute \(O = PV\). For a 32K-token prompt with 32 heads, \(S\) in bf16 is \(32 \times 32768^2 \times 2\) bytes = 64 GiB per layer. Even processed head by head, the time goes into moving those matrices, not into the math.

FlashAttention (Dao et al., 2022) never materializes \(S\) or \(P\) in HBM. It loads a tile of query rows into the GPU's small on-chip SRAM, streams tiles of K and V past it, and keeps a running softmax for each query row. What makes this possible is the online softmax (Milakov & Gimelshein, 2018): you can compute a softmax-weighted sum in one pass if you keep a running maximum and rescale earlier partial results whenever the maximum grows.

$$\htmlClass{t1}{m_j} = \max\!\big(\htmlClass{t1}{m_{j-1}},\ \max_k \htmlClass{t2}{s_{k}}\big), \quad \htmlClass{t3}{\ell_j} = e^{\htmlClass{t1}{m_{j-1}} - \htmlClass{t1}{m_j}}\,\htmlClass{t3}{\ell_{j-1}} + \sum_{k} e^{\htmlClass{t2}{s_k} - \htmlClass{t1}{m_j}}, \quad \htmlClass{t4}{o_j} = e^{\htmlClass{t1}{m_{j-1}} - \htmlClass{t1}{m_j}}\,\htmlClass{t4}{o_{j-1}} + \sum_{k} e^{\htmlClass{t2}{s_k} - \htmlClass{t1}{m_j}}\,\htmlClass{t5}{v_k}, \quad \htmlClass{t6}{O} = \frac{\htmlClass{t4}{o_{\text{last}}}}{\htmlClass{t3}{\ell_{\text{last}}}}$$
\(m_j\)
running maximum of all scores seen through tile \(j\), kept for numerical stability
\(s_k\)
scores \(q \cdot k_k / \sqrt{d}\) for the keys \(k\) in the current tile
\(\ell_j\)
running softmax denominator, rescaled whenever the max changes
\(o_j\)
running un-normalized output: the weighted sum of values so far
\(v_k\)
value vectors in the current tile
\(O\)
final attention output for this query row, exactly equal to softmax(S)V

In wordsProcess keys a tile at a time. If a new tile contains a bigger score than any before, shrink the old running sums by \(e^{m_{\text{old}} - m_{\text{new}}}\) so everything stays on the same scale. Divide by the total at the end.

Why it mattersOnly \(m\), \(\ell\), and \(o\) per query row need to persist, so extra memory drops from \(O(T^2)\) to \(O(T)\), and the \(T \times T\) matrices never touch HBM.

The output is exact, the same as standard attention up to floating-point rounding. The paper reported several-fold wall-clock speedups for attention and made much longer training contexts practical. FlashAttention-2 (Dao, 2023) improved how work is split across the GPU, and FlashAttention-3 (Shah et al., 2024) uses Hopper-specific features such as asynchronous copies and fp8.

Pitfall · FlashAttention is not sub-quadratic

It removes the \(O(T^2)\) memory traffic, not the \(O(T^2)\) compute. FLOPs are the same (slightly more in the backward pass, which recomputes scores instead of storing them). A 128K-token prefill is still quadratic in time; it just doesn't also run out of memory.

Decode is a different shape: one query row per sequence against a long cache, so there's little to tile along queries. Flash-Decoding splits the work along the KV length instead, so many GPU cores each handle a slice of the cache, then merges their partial results with the same max-and-rescale trick.

Sampling: turning logits into a token

Every forward pass ends with a vector of logits \(z\), one score per vocabulary entry (128,256 entries for Llama 3). The sampler turns that vector into one token. It's a small piece of code, and it decides whether a long answer stays coherent, wanders, or falls into a loop.

Greedy decoding takes \(\arg\max_i z_i\). It's fine for short extractions and classification-style outputs, but on long open-ended text it tends to fall into loops and bland, repetitive phrasing (Holtzman et al., 2019). Everything else samples from a reshaped distribution.

$$\htmlClass{t1}{p_i} = \frac{\exp(\htmlClass{t2}{z_i} / \htmlClass{t3}{T})}{\sum_{k} \exp(\htmlClass{t2}{z_k} / \htmlClass{t3}{T})}$$
\(p_i\)
probability of token \(i\)
\(z_i\)
the model's logit (raw score) for token \(i\)
\(T\)
temperature. \(T \lt 1\) sharpens, \(T \gt 1\) flattens, \(T \to 0\) becomes greedy

In wordsDivide every score by \(T\) before the softmax. Small \(T\) stretches the gaps between scores, so the leader takes nearly all the probability. Large \(T\) shrinks the gaps, so the tail gets more.

Why it mattersTemperature never removes a token: at any \(T \gt 0\), a nonsense token keeps some nonzero probability. Over hundreds of steps, that tail eventually gets sampled. Truncation filters exist to cut it off.

Truncation: top-k, top-p, min-p

Top-k keeps the \(k\) highest-probability tokens and renormalizes. It's simple but blind to shape: \(k = 40\) is too many when the model is certain and too few when 200 continuations are reasonable. Top-p, or nucleus sampling (Holtzman et al., 2019), adapts by keeping as many tokens as it takes to cover probability mass \(p\).

$$\htmlClass{t1}{S_p} = \text{smallest set of highest-probability tokens with } \sum_{i \in \htmlClass{t1}{S_p}} \htmlClass{t2}{p_i} \ge \htmlClass{t3}{p}, \qquad \htmlClass{t4}{p'_i} = \frac{\htmlClass{t2}{p_i}}{\sum_{j \in \htmlClass{t1}{S_p}} \htmlClass{t2}{p_j}} \ \text{ for } i \in \htmlClass{t1}{S_p}$$
\(S_p\)
the nucleus: the tokens that survive
\(p_i\)
probabilities before truncation (after temperature, in most engines)
\(p\)
the top-p threshold, e.g. 0.9. \(p = 1\) disables it
\(p'_i\)
renormalized probabilities actually sampled from

In wordsSort tokens by probability and walk down the list until you've covered \(p\) of the mass. Keep those, drop the rest, rescale to sum to 1.

Why it mattersWhen the model is confident, the nucleus might be one token. When it's unsure, it might be hundreds. Its weak spot: at high temperature the distribution flattens, and covering 90% of the mass can admit a long tail of junk.

$$\text{keep token } i \iff \htmlClass{t1}{p_i} \ge \htmlClass{t2}{p_{\min}} \cdot \htmlClass{t3}{\max_j p_j}$$
\(p_i\)
probability of the candidate token
\(p_{\min}\)
relative threshold, typically 0.05–0.1
\(\max_j p_j\)
probability of the single most likely token

In wordsKeep any token that's at least \(p_{\min}\) as likely as the favourite. If the favourite has 0.9, the bar is 0.045; if it has 0.2, the bar drops to 0.01.

Why it mattersThe cutoff scales with the model's confidence, which keeps output coherent at higher temperatures where top-p lets junk in (Nguyen et al., 2024). It's available in llama.cpp, vLLM, and transformers.

Order of operations differs between engines

Hugging Face transformers and vLLM apply temperature first, then the truncation filters, so temperature changes which tokens survive top-p. llama.cpp's default sampler chain applies temperature last, after top-k, top-p, and min-p, so temperature only reshapes the survivors. The same settings can behave differently across stacks; toggle the order in the widget to see it.

Think first: at temperature 0.2, does top-p = 0.9 still change anything in the widget's distribution?
Barely. At \(T = 0.2\) the logit gap between " cake" (3.2) and " pie" (2.9) becomes 1.5 after dividing by 0.2, so " cake" gets about 81% and " pie" about 18%. The nucleus is just those two tokens, and the ten tokens it cuts held about 1% of the mass between them. Truncation matters most at high temperature, which is exactly where people turn it on.
Pitfall · "temperature 0" is not a determinism guarantee

Greedy decoding is deterministic on paper. On a serving engine, the batch your request lands in changes kernel choices and floating-point reduction order, which can flip near-tied logits, and one flipped token changes the rest of the answer. If you need reproducibility for evals, fix the seed, run batch 1, or measure the variance instead of assuming there is none.

Two more controls sit in the same place in the pipeline. Repetition, frequency, and presence penalties subtract from the logits of tokens that already appeared. Constrained decoding (JSON schemas, grammars, tool-call formats) masks out every token that would make the output invalid before sampling. Module 12 relies on it.

Speculative decoding

Decode leaves the tensor cores almost idle. A forward pass over 5 positions costs about the same as a pass over 1, because both read the weights once (it's a tiny prefill). Speculative decoding (Leviathan et al., 2023; Chen et al., 2023, independently) puts that spare compute to work: guess several tokens cheaply, then have the big model check all of them in one pass.

  1. A small, fast draft model \(q\) proposes \(\gamma\) tokens, one at a time.
  2. The large target model \(p\) runs once over the context plus all \(\gamma\) drafts, producing its own distribution at every one of the \(\gamma + 1\) positions.
  3. Walk the drafts left to right. Accept draft token \(x\) with probability \(\min(1, p(x)/q(x))\). At the first rejection, sample a replacement from the normalized residual \(\max(0, p - q)\) and stop. If every draft is accepted, take one bonus token from the target's last position.

Under that rule, the accepted tokens are distributed exactly as if the target had sampled them itself. Speculative decoding is lossless: it changes speed, not outputs.

$$\htmlClass{t1}{E[\text{tokens per step}]} = \frac{1 - \htmlClass{t2}{\alpha}^{\htmlClass{t3}{\gamma}+1}}{1 - \htmlClass{t2}{\alpha}}, \qquad \htmlClass{t4}{\text{speedup}} = \frac{1 - \htmlClass{t2}{\alpha}^{\htmlClass{t3}{\gamma}+1}}{(1 - \htmlClass{t2}{\alpha})(\htmlClass{t3}{\gamma}\,\htmlClass{t5}{c} + 1)}$$
\(E[\cdot]\)
expected tokens produced per target forward pass, between 1 and \(\gamma + 1\)
\(\alpha\)
acceptance rate: probability a draft token is accepted (assumed independent per token)
\(\gamma\)
draft length: tokens proposed per step
speedup
expected wall-clock improvement over plain decoding with the target alone
\(c\)
cost ratio: time of one draft step ÷ time of one target step

In wordsTokens per step is a geometric series: you get the first draft with probability \(\alpha\), the first two with \(\alpha^2\), and so on, plus the one token the target always contributes. Speedup divides that by the step's cost: one target pass plus \(\gamma\) draft passes.

Why it matters\(\alpha = 0.8\), \(\gamma = 4\), \(c = 0.05\): 3.36 tokens per step at a cost of 1.2 target passes, about 2.8× faster. Longer drafts give diminishing returns because \(\alpha^{\gamma}\) shrinks fast while draft cost grows linearly.

Where drafts come from in practice: a smaller model from the same family (it must share the tokenizer), n-gram or prompt lookup drafting that copies spans from the context (very effective for code edits and RAG answers that quote sources), extra prediction heads trained on the target (Medusa, Cai et al., 2024; EAGLE, Li et al., 2024), or multi-token-prediction heads built into the model during pretraining, as in DeepSeek-V3.

Where it stops paying

The "verification is free" assumption only holds while decode is memory-bound. At large batch sizes the target pass is already closer to compute-bound, so widening it to \(\gamma + 1\) positions per sequence costs real time, and rejected drafts burn compute other requests could have used. Gains are largest for single-user, latency-sensitive serving. \(\alpha\) also depends heavily on content: high for code and boilerplate, lower for creative writing.

Long context: cost, positions, and what models actually use

What grows with T

Three costs grow with sequence length, at different rates:

  • KV memory grows linearly: 128 KiB per token for Llama-3-8B.
  • Decode attention grows linearly per step: each new token reads all \(T\) cached keys and values.
  • Prefill attention grows quadratically: every one of \(T\) queries scores against up to \(T\) keys.
$$\htmlClass{t1}{F_{\text{prefill}}} \approx \underbrace{2\,\htmlClass{t2}{N}\,\htmlClass{t3}{T}}_{\text{matmuls}} + \underbrace{2\,\htmlClass{t4}{L}\,\htmlClass{t5}{d}\,\htmlClass{t3}{T}^{2}}_{\text{causal attention}}$$
\(F_{\text{prefill}}\)
total FLOPs to prefill a prompt
\(N\)
parameters used in matmuls (≈ 7.5B for Llama-3-8B)
\(T\)
prompt length in tokens
\(L\)
number of layers
\(d\)
attention width, \(n_{\text{heads}} \cdot d_{\text{head}}\) (4096 for Llama-3-8B)

In words\(QK^\top\) and \(PV\) each cost \(2T^2d\) per layer; the causal mask lets kernels skip about half, leaving \(2LdT^2\). The linear part is the familiar 2 FLOPs per parameter per token from Module 07.

Why it mattersThe two terms are equal at \(T = N/(Ld)\): about 57K tokens for Llama-3-8B. At 128K tokens, attention is more than twice the cost of every other matmul combined, and prefill time grows roughly with \(T^2\) from there.

Positions beyond training: RoPE scaling

RoPE (Module 06) encodes position by rotating each pair of dimensions in \(q\) and \(k\) by an angle proportional to the position, with a different frequency for each pair. The dot product then depends only on relative distance. A model trained to 8K tokens has only seen the angle combinations that occur within 8K. Past that, the slowly rotating low-frequency pairs reach angles it never saw, and quality collapses, usually abruptly.

$$\htmlClass{t1}{\phi_i}(\htmlClass{t2}{m}) = \htmlClass{t2}{m} \cdot \htmlClass{t3}{\beta}^{-2i/\htmlClass{t4}{d}}, \qquad \text{PI: } \htmlClass{t2}{m} \to \frac{\htmlClass{t2}{m}}{\htmlClass{t5}{s}}, \qquad \text{NTK-aware: } \htmlClass{t3}{\beta} \to \htmlClass{t3}{\beta} \cdot \htmlClass{t5}{s}^{\,\htmlClass{t4}{d}/(\htmlClass{t4}{d}-2)}$$
\(\phi_i\)
rotation angle applied to dimension pair \(i\) (pairs \(i = 0 \dots d/2-1\))
\(m\)
token position
\(\beta\)
RoPE base: 10,000 in the original paper, 500,000 in Llama 3
\(d\)
head dimension
\(s\)
extension factor: target length ÷ trained length (e.g. 4 for 32K → 128K)

In wordsPosition interpolation squeezes all positions back into the trained range by dividing them by \(s\). NTK-aware scaling raises the base instead, which stretches the slow rotations a lot and leaves the fast ones almost unchanged.

Why it mattersThis is how most models get from their pretraining length to their advertised length, usually with a short fine-tune on long documents afterwards.

  • Position interpolation (Chen et al., 2023) works with a short fine-tune, but it compresses the high-frequency pairs too, which blurs distinctions between nearby tokens.
  • NTK-aware scaling (an open-source community proposal, 2023) keeps local resolution and works somewhat even without fine-tuning.
  • YaRN (Peng et al., 2023) treats frequency bands separately: high-frequency pairs untouched, low-frequency pairs interpolated, a blend in between, plus a small attention-temperature correction. It extends well with little fine-tuning. Qwen2.5's docs, for example, describe enabling YaRN with factor 4 to go from 32K to 128K. Llama 3.1 uses its own frequency-dependent scaling in the same spirit.

Sliding-window attention

Another approach bounds the cost: let each layer attend only to the last \(W\) tokens. Mistral 7B v0.1 used a 4,096-token window in every layer. Gemma 2 alternates sliding-window and global layers, and Gemma 3 uses five local layers (1,024-token windows) per global layer. Local layers' KV caches stop growing at \(W\) tokens; only the global layers pay full price. Information from far back can still reach the current token by hopping through layers, since \(L\) stacked windows give a reach of about \(L \cdot W\), but each hop loses detail.

Lost in the middle

Fitting a document in the window doesn't mean the model uses it well. Liu et al. (2023) gave models a question and 20 retrieved documents, exactly one containing the answer, and moved that document's position. Accuracy was highest when the answer was at the start or the end and sagged in the middle. For one model, an answer in the middle did worse than giving it no documents at all.

Effective context vs advertised context

The advertised number is the length the model accepts without errors. The number that matters is the length at which your task still works. "Needle in a haystack" tests, which hide one odd sentence in filler text and ask for it back, are passed by most recent long-context models, so they no longer separate good from bad. RULER (Hsieh et al., 2024) added multi-needle retrieval, variable tracking across the context, and aggregation tasks, and found that many models claiming 32K or more fell well below their own short-context scores before reaching their advertised length. Tasks that need the model to combine many facts spread through the context degrade first.

MLE angle · using long context well

Put stable instructions at the start and the actual question at the end. Retrieve fewer, better chunks (Module 11) instead of filling the window. Compact long agent histories (Module 12). Evaluate at the context lengths your traffic actually has, not at 2K. And remember that every token you add costs KV memory for the whole request and prefill time that grows faster than linearly.

Prefix caching

Many requests start the same way: a system prompt, tool definitions, few-shot examples, a document being asked about repeatedly, the earlier turns of a chat. If two requests share their first \(n\) tokens exactly, their KV cache for those \(n\) positions is identical, because the KV at position \(t\) depends only on tokens \(\le t\). So keep it, and skip that part of prefill next time.

  • vLLM automatic prefix caching hashes each full KV block together with the hash of every block before it. A new request looks up its blocks by hash, and hits reuse the physical blocks directly, using PagedAttention's reference counts.
  • SGLang's RadixAttention (Zheng et al., 2024) keeps a radix tree over cached token sequences with LRU eviction, which suits branching workloads like agents and tree search.
  • API providers sell the same mechanism as "prompt caching": cached input tokens are billed at a discount and prefill faster. Rates, minimum lengths, and cache lifetimes differ by provider; check current docs.
$$\htmlClass{t1}{\text{TTFT}} \approx \htmlClass{t6}{t_{\text{queue}}} + \frac{\htmlClass{t2}{T_{\text{prompt}}} - \htmlClass{t3}{T_{\text{hit}}}}{\htmlClass{t4}{R_{\text{prefill}}}}, \qquad \htmlClass{t5}{C_{\text{input}}} = \htmlClass{t7}{\pi}\,\big[(\htmlClass{t2}{T_{\text{prompt}}} - \htmlClass{t3}{T_{\text{hit}}}) + \rho\,\htmlClass{t3}{T_{\text{hit}}}\big]$$
TTFT
time to first token
\(t_{\text{queue}}\)
time waiting to be scheduled
\(T_{\text{prompt}}\)
total prompt tokens
\(T_{\text{hit}}\)
tokens of the prompt's prefix found in the cache
\(R_{\text{prefill}}\)
prefill throughput, tokens per second
\(C_{\text{input}}\)
billed input cost
\(\pi\)
price per uncached input token; \(\rho\) is the cached-token discount ratio (e.g. 0.1 means 90% off)

In wordsOnly the uncached tail of the prompt needs prefill, and only that tail is billed at full price.

Why it mattersAn agent turn with a 20K-token prompt where 18K tokens (tools plus history) are unchanged, prefilled at an illustrative 10K tokens/s: TTFT drops from 2.0 s to 0.2 s. At \(\rho = 0.1\), billed input falls from 20K to 3.8K token-equivalents, 81% less.

Pitfall · one changed token invalidates everything after it

A timestamp in the first line of the system prompt, tool definitions serialized in a different order each request, a user ID placed before the instructions: each makes every later token a cache miss, because the cache matches prefixes only. Put stable content first and volatile content last. Caches are also evicted under memory pressure or after a provider's TTL, so a hit is likely, never guaranteed.

TTFT. Look at prompt length and queueing first. MLE angle · measure distributions, not averages

Report p50, p90, and p99 for TTFT and ITL at a stated request rate and input/output length mix. Means hide the stalls users actually notice. Measure with streaming, from the client's side, under a realistic load, and keep the load generator's settings in the report so the numbers can be reproduced.

2. A KV-cache decode loop from scratch

A toy one-layer model with GQA is enough to see the mechanics: prefill fills the cache, each decode step adds one row per KV head, and the result matches recomputing everything from scratch.


import torch
import torch.nn.functional as F

torch.manual_seed(0)
VOCAB, d, H, H_KV = 100, 64, 8, 2          # 8 query heads share 2 KV heads (GQA, group of 4)
dh = d // H
E  = torch.randn(VOCAB, d) * 0.5           # embedding, reused as the unembedding
Wq = torch.randn(d, H * dh) / d ** 0.5
Wk = torch.randn(d, H_KV * dh) / d ** 0.5
Wv = torch.randn(d, H_KV * dh) / d ** 0.5
Wo = torch.randn(H * dh, d) / d ** 0.5

def forward(ids, cache=None):
    """ids: (t,) NEW token ids. cache: None or {"K","V"} of shape (H_KV, T_past, dh).
    No RoPE or MLP here; a real model applies RoPE to k before caching it."""
    x = E[ids]                                             # (t, d)
    t = x.shape[0]
    q = (x @ Wq).view(t, H, dh).transpose(0, 1)            # (H, t, dh)
    k = (x @ Wk).view(t, H_KV, dh).transpose(0, 1)         # (H_KV, t, dh)
    v = (x @ Wv).view(t, H_KV, dh).transpose(0, 1)
    if cache is not None:                                  # reuse K, V of every earlier position
        k = torch.cat([cache["K"], k], dim=1)
        v = torch.cat([cache["V"], v], dim=1)
    T = k.shape[1]
    mask = torch.ones(t, T, dtype=torch.bool).tril(diagonal=T - t)   # causal, offset by past length
    g = H // H_KV                                          # expand KV heads to match query heads
    o = F.scaled_dot_product_attention(q, k.repeat_interleave(g, 0),
                                       v.repeat_interleave(g, 0), attn_mask=mask)
    h = x + o.transpose(0, 1).reshape(t, H * dh) @ Wo      # residual
    return h[-1] @ E.T, {"K": k, "V": v}                   # next-token logits, updated cache

def greedy_no_cache(prompt, n):
    ids = prompt.clone()
    for _ in range(n):
        logits, _ = forward(ids)                           # re-run the WHOLE sequence every step
        ids = torch.cat([ids, logits.argmax().view(1)])
    return ids

def greedy_with_cache(prompt, n):
    logits, cache = forward(prompt)                        # prefill: all prompt positions at once
    out = [prompt]
    for i in range(n):
        nxt = logits.argmax().view(1)
        out.append(nxt)
        if i < n - 1:
            logits, cache = forward(nxt, cache)            # decode: ONE new position per step
    return torch.cat(out), cache

prompt = torch.tensor([5, 17, 42, 8, 99, 3])
a = greedy_no_cache(prompt, 20)
b, cache = greedy_with_cache(prompt, 20)
print(a.tolist())
print("same tokens:", torch.equal(a, b))                   # the cache changes cost, not results
print("cache shape per tensor:", tuple(cache["K"].shape))  # (H_KV, prompt + generated - 1, dh)
print("cache bytes:", sum(t.numel() * t.element_size() for t in cache.values()))

Llama-3-70B (80 layers, 8 KV heads, head dim 128) holds one 32,768-token conversation with a bf16 KV cache. How big is the cache?

  1. 2.5 GiB
  2. 10 GiB
  3. 40 GiB
  4. 80 GiB
2 × 80 × 8 × 128 × 2 = 327,680 bytes = 320 KiB per token; × 32,768 tokens = 10 GiB. 40 GiB is the same model at its full 128K context. 80 GiB is what 32K would cost with full MHA (64 KV heads).

On an H100, you raise the decode batch from 8 to 16 for short (1K-token) conversations with Llama-3-8B in bf16. To first order, what happens?

  1. Step time doubles, so total throughput is unchanged
  2. Step time halves
  3. Step time barely changes, so total tokens/s nearly doubles
  4. The GPU becomes compute-bound
Decode intensity ≈ batch size ≈ 16 FLOPs/byte, far below the H100's ridge of ~295, so the step is set by reading 15 GB of weights. Eight more 1K-token caches add about 1 GiB of reads to the ~15 GB per step: under 10% more time for twice the tokens.

After temperature, the probabilities are [0.50, 0.20, 0.15, 0.10, 0.05]. With top-p = 0.75 and no other filter, what is the top token's final probability?

  1. ≈ 0.59, because three tokens survive
  2. 0.50, because top-p doesn't renormalize
  3. ≈ 0.71, because two tokens survive
  4. 1.0, because top-p keeps only the top token
Cumulative mass is 0.50, 0.70, 0.85. Two tokens only reach 0.70 < 0.75, so the third is needed. Renormalize over 0.85: 0.50 / 0.85 ≈ 0.588.

Speculative decoding with acceptance rate α = 0.8 and draft length γ = 4. How many tokens does each target forward pass produce on average?

  1. 3.2 (0.8 × 4)
  2. 4
  3. 5
  4. ≈ 3.36
(1 − 0.8⁵) / (1 − 0.8) = (1 − 0.328) / 0.2 ≈ 3.36. That counts the accepted drafts plus the one token the target always contributes. Five is the maximum, reached only when every draft is accepted.

What does FlashAttention change about attention over a T-token prompt?

  1. It approximates softmax, so FLOPs drop from O(T²) to O(T)
  2. Same exact output and FLOPs, but the T×T score matrix never goes to HBM, so memory traffic and extra memory drop
  3. It caches keys and values between requests
  4. It only applies during decode
FlashAttention is exact. It tiles Q, K, V through on-chip SRAM and uses online softmax so S and P never hit HBM. Compute stays O(T²); memory traffic and extra memory fall to O(T). Reuse between requests is prefix caching, a different technique.

Why does batching improve decode throughput much less at 64K-token contexts than at 1K?

  1. Long prompts make decode compute-bound
  2. RoPE scaling slows down each step
  3. Each sequence brings its own KV cache, so bytes read per step grow with batch, and attention's FLOPs per byte stays near the GQA group size
  4. Continuous batching is disabled for long contexts
Weight reads are shared across the batch; KV reads are not. At 64K, one Llama-3-8B sequence's cache is 8 GiB, so the KV reads swamp the 15 GB of weights and intensity stays low no matter how many sequences you add (and they quickly stop fitting in memory too).

An agent's prompt is 20K tokens: 18K stable (tools, history) and 2K new per turn, served with prefix caching. A teammate adds the current timestamp to the first line of the system prompt. What happens to TTFT?

  1. It jumps by roughly 10×, because every token after the timestamp is now a cache miss
  2. Nothing: the cache still matches the other 18K tokens
  3. It rises slightly: only the timestamp tokens are recomputed
  4. It falls, because unique prompts skip the cache lookup
Prefix caches match exact prefixes, because each position's K and V depend on every earlier token. Changing line one invalidates all 20K tokens, so prefill goes from ~2K tokens to ~20K. Put volatile content at the end.
