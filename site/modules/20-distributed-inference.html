Module 20 · Inference engineering II

Distributed inference: one model, many GPUs

Llama-3.1-70B in bf16 is 141 GB of weights, and an H100 holds 80 GB. DeepSeek-V3 has 671B parameters spread over 256 experts per layer. Serving models like these means cutting them into pieces, putting the pieces on different GPUs, and paying for every byte the pieces exchange. This module is about choosing the cuts so that bill stays small.

~3.5 hoursprereqs: 07, 08, 09hands-on: vLLM, SGLang, nccl-tests, torch.distributed

By the end you can

  1. Say whether a deployment is short on memory, throughput, or latency, and name the parallelism axis that fixes each.
  2. Estimate the time of an all-reduce from message size, GPU count, and link bandwidth, and read busbw from nccl-tests.
  3. Explain why tensor parallelism costs two all-reduces per layer, and predict when it stops paying off over PCIe or across nodes.
  4. Reason about MoE serving: all-to-all traffic, hot experts, capacity factors, and why the slowest GPU sets the pace.
  5. Size disaggregated prefill/decode and KV offloading by comparing transfer time against recompute time.
  6. Pick a TP × PP × DP (× EP) layout for a given model and cluster, then measure it.

When one GPU isn't enough

Three different problems push a deployment past one GPU, and each has its own fix. Picking the wrong one is the most common way to end up with an expensive layout that doesn't help.

Memory

It doesn't fit

Weights plus KV cache exceed one GPU's memory. Llama-3.1-70B at bf16 needs 141 GB before a single token of context. Nothing short of splitting the model (or quantizing it, Module 09) will help.

Throughput

It fits, but too few users

An 8B model fits on one H100 with room to spare, yet one GPU only has so much KV memory and so many FLOPs. If the queue grows, you want more copies of the model, not a model split across more GPUs.

Latency

Each token is too slow

At low batch, decode time is weight bytes divided by memory bandwidth (Module 08). Split the weights over 4 GPUs and each reads a quarter, so a step can finish up to 4× sooner, minus the cost of talking.

The first question is always the memory one, because it's binary. Count the bytes:

$$\htmlClass{t1}{G_{\min}} = \left\lceil \frac{\htmlClass{t2}{M_W} + \htmlClass{t3}{M_{KV}} + \htmlClass{t4}{M_{\text{act}}}}{\htmlClass{t5}{u} \cdot \htmlClass{t6}{M_{\text{GPU}}}} \right\rceil$$
\(G_{\min}\)
fewest GPUs a single copy of the model can live on (round up to a degree your engine supports, usually a power of 2)
\(M_W\)
weight bytes: parameters × bits / 8
\(M_{KV}\)
KV cache you want resident: tokens in flight × KV bytes per token (Module 08)
\(M_{\text{act}}\)
activations, workspace, CUDA graphs, communication buffers: a few GB per GPU
\(u\)
usable fraction of memory, typically 0.85–0.92 (vLLM's --gpu-memory-utilization defaults to 0.9)
\(M_{\text{GPU}}\)
memory per GPU (H100: 80 GB, H200: 141 GB)

In wordsAdd up everything that must sit in GPU memory at once and divide by what one GPU can actually give you.

Why it mattersLlama-3.1-70B, bf16, 32 concurrent users at 8K tokens: 141 GB of weights + 32 × 8,192 × 320 KB ≈ 86 GB of KV + ~10 GB overhead ≈ 237 GB. Divided by 72 GB usable per H100, that's 3.3, so 4 GPUs. Halve the users and you still need 2.7, which becomes 4 because TP degrees come in powers of two. Quantize the weights to fp8 and halve the users (70.6 + 43 + 10 ≈ 124 GB) and it fits on 2.

Think first: an 8B model runs fine on one GPU, but you need to serve twice as many users. TP=2, or two replicas?
Two replicas. Each replica keeps its own full KV memory, so capacity doubles, and replicas never talk to each other. TP=2 also doubles memory, but every layer now pays two all-reduces, and the per-GPU KV room only grows by the half of the weights each GPU no longer stores (8 GB, about 14% more). Reach for TP=2 only if the per-token latency target isn't met on one GPU.

Collective communication primitives

Every multi-GPU scheme in this module is built from a handful of communication patterns. They come from the MPI world and have the same names everywhere.

Definition · Rank, world, collective

Each participating process (one per GPU, usually) is a rank, numbered 0 to \(p-1\). The set of ranks that communicate is a group or communicator, with world size \(p\). A collective is an operation every rank in the group calls together, such as "sum this tensor across all of us". Nobody returns until their part is done, so one slow rank holds up the whole group.

On NVIDIA GPUs the collectives come from NCCL (NVIDIA Collective Communications Library, pronounced "nickel"). AMD's equivalent is RCCL. PyTorch's torch.distributed with the "nccl" backend calls it, and vLLM, SGLang and TensorRT-LLM all use it, sometimes swapping in custom kernels for small messages (more in § communication tricks). NCCL figures out the topology (NVLink, PCIe, network cards) and picks an algorithm and transport for each call.

Ring all-reduce

The obvious way to sum a tensor across \(p\) GPUs is for everyone to send their copy to rank 0, which adds them and sends the result back. Rank 0's link then carries \(2(p-1)S\) bytes while every other link sits idle. The ring algorithm spreads the load evenly. Arrange the GPUs in a circle and split the tensor into \(p\) chunks.

  1. Reduce-scatter phase (\(p-1\) steps). Each GPU sends one chunk to its right neighbour and adds the chunk arriving from its left neighbour into its own copy. Each step shifts which chunk is in flight. After \(p-1\) steps, each GPU holds one chunk that contains the sum from all \(p\) GPUs.
  2. All-gather phase (\(p-1\) steps). The finished chunks travel around the ring once more, overwriting instead of adding, until every GPU has all of them.
$$\htmlClass{t1}{t_{\text{AR}}} \approx 2\,\frac{\htmlClass{t2}{p}-1}{\htmlClass{t2}{p}} \cdot \frac{\htmlClass{t3}{S}}{\htmlClass{t4}{BW}} \;+\; 2(\htmlClass{t2}{p}-1)\,\htmlClass{t5}{\alpha}$$
\(t_{\text{AR}}\)
wall-clock time of one all-reduce
\(p\)
number of GPUs in the group
\(S\)
size of the tensor being reduced, in bytes (same on every GPU)
\(BW\)
per-direction bandwidth of the slowest link in the ring
\(\alpha\)
fixed latency per step: kernel launch, synchronization, wire latency. Microseconds

In wordsEach GPU ships almost two full copies of the tensor, at the speed of the worst link, plus a small fixed cost for each of the \(2(p-1)\) steps.

Why it mattersThe bandwidth term barely depends on \(p\): going from 2 to 8 GPUs raises it from \(1.0\,S/BW\) to \(1.75\,S/BW\). The latency term grows linearly with \(p\). Large messages are bandwidth-bound and scale well; tiny messages, like one decode token's activations, are latency-bound and get worse as you add GPUs.

Benchmarks report two bandwidth numbers, and the difference trips people up.

$$\htmlClass{t1}{\text{algbw}} = \frac{\htmlClass{t2}{S}}{\htmlClass{t3}{t}}, \qquad \htmlClass{t4}{\text{busbw}} = \htmlClass{t1}{\text{algbw}} \cdot \frac{2(\htmlClass{t5}{p}-1)}{\htmlClass{t5}{p}}$$
algbw
"algorithm bandwidth": tensor size divided by elapsed time. What your application experiences
\(S\)
bytes in the tensor
\(t\)
measured all-reduce time
busbw
"bus bandwidth": algbw corrected for how many bytes the ring actually moves per GPU. Comparable to the link's rated speed
\(p\)
number of ranks

In wordsFor an all-reduce, each GPU really pushes \(2(p-1)/p\) times the tensor size, so busbw scales algbw up by that factor. For all-gather and reduce-scatter the factor is \((p-1)/p\).

Why it mattersbusbw is independent of \(p\) for an ideal ring, so you can compare it straight against hardware specs. If 8 H100s on NVLink show a busbw near the per-direction NVLink figure at 1 GB messages, the fabric is healthy. If it's a fraction of that, something's wrong (a GPU on the wrong PCIe switch, NVLink down, peer-to-peer disabled).

The ring is a model, not a promise

NCCL chooses among ring, tree, and (on NVSwitch systems) NVLink SHARP algorithms, where the switch itself does the summing, plus several wire protocols tuned for small or large messages. For small messages it will beat the ring formula; for multi-node jobs, tree or hierarchical schemes change the latency term to roughly \(\log p\). Use the formula for intuition and nccl-tests (hands-on) for numbers.

Tensor parallelism for inference

Tensor parallelism (TP) splits each weight matrix across GPUs so every GPU does a slice of every layer. The scheme everyone uses comes from Megatron-LM (Shoeybi et al., 2019), which Module 07 covered for training. Inference uses the same split with no backward pass, so the rules are simpler and the costs show up differently.

Two kinds of split, and the trick is to alternate them:

  • A column-parallel linear layer \(Y = XA\) splits \(A\) by columns: \(A = [A_1 \; A_2]\). GPU \(i\) computes \(XA_i\), a slice of the output features. Nothing needs to be exchanged, as long as every GPU has the full input \(X\).
  • A row-parallel linear layer \(Z = YB\) splits \(B\) by rows. If GPU \(i\) already holds the matching slice of input features \(Y_i\), it computes \(Y_iB_i\), a full-size partial sum. The true output is \(\sum_i Y_iB_i\), which takes one all-reduce.

Column-parallel followed by row-parallel needs exactly one all-reduce, at the end. A transformer layer has two such pairs:

  1. Attention. The Q, K and V projections are column-parallel by heads: with 64 query heads and TP=4, each GPU gets 16 query heads and the matching share of KV heads. Each GPU runs attention for its own heads against its own slice of the KV cache, so the cache is sharded for free. The output projection \(W_O\) is row-parallel, followed by all-reduce #1.
  2. MLP. The gate and up projections are column-parallel (each GPU gets \(d_{ff}/t\) hidden units, and SiLU acts element-wise on its slice). The down projection is row-parallel, followed by all-reduce #2.
$$\htmlClass{t1}{V_{\text{layer}}} = \htmlClass{t2}{2} \cdot \htmlClass{t3}{b} \cdot \htmlClass{t4}{d} \cdot \htmlClass{t5}{T}$$
\(V_{\text{layer}}\)
total size of the tensors all-reduced in one layer (before the ring's \(2(t-1)/t\) factor)
2
two all-reduces per layer: after attention's output projection and after the MLP's down projection
\(b\)
bytes per activation element (bf16: 2)
\(d\)
hidden size (model dimension)
\(T\)
tokens in this forward step: prompt tokens in prefill, one per running sequence in decode

In wordsEach all-reduce carries one hidden vector per token, and there are two per layer.

Why it mattersLlama-3.1-70B (\(d = 8192\), 80 layers) decoding one token: 2 × 2 × 8192 = 32 KB per layer, 2.6 MB per step. That's tiny in bytes but it's 160 separate synchronizations, so decode TP is latency-bound. Prefilling 4,096 tokens: 134 MB per layer, 10.7 GB per forward pass. That's bandwidth-bound.

In the bandwidth-bound regime, a simplification falls out. A dense layer does about \(24\,T d^2\) FLOPs (four \(d\times d\) attention projections and an MLP with \(d_{ff} = 4d\), two FLOPs per multiply-add), split \(t\) ways. Communication is \(2\cdot 2\frac{t-1}{t}\cdot T d b\) bytes per GPU. Divide one by the other and \(T\) cancels:

$$\frac{\htmlClass{t1}{t_{\text{comm}}}}{\htmlClass{t2}{t_{\text{compute}}}} \approx \frac{(\htmlClass{t3}{t}-1)\,\htmlClass{t4}{b}\,\htmlClass{t5}{F}}{6\,\htmlClass{t6}{d}\,\htmlClass{t7}{BW}}$$
\(t_{\text{comm}}\)
time spent in TP all-reduces per layer (no overlap)
\(t_{\text{compute}}\)
time spent in that layer's matmuls
\(t\)
TP degree
\(b\)

\(F\)

\(d\)

\(BW\)

In wordsFaster GPUs and more TP ranks make communication relatively worse; wider models and faster links make it better. The number of tokens doesn't matter once messages are large.

Why it matters70B model (\(d = 8192\)), \(t = 8\), \(F = 600\) TFLOP/s: over NVLink at ~450 GB/s the ratio is about 0.38. Over PCIe Gen5 at ~64 GB/s it's 2.7, so the GPUs spend most of their time waiting. Across nodes at 50 GB/s with \(t = 16\), it's 7.3. That's why TP lives inside an NVLink domain.

In decode, the weight reads dominate compute and the all-reduces are small, so the step time looks like this:

$$\htmlClass{t1}{t_{\text{token}}} \approx \frac{\htmlClass{t2}{M_W}}{\htmlClass{t3}{t}\cdot \htmlClass{t4}{B_{\text{HBM}}}} + 2\htmlClass{t5}{L}\cdot \htmlClass{t6}{t_{\text{AR}}}$$
\(t_{\text{token}}\)

\(M_W\)
total weight bytes
\(t\)

\(B_{\text{HBM}}\)

\(L\)

\(t_{\text{AR}}\)

In wordsThe first term shrinks as you add GPUs; the second doesn't, and its per-call latency creeps up with \(t\).

Why it matters70B bf16 at TP=8: 141 GB / (8 × 2.7 TB/s) ≈ 6.5 ms of weight reads, plus 160 all-reduces at ~15 µs ≈ 2.4 ms. Communication is over a quarter of the step. Going from TP=4 to TP=8 saves 6.5 ms of reads but adds latency to every all-reduce, so the speedup is well under 2×. Illustrative numbers; measure your own.

Pitfall · heads have to divide

TP splits attention by heads, so the number of query heads must be divisible by \(t\). Qwen2.5-32B has 40 query heads: TP=8 works (5 each), TP=16 doesn't. KV heads are the subtler limit. Llama-3.1-70B has 8 KV heads; at TP=16 each KV head must be stored on two GPUs, so the KV cache stops shrinking per GPU and you've paid for 16 GPUs to get the KV capacity of 8. With GQA (Module 08), TP beyond the KV-head count is usually a mistake.

MLE angle · check the topology before choosing TP

Run nvidia-smi topo -m. NV# between two GPUs means NVLink; PIX, PXB, PHB or SYS mean the traffic goes through PCIe switches, the CPU's root complex, or across CPU sockets. A "4-GPU box" of PCIe cards may have half its pairs crossing sockets. TP=2 on a pair that shares a PCIe switch can be fine; TP=4 across sockets on PCIe often runs slower than two TP=2 replicas.

Making TP communication cheaper

Since TP's all-reduces sit on the critical path of every decode step, engines have built a stack of cheaper ways to do them. You don't need to implement these, but you should recognize them in a profile and in engine flags.

TechniqueWhat it doesWhere it shows up
One-shot / two-shot all-reduceFor small messages, each GPU reads its peers' buffers directly over NVLink and sums locally (one-shot), or does a single reduce-scatter + all-gather round (two-shot). Two or three synchronizations instead of \(2(p-1)\).vLLM's "custom all-reduce", TensorRT-LLM and FlashInfer kernels. Usually on by default for NVLink-connected GPUs.
NVLink SHARP (NVLS)The NVSwitch performs the reduction in the switch, so each GPU sends its data once and receives the result once.H100/B200 NVSwitch systems; NCCL picks it automatically when available.
Fused all-reduce + residual + RMSNormThe next layer's norm needs the all-reduced result anyway, so one kernel does the sum, the residual add and the normalization, saving launches and memory round trips.TensorRT-LLM, recent vLLM and SGLang kernels.
Sequence parallelismReplaces each all-reduce with a reduce-scatter and an all-gather, and runs the norms on \(1/t\) of the tokens in between. Same bytes, less redundant work.Mostly prefill and training (Korthikanti et al., 2022).

Intuition

In decode, an all-reduce is like a meeting where everyone shares one sentence. The sentence takes no time to say; scheduling the meeting is the cost. The techniques above either hold fewer meetings, make them shorter, or fold them into work you were doing anyway.

Pipeline parallelism for inference

Pipeline parallelism (PP) splits the model by depth. With PP=4 and 80 layers, GPU 0 holds layers 1–20, GPU 1 holds 21–40, and so on. Each stage hands its output activations (\(T\cdot d\cdot b\) bytes) to the next stage with a point-to-point send. That's one small transfer per stage boundary per step, instead of TP's two all-reduces per layer, so PP tolerates slow links, including the network between nodes.

The catch is that PP doesn't make a single sequence any faster. A decode step still has to pass through all 80 layers, one stage after another, and while stage 2 is working, stages 0, 1 and 3 have nothing to do for that sequence. To keep every stage busy you need several independent groups of sequences (micro-batches) in flight, staggered so that each stage works on a different one. Inference has no backward pass, so there is no gradient bubble as in training (Module 07), but there is a dependency: token \(n+1\) of a sequence can't enter stage 0 until token \(n\) has left the last stage.

$$\htmlClass{t1}{\text{TPOT}} \approx \max(\htmlClass{t2}{m},\htmlClass{t3}{p})\cdot\frac{\htmlClass{t4}{t_1}}{\htmlClass{t3}{p}} + (\htmlClass{t3}{p}-1)\,\htmlClass{t5}{t_{\text{hop}}}, \qquad \htmlClass{t6}{\text{util}} = \frac{\min(\htmlClass{t2}{m},\htmlClass{t3}{p})}{\htmlClass{t3}{p}}$$
TPOT
time per output token for one sequence
\(m\)
micro-batches in flight (independent groups of sequences)
\(p\)
pipeline stages
\(t_1\)
time for the whole model to process one micro-batch step, as if on one GPU
\(t_{\text{hop}}\)
time to send activations between adjacent stages
util
fraction of time each stage is busy

In wordsWith up to \(p\) micro-batches, a token still takes one full trip through the model, and utilization rises with every micro-batch you add. Beyond \(p\), utilization is maxed and the extra micro-batches just wait in line, so latency goes up.

Why it matters70B bf16 on 4 GPUs. With PP=4, \(t_1 \approx\) 141 GB / 2.7 TB/s ≈ 52 ms, so TPOT is about 52 ms whatever you do, and you need 4 micro-batches to use the GPUs fully. With TP=4 the same model decodes in roughly 13–16 ms per token. PP buys capacity and throughput; TP buys latency.

PP earns its place in three situations. The most common is crossing nodes: a model that needs two 8-GPU servers is usually laid out as TP=8 inside each server and PP=2 across them, so only one activation transfer per step goes over the network. It also suits high-throughput batch jobs, where there are always enough sequences to fill the pipeline and nobody is watching per-token latency. And on PCIe-only machines, where TP's all-reduces are too expensive, PP's point-to-point traffic is cheap enough to ignore.

Where it hurts: interactive traffic at low load (bubbles), and uneven stages. The embedding layer, the LM head and the sampler sit on the first and last stages, so equal layer counts don't mean equal work. Engines let you shift layers between stages for that reason.

Data-parallel replicas, and when they win

Data parallelism (DP) for inference just means running several independent copies of the model, each on its own GPU or GPU group, with a load balancer in front. Replicas exchange nothing during a forward pass. If the model fits, this is the simplest and most efficient way to add throughput: no all-reduce, no pipeline bubbles, and a GPU failure takes out one replica instead of the whole service.

When should you stop adding TP and start adding replicas? KV room decides it:

$$\htmlClass{t1}{M_{KV}^{\text{room}}}(\htmlClass{t2}{t}) = \htmlClass{t2}{t}\cdot \htmlClass{t3}{u}\,\htmlClass{t4}{M_{\text{GPU}}} - \htmlClass{t5}{M_W} - \htmlClass{t2}{t}\cdot\htmlClass{t6}{M_{\text{act}}}$$
\(M_{KV}^{\text{room}}\)
memory left for KV cache in one model instance
\(t\)
GPUs in the instance (TP × PP)
\(u\)
usable memory fraction
\(M_{\text{GPU}}\)
memory per GPU
\(M_W\)
weight bytes, paid once per instance regardless of \(t\)
\(M_{\text{act}}\)
per-GPU overhead (activations, buffers)

In wordsThe weights are a fixed tax per instance. Spreading one instance over more GPUs dilutes that tax, so KV room grows faster than the GPU count while weights are a big share of memory, and roughly in proportion once they aren't.

Why it mattersIt tells you whether bigger instances or more instances give more concurrent users per GPU. See the table below.

So the rule is: use the smallest instance that fits the model with healthy KV room and meets your latency target, then replicate. A model that fits on one GPU with plenty of KV memory should almost always be served as TP=1 replicas. Raising TP from there buys lower per-token latency at the cost of all-reduce overhead and slightly lower throughput per GPU.

Replicas aren't free either

Each replica keeps its own prefix cache (Module 08). Spread a shared system prompt or a multi-turn conversation across 8 replicas with a round-robin balancer and you may compute the same prefix 8 times. Cache-aware routing, which sends requests with the same prefix to the same replica, becomes important as replica count grows (Module 21 covers the routing layer).

Mixture-of-experts serving and expert parallelism

A mixture-of-experts (MoE) layer replaces the single MLP with \(E\) smaller MLPs ("experts") and a router: a small linear layer that scores each token against every expert and sends the token to its top-\(k\). The token's output is the router-weighted sum of those \(k\) experts' outputs. Many MoE models also have one or more shared experts that every token uses. DeepSeek-V3 has 256 routed experts and 1 shared expert per MoE layer, with \(k = 8\): 671B parameters in total, about 37B used per token.

That split between total and active parameters is the whole appeal and the whole problem. Compute per token looks like a 37B model, but memory looks like a 671B model. You need many GPUs just to hold the weights, and then each GPU only has a small fraction of the experts.

Expert parallelism (EP) puts different experts on different GPUs. With \(E = 64\) and EP=8, each GPU owns 8 experts. Attention runs wherever the token's sequence lives, then each MoE layer needs two all-to-all exchanges:

  1. Dispatch: every GPU sends each token's hidden vector to the GPUs that own its chosen experts.
  2. Each GPU runs its experts on whatever tokens arrived, as a grouped GEMM over variable-sized groups.
  3. Combine: results go back to the tokens' home GPUs, where they're weighted and summed.
$$\htmlClass{t1}{V_{\text{a2a}}} \approx \htmlClass{t2}{T_{\text{loc}}}\cdot\htmlClass{t3}{k}\cdot\htmlClass{t4}{d}\cdot\htmlClass{t5}{b}\cdot\left(1-\frac{1}{\htmlClass{t6}{EP}}\right)$$
\(V_{\text{a2a}}\)
bytes each GPU sends in one direction (dispatch; combine is similar)
\(T_{\text{loc}}\)
tokens that live on this GPU in this step
\(k\)
experts per token (top-\(k\))
\(d\)
hidden size
\(b\)
bytes per element on the wire (fp8 dispatch: 1; bf16: 2)
\(EP\)
expert-parallel degree. A fraction \(1/EP\) of picks land on local experts and never leave

In wordsEvery token gets copied \(k\) times, once per chosen expert, and almost all of those copies travel to another GPU.

Why it mattersDeepSeek-V3-sized (\(d = 7168\), \(k = 8\)), 128 decode tokens per GPU, fp8 dispatch, EP=64: about 7.2 MB out per layer, and roughly twice that coming back in bf16. Multiply by ~58 MoE layers and it's over a gigabyte of all-to-all per decode step per GPU, much of it across the network. This is why large-scale EP depends so heavily on all-to-all kernels (DeepSeek open-sourced theirs as DeepEP) and on network bandwidth.

Load imbalance, capacity, and hot experts

The all-to-all is synchronous: the layer finishes when the busiest GPU finishes. Routers are trained to spread load, but at inference time the traffic is whatever your users send. A batch full of Python code or one language can concentrate tokens on a few experts.

$$\htmlClass{t1}{C} = \left\lceil \htmlClass{t2}{c_f}\cdot\frac{\htmlClass{t3}{T}\cdot\htmlClass{t4}{k}}{\htmlClass{t5}{E}} \right\rceil, \qquad \htmlClass{t6}{I} = \frac{\max_g \htmlClass{t7}{n_g}}{\operatorname{mean}_g \htmlClass{t7}{n_g}}$$
\(C\)
capacity: the most tokens one expert will accept (or the buffer it's sized for)
\(c_f\)
capacity factor: slack over perfect balance, often 1.0–2.0
\(T\)
tokens in the step (across the EP group)
\(k\)
experts per token
\(E\)
number of routed experts
\(I\)
imbalance: busiest GPU's load over the average. Step time scales with it
\(n_g\)
token-expert assignments that land on GPU \(g\)

In wordsPerfect balance gives every expert \(Tk/E\) tokens. The capacity factor says how much over that you allow. Imbalance says how far the hottest GPU sits above average.

Why it mattersWith \(I = 2\), every GPU waits for one that has twice the average work, and your expensive cluster runs at about half its MoE throughput. In training, tokens past capacity are often dropped. Inference engines generally don't drop tokens, since that changes outputs, so imbalance shows up as time instead, and \(C\) becomes a buffer-sizing number.

What engines do about hot experts:

  • Redundant experts. Keep extra copies of the most loaded experts on otherwise idle GPUs and split their traffic. This needs load statistics, and the hot set drifts with the workload, so it gets recomputed periodically. DeepSeek published an expert-placement balancer (EPLB) for this.
  • Placement. Put experts that are often co-selected on different GPUs, and keep each token's experts on as few nodes as possible so most traffic stays on NVLink.
  • Data-parallel attention. With MLA (DeepSeek's latent attention), each token caches one compressed latent vector shared by all heads, so splitting heads across TP ranks would replicate the cache on every rank. Engines instead run attention data-parallel, with each GPU owning different requests, and only the experts expert-parallel. SGLang calls this "DP attention".
Case study · DeepSeek-V3 deployment, as reported

The DeepSeek-V3 technical report (DeepSeek-AI, 2024) describes its serving layout roughly as follows. Treat the specifics as that team's configuration at publication time, not a recipe. Prefill used a minimum unit of 4 nodes (32 H800 GPUs): attention with TP=4 plus sequence parallelism and DP=8, and experts with EP=32, plus redundant copies of high-load experts. Decode used a much larger unit of about 40 nodes (320 GPUs) with EP across all of them, roughly one routed expert per GPU, and some GPUs dedicated to redundant and shared experts. Dispatch traffic was quantized to fp8 and the all-to-all used NVLink within a node and InfiniBand across nodes. The point to take away: decode wants very wide EP so each GPU's expert weights are read by many tokens per step, which pushes the memory-bound expert GEMMs toward being compute-bound.

Choosing a parallelism layout

The axes compose. An instance can be TP=8 × PP=2 (16 GPUs), and you can run 4 such instances (DP=4) on 64 GPUs. MoE models add EP for the expert layers, usually overlapping the same GPUs that do DP or TP for attention. A layout that works well usually follows these rules, in order:

  1. Fit first. Find the smallest instance (TP × PP) that holds the weights plus the KV cache you need for your target concurrency.
  2. TP inside the fastest domain. TP's traffic is the chattiest, so it gets NVLink. On standard 8-GPU servers that caps TP at 8. Rack-scale NVLink systems (such as GB200 NVL72) stretch the domain further.
  3. PP (or EP) across slower links. If one node isn't enough, add pipeline stages across nodes rather than stretching TP over the network.
  4. DP for everything else. Replicate the instance to fill the remaining GPUs and meet throughput.
  5. Then check latency. If TPOT is too high, raise TP inside the node (and shrink DP), or consider speculative decoding (Module 08).

Disaggregated prefill and decode

Prefill and decode stress hardware in opposite ways (Module 08). Prefill is compute-bound: thousands of tokens per weight read. Decode is bandwidth-bound: one token per sequence per step, many sequences batched to amortize the weight read. When both share a GPU, they get in each other's way:

  • A 32K-token prompt arrives. Its prefill takes hundreds of milliseconds, and while it runs, every in-flight decode sequence on that GPU waits. Users see a stall in the token stream, and TPOT tail latency spikes.
  • The reverse also happens: a GPU full of decode batches delays new prefills, so TTFT climbs.
  • You can't tune one setup for both. Prefill wants high TP for fast TTFT and doesn't need much KV memory. Decode wants large batches, lots of KV memory, and maybe lower TP.

Chunked prefill (Module 19) softens the first problem by slicing prompts into pieces interleaved with decode steps. Disaggregation removes it: run prefill on one pool of GPUs and decode on another, and ship each request's KV cache from the first to the second when prefill finishes.

Three research systems shaped the idea. Each is described here at the level of its published design; check the papers for details.

  • DistServe (Zhong et al., 2024) separates the phases and chooses parallelism and GPU counts for each so as to maximize goodput: requests per second that meet both a TTFT and a TPOT target.
  • Splitwise (Patel et al., 2024) makes the same split and observes that the decode phase can run on cheaper or older GPUs, since it needs memory bandwidth and capacity more than FLOPs.
  • Mooncake (Qin et al., 2024), the serving system behind Moonshot AI's Kimi, builds the design around the KV cache: a cluster-wide pool of KV in CPU DRAM and SSD that both prefill and decode nodes can read and write, with a scheduler that routes on cache hits.

Production engines have adopted the pattern: vLLM and SGLang both have disaggregated-serving modes with pluggable KV transfer backends. The APIs are moving quickly, so check current docs.

$$\htmlClass{t1}{t_{\text{xfer}}} = \frac{\htmlClass{t2}{P}\cdot\htmlClass{t3}{m_{KV}}}{\htmlClass{t4}{BW_{\text{link}}}}, \qquad \htmlClass{t3}{m_{KV}} = 2\,\htmlClass{t5}{L}\,\htmlClass{t6}{n_{kv}}\,\htmlClass{t7}{d_{h}}\,b$$
\(t_{\text{xfer}}\)
time to move one request's KV cache from prefill to decode
\(P\)
prompt length in tokens
\(m_{KV}\)
KV bytes per token across all layers (Llama-3.1-70B, bf16: 320 KB)
\(BW_{\text{link}}\)
achieved bandwidth between the two instances; can be several NICs in parallel when the KV is sharded across TP ranks
\(L\)
layers
\(n_{kv}\)

\(d_h\)
head dimension (\(b\): bytes per element)

In wordsThe KV cache is a big tensor; moving it takes its size divided by the pipe.

Why it matters70B, 8K-token prompt: 2.7 GB. Over one 400 Gb/s NIC (50 GB/s), 54 ms. Over eight NICs in parallel (TP=8, each rank sends its own shard), about 7 ms. The prefill itself takes several hundred milliseconds on 4–8 H100s, so if the transfer streams layer by layer as prefill proceeds, it's almost entirely hidden. Over 100 GbE TCP with a small model and a fast prefill, it isn't.

When disaggregation doesn't pay

It adds a second pool to size and autoscale, a transfer path that can fail, and a router that has to know about both. At small scale, with short prompts, or when TTFT and TPOT targets are loose, chunked prefill on colocated instances is simpler and often just as good. The win grows with long prompts, strict TPOT targets, and enough traffic to keep both pools busy.

KV cache offloading and tiered storage

Prefix caching (Module 08) reuses KV blocks that are still in GPU memory. But HBM is small, and the cache gets evicted within minutes on a busy server. A lot of traffic repeats long prefixes over longer spans: multi-turn chats where every turn resends the history, agents that resend the same tool definitions and file contents, RAG over the same popular documents. Keeping evicted KV in a bigger, slower tier and loading it back can be much cheaper than recomputing it.

Systems like LMCache (an open-source KV caching layer that plugs into vLLM and SGLang), and the KV-centric design of Mooncake, store KV in chunks keyed by a hash of the token prefix. When a request arrives, the engine looks up the longest cached prefix across tiers, loads those chunks into HBM (ideally overlapped with computing the rest), and only prefills the new tokens. The engine integration points (vLLM's KV connector interface, for example) are still evolving, so check the current docs before building on one.

$$\underbrace{\frac{\htmlClass{t1}{P}\cdot\htmlClass{t2}{m_{KV}}}{\htmlClass{t3}{BW_{\text{tier}}}}}_{\text{reload}} \;\lt\; \underbrace{\frac{2\htmlClass{t4}{N}\htmlClass{t1}{P} + 2\htmlClass{t5}{L}\,\htmlClass{t6}{d_{\text{attn}}}\,\htmlClass{t1}{P}^2}{\htmlClass{t7}{F_{\text{eff}}}}}_{\text{recompute (prefill)}}$$
\(P\)
length of the cached prefix in tokens
\(m_{KV}\)
KV bytes per token
\(BW_{\text{tier}}\)
bandwidth from the tier holding the KV into HBM
\(N\)
parameters used per token (active parameters for MoE)
\(L\)
layers
\(d_{\text{attn}}\)
attention width, heads × head dim (causal attention costs about \(2 L d_{\text{attn}} P^2\) FLOPs)
\(F_{\text{eff}}\)
achieved prefill FLOP/s

In wordsLoading costs bytes over bandwidth and grows linearly with the prefix. Recomputing costs FLOPs over compute and grows faster than linearly, because attention is quadratic. The longer the prefix, the more reloading wins.

Why it mattersLlama-3.1-8B, 32K-token prefix: 4.3 GB of KV. From CPU DRAM at ~50 GB/s that's ~86 ms. Recomputing is ~0.8 PFLOP, about 2 s at 400 TFLOP/s. Reload wins by ~20×. Even a single NVMe drive at ~7 GB/s (0.6 s) beats recompute here. The comparison flips for short prefixes on slow tiers, and for models with tiny KV per token relative to their FLOPs.

Pitfall · the GPU must not wait for the disk

A reload that takes 86 ms helps only if the engine schedules around it: start loading as soon as the request is admitted, run other requests meanwhile, and load layer by layer so layer 1 can compute while layer 2's KV is still arriving. A synchronous load that stalls the whole batch can cost more total throughput than recomputing would have.

Long context across GPUs

A single long sequence can outgrow one GPU in two ways. The KV cache can get too big: Llama-3.1-8B at 1M tokens needs 131 GB of KV, more than an H100 holds before counting the weights. Or the prefill can get too slow: attention for that 1M-token prompt is about \(2\cdot 32\cdot 4096\cdot (10^6)^2 \approx 2.6\times10^{17}\) FLOPs, roughly seven minutes on one H100 at 600 TFLOP/s. TP doesn't fix either well, because it splits heads, not positions. Context parallelism (CP) splits the sequence itself.

Ring attention for prefill

Split the prompt into \(p\) chunks, one per GPU. Each GPU computes Q, K and V for its own chunk. Attention needs every query to see every (earlier) key, so the K/V chunks travel around a ring: at each step, each GPU computes attention between its queries and the K/V chunk it currently holds, while sending that chunk to the next GPU and receiving the next one. Partial results are merged with the same running-max trick FlashAttention uses (Module 08). This is Ring Attention (Liu et al., 2023).

$$\frac{4\,\htmlClass{t1}{c}^2\,\htmlClass{t2}{d}}{\htmlClass{t3}{F}} \;\ge\; \frac{2\,\htmlClass{t1}{c}\,\htmlClass{t4}{d_{kv}}\,\htmlClass{t5}{b}}{\htmlClass{t6}{BW}} \quad\Longrightarrow\quad \htmlClass{t1}{c} \;\ge\; \frac{\htmlClass{t4}{d_{kv}}\,\htmlClass{t5}{b}\,\htmlClass{t3}{F}}{2\,\htmlClass{t2}{d}\,\htmlClass{t6}{BW}}$$
\(c\)
chunk length: tokens per GPU
\(d\)
query width (heads × head dim)
\(F\)
achieved FLOP/s per GPU
\(d_{kv}\)
KV width (KV heads × head dim); smaller than \(d\) with GQA
\(b\)
bytes per element
\(BW\)
per-direction bandwidth to the next GPU in the ring

In wordsCompute on a block pair grows with \(c^2\) and the transfer grows with \(c\), so big enough chunks always hide the communication. The formula gives the threshold (per layer, full block; causal diagonal blocks have half the work).

Why it mattersLlama-3.1-70B (\(d = 8192\), \(d_{kv} = 1024\)), bf16, 600 TFLOP/s, across nodes at 50 GB/s: \(c \ge\) ~1,500 tokens. Without GQA (\(d_{kv} = d\)) it would be ~12,000. CP pays off for very long prompts and is wasteful for short ones.

Decode with a sharded KV cache

During decode, the new token's query is tiny but the KV cache is huge and already spread across GPUs. So the query goes to every GPU instead: each computes attention over its own KV shard and returns a partial output with two scalars per head, its local max score and its local sum of exponentials. A cheap merge produces the exact result.

$$\htmlClass{t1}{o} = \frac{\sum_i e^{\htmlClass{t2}{m_i}-\htmlClass{t3}{m}}\,\htmlClass{t4}{\ell_i}\,\htmlClass{t5}{o_i}}{\sum_i e^{\htmlClass{t2}{m_i}-\htmlClass{t3}{m}}\,\htmlClass{t4}{\ell_i}}, \qquad \htmlClass{t3}{m}=\max_i \htmlClass{t2}{m_i}$$
\(o\)
exact attention output, as if computed over the whole sequence
\(m_i\)
maximum attention score within shard \(i\)
\(m\)
global maximum, for numerical stability
\(\ell_i\)
\(\sum_{j \in i} e^{s_j - m_i}\): shard \(i\)'s softmax denominator
\(o_i\)
shard \(i\)'s normalized attention output

In wordsEach shard reports its answer plus how much total probability mass it holds. Weight each answer by its mass and renormalize.

Why it mattersOnly \(d_h + 2\) numbers per head travel per shard per layer, independent of context length. That's what makes million-token decode across GPUs practical.

A different approach, DeepSpeed-Ulysses (Jacobs et al., 2023), uses an all-to-all to switch from "each GPU has some positions, all heads" to "each GPU has all positions, some heads" around the attention computation. It's simpler but can't use more GPUs than there are KV heads. Context parallelism for training appears briefly in Module 07; for inference it's mainly a long-prompt prefill tool.

Multi-node realities

Inside an 8-GPU server, NVLink gives each GPU hundreds of GB/s to its peers. Leave the box and you're on a network card. The table shows the cliff. All figures are approximate per-GPU numbers; check your hardware.

LinkPer direction, approx.Notes
NVLink 4 (H100, via NVSwitch)~450 GB/sOften quoted as 900 GB/s, which counts both directions

The pieces that make the network usable

RDMA (remote direct memory access) lets a network card write into another machine's memory without involving either CPU. InfiniBand was designed around it. RoCE (RDMA over Converged Ethernet) brings it to Ethernet, at the price of more switch tuning to keep the network lossless. GPUDirect RDMA goes one step further and lets the NIC read and write GPU memory directly over PCIe, so data never bounces through host memory. Without it, every transfer pays an extra copy and some CPU time.

None of this helps if traffic takes the wrong path. NCCL works out which NIC is closest to each GPU, but containers and VMs can hide the PCIe layout from it. Set NCCL_DEBUG=INFO and read which transports it chose: NET/Socket where you expected NET/IB means you're on plain TCP and something is misconfigured.

Failure domains and stragglers

A model instance spread across \(G\) GPUs is one failure domain: if any of them fails, the instance stops. Hardware faults are rare per GPU, but they multiply.

$$\htmlClass{t1}{P_{\text{up}}} = (1-\htmlClass{t2}{f})^{\htmlClass{t3}{G}}, \qquad \htmlClass{t4}{t_{\text{step}}} = \max_{i \le \htmlClass{t3}{G}} \htmlClass{t5}{t_i}$$
\(P_{\text{up}}\)
probability the instance survives a period without any GPU fault
\(f\)
per-GPU fault probability over that period (assumed independent)
\(G\)
GPUs in one instance
\(t_{\text{step}}\)
time of one synchronous step
\(t_i\)
time rank \(i\) takes for its share of the step

In wordsEvery GPU has to be healthy for the instance to be up, and every GPU has to finish for the step to finish.

Why it mattersWith an illustrative \(f = 0.1\%\) per GPU per day, an 8-GPU instance has a 0.8% chance of a fault each day, and a 320-GPU decode unit has a 27% chance. Separately, one GPU running 20% slow (thermal throttling, a degraded NVLink lane, a noisy network neighbour) slows its entire instance by 20%. Wide instances need health checks, fast replacement, and spare capacity; DP replicas fail independently and degrade gracefully.

MLE angle · admit nodes only after a burn-in

Before a node joins a serving pool, run a short all_reduce_perf within the node and between it and a known-good neighbour, and compare busbw to a baseline. Tools like NVIDIA's DCGM diagnostics catch failing memory and links. A node that's 30% slow on all-reduce today often becomes the one that crashes next week.

2. The same measurement from PyTorch


import os
import torch
import torch.distributed as dist

def main():
    dist.init_process_group("nccl")
    rank, world = dist.get_rank(), dist.get_world_size()
    torch.cuda.set_device(int(os.environ["LOCAL_RANK"]))

    for size_bytes in [2 ** k for k in range(10, 31, 2)]:      # 1 KiB .. 1 GiB
        x = torch.zeros(size_bytes // 2, dtype=torch.bfloat16, device="cuda")
        for _ in range(5):                                     # warm-up: NCCL sets up lazily
            dist.all_reduce(x)
        torch.cuda.synchronize()

        iters = 20
        start = torch.cuda.Event(enable_timing=True)
        end = torch.cuda.Event(enable_timing=True)
        start.record()
        for _ in range(iters):
            dist.all_reduce(x)
        end.record()
        torch.cuda.synchronize()

        t = start.elapsed_time(end) / 1e3 / iters              # seconds per all-reduce
        algbw = size_bytes / t / 1e9
        busbw = algbw * 2 * (world - 1) / world
        if rank == 0:
            print(f"{size_bytes / 1e6:10.3f} MB {t * 1e6:10.1f} us "
                  f"algbw {algbw:7.1f} GB/s  busbw {busbw:7.1f} GB/s")

    dist.destroy_process_group()

if __name__ == "__main__":
    main()
