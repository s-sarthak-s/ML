Kernels, compilers & profiling

A model is a list of GPU kernels. How many there are, how many bytes each one moves, and how long the CPU takes to launch them decide most of what you see as "speed". This module opens up that list: why fusing ops helps, how a matmul reuses data, how to write a Triton kernel, what FlashAttention does inside, how torch.compile and CUDA graphs remove overhead, and how to read a profiler trace and say what's wrong.

What a kernel is, and what eager PyTorch does per op

A kernel is a function that runs on the GPU. You launch it over a grid of thread blocks; each block lands on one streaming multiprocessor (SM), and its threads work on a slice of the data. Module 17 covers the hardware side: SMs, warps, the small fast on-chip SRAM, and the large slower HBM. Here the question is software: what turns y = torch.relu(x @ W) into work on that hardware, and what does each step cost?

In eager mode, the default way PyTorch runs, each op you call is executed right away. The Python call goes through a C++ binding into the dispatcher, which looks at the tensors' dispatch keys (does this need autograd? is autocast on? which device?) and routes the call layer by layer until it reaches a backend implementation in ATen, PyTorch's C++ op library. That implementation picks a kernel (a cuBLAS GEMM for the matmul, a generated elementwise kernel for the ReLU), computes a grid size, and calls cudaLaunchKernel. The launch puts the kernel on a CUDA stream, a FIFO queue the GPU drains in order, and returns. Python moves on before the GPU has started.

Definition · Launch overhead

The CPU time spent per op before the GPU can start it: Python, argument parsing, dispatch, allocator, and the driver call. For eager PyTorch it is typically in the range of a few to around ten microseconds per op on a modern server CPU (a rough, version-dependent figure; measure yours). The raw cudaLaunchKernel call is a few microseconds of that. On the GPU side, a kernel also has a small fixed start-up and tail cost of roughly a microsecond or two, even when it does almost nothing.

$$\htmlClass{t1}{t_{\text{kernel}}} \approx \max\!\left(\frac{\htmlClass{t2}{F}}{\htmlClass{t3}{P_{\text{peak}}}},\ \frac{\htmlClass{t4}{Q}}{\htmlClass{t5}{BW}}\right) + \htmlClass{t6}{t_{\text{fixed}}}$$
\(t_{\text{kernel}}\)
time from kernel start to kernel end on the GPU
\(F\)
floating-point operations the kernel performs
\(P_{\text{peak}}\)
peak compute for the dtype used (H100 SXM bf16 dense: 989 TFLOP/s)
\(Q\)
bytes moved to and from HBM
\(BW\)
HBM bandwidth (H100 SXM: 3.35 TB/s)
\(t_{\text{fixed}}\)
fixed start-up and tail cost, around 1–2 µs (approximate)

In wordsA kernel is limited by whichever runs out first, the math units or the memory bus, plus a small constant. This is the roofline from Module 08, applied to one kernel instead of a whole model.

Why it mattersA ReLU over 1M bf16 elements moves 4 MB: 4 MB ÷ 3.35 TB/s ≈ 1.2 µs, so the fixed cost is as large as the work. Below a few million elements, the per-kernel constants dominate, and the CPU's launch cost can be larger still.

Now a worked example that shows up in every LLM serving stack. Decoding one token of Llama-3-8B at batch 1 on an H100 reads about 15 GB of bf16 weights, which takes at least 15 GB ÷ 3.35 TB/s ≈ 4.5 ms (Module 08). A straightforward eager implementation issues a lot of kernels per step: each of the 32 layers has its projections, but also an RMSNorm written as several elementwise ops, rotary embeddings as several more, cache updates, residual adds, and the SwiGLU multiply. A rough count: about 1,000 kernels per token. At ~5 µs of CPU time each, that is ~5 ms of launching, more than the 4.5 ms the GPU needs. The GPU is waiting on Python.

Pitfall · timing asynchronous code

t0 = time.time(); y = model(x); print(time.time() - t0) measures how long it took to enqueue the work, not to do it. Call torch.cuda.synchronize() before reading the clock, or use CUDA events or triton.testing.do_bench, which do this for you and also handle warm-up.

Why fusion matters

Take a chain of elementwise ops, say y = gelu(x * scale + bias). In eager mode each op is its own kernel, and each kernel reads its input from HBM and writes its output back to HBM, because that's the only place tensors live between kernels. The intermediate results go out to main memory and come straight back. A fused kernel does all the arithmetic on each element while it sits in registers, so it reads the input once and writes the output once.

$$\htmlClass{t1}{Q_{\text{unfused}}} = (2\htmlClass{t2}{k} + \htmlClass{t3}{r})\,\htmlClass{t4}{N}\,\htmlClass{t5}{b}, \qquad \htmlClass{t6}{Q_{\text{fused}}} = (2 + \htmlClass{t3}{r})\,\htmlClass{t4}{N}\,\htmlClass{t5}{b}$$
\(Q_{\text{unfused}}\)
HBM bytes when each op is its own kernel
\(k\)
ops in the chain. There are \(k+1\) full-size tensors (input, \(k-1\) intermediates, output); each intermediate is written once and read once, so \(2k\) passes in total
\(r\)
extra full-size inputs somewhere in the chain (a residual, a gate tensor). Both versions must read them
\(N\)
elements per tensor
\(b\)
bytes per element (2 for bf16)
\(Q_{\text{fused}}\)
HBM bytes for one fused kernel: one read, one write, plus the extra inputs

In wordsEvery kernel boundary in a chain costs a round trip to main memory. Fusing \(k\) ops removes \(k-1\) round trips and \(k-1\) launches.

Why it mattersElementwise ops do a handful of FLOPs per element, far below any GPU's ridge point, so their time is their traffic. Speedup from fusion is about \((2k+r)/(2+r)\) in the bandwidth regime, and about \(k\) when launches dominate.

This is why the important "small" ops in LLMs get hand-fused kernels: RMSNorm (square, mean, rsqrt, multiply, multiply by weight), RoPE, SwiGLU's silu(gate) * up, residual-add-plus-norm, and the sampler's temperature-softmax-top-p chain. It is also most of what torch.compile does for you (below).

Intuition

Unfused code is a kitchen where the cook puts every ingredient back in the walk-in fridge after each step: chop, back in the fridge; fetch, season, back in the fridge. Fusion keeps the bowl on the counter. The cooking takes the same time; the walking disappears.

Fusion has limits

You can't fuse freely across a reduction that needs all elements before anyone can continue (a softmax needs the row max first), or across a matmul without changing the matmul kernel itself. Fusing a matmul with what follows it (bias, activation, quantize) is done in the GEMM's epilogue, the code that runs on the output tile while it is still in registers. Fusing what comes before a matmul (a norm, a dequantize) goes into its prologue and is harder, because the GEMM loads its inputs many times (next section).

Tiling and data reuse in matmul

An elementwise op touches each byte once, so there is nothing to reuse. A matmul is the opposite: in \(C = AB\) with \(A\) of size \(M \times K\) and \(B\) of size \(K \times N\), each element of \(A\) is used \(N\) times (once per column of \(C\)). If every use fetched it from HBM again, a matmul would be as memory-bound as a ReLU. Tiling is how a GEMM kernel avoids that.

Each thread block owns one \(B_M \times B_N\) tile of the output. It walks along the shared \(K\) dimension in steps of \(B_K\). At each step it copies a \(B_M \times B_K\) tile of \(A\) and a \(B_K \times B_N\) tile of \(B\) into shared memory (the programmer-managed part of on-chip SRAM), and the threads multiply them into an accumulator that lives in registers. Every element of the \(A\) tile is now reused \(B_N\) times from SRAM instead of being fetched \(B_N\) times from HBM. When the \(K\) loop finishes, the block writes its output tile once.

$$\htmlClass{t1}{L_A} = \htmlClass{t2}{M}\,\htmlClass{t3}{K}\cdot\frac{\htmlClass{t4}{N}}{\htmlClass{t5}{B_N}}, \qquad \htmlClass{t6}{L_B} = \htmlClass{t3}{K}\,\htmlClass{t4}{N}\cdot\frac{\htmlClass{t2}{M}}{\htmlClass{t7}{B_M}} \qquad \xrightarrow{\ M=N=K,\ B_M=B_N=T\ } \qquad L_A + L_B = \frac{2N^3}{T}$$
\(L_A\)
elements of \(A\) loaded from global memory in total
\(M\)
rows of \(A\) and \(C\) (tokens, in an LLM layer)
\(K\)
shared inner dimension (the hidden size)
\(N\)
columns of \(B\) and \(C\) (output features)
\(B_N\)
output-tile width: each \(A\) element is loaded once per column of tiles, \(N/B_N\) times
\(L_B\)
elements of \(B\) loaded in total
\(B_M\)
output-tile height: each \(B\) element is loaded \(M/B_M\) times

In wordsWithout tiling, each element is fetched \(N\) times. With tile size \(T\), it's fetched \(N/T\) times. The reuse factor is \(T\).

Why it mattersFor an 8192-square bf16 matmul with 128-wide tiles, each element is fetched 64 times instead of 8192. The ideal lower bound is reading \(A\) and \(B\) once and writing \(C\) once.

$$\htmlClass{t1}{\text{AI}_{\text{tile}}} = \frac{2\,\htmlClass{t2}{B_M}\,\htmlClass{t3}{B_N}\,\htmlClass{t4}{B_K}}{(\htmlClass{t2}{B_M}+\htmlClass{t3}{B_N})\,\htmlClass{t4}{B_K}\,\htmlClass{t5}{b}} = \frac{2\,\htmlClass{t2}{B_M}\,\htmlClass{t3}{B_N}}{(\htmlClass{t2}{B_M}+\htmlClass{t3}{B_N})\,\htmlClass{t5}{b}} \qquad \xrightarrow{\ B_M=B_N=T\ } \qquad \frac{T}{b}$$
\(\text{AI}_{\text{tile}}\)
FLOPs per byte loaded from global memory, per \(K\) step
\(B_M\)
tile rows
\(B_N\)
tile columns
\(B_K\)
depth of each step. It cancels: deeper steps don't add reuse, they only cut loop overhead
\(b\)
bytes per element (2 for bf16, 1 for fp8)

In wordsA bigger output tile does more math per byte fetched. Square is best for a fixed tile area.

Why it mattersTiles can't grow forever. The input tiles must fit in shared memory (up to about 227 KB per block on H100) times the number of pipeline stages, and the fp32 accumulator must fit in registers (256 KB per SM on H100). That's why production GEMMs use tiles like 128×128 or 128×256, not 1024×1024.

Where the L2 cache comes in

The \(T/b\) intensity counts loads from global memory, which includes the L2 cache. With 128-wide bf16 tiles that's 64 FLOP/B, well below the H100's HBM ridge point of ~295. GEMMs still reach a large fraction of peak because neighbouring thread blocks read the same \(A\) and \(B\) tiles at nearly the same time, and the second read hits the 50 MB L2 instead of HBM. Kernels launch blocks in a "grouped" or "swizzled" order precisely to raise that hit rate. So actual HBM traffic sits between the tile-level number and the compulsory minimum.

Triton: writing kernels in Python

Writing CUDA C++ means thinking about individual threads, warps, shared-memory bank conflicts, and tensor-core instruction shapes. Triton (Tillet, Kung & Cox, 2019; developed at OpenAI) raises the level by one notch: you write a program that handles a whole block of elements as if it were a small array, and the compiler decides how to spread that block across threads, when to use shared memory, and how to vectorize loads. It's the language TorchInductor generates, and many open-source LLM kernels (in vLLM, SGLang, and Liger-Kernel, for example) are written in it.

Definition · The Triton programming model

You launch a grid of program instances. Each instance asks tl.program_id(axis) which one it is, builds a vector of offsets with tl.arange(0, BLOCK), loads that block with tl.load(ptr + offsets, mask=...), computes on it with array ops (+, tl.exp, tl.max, tl.dot), and writes with tl.store. The mask turns off lanes that fall past the end of the data. BLOCK must be a compile-time constant (tl.constexpr) and, for tl.arange, a power of two.

$$\htmlClass{t1}{G} = \left\lceil \frac{\htmlClass{t2}{n}}{\htmlClass{t3}{\text{BLOCK}}} \right\rceil, \qquad \htmlClass{t4}{\text{offs}}_{\htmlClass{t5}{p}} = \htmlClass{t5}{p}\cdot\htmlClass{t3}{\text{BLOCK}} + [0, 1, \ldots, \htmlClass{t3}{\text{BLOCK}}-1], \qquad \htmlClass{t6}{\text{mask}}_{\htmlClass{t5}{p}} = \htmlClass{t4}{\text{offs}}_{\htmlClass{t5}{p}} \lt \htmlClass{t2}{n}$$
\(G\)
number of program instances to launch (triton.cdiv(n, BLOCK))
\(n\)
number of elements in the tensor
BLOCK
elements handled by one program instance
offs
the element indices this instance touches
\(p\)
the instance's program_id, from 0 to \(G-1\)
mask
which lanes are in bounds. Only the last instance has any lanes switched off

In wordsChop the tensor into equal blocks, give each block to one program, and switch off the lanes that hang over the end.

Kernel 1: vector add, line by line


import torch
import triton
import triton.language as tl

@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n_elements, BLOCK_SIZE: tl.constexpr):
    pid = tl.program_id(axis=0)                  # which block am I?
    block_start = pid * BLOCK_SIZE
    offsets = block_start + tl.arange(0, BLOCK_SIZE)   # vector of BLOCK_SIZE indices
    mask = offsets < n_elements                 # lanes past the end are off
    x = tl.load(x_ptr + offsets, mask=mask)       # one coalesced, vectorized load
    y = tl.load(y_ptr + offsets, mask=mask)
    tl.store(out_ptr + offsets, x + y, mask=mask)

def add(x: torch.Tensor, y: torch.Tensor) -> torch.Tensor:
    out = torch.empty_like(x)
    n = out.numel()
    grid = lambda meta: (triton.cdiv(n, meta["BLOCK_SIZE"]),)   # G = ceil(n / BLOCK)
    add_kernel[grid](x, y, out, n, BLOCK_SIZE=1024)
    return out
  • @triton.jit compiles the function the first time it's called with a given set of argument types and constexpr values, then caches the binary.
  • Tensor arguments arrive as pointers to their first element. x_ptr + offsets is a vector of addresses, one per lane.
  • Adjacent lanes read adjacent addresses, so the hardware merges the loads into a few wide memory transactions (coalescing). This is what lets a simple kernel reach most of peak bandwidth.
  • kernel[grid](...) is the launch. grid can be a tuple or a function of the meta-parameters, which matters once the block size is autotuned.

Kernel 2: fused row-wise softmax

Softmax over the last dimension needs a reduction (max, then sum) before it can write anything. If a whole row fits in one block, one program can load the row once, do every step in registers, and write once: 2 passes over memory instead of the ~8 that a naive eager version makes (max, subtract, exp, sum, divide, each reading and most writing a full tensor).


@triton.jit
def softmax_kernel(out_ptr, in_ptr, in_row_stride, out_row_stride, n_cols,
                   BLOCK_SIZE: tl.constexpr):
    row = tl.program_id(0)                               # one program per row
    cols = tl.arange(0, BLOCK_SIZE)                      # BLOCK_SIZE >= n_cols
    mask = cols < n_cols
    x = tl.load(in_ptr + row * in_row_stride + cols, mask=mask,
                other=-float("inf"))                     # padded lanes: -inf, so exp() = 0
    x = x.to(tl.float32)                                 # do the math in fp32
    x = x - tl.max(x, axis=0)                            # numerically stable (next section)
    num = tl.exp(x)
    den = tl.sum(num, axis=0)
    tl.store(out_ptr + row * out_row_stride + cols, num / den, mask=mask)   # cast to out dtype

def softmax(x: torch.Tensor) -> torch.Tensor:
    n_rows, n_cols = x.shape
    BLOCK_SIZE = triton.next_power_of_2(n_cols)
    num_warps = 4 if BLOCK_SIZE <= 2048 else (8 if BLOCK_SIZE <= 8192 else 16)
    out = torch.empty_like(x)
    softmax_kernel[(n_rows,)](out, x, x.stride(0), out.stride(0), n_cols,
                              BLOCK_SIZE=BLOCK_SIZE, num_warps=num_warps)
    return out
  • other=-float("inf") fills masked lanes with \(-\infty\). They can't win the max, and \(e^{-\infty} = 0\) adds nothing to the sum. Using 0 instead would be a real bug for rows of negative logits.
  • tl.max(x, axis=0) and tl.sum are block-wide reductions. Triton generates the warp shuffles and shared-memory exchanges for you.
  • in_row_stride lets the kernel handle non-contiguous rows (a slice of a bigger tensor). Strides are in elements, not bytes.
  • This design holds the whole row in registers, so it works up to tens of thousands of columns. Past that, registers spill and you switch to a loop over column chunks using the online softmax.

Autotuning

The best BLOCK_SIZE, num_warps, and (for loops) num_stages depend on the GPU and the problem size. @triton.autotune takes a list of configs and a key. The first time it sees a new value of the key arguments, it benchmarks every config and caches the fastest for that key.


@triton.autotune(
    configs=[
        triton.Config({"BLOCK_SIZE": 256},  num_warps=2),
        triton.Config({"BLOCK_SIZE": 1024}, num_warps=4),
        triton.Config({"BLOCK_SIZE": 4096}, num_warps=8),
    ],
    key=["n_elements"],          # re-tune when this argument changes
)
@triton.jit
def add_kernel_tuned(x_ptr, y_ptr, out_ptr, n_elements, BLOCK_SIZE: tl.constexpr):
    ...                          # same body as add_kernel

# launch without passing BLOCK_SIZE; the grid lambda reads the chosen value
grid = lambda meta: (triton.cdiv(n, meta["BLOCK_SIZE"]),)
add_kernel_tuned[grid](x, y, out, n)
Pitfall · autotuning in production

The first call for each new key value runs every config, which can take seconds. If the key is something that varies per request (like the exact sequence length), every new length triggers a tuning run. Key on bucketed sizes, or tune ahead of time and pin the configs.

Softmax and reductions on GPUs

Softmax (Module 03) shows up in every attention layer and every sampler, and it is a reduction.

$$\text{softmax}(\htmlClass{t1}{x})_j = \frac{e^{\htmlClass{t1}{x_j} - \htmlClass{t2}{m}}}{\htmlClass{t4}{d}}, \qquad \htmlClass{t4}{d} = \sum_{k=1}^{\htmlClass{t3}{n}} e^{\htmlClass{t1}{x_k} - \htmlClass{t2}{m}}, \qquad \htmlClass{t2}{m} = \max_k \htmlClass{t1}{x_k}$$
\(x\)
the row of logits or attention scores
\(m\)
the row maximum. Subtracting it changes nothing mathematically (it cancels between numerator and denominator)
\(n\)
row length
\(d\)
the normalizer (denominator)

In wordsShift the row so its largest value is 0, exponentiate, divide by the total.

Why it matters\(e^{89}\) already overflows fp32. After the shift every exponent is \(\le 0\), so every term is in \((0, 1]\) and the sum is between 1 and \(n\). The cost: a naive implementation now needs three passes over the data (find max, sum, normalize).

For a kernel that streams a row it can't hold all at once, three passes means reading it from HBM three times. Milakov & Gimelshein (2018) noticed that the max and the sum can be computed together in one pass, as long as you fix up the running sum whenever the max changes.

$$\htmlClass{t1}{m_i} = \max(\htmlClass{t1}{m_{i-1}},\, \htmlClass{t2}{x_i}), \qquad \htmlClass{t3}{d_i} = \htmlClass{t3}{d_{i-1}}\cdot \htmlClass{t4}{e^{m_{i-1} - m_i}} + e^{\htmlClass{t2}{x_i} - \htmlClass{t1}{m_i}}, \qquad m_0 = -\infty,\ d_0 = 0$$
\(m_i\)
running maximum after seeing \(x_1 \ldots x_i\)
\(x_i\)
the next element (or the max of the next chunk, in a blocked kernel)
\(d_i\)
running normalizer, always equal to \(\sum_{j \le i} e^{x_j - m_i}\)
\(e^{m_{i-1}-m_i}\)
rescale factor: 1 if the max didn't change, less than 1 if it grew

In wordsKeep a running sum measured relative to the biggest value seen so far. When a bigger value shows up, shrink the old sum to the new reference point and keep going.

Why it mattersTwo passes instead of three for a plain softmax. More importantly, when the softmax feeds a weighted sum (as in attention), the output can be rescaled the same way, so the whole thing becomes one pass. That single idea is FlashAttention.

Think first: can two GPU blocks each compute (m, d) for half a row and then combine?
Yes. Given \((m_a, d_a)\) and \((m_b, d_b)\), the combined pair is \(m = \max(m_a, m_b)\), \(d = d_a e^{m_a - m} + d_b e^{m_b - m}\). The operation is associative, so it works as a tree reduction across warps, across blocks, or across GPUs. Split-KV decoding (below) is exactly this applied to attention.
MLE angle · reductions and precision

Accumulate reductions in fp32 even when inputs are bf16; bf16 keeps only 7 mantissa bits (about 2–3 significant decimal digits), so a long running sum in bf16 stops absorbing small terms once it has grown large (Module 09). The order of a parallel reduction also changes the rounding, which is one reason GPU results differ in the last bits between batch sizes and between kernels. If you need bit-exact reproducibility across batch sizes, you need kernels designed for it.

FlashAttention internals

Module 08 introduced FlashAttention (Dao et al., 2022) as "exact attention without the \(T \times T\) matrix" and gave the per-row online-softmax update. Here is how the kernel is organized, why it moves fewer bytes, and what the second and third versions changed.

The loop structure

Split \(Q\) into row blocks \(Q_i\) of \(B_r\) rows, and \(K\), \(V\) into blocks \(K_j\), \(V_j\) of \(B_c\) rows. In FlashAttention-2's ordering, each thread block owns one \(Q_i\) (for one batch element and head). It loads \(Q_i\) into SRAM once, then streams \(K_j, V_j\) pairs past it. For each pair it computes a \(B_r \times B_c\) score tile in SRAM, updates running statistics, and accumulates into an output tile that stays on chip. After the last \(K_j\), it normalizes and writes \(O_i\) once.

$$\htmlClass{t2}{S_{ij}} = \frac{Q_i K_j^{\top}}{\sqrt{d}}, \quad \htmlClass{t1}{m_i^{(j)}} = \max\!\big(\htmlClass{t1}{m_i^{(j-1)}},\ \mathrm{rowmax}(\htmlClass{t2}{S_{ij}})\big), \quad \htmlClass{t3}{\tilde P_{ij}} = e^{\htmlClass{t2}{S_{ij}} - \htmlClass{t1}{m_i^{(j)}}}, \quad \htmlClass{t4}{\ell_i^{(j)}} = e^{\htmlClass{t1}{m_i^{(j-1)}} - \htmlClass{t1}{m_i^{(j)}}}\,\htmlClass{t4}{\ell_i^{(j-1)}} + \mathrm{rowsum}(\htmlClass{t3}{\tilde P_{ij}})$$ $$\htmlClass{t5}{O_i^{(j)}} = \mathrm{diag}\!\big(e^{\htmlClass{t1}{m_i^{(j-1)}} - \htmlClass{t1}{m_i^{(j)}}}\big)\,\htmlClass{t5}{O_i^{(j-1)}} + \htmlClass{t3}{\tilde P_{ij}}\,\htmlClass{t6}{V_j}, \qquad O_i = \mathrm{diag}\big(\htmlClass{t4}{\ell_i}\big)^{-1}\,\htmlClass{t5}{O_i^{(\text{last})}}, \qquad \htmlClass{t7}{L_i} = \htmlClass{t1}{m_i} + \log \htmlClass{t4}{\ell_i}$$
\(S_{ij}\)
\(B_r \times B_c\) score tile: queries in block \(i\) against keys in block \(j\). Lives only in SRAM/registers
\(m_i^{(j)}\)
per-row running max after \(j\) key blocks (a vector of length \(B_r\))
\(\tilde P_{ij}\)
un-normalized probabilities for this tile
\(\ell_i\)
per-row running softmax denominator
\(O_i\)
\(B_r \times d\) output accumulator, rescaled whenever a row's max grows
\(V_j\)
value block \(j\)
\(L_i\)
per-row log-sum-exp, saved for the backward pass (\(N\) numbers per head, not \(N^2\))

In wordsThe per-row recurrence from the previous section, done for a whole tile of rows at once, with two matmuls (\(Q_iK_j^\top\) and \(\tilde P_{ij}V_j\)) that run on tensor cores. Division by \(\ell\) is delayed until the very end.

Why it mattersThe backward pass doesn't store \(P\) either. It recomputes each \(S_{ij}\) tile from \(Q\), \(K\), and the saved \(L_i\). That costs extra FLOPs but saves \(O(N^2)\) memory, which is the trade that made long-context training practical.

Why it moves fewer bytes

Standard attention writes \(S\) to HBM, reads it for the softmax, writes \(P\), and reads \(P\) for the \(PV\) matmul: four passes over an \(N \times N\) matrix per head. FlashAttention reads \(Q\) and writes \(O\) once, and reads \(K\), \(V\) once per query block.

$$\htmlClass{t1}{Q_{\text{std}}} = \Theta\!\left(\htmlClass{t3}{N}\htmlClass{t4}{d} + \htmlClass{t3}{N}^2\right), \qquad \htmlClass{t2}{Q_{\text{flash}}} = \Theta\!\left(\frac{\htmlClass{t3}{N}^2\,\htmlClass{t4}{d}^2}{\htmlClass{t5}{M}}\right) \quad \text{for } \htmlClass{t4}{d} \le \htmlClass{t5}{M} \le \htmlClass{t3}{N}\htmlClass{t4}{d}$$
\(Q_{\text{std}}\)
HBM accesses (in elements) for standard attention, per head
\(Q_{\text{flash}}\)
HBM accesses for FlashAttention, per head
\(N\)
sequence length
\(d\)
head dimension (64–256 in practice)
\(M\)
on-chip SRAM size, in elements

In wordsBlocks are about \(M/d\) rows tall, so \(K\) and \(V\) (size \(Nd\)) are re-read \(N \div (M/d)\) times: \(Nd \cdot Nd/M\). Standard attention pays \(N^2\) regardless. FlashAttention wins whenever \(d^2\) is well below \(M\).

Why it mattersWith \(d = 128\) and roughly 100K elements of SRAM, \(d^2/M \approx 0.16\): several times fewer accesses, and no \(N^2\) buffer at all. The paper also proves no exact attention algorithm can do asymptotically better across the whole range of \(M\).

FlashAttention-2 and -3

FlashAttention-2 (Dao, 2023) kept the algorithm and reorganized the work. It parallelizes over query blocks, not just batch and heads, so long sequences with small batches still fill the GPU. It swaps the loop order so each thread block owns its \(O_i\) and never has to write partial outputs back. It splits work across warps so they don't need to exchange partial results through shared memory, and it trims non-matmul FLOPs (the delayed division above), because on A100 a non-matmul FLOP costs roughly 16 times more than a tensor-core FLOP (19.5 vs 312 TFLOP/s). The paper reports roughly 2× over the first version and 50–73% of A100 peak in the forward pass.

FlashAttention-3 (Shah et al., 2024) targets Hopper (H100) specifically. In outline, the paper's main ideas are: use the Tensor Memory Accelerator (TMA) to copy tiles asynchronously, with some warps acting as producers that only load data and others as consumers that only compute ("warp specialization"); overlap the softmax of one tile with the matmuls of another so the slow exponentials hide behind tensor-core work; and support FP8 with block-wise scaling and an incoherent-processing trick (a random orthogonal transform that spreads outliers) to limit quantization error. The paper reports up to roughly 1.5–2× over FlashAttention-2 on H100 in fp16. Check the current release notes for supported GPUs and features; they change often.

Pitfall · "Flash" is not a different model

FlashAttention computes the same function as standard attention, up to floating-point rounding. Swapping it in should change logits only in the last few bits. If your eval moves meaningfully after switching attention backends, look for a bug: a mask, a scale factor, or a dtype mismatch.

Decode attention kernels

During decode each sequence brings one query token per step. FlashAttention's parallelism comes from batch × heads × query blocks, and with one query token there's only one query block. At batch 1 with 8 KV heads, that's 8 thread blocks on a GPU with 132 SMs: about 6% of the machine streams the whole KV cache while the rest waits. At long context this attention step can take longer than reading the weights.

Flash-Decoding (Dao, Haziza, Massa & Sizov, 2023) adds a parallel dimension: split the KV sequence into chunks. Each chunk gets its own thread block, which computes a partial output \(O_s\) together with its own max \(m_s\) and normalizer \(\ell_s\). A small second kernel combines them with the associative rule from the online softmax.

$$\htmlClass{t1}{m} = \max_s \htmlClass{t2}{m_s}, \qquad \htmlClass{t3}{O} = \frac{\sum_s e^{\htmlClass{t2}{m_s} - \htmlClass{t1}{m}}\,\htmlClass{t4}{\ell_s}\,\htmlClass{t5}{O_s}}{\sum_s e^{\htmlClass{t2}{m_s} - \htmlClass{t1}{m}}\,\htmlClass{t4}{\ell_s}}$$
\(m\)
global max over all chunks
\(m_s\)
max score within chunk \(s\)
\(O\)
final attention output, identical to unsplit attention
\(\ell_s\)
softmax denominator within chunk \(s\), relative to \(m_s\)
\(O_s\)
chunk's own normalized output: softmax over its keys times its values

In wordsEach chunk did a correct softmax over its own keys. Weight each chunk's answer by how much probability mass it holds, after putting all the chunks on a common scale.

Why it mattersThe merge reads only \(s \times d\) numbers per head, tiny next to the KV cache. In practice, kernels often store \(\log \ell_s + m_s\) (one log-sum-exp per chunk) instead of the pair.

Paged attention kernels

Serving engines store the KV cache in fixed-size blocks with a per-sequence block table (Module 08 · PagedAttention). The attention kernel then can't assume one contiguous tensor per sequence. Inside the KV loop, for logical block \(j\) it reads phys = block_table[seq, j] and computes the address as kv_base + phys * block_stride + offset. With blocks of 16 tokens × 8 heads × 128 dims in bf16, each block is 32 KB per layer for K, the same for V, which is plenty to keep loads wide and coalesced. The cost is an extra indirect load per block and less freedom to prefetch. Several FlashAttention-style kernels and libraries (vLLM's own kernels, FlashInfer, and FlashAttention's KV-cache entry point) accept a block table directly; names and arguments differ by version.

MLE angle · GQA changes the arithmetic

With grouped-query attention (Module 08), 4 query heads share each KV head in Llama-3-8B. A good decode kernel loads each K/V tile once and uses it for all 4 query heads, turning a matrix–vector product into a skinny matrix–matrix product with 4× the intensity. Kernels that loop over query heads separately read the cache 4 times. This is one of the first things to check when a decode attention kernel benchmarks slowly.

Quantized GEMM kernels

Module 09 covered the formats. Here's what the kernel does with them. Two very different designs cover most of practice.

Weight-only (W4A16): dequantize in registers

The weights sit in HBM as packed 4-bit integers plus a scale (and maybe a zero point) per group of 64–128. The kernel loads the packed weights, which is a quarter of the bf16 bytes. It unpacks and dequantizes them in registers (\(\hat w = s \cdot (q - z)\)), and feeds the bf16/fp16 values to ordinary tensor-core instructions. Dequantized weights never touch HBM. Because decode is bandwidth-bound, a step reads about 4× fewer bytes and runs up to about 4× faster (Module 09's decode ceiling).

Doing this at full speed is fiddly. The Marlin kernel (Frantar et al., 2024) is the one to read. In outline (see the paper for the exact scheme): weights are reshuffled offline into the exact order the tensor-core fragments want, so each thread can load 128 bits with one instruction and use them without moving data between threads; the int4 → fp16 conversion uses bit tricks (merging the 4-bit value into an fp16 bit pattern, then one subtraction) instead of slow conversion instructions; and loads are pipelined asynchronously so memory stays busy. The paper reports close to the ideal ~4× over fp16 for batch sizes up to about 16–32 on Ampere-class GPUs. As the batch grows, the GEMM becomes compute-bound, the dequant arithmetic stops being free, and the advantage shrinks toward zero.

FP8 GEMMs: low-precision math, not just storage

On Hopper and newer GPUs, tensor cores multiply FP8 (E4M3 or E5M2) inputs directly, at about twice the bf16 rate, and accumulate in higher precision. Now both operands are quantized (W8A8), so you need scales for both, and the question is where the scales apply.

$$\htmlClass{t1}{Y_{ij}} = \sum_{\htmlClass{t2}{g}} \htmlClass{t3}{s^{X}_{i,g}}\; \htmlClass{t4}{s^{W}_{g,j}} \sum_{k \in \htmlClass{t2}{g}} \htmlClass{t5}{X^{q}_{ik}}\; \htmlClass{t6}{W^{q}_{kj}}$$
\(Y_{ij}\)
output element, accumulated in fp32
\(g\)
a block of the \(K\) dimension (e.g. 128 wide) that shares scales
\(s^X_{i,g}\)
activation scale for row \(i\), block \(g\). Computed on the fly per token
\(s^W_{g,j}\)
weight scale for block \(g\), column block \(j\). Computed offline
\(X^q\)
fp8 activations
\(W^q\)
fp8 weights

In wordsMultiply fp8 numbers on tensor cores for one block of \(K\) at a time, then multiply the partial sum by that block's two scales and add it to an fp32 total.

Why it mattersWith per-tensor scales, both \(s\)'s are constants: pull them out of the sum and apply them once in the epilogue, for free. With per-block scales, the kernel has to stop every block to rescale and add into fp32, which costs some speed but contains outliers. DeepSeek-V3's report describes this design (1×128 activation tiles, 128×128 weight blocks), partly because Hopper's fp8 accumulation was not precise enough on its own. Blackwell adds hardware support for block scales ("microscaling" formats such as MXFP8 and MXFP4), which makes this cheaper.

Decode · small batch

Weight-only wins

Time ≈ weight bytes ÷ bandwidth. Halving or quartering the weight bytes is a direct speedup. Activations are tiny, so quantizing them buys nothing. W4A16 or W8A16 kernels.

Prefill · large batch

Low-precision math wins

Time ≈ FLOPs ÷ peak. W4A16 still multiplies in bf16, so it can't help and may lose to dequant overhead. FP8 W8A8 doubles the peak. Many deployments run FP8 for exactly this reason.

Compilers: torch.compile and friends

Writing a fused kernel for every pattern doesn't scale. A graph compiler looks at a whole sequence of ops, fuses what it can, and generates the kernels. torch.compile (introduced with PyTorch 2.0; described in Ansel et al., 2024) is the PyTorch-native one, and it has three stages.

  • TorchDynamo hooks into CPython's frame evaluation and reads your function's bytecode as it runs. It records tensor ops into an FX graph and records guards: checks on input shapes, dtypes, devices, and any Python values the trace depended on.
  • AOTAutograd traces the backward pass at compile time, decomposes ops into a smaller core set, and decides which activations to save and which to recompute.
  • TorchInductor lowers the graph to a loop-level IR, groups compatible loops into fused kernels, and emits Triton source you can actually read (set TORCH_LOGS="output_code").

Graph breaks and recompiles

When Dynamo hits something it can't put in a graph, it inserts a graph break: it compiles what it has so far, runs the troublesome code in plain Python, and starts a new graph afterwards. Common causes: calling .item() or .tolist(), if on a tensor's value, print, unsupported third-party calls, and some in-place tricks. Each break costs a return to Python and blocks fusion across the boundary. torch._dynamo.explain(fn)(x) or TORCH_LOGS="graph_breaks" lists them, with reasons.

When a guard fails, say a new input shape, Dynamo recompiles. By default, after a dimension changes once, it tries to recompile with that dimension symbolic so later sizes reuse the same code ("automatic dynamic shapes"). Past a per-function recompile limit (8 by default in recent releases), it gives up and runs that function eagerly, with a warning that's easy to miss. TORCH_LOGS="recompiles" tells you which guard failed.

Other compilers you'll meet

TensorRT is NVIDIA's ahead-of-time inference compiler. It takes a whole network, fuses layers, picks the fastest kernel for each layer and shape by benchmarking ("tactics"), and builds an engine for one specific GPU. TensorRT-LLM builds on it with LLM-specific kernels and serving features. XLA is the compiler behind JAX and TensorFlow (and PyTorch/XLA); it compiles whole programs to fused kernels and is the standard path to TPUs. All three make the same trade: more ahead-of-time compilation, faster kernels, less room for dynamic shapes and Python control flow.

Pitfall · benchmarking the compile

The first call to a compiled function includes compilation, which can take from seconds to minutes. Time steady-state calls only, after warm-up, and run warm-up with the same shapes you'll benchmark. Otherwise you're timing the compiler, or a recompile.

CUDA graphs

Fusion reduces the number of kernels. A CUDA graph removes the per-kernel CPU cost of the ones that remain. You run the step once in capture mode: kernels aren't executed, they're recorded, with their exact arguments and memory addresses, into a graph. Afterwards one replay() call submits the whole recorded sequence with a single launch, and the GPU runs the kernels back to back without the CPU touching each one.

$$\htmlClass{t1}{t_{\text{eager}}} \approx \max\!\Big(\htmlClass{t2}{n}\cdot\htmlClass{t3}{t_{\text{launch}}},\ \sum_{i=1}^{\htmlClass{t2}{n}} \htmlClass{t4}{t_i}\Big), \qquad \htmlClass{t5}{t_{\text{graph}}} \approx \htmlClass{t6}{t_{\text{replay}}} + \sum_{i=1}^{\htmlClass{t2}{n}} \htmlClass{t4}{t_i}$$
\(t_{\text{eager}}\)
step time when every kernel is launched from Python
\(n\)
kernels per step
\(t_{\text{launch}}\)
CPU cost per eager op (several µs, approximate)
\(t_i\)
GPU time of kernel \(i\)
\(t_{\text{graph}}\)
step time when the step is replayed as one graph
\(t_{\text{replay}}\)
one-off cost of launching the graph (around 10 µs here, illustrative)

In wordsEager mode overlaps CPU launching with GPU work, so the slower of the two sets the pace. With a graph, the CPU cost is nearly gone and the GPU's own work sets the pace.

Why it mattersGraphs help exactly when \(n \cdot t_{\text{launch}} \gt \sum t_i\): many small kernels, which is small-batch decode. For prefill, where kernels are long, they change almost nothing.

What a graph requires

  • Static shapes. The kernels, grid sizes, and arguments are frozen at capture. A different batch size needs a different graph.
  • Static memory addresses. The graph reads and writes the same buffers on every replay. You copy new inputs into the captured input tensors and read outputs from the captured output tensors.
  • No CPU work inside. No host syncs, no .item(), no Python branches on tensor values, no new allocations from the CPU during capture. Whatever the CPU did during capture is not replayed.

That's why serving engines capture a set of graphs, one per batch-size bucket (for example 1, 2, 4, 8, then steps of 8 or 16 up to a few hundred), during start-up. At run time the batch is padded up to the nearest captured size, and the padding rows are wasted work. Very large batches fall back to eager or piecewise execution, where launch overhead no longer matters. Capture is part of why engine start-up takes a while and why graphs reserve some memory. vLLM exposes the capture sizes and an --enforce-eager switch to turn graphs off when debugging.

Think first: a captured graph contains attention over a KV cache that grows every step. How can a static graph handle a growing context?
The graph's shapes are static but the values in its buffers aren't. The attention kernel reads the current sequence lengths and block tables from device tensors that the engine updates before each replay, and it loops over however many KV blocks those tensors say. The grid is sized for the maximum, and blocks with nothing to do exit early. Kernels written for graph capture take their dynamic quantities from device memory, not from CPU-side launch arguments.

Measuring efficiency: MFU and MBU

"Is this fast?" needs a reference. The two standard ones compare what you achieved to what the hardware could do, in the resource that should be the bottleneck.

$$\htmlClass{t1}{\text{MFU}} = \frac{\htmlClass{t2}{c}\cdot\htmlClass{t3}{N_{\text{params}}}\cdot\htmlClass{t4}{\text{tokens/s}}}{\htmlClass{t5}{P_{\text{peak}}}}$$
MFU
fraction of peak compute spent on the model's own math
\(c\)
FLOPs per parameter per token: 6 for training (forward + backward), 2 for inference
\(N_{\text{params}}\)
parameters (active parameters for a mixture-of-experts model)
tokens/s
measured throughput per GPU
\(P_{\text{peak}}\)
dense peak for the dtype (H100 bf16: 989 TFLOP/s)

In wordsCount only the FLOPs the model mathematically requires, not recomputation or padding, and divide by what the chip could do in that time.

Why it mattersIntroduced in the PaLM paper (Chowdhery et al., 2022) so different setups could be compared fairly. Illustrative: an 8B model training at 8,000 tokens/s per H100 is \(6 \times 8\times10^9 \times 8000 \approx 3.8\times10^{14}\) FLOP/s, about 39% MFU. The formula leaves out attention FLOPs, which matter at long context; some reports add them, so check which convention a number uses.

$$\htmlClass{t1}{\text{MBU}} = \frac{\big(\htmlClass{t2}{M_W} + \htmlClass{t3}{M_{KV}}\big)\cdot \htmlClass{t4}{\text{tokens/s}}}{\htmlClass{t5}{BW_{\text{peak}}}}$$
MBU
fraction of peak memory bandwidth spent on bytes the model has to read
\(M_W\)
weight bytes read per token (all weights for a dense model)
\(M_{KV}\)
KV-cache bytes read per token: bytes per cached token × current context
tokens/s
measured decode speed for one sequence
\(BW_{\text{peak}}\)
spec-sheet memory bandwidth

In wordsAt batch 1, every token requires reading the whole model. Multiply those bytes by tokens per second to get the bandwidth you achieved, then compare with the spec sheet.

Why it mattersDecode at small batch is bandwidth-bound, so MFU is meaningless there (it will read 1%). MBU tells you how close you are to the decode speed ceiling from Module 09. For batch \(B\), use bytes read per step (weights once, plus every sequence's KV) × steps per second.

Interpreting the number

Rough bands, from experience rather than a standard: well-optimized engines reach roughly 60–85% MBU at batch 1 on large GPUs. Something like 30–60% suggests overhead such as launches, syncs, or a slow attention kernel. Under 30% usually means the GPU is idle much of the time, typically launch-bound eager code. Over 100% means the formula doesn't match what's running: a mixture-of-experts model (use active parameters), speculative decoding (several tokens per weight read), batch above 1, or a wrong bit width.

Profiling: finding where the time goes

MFU and MBU tell you whether you're slow. A trace tells you why. Three tools cover nearly everything, from coarse to fine.

PyTorch profiler

Which ops, which kernels

torch.profiler records CPU ops and the CUDA kernels they launched, with shapes and Python stacks. Exports a trace you open in a trace viewer (Perfetto or chrome://tracing). Start here.

Nsight Systems

The whole timeline

nsys shows CPU threads, CUDA API calls, kernels, memory copies, and NVTX ranges on one timeline, with low overhead. Best for gaps, launch-bound regions, syncs, and multi-GPU communication.

Nsight Compute

Inside one kernel

ncu replays a single kernel many times to collect hardware counters: achieved memory throughput, compute throughput, occupancy, cache hit rates, and a roofline chart. Use it once you know which kernel is slow.

$$\htmlClass{t1}{u} = \frac{\sum_i \htmlClass{t2}{t_i}}{\htmlClass{t3}{T_{\text{wall}}}}$$
\(u\)
fraction of wall-clock time the GPU is running at least one kernel
\(t_i\)
duration of kernel \(i\) in the trace window (merge overlapping kernels on different streams)
\(T_{\text{wall}}\)
length of the window, e.g. one decode step

In wordsAdd up how long kernels ran, divide by how long the step took. The remainder is time the GPU spent waiting for you.

Why it mattersCheck this first. If \(u\) is 40%, no kernel optimization can give more than 2.5× until you fix the gaps. If \(u\) is 98%, the gaps don't matter and you go kernel by kernel. Note that "GPU utilization" in nvidia-smi is this kind of number, not how hard the SMs are working: a single tiny kernel running all the time shows 100%.

1. Triton softmax vs torch, measured in GB/s


import torch
import triton
import triton.language as tl
from triton.testing import do_bench

@triton.jit
def softmax_kernel(out_ptr, in_ptr, in_row_stride, out_row_stride, n_cols,
                   BLOCK_SIZE: tl.constexpr):
    row = tl.program_id(0)
    cols = tl.arange(0, BLOCK_SIZE)
    mask = cols < n_cols
    x = tl.load(in_ptr + row * in_row_stride + cols, mask=mask, other=-float("inf")).to(tl.float32)
    x = x - tl.max(x, axis=0)
    num = tl.exp(x)
    tl.store(out_ptr + row * out_row_stride + cols, num / tl.sum(num, axis=0), mask=mask)

def triton_softmax(x):
    n_rows, n_cols = x.shape
    BLOCK_SIZE = triton.next_power_of_2(n_cols)
    num_warps = 4 if BLOCK_SIZE <= 2048 else (8 if BLOCK_SIZE <= 8192 else 16)
    out = torch.empty_like(x)
    softmax_kernel[(n_rows,)](out, x, x.stride(0), out.stride(0), n_cols,
                              BLOCK_SIZE=BLOCK_SIZE, num_warps=num_warps)
    return out

def naive_softmax(x):
    # five eager kernels, ~8 full passes over memory
    x_max = x.max(dim=1, keepdim=True).values
    z = x - x_max
    num = torch.exp(z)
    den = num.sum(dim=1, keepdim=True)
    return num / den

PEAK_GBPS = 3350          # set to your GPU's spec-sheet bandwidth (H100 SXM shown)
torch.manual_seed(0)
for n_cols in (1024, 4096, 16384, 32768):
    x = torch.randn(4096, n_cols, device="cuda", dtype=torch.float32)
    ref = torch.softmax(x, dim=1)
    err = (triton_softmax(x) - ref).abs().max().item()
    assert err < 1e-3, err
    bytes_moved = 2 * x.numel() * x.element_size()   # one read + one write: the ideal
    for name, fn in [("naive", naive_softmax),
                     ("torch", lambda t: torch.softmax(t, dim=1)),
                     ("triton", triton_softmax)]:
        ms = do_bench(lambda: fn(x))
        gbps = bytes_moved / (ms * 1e-3) / 1e9
        print(f"cols={n_cols:6d} {name:7s} {ms * 1e3:9.1f} us {gbps:7.0f} GB/s ({100 * gbps / PEAK_GBPS:4.1f}% of peak)")

Predict before running: the naive version makes about four times as many passes as the fused ones, so it should run at about a quarter of their effective GB/s on large inputs. torch.softmax is already a single fused kernel, so matching it is a good result; beating it on some shapes is possible. Note that GB/s here counts the ideal bytes (one read, one write), so the naive version's "GB/s" is an effective number, not its real bus traffic.

3. torch.compile on an MLP block


import torch, torch.nn as nn, torch.nn.functional as F
from triton.testing import do_bench

class SwiGLU(nn.Module):
    def __init__(self, d=4096, h=14336):
        super().__init__()
        self.gate = nn.Linear(d, h, bias=False)
        self.up = nn.Linear(d, h, bias=False)
        self.down = nn.Linear(h, d, bias=False)
        self.norm = nn.RMSNorm(d)
    def forward(self, x):
        y = self.norm(x)
        return x + self.down(F.silu(self.gate(y)) * self.up(y))

m = SwiGLU().cuda().to(torch.bfloat16).eval()
mc = torch.compile(m, mode="max-autotune")        # compiles lazily, on first call
for batch in (1, 8, 2048):
    x = torch.randn(batch, 4096, device="cuda", dtype=torch.bfloat16)
    with torch.no_grad():
        eager = do_bench(lambda: m(x))
        mc(x); mc(x)                               # new shape: (re)compile, then warm up
        comp = do_bench(lambda: mc(x))
    print(f"batch={batch:5d} eager {eager * 1e3:8.1f} us   compiled {comp * 1e3:8.1f} us")

# see what it generated and why it broke or recompiled:
#   TORCH_LOGS="output_code,graph_breaks,recompiles" python compile_mlp.py

Predict first. At batch 1 and 8 the three GEMMs are weight-bandwidth-bound (about 350 MB of bf16 weights), and compile can only fuse the norm and the silu * up, so expect a modest gain. At batch 2048 the GEMMs are compute-bound; the gain depends on autotuning beating cuBLAS, which it usually doesn't on these shapes. Each new batch size triggers a recompile, which the log will show.

4. CUDA graph capture by hand


import torch, torch.nn as nn
from triton.testing import do_bench

# 32 small blocks: ~160 short kernels per call, a launch-bound shape like batch-1 decode
model = nn.Sequential(*[nn.Sequential(nn.Linear(1024, 2816), nn.SiLU(), nn.Linear(2816, 1024))
                        for _ in range(32)]).cuda().to(torch.bfloat16).eval()
static_x = torch.randn(1, 1024, device="cuda", dtype=torch.bfloat16)

with torch.no_grad():
    s = torch.cuda.Stream()
    s.wait_stream(torch.cuda.current_stream())
    with torch.cuda.stream(s):                 # warm up on a side stream before capture
        for _ in range(3):
            model(static_x)
    torch.cuda.current_stream().wait_stream(s)

    g = torch.cuda.CUDAGraph()
    with torch.cuda.graph(g):                  # record, don't run
        static_y = model(static_x)

    def graph_step(new_x):
        static_x.copy_(new_x)                  # write into the captured input buffer
        g.replay()                             # one launch for the whole sequence
        return static_y                        # captured output buffer (clone it to keep it)

    x = torch.randn_like(static_x)
    assert torch.allclose(graph_step(x), model(x), atol=1e-2)
    print("eager us:", do_bench(lambda: model(x)) * 1e3)
    print("graph us:", do_bench(lambda: graph_step(x)) * 1e3)

7. On a Mac: custom Metal kernels in MLX

MLX exposes a way to compile a Metal kernel from a source string: mx.fast.metal_kernel. The API below matches the MLX documentation at the time of writing; check the current docs, since it has changed between releases. The model is close to CUDA's: each thread knows its position in the grid, and grid counts threads, not threadgroups.


import mlx.core as mx

source = """
    uint i = thread_position_in_grid.x;
    out[i] = a[i] + b[i];
"""
kernel = mx.fast.metal_kernel(
    name="vec_add",
    input_names=["a", "b"],
    output_names=["out"],
    source=source,
)

a = mx.random.normal((1 << 24,)); b = mx.random.normal((1 << 24,))
(out,) = kernel(
    inputs=[a, b],
    grid=(a.size, 1, 1),            # total threads: exactly one per element, so no bounds check
    threadgroup=(256, 1, 1),
    output_shapes=[a.shape],
    output_dtypes=[a.dtype],
)
mx.eval(out)
print(mx.abs(out - (a + b)).max())

A chain of 4 elementwise ops (no extra inputs) runs on a tensor of 64M bf16 elements on an H100 (3.35 TB/s). Roughly how long does it take unfused vs fused, ignoring launch cost?

  1. 80 µs vs 40 µs
  2. 160 µs vs 80 µs
  3. 320 µs vs 80 µs
  4. 320 µs vs 320 µs: fusion doesn't change memory traffic
Unfused: \(2k \cdot N \cdot b = 8 \times 64\text{M} \times 2\) B ≈ 1.07 GB → ≈ 320 µs. Fused: one read and one write, \(2 \times 64\text{M} \times 2\) ≈ 268 MB → ≈ 80 µs. The 4× comes entirely from removing the intermediate round trips.

A square 8192 × 8192 bf16 matmul uses 128 × 128 output tiles. How many times is each element of \(A\) fetched from global memory, and what is the tile-level arithmetic intensity?

  1. 64 times; 64 FLOP/B
  2. 8192 times; 1 FLOP/B
  3. 128 times; 128 FLOP/B
  4. Once; about 5,500 FLOP/B
Each element of \(A\) is loaded once per column of output tiles: \(N/T = 8192/128 = 64\). Tile intensity is \(T/b = 128/2 = 64\) FLOP/B. "Once" is the compulsory minimum, which only L2 reuse gets close to; 8192 is the no-tiling case.

In the online softmax, the running max goes from \(m_{i-1} = 2\) to \(m_i = 5\) when \(x_i = 5\) arrives. What happens to the running normalizer?

  1. It's reset to 0 and recomputed from scratch
  2. \(d_i = d_{i-1} + e^{5}\)
  3. \(d_i = d_{i-1} \cdot e^{3} + 1\)
  4. \(d_i = d_{i-1} \cdot e^{-3} + 1\)
\(d_i = d_{i-1}\, e^{m_{i-1} - m_i} + e^{x_i - m_i} = d_{i-1} e^{2-5} + e^{0}\). Old terms were measured relative to 2; relative to the new max 5 they're smaller by \(e^{-3}\). The normalizer stays between 1 and \(i\), so it never overflows.

Llama-3-8B in bf16 (~16 GB of weights) decodes at 60 tokens/s at batch 1 and short context on an H100 SXM (3.35 TB/s). What is the MBU, and what's the most likely next step?

  1. About 90%; nothing left to gain without quantization
  2. About 29%; look for launch overhead and syncs, e.g. add CUDA graphs
  3. About 3%; the GPU is compute-bound, so buy more FLOPs
  4. Can't be computed without knowing the FLOPs
16 GB × 60/s ≈ 0.96 TB/s, which is 0.96 ÷ 3.35 ≈ 29%. That low a fraction at batch 1 usually means the GPU is idle much of the step, typically launch-bound eager code. CUDA graphs and fused kernels are the usual fix. MFU would be about 1% and tells you nothing here.

Why does Flash-Decoding (split-KV) speed up batch-1 decode at 32K context but help little at batch 64 and short context?

  1. It reduces the number of FLOPs in attention
  2. It compresses the KV cache
  3. At batch 1 there are too few (batch × head) work units to fill the SMs, so splitting the KV length adds parallelism; at batch 64 the GPU is already full
  4. It only works with FP8
With 8 KV heads at batch 1 there are 8 work units for 132 SMs. Splitting a 32K cache into chunks gives each SM a share. At batch 64 there are already 512 units, so extra splitting only adds the merge cost. FLOPs and bytes are unchanged; only the parallelism changes.

You wrap a model in torch.compile. Its forward contains if mask.sum().item() > 0:, and requests arrive with many different sequence lengths. Which pair of problems should you expect?

  1. Out-of-memory errors and NaNs
  2. Slower compile only on the first call, then no issues
  3. The compiled model returns different numbers from eager
  4. A graph break at .item(), and recompiles as lengths change (until dynamic shapes or the recompile limit kick in)
.item() copies a value to the CPU, and Dynamo can't trace a Python branch on it, so it breaks the graph there (and syncs). New sequence lengths fail shape guards and trigger recompiles; after the recompile limit, the function falls back to eager. TORCH_LOGS="graph_breaks,recompiles" shows both.

A decode trace shows GPU kernels of about 3 µs each separated by 6 µs gaps, while the CPU thread is busy the whole time with launch calls. Which change will help most?

  1. A GPU with more memory bandwidth
  2. Capture the step in a CUDA graph (or fuse ops to cut the kernel count)
  3. Use a larger tile size in the GEMMs
  4. Switch the attention kernel to FlashAttention-3
The GPU is busy about a third of the time, and the CPU is the bottleneck. A faster GPU would make the kernels shorter and the gaps relatively bigger. Removing per-kernel CPU cost, through graphs or fewer kernels, is the only change that removes the gaps.
