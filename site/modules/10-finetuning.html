Module 10 · Adapting models

Fine-tuning: teaching a model new habits

Full fine-tuning of an 8B model needs about 128 GB of GPU memory before a single activation is stored. A rank-16 LoRA adapter on every linear layer of the same model is 42 million parameters, an 84 MB file, and with QLoRA the whole job fits on one 24 GB card. This module covers what fine-tuning can and can't do, how to run it end to end, and how preference tuning (RLHF, DPO, GRPO) pushes a model past imitation.

~5 hoursprereqs: 03, 07, 09hands-on: TRL, PEFT, MLX, vLLM

By the end you can

  1. Decide between prompting, RAG, and fine-tuning for a concrete problem, and say why fine-tuning is a poor way to add facts.
  2. Write the SFT loss with a loss mask, build a JSONL chat dataset, and catch template, EOS, and train/serve drift bugs before they cost you a run.
  3. Compute LoRA parameter counts and training memory for full fine-tuning, LoRA, and QLoRA on a given model and GPU.
  4. Pick starting hyperparameters, read train/validation curves, and stop before overfitting or catastrophic forgetting set in.
  5. Derive what the RLHF reward model, PPO, DPO, and GRPO each optimize, and explain what DPO's β and GRPO's group baseline do.
  6. Run a LoRA fine-tune with TRL or MLX, serve the adapter with vLLM, and show it beats a prompted baseline on held-out data without regressing elsewhere.

What fine-tuning is, and what it isn't

Fine-tuning means taking a model that has already been trained and continuing to train it on a much smaller dataset of your own. The weights and the next-token objective stay the same; what changes is that the gradient now points at your examples. A few hundred well-chosen examples can change how a model behaves in ways no prompt reliably will.

The important word is behaves. Fine-tuning is very good at changing:

  • Format: always emit valid JSON with these four keys, always call tools with this schema, never add a preamble.
  • Style and voice: your support team's tone, terse commit messages, a house style for legal summaries.
  • Narrow skills: classify tickets into your 40 categories, extract fields from invoices, translate your DSL into SQL.
  • Cost and latency: a 3B model fine-tuned on a task can match a much larger prompted model on that one task, and you can drop the 2,000-token instruction block from every request.

It is a weak tool for adding lots of new facts. A model trained on your product docs for a few epochs will learn their vocabulary and tone, but it won't reliably recall that the refund window changed from 30 to 45 days last Tuesday, and it can't cite where it read that. Ovadia et al. (2023) compared the two directly and found retrieval beat unsupervised fine-tuning for knowledge injection across their tasks. Gekhman et al. (2024) found that examples containing genuinely new knowledge are learned slowly and, once learned, make the model more prone to hallucinate. When the gap is knowledge, especially knowledge that changes, use retrieval (Module 11).

Intuition

Pretraining gives the model a library. Fine-tuning teaches it a job: how to read a request, which shelf to walk to, how to write the answer up. If the book it needs isn't in the library, training it harder on the job won't put the book there. Hand it the book at request time instead.

Think first: your model writes great answers but wraps the JSON in markdown fences 8% of the time. Prompt, RAG, or fine-tune?
Try prompting and constrained decoding first: a schema-constrained or JSON-mode sampler (structured outputs, supported by vLLM, llama.cpp, and most APIs) removes the fences at decode time with zero training. If you also need the model to follow a subtle extraction policy that the prompt keeps missing, that's a behaviour gap, and a few hundred SFT examples is the right next step. RAG doesn't help, because nothing is missing from the model's knowledge.

The post-training pipeline

The "chat model" you call through an API is a base model that went through several stages of post-training. Knowing the stages tells you where your own fine-tune sits and which knobs each stage turns.

StageDataObjectiveWhat it changes
PretrainingTrillions of web, code, book tokensNext-token cross-entropy on everythingKnowledge, language, latent skills (Module 07)
SFT (instruction tuning)Prompt → ideal response demonstrationsCross-entropy on response tokens onlyFollows instructions, chat format, turn-taking, refusals, tool-call syntax
Preference tuningPrompt + chosen vs rejected responseReward model + PPO (RLHF), or DPO directlyWhich of several acceptable answers people prefer: helpfulness, tone, length, safety
RL with verifiable rewardsPrompts with checkable answers (math, unit tests)Policy gradient (PPO, GRPO) on a programmatic rewardMulti-step reasoning, self-checking, long chains of thought

SFT is imitation: the model can only be as good as the demonstrations. Preference tuning and RL let the model generate its own attempts and get graded, which is how it can end up better than any single demonstration it saw. That difference comes up again in the last third of this module.

Supervised fine-tuning: the objective

SFT uses exactly the pretraining loss from Module 03, with one change. A training example is a whole conversation rendered into one token sequence, but we only want the model to learn to produce the assistant's tokens. Learning to predict the user's question would waste gradient on text the model will never have to write. So each token gets a mask bit.

$$\htmlClass{t1}{\mathcal{L}_{\text{SFT}}}(\theta) = -\frac{1}{\sum_{t} \htmlClass{t2}{m_t}} \sum_{t=1}^{\htmlClass{t3}{T}} \htmlClass{t2}{m_t}\,\log \htmlClass{t4}{\pi_\theta}\big(\htmlClass{t5}{y_t} \mid \htmlClass{t6}{y_{\lt t}}\big)$$
\(\mathcal{L}_{\text{SFT}}\)
average negative log-likelihood per counted token; this is what the optimizer minimizes
\(m_t\)
loss mask: 1 if token \(t\) belongs to an assistant response (including its end-of-turn token), 0 for system, user, tool-result, and template tokens
\(T\)
length of the rendered sequence in tokens
\(\pi_\theta\)
the model's next-token distribution with weights \(\theta\) (the "policy")
\(y_t\)
the actual token at position \(t\)
\(y_{\lt t}\)
every token before it, prompt included. The prompt is still read; it just isn't scored

In wordsRun the whole conversation through the model, look at how much probability it gave to each assistant token, and push those probabilities up. Ignore the tokens the model didn't write.

Why it mattersOn an extraction task with a 2,000-token document and a 60-token JSON answer, an unmasked loss spends 97% of its signal teaching the model to write invoices. Masking puts all of it on the answer.

How the average is taken matters

The formula divides by the number of counted tokens across the batch. Some implementations instead average per sequence, then across sequences, which gives a 20-token answer the same total weight as a 2,000-token one. Neither is wrong, but switching between them changes the effective learning rate on long responses. If you port a recipe between frameworks and the loss scale looks different, this is often why.

Two other loss choices you'll see. Continued pretraining (sometimes called domain-adaptive pretraining) sets \(m_t=1\) everywhere on raw domain text, with no chat template at all. It's how you shift a model's vocabulary toward, say, clinical notes, and it is the setting where forgetting is worst. Multi-turn masking scores every assistant turn in a conversation, not just the last one, which is usually what you want for chat data.

Chat templates and data formats

A model doesn't see "messages". It sees one flat token sequence, and the chat template (a Jinja template shipped in tokenizer_config.json) decides how roles and turns are spelled with special tokens. Almost every fine-tuning dataset today is JSONL with one conversation per line:


{"messages": [
  {"role": "system", "content": "Extract invoice fields. Reply with JSON only: vendor, date (YYYY-MM-DD), total (number), currency (ISO 4217)."},
  {"role": "user", "content": "ACME Corp - Invoice #4471\nServices rendered March 2024\nTotal due: EUR 1,240.00 by 15/03/2024"},
  {"role": "assistant", "content": "{\"vendor\": \"ACME Corp\", \"date\": \"2024-03-15\", \"total\": 1240.0, \"currency\": \"EUR\"}"}
]}

The same example rendered with the Llama 3 template looks like this. Every <|…|> marker is a single special token:


<|begin_of_text|><|start_header_id|>system<|end_header_id|>

Extract invoice fields. Reply with JSON only: vendor, date (YYYY-MM-DD), total (number), currency (ISO 4217).<|eot_id|><|start_header_id|>user<|end_header_id|>

ACME Corp - Invoice #4471
Services rendered March 2024

Other dataset shapes you'll meet: {"prompt": …, "completion": …} (the prompt is masked by default in TRL), {"text": …} for continued pretraining, {"prompt", "chosen", "rejected"} for preference tuning, and messages with tool_calls and a tools list for function-calling data.


from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("Qwen/Qwen3-1.7B")

print(tok.apply_chat_template(msgs[:1], tokenize=False,
                              add_generation_prompt=True))             # serving view: must be a prefix of the training view
ids = tok.apply_chat_template(msgs, tokenize=True)
print(tok.convert_ids_to_tokens(ids)[-5:], tok.eos_token)              # does it end with the end-of-turn token?
Pitfalls that silently ruin a fine-tune

Mismatched template. Training a Llama checkpoint with a ChatML template (or a home-made ### User: format) teaches the model a second dialect. It may work in your notebook and fall apart behind a server that applies the official template.

Missing EOS / end-of-turn. If the scored tokens don't end with the token the server treats as "stop" (<|eot_id|>, <|im_end|>), the model never learns to stop and rambles until max_tokens. A base model whose tokenizer EOS differs from the template's end-of-turn token is the classic case; TRL's SFTConfig(eos_token=…) exists for it.

Train/serve drift. The serving stack renders prompts with whatever template it finds. Templates differ in small ways that matter: Llama 3.1+ templates add a "Cutting Knowledge Date / Today Date" preamble to the system turn, some Qwen templates insert a default system prompt when you pass none, and hybrid-reasoning models (Qwen3) render a <think> block that depends on enable_thinking. Train and serve with the same template and the same flags, and test with the exact production request path.

Double BOS. Tokenizing a string that already contains <|begin_of_text|> with add_special_tokens=True gives two BOS tokens. Harmless-looking, but it's a distribution shift the model never saw.

Data: quality over quantity

The single most reliable lever in fine-tuning is the dataset. LIMA (Zhou et al., 2023) fine-tuned LLaMA-65B on just 1,000 carefully curated prompt–response pairs. In the authors' human study its answers were judged equivalent to or better than GPT-4's in 43% of cases. Their reading, the superficial alignment hypothesis: nearly all knowledge comes from pretraining, and alignment mostly teaches which format and style to use. A thousand excellent examples beat fifty thousand sloppy ones for that purpose.

How many examples?

These are rules of thumb from public recipes and practitioner experience, not guarantees. The right number depends on how far the target behaviour is from what the model already does.

GoalTypical sizeNotes
Output format, schema, tone100 – 1,000Diversity of inputs matters more than count. Cover edge cases: empty fields, two currencies, malformed input.
Narrow task (extraction, classification, routing)500 – 5,000Balance classes. Include hard negatives and examples the prompted baseline gets wrong.
New sub-skill or domain style (DSL → SQL, clinical tone)5,000 – 50,000+Consider continued pretraining on raw domain text first.
General instruction following from a base model1,000 – 1MLIMA showed 1k can go far; open recipes like Tülu 3 mix close to a million to cover many skills.
Preference pairs (DPO)1,000 – 100,000Pairs where the difference is the thing you care about. Noisy labels hurt more than few labels.

Synthetic data and distillation

Most open fine-tuning recipes of the last two years (Alpaca-style sets, Tülu 3, the R1 distills) rely at least partly on data written by a stronger model. The pattern: write a few dozen seed examples by hand, have a strong model generate thousands of varied inputs and answers, then filter hard, with programmatic checks (does the JSON parse, do totals add up, do the unit tests pass) and a judge model or human spot-checks. When the outputs come from a bigger model and the student learns to imitate them, that's sequence-level distillation (covered formally near the end of this module). DeepSeek-R1's small "distilled" models were produced exactly this way: the R1 paper (DeepSeek-AI, 2025) reports SFT on roughly 800k samples curated with the large model. Check the provider's terms of use before training on API model outputs; several prohibit using them to build competing models.

Hygiene: dedup, decontamination, packing

  • Deduplicate. Exact-hash duplicates, then near-duplicates with MinHash or embedding similarity. Synthetic data is especially repetitive; a template that produced 500 near-identical invoices will be memorized, not learned from.
  • Decontaminate against every eval set. Remove training examples that overlap your held-out test set and any public benchmark you'll report, using n-gram overlap (the GPT-3 paper used 13-grams) or embedding search. A synthetic generator prompted with "examples like GSM8K" will happily reproduce GSM8K.
  • Split by source, not by row. If ten examples come from one customer's invoices, all ten belong on the same side of the train/test split; otherwise your test set measures memorization of that customer's layout.
  • Pack short examples. Padding a 150-token example to 2,048 wastes over 90% of the compute on that row. Packing concatenates several examples into one sequence; good implementations (TRL's packing=True with the default best-fit strategy) also reset position ids so examples can't attend to each other, which requires a padding-free attention kernel such as FlashAttention.
$$\htmlClass{t1}{S} = \left\lceil \frac{\htmlClass{t2}{E}\cdot \htmlClass{t3}{N}}{\htmlClass{t4}{b}\cdot \htmlClass{t5}{g}\cdot \htmlClass{t6}{n_{\text{gpu}}}} \right\rceil$$
\(S\)
number of optimizer steps (what warmup and the LR schedule are measured in)
\(E\)
epochs: full passes over the data
\(N\)
training examples (or packed sequences, if packing)
\(b\)
micro-batch: sequences per GPU per forward pass (limited by memory)
\(g\)
gradient accumulation steps: forward/backward passes summed before one update
\(n_{\text{gpu}}\)
data-parallel workers. \(b\cdot g\cdot n_{\text{gpu}}\) is the effective batch

In words2,000 examples × 3 epochs ÷ (4 × 4 × 1) = 375 steps. With 3% warmup that's 11 warmup steps.

Why it mattersSmall datasets give few steps. 200 examples at effective batch 32 is 7 steps per epoch, and a recipe tuned for 5,000 steps will behave nothing like that. Reason in steps and tokens, not epochs alone.

Full fine-tuning vs parameter-efficient methods

Full fine-tuning updates every weight. Module 07 showed what that costs with AdamW in mixed precision: the weights themselves are the smallest part of the bill.

$$\htmlClass{t1}{M_{\text{full}}} \approx \htmlClass{t2}{N}\,\big(\htmlClass{t4}{2} + \htmlClass{t5}{2} + \htmlClass{t6}{12}\big) + \htmlClass{t3}{M_{\text{act}}} = 16\,\htmlClass{t2}{N} + \htmlClass{t3}{M_{\text{act}}}$$
\(M_{\text{full}}\)
bytes of GPU memory for training (before framework overhead)
\(N\)
parameters (8B → \(8\times10^9\))
2
bf16 working copy of the weights
2
bf16 gradient for every weight
12
AdamW state in fp32: master weights (4) + first moment \(m\) (4) + second moment \(v\) (4)
\(M_{\text{act}}\)
saved activations for backprop; grows with batch × sequence length, shrinks with gradient checkpointing

In wordsEvery parameter costs about 16 bytes to train, versus 2 bytes to serve. An 8B model needs about 128 GB before activations, so more than one 80 GB GPU, sharded with FSDP or ZeRO-3.

Parameter-efficient fine-tuning (PEFT) freezes the pretrained weights and trains a small number of new or selected parameters. Frozen weights need no gradient and no optimizer state, so they cost only their storage. The main families:

Additive · adapters

Insert small trainable layers

Houlsby et al. (2019) added bottleneck MLPs inside each block. Effective, but they add sequential compute at inference that you can't remove.

Soft prompts

Train virtual tokens

Prefix- and prompt-tuning learn embedding vectors prepended to the input. Tiny, but they eat context length and trail LoRA on most LLM tasks.

Reparameterize · LoRA

Train a low-rank update

Learn \(\Delta W = BA\) beside each frozen matrix. Mergeable into the weights after training, so zero inference overhead. The default today.

Full fine-tuning still has its place. When you have a lot of data and need the model to absorb a lot (continued pretraining on a new language, large-scale code), LoRA learns less. Biderman et al. (2024), in a paper titled LoRA Learns Less and Forgets Less, found full fine-tuning clearly ahead on code and math continued pretraining, while LoRA kept more of the base model's other abilities. For the typical product task, a few thousand examples and a narrow skill, LoRA usually lands close to full fine-tuning at a fraction of the cost.

LoRA: low-rank adaptation

LoRA (Hu et al., 2021) rests on one empirical bet: the change fine-tuning makes to a weight matrix has low intrinsic rank. You don't need a full 4096×4096 matrix of independent updates; a product of two thin matrices captures most of it.

$$\htmlClass{t1}{h} = \htmlClass{t2}{W_0}\,\htmlClass{t3}{x} + \frac{\htmlClass{t4}{\alpha}}{\htmlClass{t5}{r}}\,\htmlClass{t6}{B}\,\htmlClass{t7}{A}\,\htmlClass{t3}{x}, \qquad \htmlClass{t6}{B}\in\mathbb{R}^{d\times \htmlClass{t5}{r}},\;\; \htmlClass{t7}{A}\in\mathbb{R}^{\htmlClass{t5}{r}\times k},\;\; \htmlClass{t5}{r}\ll\min(d,k)$$
\(h\)
layer output, a vector of size \(d\) (e.g. the query vector from q_proj)
\(W_0\)
the pretrained \(d\times k\) weight matrix. Frozen: no gradient, no optimizer state
\(x\)
layer input, a vector of size \(k\)
\(\alpha\)
scaling hyperparameter (lora_alpha). Together with \(r\) it sets how loud the update is
\(r\)
rank: width of the bottleneck. Typical 8–64, versus \(d=4096\)
\(B\)
up-projection \(r\to d\). Initialized to zero
\(A\)
down-projection \(k\to r\). Initialized randomly (Gaussian in the paper; Kaiming-uniform in PEFT)

In wordsKeep the original layer exactly as it was, and add a side path that squeezes the input down to \(r\) numbers and expands it back. Only the side path learns.

Why it mattersBecause \(B=0\) at the start, \(BA=0\): step zero is exactly the pretrained model, and training starts from a known-good point instead of a randomly perturbed one. \(A\) must not also be zero, because then the gradients of both matrices would be zero and nothing would ever move.

$$\htmlClass{t1}{P_{\text{LoRA}}} = \htmlClass{t2}{r}\,(\htmlClass{t3}{d} + \htmlClass{t4}{k}) \qquad\text{versus}\qquad \htmlClass{t3}{d}\,\htmlClass{t4}{k}\;\text{ for a full update}$$
\(P_{\text{LoRA}}\)
trainable parameters added for one weight matrix: \(B\) has \(dr\), \(A\) has \(rk\)
\(r\)
rank
\(d\)
output dimension of the matrix
\(k\)
input dimension of the matrix

In wordsCost grows with the sum of the dimensions, not their product. A 4096×4096 q_proj at \(r=16\): \(16\times8192 = 131{,}072\) parameters, against 16.8M for the full matrix, or 0.78%.

Why it mattersLlama-3-8B with \(r=16\) on all seven linear layers in all 32 blocks adds 41.9M parameters, 0.52% of the model. In bf16 that's an 84 MB adapter file you can version, ship, and hot-swap.

Why low rank works

Any matrix can be written as a sum of rank-1 pieces ordered by importance, via the singular value decomposition. Keeping the top \(r\) pieces gives the best possible rank-\(r\) approximation. If the fine-tuning update concentrates its energy in a few directions, a small \(r\) captures most of it. Hu et al. found exactly this on GPT-3: very low ranks (even \(r=1\) to 4 on \(W_q\) and \(W_v\)) were competitive with full fine-tuning on their benchmarks.

$$\htmlClass{t1}{\Delta W_r} = \sum_{i=1}^{\htmlClass{t2}{r}} \htmlClass{t3}{\sigma_i}\,\htmlClass{t4}{u_i}\,\htmlClass{t5}{v_i}^{\top}, \qquad \text{energy}(\htmlClass{t2}{r}) = \frac{\sum_{i\le \htmlClass{t2}{r}}\htmlClass{t3}{\sigma_i}^2}{\sum_{i}\htmlClass{t3}{\sigma_i}^2}$$
\(\Delta W_r\)
the closest rank-\(r\) matrix to \(\Delta W\) in Frobenius norm (no other rank-\(r\) matrix does better)
\(r\)
how many components we keep
\(\sigma_i\)
singular values, sorted largest first: how much each direction contributes
\(u_i\)
left singular vector: an output direction
\(v_i\)
right singular vector: the input direction that triggers it

In wordsThe relative error of the approximation is \(\sqrt{1-\text{energy}}\). When the singular values fall off fast, a handful of components carry nearly all of the update.

Why it mattersLoRA doesn't compute an SVD. It learns \(B\) and \(A\) by gradient descent directly. But this is the ceiling it's working under: rank \(r\) can capture at most this much of any target update.

Think first: you merge a LoRA adapter into the base weights. How much slower is inference?
Not at all. \(W_0 + \tfrac{\alpha}{r}BA\) is just another \(d\times k\) matrix, the same shape and dtype as before. The catch: merging into a quantized base requires dequantizing, adding, and re-quantizing, which adds rounding error. Merge into the 16-bit weights, then quantize the merged model (Module 09).

LoRA knobs: scaling, targets, rsLoRA, DoRA

α and r

The update is multiplied by \(\gamma = \alpha/r\). The intent is that you can change \(r\) without retuning the learning rate. Common practice: set \(\alpha = r\) (\(\gamma=1\)) or \(\alpha = 2r\) (\(\gamma=2\)), and tune the learning rate.

$$\htmlClass{t1}{\gamma_{\text{LoRA}}} = \frac{\htmlClass{t2}{\alpha}}{\htmlClass{t3}{r}}, \qquad \htmlClass{t4}{\gamma_{\text{rsLoRA}}} = \frac{\htmlClass{t2}{\alpha}}{\sqrt{\htmlClass{t3}{r}}}$$
\(\gamma_{\text{LoRA}}\)
original scaling: the update shrinks as \(1/r\) when you raise the rank
\(\alpha\)
lora_alpha, a constant you pick
\(r\)
rank
\(\gamma_{\text{rsLoRA}}\)
rank-stabilized scaling (Kalajdzievski, 2023): shrinks only as \(1/\sqrt{r}\)

In wordsWith \(\alpha/r\) at fixed \(\alpha\), going from \(r=8\) to \(r=128\) divides the update by 16, so high-rank adapters learn slowly and look no better than low-rank ones. Dividing by \(\sqrt r\) keeps the update's size stable as rank grows.

Why it mattersIf you sweep rank and see no gain above 16, try use_rslora=True before concluding rank doesn't matter.

Frameworks disagree on the knob

PEFT uses lora_alpha and computes \(\alpha/r\). mlx-lm exposes a scale that multiplies \(BA\) directly, defaulting to 20 at rank 8, which is ten times PEFT's common \(\alpha/r = 2\). That's one reason mlx-lm's default learning rate (1e-5) is an order of magnitude below the usual PEFT LoRA rate. Don't copy hyperparameters between frameworks without converting the scale.

Which modules to target

The original paper adapted only q_proj and v_proj. The QLoRA paper (Dettmers et al., 2023) found that adapting all linear layers (attention q, k, v, o and the MLP gate, up, down) was needed to match full fine-tuning, and that once you did, rank mattered much less. In Llama-3-8B the three MLP matrices hold about 80% of each block's parameters; leaving them frozen leaves most of the model's capacity out of reach. Start with target_modules="all-linear", which PEFT resolves to every linear layer except the output head. Embeddings and lm_head are normally left frozen unless you add new tokens, in which case you must train (or at least save) them via modules_to_save.

DoRA

DoRA (Liu et al., 2024) splits each weight into a magnitude and a direction and lets LoRA update only the direction, while a separate small vector learns the magnitude. Full fine-tuning tends to change the two somewhat independently; plain LoRA couples them.

$$\htmlClass{t1}{W'} = \htmlClass{t2}{m}\odot\frac{\htmlClass{t3}{W_0} + \htmlClass{t4}{BA}}{\big\lVert \htmlClass{t3}{W_0} + \htmlClass{t4}{BA} \big\rVert_{\htmlClass{t5}{c}}}$$
\(W'\)
the effective adapted weight
\(m\)
trainable magnitude vector, one scalar per column, initialized to \(\lVert W_0\rVert_c\)
\(W_0\)
frozen pretrained weight
\(BA\)
ordinary LoRA update, now only steering direction
\(c\)
norm taken column by column, so every column of the fraction is a unit vector

In wordsPoint each column where LoRA says, then rescale it to a learned length.

Why it mattersReported gains over LoRA are consistent but modest, and largest at low ranks. It costs some training speed (the norm must be recomputed each step) and still merges into a plain matrix afterwards. In PEFT it's use_dora=True; in mlx-lm --fine-tune-type dora.

QLoRA: fine-tuning on one GPU

LoRA removes gradients and optimizer state for the frozen weights, but the frozen weights still sit in memory in bf16: 16 GB for an 8B model. QLoRA (Dettmers et al., 2023) quantizes them too. Their headline: fine-tuning a 65B model on a single 48 GB GPU, with results matching 16-bit LoRA on their benchmarks. Four ingredients:

  1. 4-bit NormalFloat (NF4) for the frozen base. Sixteen levels placed at quantiles of a normal distribution, in blocks of 64 weights with one absmax scale each (Module 09).
  2. bf16 LoRA adapters on top. In each forward pass the 4-bit block is dequantized to bf16 on the fly, multiplied, and thrown away. Gradients flow through the dequantized weights to \(A\) and \(B\), but the 4-bit weights themselves never change.
  3. Double quantization: the per-block fp32 scales are themselves quantized to 8 bits, in blocks of 256. That drops the scale overhead from 0.5 to about 0.127 bits per weight.
  4. Paged optimizers: optimizer state lives in unified memory that can be paged to CPU RAM, so a long sequence that briefly spikes memory doesn't crash the run.
$$\htmlClass{t1}{M_{\text{QLoRA}}} \approx \htmlClass{t2}{N_{\text{lin}}}\cdot\frac{\htmlClass{t3}{4.127}}{8} \;+\; 2\,\htmlClass{t4}{N_{\text{emb}}} \;+\; 16\,\htmlClass{t5}{P_{\text{LoRA}}} \;+\; \htmlClass{t6}{M_{\text{act}}}$$
\(M_{\text{QLoRA}}\)
training memory in bytes
\(N_{\text{lin}}\)
parameters in the quantized linear layers (everything except embeddings and output head)
4.127
bits per weight: 4 for NF4 + \(8/64\) for the 8-bit scales + \(32/(64\cdot256)\) for the second-level scales
\(N_{\text{emb}}\)
embedding and lm_head parameters, which bitsandbytes leaves in bf16 (2 bytes)
\(P_{\text{LoRA}}\)
adapter parameters. 16 bytes each: fp32 weight, gradient, and two Adam moments
\(M_{\text{act}}\)
activations, which quantizing the weights does not shrink

In wordsLlama-3-8B: 6.98B linear params × 4.127/8 ≈ 3.6 GB, plus 1.05B embedding/head params × 2 ≈ 2.1 GB, plus 42M adapter params × 16 ≈ 0.67 GB. About 6.4 GB before activations, versus 128 GB for full fine-tuning.

Why it mattersOnce the weights are small, activations and the logits tensor (sequence × 128K vocabulary) dominate. Gradient checkpointing and a modest micro-batch then decide whether you fit, not the model size.

QLoRA trades speed for memory

Dequantizing every block on every forward and backward pass makes QLoRA steps measurably slower than bf16 LoRA. If the bf16 base fits, prefer plain LoRA. And remember the deployment side: an adapter trained against an NF4 base saw slightly different weights than the bf16 model you may serve. In practice the mismatch is small, but evaluate the exact artifact you ship.

Reading the loss curves

Fine-tuning runs are short, so you can watch them closely. Training loss almost always falls. The question is what validation loss (same distribution, never trained on) does. A typical small-data run looks like this: both fall fast in the first epoch, validation flattens, then turns up as the model starts memorizing individual examples. Training loss often drops in visible steps at epoch boundaries, which is the model recognizing examples it has seen before. Treat those steps as a warning and check validation loss at each one.

Validation loss is a proxy

Lower loss usually means better task performance, but not always. For extraction, a run can keep improving exact-match accuracy slightly after validation loss bottoms out, or get worse while loss still looks fine (more confident, more wrong). Save checkpoints along the way and pick by your task metric on the validation set, with loss as a guide.

Catastrophic forgetting, and evaluating a fine-tune

Gradient descent doesn't know which of the model's abilities you care about. Train an instruct model on 5,000 invoice extractions and every update pushes it toward "output JSON". Ask it to write a poem afterwards and you may get {"poem": …}. Or it answers in your extraction format but has lost some of its general reasoning. This is catastrophic forgetting (McCloskey and Cohen, 1989): new training overwrites what earlier training put in the same weights.

How much you lose depends on how far and how long you push. Ways to push less:

  • Use LoRA at a modest rank. The update is restricted to a low-rank subspace, so it can disturb less, which is the "forgets less" half of Biderman et al. (2024).
  • Lower the learning rate and stop early. Most of the drift happens in the steps after the task is already learned.
  • Replay: mix 5–20% general instruction data (or samples generated by the original model on varied prompts) into your training set. A rule of thumb, not a law; tune it against your regression suite.
  • Anchor to the original model. RLHF does this with a KL penalty (next section), and InstructGPT also mixed pretraining gradients into PPO ("PPO-ptx") to reduce regressions on public benchmarks.
  • Don't merge what you don't need to. A separate adapter only applies to requests routed to it; the base model is untouched for everything else.

Evaluating a fine-tune

The question isn't "is the loss low". It's "is this model better than the cheapest alternative, on the thing we ship, without breaking the rest". That takes four measurements:

  1. A held-out test set from the production distribution, deduplicated against training data, split by source, and never used for any decision until the end. Use the validation set to pick checkpoints; touch the test set once.
  2. Task metrics you can compute: JSON validity rate, per-field exact match, F1 for classification, pass@1 for code. Where outputs are free-form, an LLM judge with a written rubric and pairwise comparisons, spot-checked against human labels (Module 13).
  3. The prompted baseline: the same base model with your best prompt and a few examples, and ideally a stronger API model too. If the fine-tune doesn't clearly beat a good prompt, you've bought a training pipeline for nothing. Report the difference with a bootstrap confidence interval, not a single number.
  4. A regression suite on general capability: a few hundred items from something like IFEval (instruction following), MMLU or ARC (knowledge), GSM8K (arithmetic reasoning), plus your own canary prompts for tone and safety. Compare to the base model you started from.
MLE angle · evaluate what you serve

Run evals through the production path: the same inference server, chat template, sampling parameters, and quantization as deployment. When a fine-tune looks worse in production than in your notebook, check template drift and merged-then-quantized artifacts first; neither shows up in an offline eval that skips the serving path.

Preference tuning: RLHF and DPO

SFT needs someone to write the ideal answer. For many qualities (helpfulness, tone, choosing the right level of detail) it's far easier to look at two answers and say which is better than to write the perfect one. Preference tuning learns from those comparisons.

RLHF

The InstructGPT recipe (Ouyang et al., 2022) has three steps. Their labelers preferred outputs of the 1.3B InstructGPT model to those of the 175B GPT-3, despite over 100× fewer parameters.

$$\htmlClass{t1}{\mathcal{L}_{\text{RM}}}(\phi) = -\,\mathbb{E}_{(x,\,y_w,\,y_l)}\Big[\log \htmlClass{t2}{\sigma}\big(\htmlClass{t3}{r_\phi}(x, \htmlClass{t4}{y_w}) - \htmlClass{t3}{r_\phi}(x, \htmlClass{t5}{y_l})\big)\Big]$$
\(\mathcal{L}_{\text{RM}}\)
loss for training the reward model with parameters \(\phi\)
\(\sigma\)
sigmoid, \(\sigma(z) = 1/(1+e^{-z})\), turning a score gap into a probability
\(r_\phi\)
reward model: usually the SFT model with its LM head replaced by a scalar output
\(y_w\)
the response the labeler preferred ("winner", chosen)
\(y_l\)
the response they rejected ("loser")

In wordsThe Bradley–Terry model says \(P(y_w \succ y_l) = \sigma(r_w - r_l)\). Train the scorer so the preferred answer gets the higher score, by a margin that matches how consistently people prefer it.

Why it mattersOnly score differences are learned; the absolute level is arbitrary. That's why reward models are often normalized before RL.

$$\max_{\htmlClass{t1}{\pi_\theta}}\;\; \mathbb{E}_{x\sim\mathcal{D},\; y\sim\htmlClass{t1}{\pi_\theta}(\cdot\mid x)}\big[\htmlClass{t2}{r_\phi}(x,y)\big] \;-\; \htmlClass{t3}{\beta}\;\mathbb{D}_{\text{KL}}\big(\htmlClass{t1}{\pi_\theta}(\cdot\mid x)\,\Vert\,\htmlClass{t4}{\pi_{\text{ref}}}(\cdot\mid x)\big)$$
\(\pi_\theta\)
the policy being trained; it generates its own responses \(y\)
\(r_\phi\)
the frozen reward model's score
\(\beta\)
KL coefficient: how strongly to stay close to the reference
\(\pi_{\text{ref}}\)
frozen reference policy, normally the SFT model

In wordsGenerate answers that score well, but don't drift far from the model you started with.

Why it mattersThe reward model is an imperfect proxy trained on limited data. Without the KL term, the policy finds outputs that fool it (reward hacking): longer answers, flattery, repeated phrases the RM happens to like. The KL term also limits forgetting.

The objective is optimized with PPO (Schulman et al., 2017). For a language model, each generated token is an "action", the prompt plus tokens so far is the "state", and the reward arrives at the end of the sequence (with the KL penalty often applied per token).

$$\htmlClass{t1}{\mathcal{J}^{\text{CLIP}}}(\theta) = \mathbb{E}_t\Big[\min\big(\htmlClass{t2}{\rho_t}\,\htmlClass{t3}{\hat A_t},\;\; \text{clip}(\htmlClass{t2}{\rho_t},\,1-\htmlClass{t4}{\epsilon},\,1+\htmlClass{t4}{\epsilon})\,\htmlClass{t3}{\hat A_t}\big)\Big], \qquad \htmlClass{t2}{\rho_t} = \frac{\pi_\theta(a_t\mid s_t)}{\htmlClass{t5}{\pi_{\theta_{\text{old}}}}(a_t\mid s_t)}$$
\(\mathcal{J}^{\text{CLIP}}\)
objective to maximize (the loss is its negative)
\(\rho_t\)
probability ratio: how much more (or less) likely the current policy makes token \(a_t\) than the policy that generated it
\(\hat A_t\)
advantage: was this token better (\(\gt 0\)) or worse (\(\lt 0\)) than expected? Estimated from rewards and the value model (GAE)
\(\epsilon\)
clip range, typically 0.2: the ratio is only allowed to pull within \([0.8, 1.2]\)
\(\pi_{\theta_{\text{old}}}\)
the policy snapshot that sampled this batch

In wordsMake good tokens more likely and bad tokens less likely, but once a token's probability has moved more than about 20% from where it was when sampled, stop pushing it further on this batch.

Why it mattersThe same batch of samples is reused for several gradient steps. Clipping keeps those steps from overshooting into a policy the samples no longer describe, which is the main source of RL instability.

DPO: preference tuning without RL

Rafailov et al. (2023) noticed that the RLHF objective has a closed-form optimum: \(\pi^*(y\mid x) \propto \pi_{\text{ref}}(y\mid x)\,\exp\!\big(r(x,y)/\beta\big)\). Rearranged, any policy implicitly defines a reward, \(\hat r(x,y) = \beta\log\frac{\pi_\theta(y\mid x)}{\pi_{\text{ref}}(y\mid x)}\) (up to a term that depends only on \(x\) and cancels in comparisons). Substitute that into the Bradley–Terry loss, and you can train the policy directly on preference pairs. No reward model, no sampling, no PPO. The paper's title says it: your language model is secretly a reward model.

$$\htmlClass{t1}{\mathcal{L}_{\text{DPO}}} = -\,\mathbb{E}_{(x,y_w,y_l)}\Big[\log\sigma\Big(\htmlClass{t2}{\beta}\Big(\log\frac{\htmlClass{t3}{\pi_\theta}(\htmlClass{t5}{y_w}\mid x)}{\htmlClass{t4}{\pi_{\text{ref}}}(\htmlClass{t5}{y_w}\mid x)} - \log\frac{\htmlClass{t3}{\pi_\theta}(\htmlClass{t6}{y_l}\mid x)}{\htmlClass{t4}{\pi_{\text{ref}}}(\htmlClass{t6}{y_l}\mid x)}\Big)\Big)\Big]$$
\(\mathcal{L}_{\text{DPO}}\)
a binary classification loss: "is the chosen response the chosen one?"
\(\beta\)
the same KL strength as in RLHF. Higher β = stay closer to the reference; typical 0.1
\(\pi_\theta\)
the policy being trained. \(\log\pi_\theta(y\mid x)\) is the sum of token log-probs of the response
\(\pi_{\text{ref}}\)
frozen reference (the SFT model). Its log-probs can be precomputed once
\(y_w\)
chosen response
\(y_l\)
rejected response

In wordsEach fraction asks "how much more likely is this response under my model than under the reference?" Make that boost bigger for the chosen answer than for the rejected one. The gap, times β, goes through the same sigmoid as the reward model loss.

Why it mattersDPO is as cheap and stable as SFT: two forward passes per pair through the policy, two through the reference, no generation. That's why it became the default first preference method for open models.

$$\nabla_\theta\mathcal{L}_{\text{DPO}} = -\beta\;\mathbb{E}\Big[\,\htmlClass{t1}{\sigma\big(\hat r(x,y_l) - \hat r(x,y_w)\big)}\,\big(\htmlClass{t2}{\nabla_\theta\log\pi_\theta(y_w\mid x)} - \htmlClass{t3}{\nabla_\theta\log\pi_\theta(y_l\mid x)}\big)\Big]$$
\(\sigma(\hat r_l - \hat r_w)\)
per-pair weight \(=\sigma(-\beta\cdot\text{margin})\): near 1 when the model currently ranks the pair wrong, near 0 when it's already confidently right
\(\nabla\log\pi_\theta(y_w)\)
direction that makes the chosen response more likely
\(\nabla\log\pi_\theta(y_l)\)
direction that makes the rejected response more likely (subtracted, so pushed down)

In wordsPush chosen up and rejected down, weighted by how wrong the model currently is about this pair. Pairs it already gets right fade out of the gradient.

DPO failure modes

The loss only cares about the gap. It can fall while the log-probability of both responses drops, which pushes probability mass onto text that appeared in neither. Watch logps/chosen as well as the margin. DPO also learns whatever separates chosen from rejected: if chosen answers are systematically longer, you get a model that rambles. And it works best on pairs sampled from a model close to the one you're training ("on-policy" data); pairs from an unrelated model give a weaker signal. Variants like IPO, KTO, ORPO, and SimPO each target one of these issues.

GRPO and RL with verifiable rewards

For math and code you don't need a learned reward model at all: you can check the answer. A unit test passes or fails; the final number matches or doesn't. Lambert et al. (2024, Tülu 3) named this RL with verifiable rewards (RLVR). It's the engine behind reasoning models: DeepSeek-R1 (DeepSeek-AI, 2025) was trained with rule-based accuracy and format rewards; in its R1-Zero variant, long chains of thought with self-checking emerged from RL alone, with no SFT demonstrations at all.

The algorithm most open work uses is GRPO, Group Relative Policy Optimization, introduced in DeepSeekMath (Shao et al., 2024). It keeps PPO's clipped ratio but drops the value model. Instead of a learned critic predicting how good a state is, it samples a group of \(G\) answers to the same prompt and uses the group itself as the baseline.

$$\htmlClass{t1}{\hat A_i} = \frac{\htmlClass{t2}{r_i} - \operatorname{mean}\big(\htmlClass{t3}{\{r_1,\dots,r_{\htmlClass{t4}{G}}\}}\big)}{\operatorname{std}\big(\htmlClass{t3}{\{r_1,\dots,r_{\htmlClass{t4}{G}}\}}\big)}$$
\(\hat A_i\)
advantage for every token of the \(i\)-th sampled answer
\(r_i\)
its reward, e.g. 1 if the final answer is correct, 0 if not (plus optional format reward)
\(\{r_1..r_G\}\)
rewards of all answers sampled for the same prompt
\(G\)
group size, typically 8–64

In wordsAn answer is "good" if it beat its siblings. If 2 of 8 attempts are correct, those two get a large positive advantage and the six wrong ones a small negative one.

Why it mattersIf all 8 are right, or all 8 wrong, every advantage is zero and the prompt teaches nothing. RLVR needs prompts at the edge of the model's ability, so curating difficulty is as important as the algorithm.

GRPO is still moving. Follow-ups such as Dr. GRPO (Liu et al., 2025) and DAPO (Yu et al., 2025) argue that dividing by the standard deviation and averaging the loss per sequence introduce biases (toward easy or hard prompts, and toward longer wrong answers), and change the normalization. Recent TRL versions default to a DAPO-style loss and to \(\beta = 0\), with no KL term at all. Read the defaults of whatever version you install.

When RL is worth it

RL fine-tuning is expensive: each step generates \(G\) full answers per prompt, so it's dominated by inference, and most setups pair the trainer with a fast generation engine such as vLLM. It pays off when you have a reliable verifier and the base model already succeeds sometimes (pass@8 well above zero). If the model never gets an answer right, there's no signal; do SFT first.

Distillation and model merging

Knowledge distillation

Distillation trains a small student to imitate a large teacher. The classic version (Hinton et al., 2015) matches the teacher's whole next-token distribution, not just its top choice. The teacher's "second guesses" carry information: that "car" is closer to "truck" than to "banana".

$$\htmlClass{t1}{\mathcal{L}_{\text{KD}}} = \htmlClass{t2}{\tau}^2\;\mathbb{D}_{\text{KL}}\Big(\operatorname{softmax}\big(\htmlClass{t3}{z^{(t)}}/\htmlClass{t2}{\tau}\big)\;\Big\Vert\;\operatorname{softmax}\big(\htmlClass{t4}{z^{(s)}}/\htmlClass{t2}{\tau}\big)\Big)$$
\(\mathcal{L}_{\text{KD}}\)
distillation loss, per token position
\(\tau\)
temperature (often 1–2). Higher \(\tau\) flattens both distributions so small probabilities matter. The \(\tau^2\) keeps gradient size comparable across temperatures
\(z^{(t)}\)
teacher logits
\(z^{(s)}\)
student logits

In wordsAt every position, make the student's softened probability distribution look like the teacher's. Usually combined with ordinary cross-entropy on the real tokens.

Why it mattersIt needs the teacher's logits, so teacher and student must share a tokenizer and you must be able to run the teacher. Google's smaller Gemma 2 models were trained with this kind of logit distillation from a larger model.

Sequence-level distillation (Kim and Rush, 2016) is simpler: have the teacher generate answers, then SFT the student on them. No logits, no shared tokenizer, works through an API. This is what "synthetic data from a stronger model" is, and it's the form behind most open "distilled" models, including DeepSeek-R1's Qwen and Llama distills.

Model merging

You can sometimes combine fine-tunes without any training, by doing arithmetic on their weights. This works when the models share a base, so their weights stay in the same "basin".

$$\htmlClass{t1}{\theta_{\text{merged}}} = \htmlClass{t2}{\theta_0} + \sum_{j} \htmlClass{t3}{\lambda_j}\,\htmlClass{t4}{\tau_j}, \qquad \htmlClass{t4}{\tau_j} = \theta_j - \htmlClass{t2}{\theta_0}$$
\(\theta_{\text{merged}}\)
weights of the merged model
\(\theta_0\)
shared base model weights
\(\lambda_j\)
mixing weight for fine-tune \(j\) (often 0.3–1)
\(\tau_j\)
"task vector": what fine-tune \(j\) changed (for LoRA, exactly \(\tfrac{\alpha}{r}BA\))

In wordsMeasure what each fine-tune added on top of the base, then add scaled versions of those changes back onto the base (Ilharco et al., 2023).

  • Linear / model soups (Wortsman et al., 2022): average the weights of several fine-tunes of the same base. Often beats each one alone on robustness.
  • SLERP: interpolate two models along the arc between their weight vectors instead of the straight line, which preserves weight norms. Two models at a time only.
  • TIES (Yadav et al., 2023): trim each task vector to its largest entries, elect a sign per parameter by majority, and average only the entries that agree. This reduces interference when merging several models.

Tools like mergekit implement all three. Merging is cheap to try and hard to predict; evaluate every merge like a new model.

Hands-on: recipes and a lab

Five recipes, from a GPU box to a MacBook to a serving endpoint. The APIs below match current TRL (which requires transformers>=4.56), PEFT, mlx-lm, and vLLM. These libraries move fast; when something errors, check inspect.signature(SFTConfig) before searching the web.

(a) LoRA SFT with TRL and PEFT


# pip install -U trl peft transformers datasets accelerate
import torch
from datasets import load_dataset
from peft import LoraConfig
from transformers import AutoModelForCausalLM, AutoTokenizer
from trl import SFTConfig, SFTTrainer

model_id = "Qwen/Qwen3-1.7B"          # or "meta-llama/Llama-3.2-3B-Instruct"
ds = load_dataset("json", data_files={"train": "data/train.jsonl",
                                      "validation": "data/valid.jsonl"})  # {"messages": [...]} per line

tok = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(model_id, dtype=torch.bfloat16)

peft_config = LoraConfig(
    r=16,
    lora_alpha=32,                    # alpha / r = 2
    lora_dropout=0.05,
    target_modules="all-linear",      # q,k,v,o,gate,up,down
    task_type="CAUSAL_LM",
)

args = SFTConfig(
    output_dir="out/extract-lora",
    num_train_epochs=2,
    per_device_train_batch_size=4,
    gradient_accumulation_steps=4,    # effective batch 16
    learning_rate=2e-4,
    lr_scheduler_type="cosine",
    warmup_ratio=0.03,
    max_length=2048,                  # was max_seq_length in older TRL
    assistant_only_loss=True,         # m_t = 1 only on assistant tokens
    packing=False,
    bf16=True,
    gradient_checkpointing=True,
    eval_strategy="steps", eval_steps=50,
    save_strategy="steps", save_steps=50,
    load_best_model_at_end=True, metric_for_best_model="eval_loss",
    logging_steps=10,
    report_to="none",
)

trainer = SFTTrainer(
    model=model,
    args=args,
    train_dataset=ds["train"],
    eval_dataset=ds["validation"],
    processing_class=tok,
    peft_config=peft_config,
)
trainer.model.print_trainable_parameters()
trainer.train()
trainer.save_model("out/extract-lora/final")   # saves only the adapter (~tens of MB)

Lab: beat the prompted baseline

Fine-tune a 1–3B instruct model (Qwen3-1.7B or Llama-3.2-3B-Instruct) for structured extraction: invoices, job postings, support tickets, anything with 4–8 fields you can grade programmatically.

  1. Build 1,000+ train, 200 validation, and 300 test examples. Generate synthetic inputs with a stronger model if you like, but write and review the gold JSON carefully. Dedup, and split by source.
  2. Measure the prompted baseline on the test set: the same base model, your best system prompt, three few-shot examples, temperature 0.
  3. Train a LoRA adapter with recipe (a) or (b). Keep the validation curves. Pick the checkpoint by validation field accuracy.
  4. Evaluate both through vLLM (recipe e) with the scorer below, and run a 200-item general eval slice (IFEval or MMLU) on base vs fine-tuned.

import json, random

FIELDS = ["vendor", "date", "total", "currency"]

def norm(field, v):
    if v is None:
        return None
    if field == "total":
        try:
            return round(float(str(v).replace(",", "")), 2)
        except ValueError:
            return None
    return str(v).strip().lower()

def score(pred_text, gold):
    try:
        pred = json.loads(pred_text)
    except json.JSONDecodeError:
        return 0, [0] * len(FIELDS)
    return 1, [int(norm(f, pred.get(f)) == norm(f, gold[f])) for f in FIELDS]

def bootstrap_diff(a, b, n=2000, seed=0):
    """95% CI of mean(a) - mean(b) for paired per-example scores."""
    rnd, k, diffs = random.Random(seed), len(a), []
    for _ in range(n):
        idx = [rnd.randrange(k) for _ in range(k)]
        diffs.append(sum(a[i] - b[i] for i in idx) / k)
    diffs.sort()
    return diffs[int(0.025 * n)], diffs[int(0.975 * n)]

You add a rank-16 LoRA adapter to a single 4096×4096 projection matrix. How many trainable parameters does that add?

  1. 65,536
  2. 131,072
  3. 262,144
  4. 16,777,216
\(B\) is 4096×16 and \(A\) is 16×4096, so \(r(d+k) = 16\times(4096+4096) = 131{,}072\). That's 0.78% of the 16.8M entries a full update would train. 65,536 counts only one of the two matrices.

Why does LoRA initialize \(B\) to zero (and \(A\) randomly)?

  1. Zero matrices take less memory to store
  2. It makes \(A\) orthogonal, which speeds up convergence
  3. It forces the adapter to stay low-rank during training
  4. So \(BA = 0\) at step zero and training starts exactly from the pretrained model, while gradients can still flow
With \(B=0\) the adapted layer computes \(W_0x\) exactly, so there's no random damage at the start. \(A\) is random because if both were zero, \(\partial L/\partial B \propto (Ax)^\top = 0\) and \(\partial L/\partial A \propto B^\top(\cdot) = 0\): nothing would ever learn. Rank is limited by the shapes, not by the init.

Your extraction dataset has ~2,000-token documents in the user turn and ~60-token JSON answers. You forget to mask the prompt. What's the most likely effect?

  1. About 97% of the loss goes into modeling the input documents, so the extraction signal is diluted and the model drifts toward generating document-like text
  2. Training crashes because the labels don't line up
  3. No effect, because the prompt tokens are identical across examples
  4. The model gets better at following the system prompt and nothing else changes
Without the mask every token is scored: 2,000 of 2,060 tokens are document text. The model spends its update budget learning to write invoices, and learns the actual task slower. Documents differ per example, so their loss is far from constant. Masking (\(m_t=0\) on the prompt) fixes this.

In DPO, what does increasing β from 0.1 to 0.5 do?

  1. It's the learning rate, so training goes five times faster
  2. It raises the sampling temperature for generating responses
  3. It strengthens the implicit KL anchor: the loss saturates after smaller moves away from the reference, so the policy stays closer to it
  4. It increases how many preference pairs are used per step
β is the KL coefficient from the RLHF objective that DPO solves in closed form. In the loss it multiplies the log-ratio margin, so with larger β a small margin already gives a low loss and a small gradient weight \(\sigma(-\beta\cdot\text{margin})\). The policy reaches "confident" with less drift from \(\pi_{\text{ref}}\). The widget in the DPO section shows the sigmoid sharpening.

A support assistant must answer from a 3,000-page policy manual that's revised every week, and cite the section it used. What's the best first approach?

  1. Full fine-tune on the manual every week
  2. RAG over the manual, optionally with a small fine-tune to teach the answer-and-cite format
  3. DPO on pairs of correct and incorrect policy answers
  4. LoRA with a very high rank so it can memorize the whole manual
The gap is knowledge, and the knowledge changes weekly and must be citable. Fine-tuning is poor at injecting many facts, can't cite sources, and would need retraining every week. Retrieval keeps facts editable. A small SFT on (retrieved context → cited answer) pairs is the common add-on.

In GRPO with \(G = 8\), the model gets all 8 sampled answers to a prompt right (reward 1 each). What does this prompt contribute to the update?

  1. A large positive update, because every answer was correct
  2. A negative update, to encourage exploration
  3. The same update as if 4 of 8 were correct
  4. Essentially nothing: every reward equals the group mean, so every advantage is zero
\(\hat A_i = (r_i - \text{mean})/\text{std}\), and each \(r_i - \text{mean} = 0\). Implementations add a small ε to the std to avoid dividing by zero, but the numerator is still zero. Prompts that are always solved or never solved give no signal, which is why RLVR datasets are filtered for difficulty.
