Module 13 · Shipping it

Evaluation & production: proving it works

LLM features rarely fail loudly. A prompt edit quietly costs a few points on one customer segment, the eval set has 80 examples so nobody can tell, and p99 latency doubled after a traffic shift nobody was watching. This module is the measurement toolkit: what to evaluate, how many examples you need before a difference is real, and the arithmetic that sizes and prices a deployment.

~3 hoursprereqs: 03, 08, 11, 12hands-on: numpy, vLLM, llama.cpp

By the end you can

  1. Pick the right kind of evaluation for a decision, and say what a public benchmark score does and doesn't tell you.
  2. Compute pass@k without bias, and put a confidence interval on any accuracy number.
  3. Decide whether model B really beats model A on the same eval set, using a paired bootstrap, and estimate how many examples that takes.
  4. Design an LLM judge, measure its agreement with humans, and correct for its known biases.
  5. Size a GPU deployment from request rate, token counts, and a latency target, and compare its cost against an API.
  6. Instrument a production system: traces, latency percentiles, drift checks, A/B guardrails, and caches that don't serve wrong answers.

Evaluation is the job

Training a model, writing a prompt, adding retrieval, swapping a quantization: each of these is a guess that the system got better. An evaluation is the measurement that confirms or kills the guess. Teams that ship good LLM products usually aren't the ones with the cleverest prompts. They can tell within an hour whether a change helped, and on which kinds of input.

Definition · eval

A fixed set of inputs, a way to run the system on them, and a scoring rule, versioned together so that two runs a month apart are comparable. Change any of the three and you have a different eval.

There isn't one evaluation. There are several families, and each answers a different question at a different point in a project's life:

Offline

Fixed inputs, automatic scores

Cheap, repeatable, fast enough to run on every commit. Blind to anything your dataset doesn't contain: new user intents, a long-tail language, the way real users phrase things.

Online

Real traffic, real outcomes

Measures what you actually care about (task completion, retention, escalations) but is slow, noisy, and exposes users to the change. You only get to run a few of these per quarter, so offline evals decide which changes get one.

Think first: your RAG assistant's thumbs-up rate rose from 61% to 64% the week you shipped a new reranker. Did the reranker help?
You can't tell yet. The traffic mix may have changed that week (a holiday, a marketing push, a new customer), thumbs are given by a small and self-selected minority of users, and 3 points could be noise at that volume. The reranker's effect should first show up offline: retrieval recall and answer accuracy on a fixed golden set, old vs new. Then an A/B test with randomized traffic isolates it online. A before/after comparison over calendar time confounds the change with everything else that changed that week.

Perplexity and public benchmarks

Perplexity: the pretraining metric

Module 03 introduced perplexity as the exponentiated cross-entropy on held-out text. It's the metric pretraining optimizes, and it stays useful wherever you need a quick, sensitive, label-free signal.

$$\htmlClass{t1}{\text{PPL}} = \exp\!\left(-\frac{1}{\htmlClass{t2}{N}} \sum_{i=1}^{\htmlClass{t2}{N}} \log \htmlClass{t3}{p_\theta}(\htmlClass{t4}{x_i} \mid \htmlClass{t5}{x_{\lt i}})\right)$$
PPL
perplexity: the effective number of equally likely tokens the model is choosing between
\(N\)
number of tokens in the evaluation text
\(p_\theta\)
the model's predicted probability
\(x_i\)
the actual \(i\)-th token
\(x_{\lt i}\)
all tokens before it (the context)

In wordsAverage the surprise (negative log-probability) of each true next token, then undo the log. A perplexity of 8 means the model is, on average, as unsure as if it were picking uniformly among 8 tokens.

Why it mattersIt's how you catch a broken quantization, a bad data mix, or a domain mismatch in minutes, before running any task eval (Module 09 uses it this way).

Perplexity has hard limits as a product metric:

  • It depends on the tokenizer. A model with a bigger vocabulary predicts fewer, longer tokens, so its per-token perplexity isn't comparable to another model's. Normalize by bytes instead (bits per byte, \(-\sum \log_2 p / \text{bytes}\)) when comparing across tokenizers.
  • It measures imitation of text, not usefulness. Instruction tuning and RLHF usually make perplexity on raw web text worse while making the model far more helpful. The distribution being matched has changed.
  • Behaviour is invisible to it. Refusing correctly, following a JSON schema, calling the right tool, not hallucinating a citation: none of these show up in the average log-probability of reference text.

Public benchmarks and what they measure

A benchmark is somebody else's eval, published so models can be compared. Read every score as "accuracy on this question set, with this prompt format and answer parser." Change the few-shot examples or the regex that extracts the final answer and scores move by several points.

Contamination

Benchmarks are published on the web, and models are trained on the web. If test questions (or their answers, or close paraphrases) were in the pretraining data, the score partly measures memory. Ways to detect or avoid it:

  • N-gram overlap between the test set and the training corpus. The GPT-3 paper used 13-gram matches. You can only run this check if you have the training data.
  • Canary strings. BIG-bench embeds a unique GUID in its files. If a model can complete the string, the files were in its training data.
  • Fresh look-alikes. Write new items with the same distribution (GSM1k for GSM8K). A drop on the fresh set is evidence of memorization.
  • Time splits. Only score items created after the training cutoff (LiveCodeBench, SWE-bench-style issue mining).

Saturation

When the best models all score within a couple of points of each other near the ceiling, the benchmark stops ranking them. The remaining errors are increasingly mislabelled items, ambiguous questions, and parser failures. Differences smaller than the label-error rate are noise. The response is a harder successor (MMLU → MMLU-Pro → GPQA) and, more usefully for you, your own eval.

What a leaderboard can't tell you

Public benchmarks shortlist candidates. They don't measure your prompts, your documents, your tools, your users' phrasing, or your latency budget. A model two points higher on MMLU-Pro can easily be worse at extracting fields from your invoices. Treat leaderboard ranks within a few points as ties, then run your task eval on the shortlist.

pass@k: grading with many samples

For code generation the scorer is unambiguous: run the unit tests. But models sample, so one attempt per problem is a noisy measurement. And for some products (an agent that can run tests and retry, a tool that shows five suggestions) the question is whether any of \(k\) attempts works. That's pass@k: the probability that at least one of \(k\) samples passes.

The obvious way to measure it is to draw exactly \(k\) samples per problem and check whether any passed. That has high variance. Chen et al. (2021), in the HumanEval paper, draw \(n \geq k\) samples per problem, count the \(c\) correct ones, and compute the probability that a random size-\(k\) subset of those \(n\) contains at least one correct sample:

$$\htmlClass{t1}{\text{pass@}k} = \mathbb{E}_{\text{problems}}\left[\,1 - \frac{\binom{\htmlClass{t2}{n} - \htmlClass{t3}{c}}{\htmlClass{t4}{k}}}{\binom{\htmlClass{t2}{n}}{\htmlClass{t4}{k}}}\,\right] \qquad \text{per problem} = 1 - \prod_{i=\htmlClass{t2}{n}-\htmlClass{t3}{c}+1}^{\htmlClass{t2}{n}} \left(1 - \frac{\htmlClass{t4}{k}}{i}\right)$$
pass@\(k\)
probability that at least one of \(k\) samples is correct, averaged over problems
\(n\)
samples actually generated per problem (the paper used 200 for HumanEval); must satisfy \(n \geq k\)
\(c\)
how many of those \(n\) samples passed the tests
\(k\)
attempts the product gets (1, 10, 100…)

In words\(\binom{n-c}{k}/\binom{n}{k}\) is the chance that a random handful of \(k\) samples drawn from your \(n\) contains only failures. One minus that is the chance it contains a success. If fewer than \(k\) samples failed, every handful has a success, and the estimate is exactly 1.

Why it mattersThe binomial form overflows for \(n = 200\), so use the product form, which never builds big numbers. The tempting plug-in \(1-(1-c/n)^k\) is biased low: it's a concave function of the estimated pass rate, so by Jensen's inequality its average falls below the truth. The subset form is exactly unbiased.

Intuition · pass@1 vs pass@10

pass@1 rewards being reliably right. pass@10 rewards being sometimes right on many problems. A model that solves 30% of attempts on every problem has pass@1 = 0.30 and pass@10 ≈ \(1 - 0.7^{10} \approx 0.97\). A model that solves 40% of problems every time and the rest never has pass@1 = 0.40 and pass@10 = 0.40. Which one you want depends on whether your product has a verifier (tests, a type checker, a human picking) that can find the good sample.

Pitfall · pass@k at temperature 0

pass@k with \(k \gt 1\) only means something if the samples differ. At temperature 0 all \(n\) samples are (nearly) identical, so pass@10 collapses to pass@1. Chen et al. tuned temperature per \(k\): low for pass@1, higher (around 0.8) for pass@100. Report the sampling settings with the number.

LLM-as-judge

Most product outputs have no unit test: summaries, support replies, explanations, agent transcripts. Human grading is the gold standard and costs minutes per item. An LLM judge is a prompt that asks a strong model to grade an output against a rubric. Zheng et al. (2023), introducing MT-Bench and Chatbot Arena, found GPT-4's pairwise judgments agreed with human experts over 80% of the time (excluding ties), about as often as the humans agreed with each other. That result made judges the default for open-ended evals. It also came with a catalogue of biases.

Designing the rubric

  1. One criterion per call. "Is every claim supported by the provided context? yes/no" is gradeable. "Rate overall quality 1–10" isn't: the judge invents its own weighting, and that weighting drifts.
  2. Prefer binary or short ordinal scales with anchors. Describe what a 1, 2, and 3 look like, ideally with an example of each. Wide numeric scales cluster around a few values and are hard to calibrate.
  3. Ask for a short justification before the score, in structured output (JSON with reasoning then verdict) so it's parseable and auditable.
  4. Give the judge what a human grader would need: the reference answer for factual questions, the retrieved passages for groundedness, the tool results for agent steps. A judge grading math without a reference mostly checks whether the solution sounds right.
Pointwise

Score one output against a rubric

Gives absolute numbers you can track over time ("groundedness 0.93") and set thresholds on. More sensitive to the judge's own calibration, and a judge-model upgrade can shift every score at once.

Pairwise

Which of two outputs is better?

Easier for judges and humans alike, and more sensitive to small improvements. Only gives relative results, needs a baseline output for each item, and is exposed to position bias.

Known biases and their mitigations

BiasWhat happensMitigation
PositionThe judge favours whichever answer appears first (or second) regardless of contentJudge both orders; count a win only if both agree, otherwise a tie

Calibrating the judge against humans

Before trusting a judge, have humans label a sample, run the judge on the same items, and measure agreement. Size the sample with the same arithmetic as any accuracy: at 85% agreement, 100 items pin it down to about ±7 points, and 300 items to about ±4. Raw percent agreement flatters: if 90% of outputs pass, a judge that always says "pass" agrees 90% of the time. Cohen's kappa subtracts the agreement you'd get by chance.

$$\htmlClass{t1}{\kappa} = \frac{\htmlClass{t2}{p_o} - \htmlClass{t3}{p_e}}{1 - \htmlClass{t3}{p_e}}, \qquad \htmlClass{t3}{p_e} = \sum_{\htmlClass{t6}{\ell}} \htmlClass{t4}{p^{\text{H}}_{\ell}}\,\htmlClass{t5}{p^{\text{J}}_{\ell}}$$
\(\kappa\)
chance-corrected agreement: 1 = perfect, 0 = no better than chance, negative = worse than chance
\(p_o\)
observed agreement: fraction of items where judge and human gave the same label
\(p_e\)
agreement expected if both labelled independently at their own base rates
\(p^{\text{H}}_{\ell}\)
fraction of items the human gave label \(\ell\)
\(p^{\text{J}}_{\ell}\)
fraction of items the judge gave label \(\ell\)
\(\ell\)
each possible label (pass/fail, or 1/2/3)

In wordsHow much of the agreement left over after chance did the judge achieve? Worked example: the human passes 70% of items and the judge passes 75%, and they agree on 85%. Chance agreement is \(0.7 \times 0.75 + 0.3 \times 0.25 = 0.60\), so \(\kappa = (0.85 - 0.60)/0.40 = 0.63\).

Why it mattersCommon rules of thumb (Landis & Koch, 1977) call 0.61–0.80 "substantial" agreement. Those bands are conventions, not laws. Compare the judge's kappa to the human–human kappa on the same items. That's the ceiling, and some tasks have a low one.

MLE angle · read the confusion matrix, not just kappa

A judge that's too lenient (passes items humans fail) and one that's too strict can have the same kappa. Decide which error is worse for your use. For a safety filter, missed failures matter most. For an eval that gates releases, false alarms waste days. Check agreement per slice too: judges are often worse on the languages and domains your eval set has fewest examples of.

Ranking from pairwise votes

Pairwise judgments (from humans or judges) give you a pile of "A beat B" results across many model pairs. To turn that pile into a ranking, assume each model has a latent strength and the probability of winning depends only on the difference. That's the Bradley–Terry model (1952). Elo ratings from chess are the same model on a base-10, 400-point scale.

$$\htmlClass{t1}{E_A} = \frac{1}{1 + 10^{(\htmlClass{t3}{R_B} - \htmlClass{t2}{R_A})/400}}, \qquad \htmlClass{t2}{R_A} \leftarrow \htmlClass{t2}{R_A} + \htmlClass{t4}{K}\,(\htmlClass{t5}{S_A} - \htmlClass{t1}{E_A})$$
\(E_A\)
predicted probability that A beats B (expected score)
\(R_A\)
rating of model A
\(R_B\)
rating of model B
\(K\)
step size of the online Elo update (e.g. 4–32)
\(S_A\)
actual outcome for A: 1 win, 0.5 tie, 0 loss

In wordsOnly the rating gap matters. 100 points ≈ 64% win probability, 200 ≈ 76%, 400 ≈ 91%. After each game, nudge the rating by how surprised you were. Bradley–Terry writes the same model as \(P(A \succ B) = \sigma(\beta_A - \beta_B)\), with \(\beta = R \ln 10 / 400\), which turns fitting the ratings into a logistic regression.

Why it mattersOnline Elo depends on the order the games were played. Chatbot Arena switched to fitting Bradley–Terry by maximum likelihood over all votes at once, with bootstrap confidence intervals. Do the same with your own pairwise evals.

Think first: model X has a rating 30 points above model Y. Your users will see one or the other. How much should you care?
A 30-point gap predicts X wins \(1/(1+10^{-30/400}) \approx 54\%\) of head-to-head votes, barely better than a coin flip, and the interval around a 30-point gap is often as wide as the gap. If Y is cheaper or faster, it probably wins on the dimensions that a preference vote doesn't measure. Ratings close together are ties until your own eval separates them.

Statistics you actually need

An eval score is an estimate from a sample of items. Run the same system on a different 200 questions drawn the same way and you'd get a different number. The question is always how different.

Standard error of an accuracy

$$\htmlClass{t1}{\text{SE}} = \sqrt{\frac{\htmlClass{t2}{\hat p}\,(1 - \htmlClass{t2}{\hat p})}{\htmlClass{t3}{n}}}, \qquad \text{95\% CI} \approx \htmlClass{t2}{\hat p} \pm \htmlClass{t4}{1.96}\,\htmlClass{t1}{\text{SE}}$$
SE
standard error: the standard deviation of the score across hypothetical re-draws of the eval set
\(\hat p\)
observed accuracy (fraction of items correct)
\(n\)
number of independent items
1.96
the normal quantile that leaves 2.5% in each tail

In wordsEach item is a coin flip with bias \(p\). The spread of the average shrinks with \(\sqrt{n}\): four times the items for half the uncertainty. At \(n = 100\) and \(\hat p = 0.8\), SE = 0.04 and the 95% CI is 80% ± 7.8 points, i.e. [72%, 88%].

Why it mattersA 100-item eval can't distinguish 80% from 85%. Most "prompt v7 beats v6" claims made on small eval sets are noise.

When the simple formula lies

The normal approximation breaks near 0% or 100% and for small \(n\) (it can give intervals outside [0, 1]). Use the Wilson interval there, shown dashed in the widget. It also assumes independent items. Five questions about the same document, or ten turns of the same conversation, are correlated, and the true SE is larger. Use a cluster bootstrap that resamples whole documents (Miller, 2024, "Adding Error Bars to Evals").

Is model B really better? Pair the comparison

You ran A and B on the same 500 items. A scored 82.0%, B scored 85.0%. Comparing two independent CIs is the wrong test, because the items are shared. Hard items are hard for both models, and easy items are easy for both. Look at the per-item difference instead:

$$\htmlClass{t1}{\bar d} = \frac{1}{\htmlClass{t2}{n}}\sum_i (\htmlClass{t3}{b_i} - \htmlClass{t4}{a_i}), \qquad \text{SE}(\htmlClass{t1}{\bar d}) = \sqrt{\frac{\sigma_A^2 + \sigma_B^2 - 2\,\htmlClass{t5}{\sigma_{AB}}}{\htmlClass{t2}{n}}}$$
\(\bar d\)
mean per-item difference = accuracy(B) − accuracy(A)
\(n\)
number of shared items
\(b_i\)
model B's score on item \(i\) (0/1 or a graded score)
\(a_i\)
model A's score on the same item
\(\sigma_{AB}\)
covariance of the two models' per-item scores; positive when they find the same items hard

In wordsShared difficulty cancels in the difference. The more the models agree item by item, the larger the covariance and the tighter the comparison. For 0/1 scores, only the items where they disagree carry information about which is better.

Why it mattersThe same eval set can detect a 3-point improvement when you pair the comparison and miss it entirely when you compare two separate confidence intervals.

The bootstrap gets the same answer without formulas, and works for any metric (F1, a judge's mean score, median latency). Resample the items with replacement, keeping each item's A and B scores together, recompute the difference, repeat a few thousand times, and read the 2.5th and 97.5th percentiles. Deep cut · McNemar's test

For 0/1 scores there's an exact test. Let \(n_{10}\) be the items only A got right and \(n_{01}\) the items only B got right. Under "no difference", each disagreement is a fair coin, so test \(n_{01}\) against Binomial\((n_{01} + n_{10}, 0.5)\). 30 disagreements split 21–9 gives a two-sided p ≈ 0.04. A 3-point gain on 500 items is only 15 net items, so whether it's significant depends entirely on how many disagreements there were.

How many examples do you need?

$$\htmlClass{t1}{n} \approx \frac{(\htmlClass{t2}{z_{1-\alpha/2}} + \htmlClass{t3}{z_{1-\beta}})^2\;\htmlClass{t4}{\sigma_d^2}}{\htmlClass{t5}{\delta}^2}$$
\(n\)
items needed (per model; they're shared in a paired eval)
\(z_{1-\alpha/2}\)
1.96 for a 5% false-positive rate (two-sided)
\(z_{1-\beta}\)
0.84 for 80% power: an 80% chance of detecting a real difference of size \(\delta\)
\(\sigma_d^2\)
variance of the per-item difference. Unpaired: \(p_A(1-p_A) + p_B(1-p_B)\). Paired 0/1: (fraction of items where models disagree) − \(\delta^2\)
\(\delta\)
the smallest difference worth detecting (e.g. 0.03 = 3 points)

In words\((1.96 + 0.84)^2 \approx 7.85\). To detect a 3-point gain at 80% accuracy, unpaired: \(7.85 \times 0.32 / 0.0009 \approx 2{,}800\) items. Paired, if the models disagree on 10% of items: \(7.85 \times 0.099 / 0.0009 \approx 860\).

Why it mattersHalving the effect you want to see quadruples the eval set. Decide the smallest improvement that would change a decision, and size the set for that, before arguing over results.

Pitfall · slicing until something is significant

Break results into 20 slices and test each at 95% confidence, and on average one slice will show a "significant" difference by chance even when nothing changed. Decide the slices you'll test in advance. Correct for many comparisons (Bonferroni: use \(\alpha / m\) for \(m\) tests, conservative but simple), and treat surprising slice results as hypotheses to confirm on fresh data.

Building a task eval set

The eval set usually outlives the prompt and the model it was first built for, so version it like code. Building it is mostly unglamorous data work.

Golden set

Real inputs, agreed answers

Sample from production logs (or realistic drafts before launch), add every bug report as a test case, and write labelling guidelines precise enough that two annotators agree. Measure their agreement; if humans can't agree on an item, fix or drop it.

Slices

Score by segment, not just overall

Tag each item with language, customer tier, input length bucket, intent, tools involved. An overall +1 can hide a −8 on Japanese or on long documents. Size the slices you care about using the sample-size formula above.

Versioning

Freeze, hash, and log

Store the set as immutable files with a content hash. Record the hash, prompt version, model ID and sampling parameters, and scorer version with every run. Keep a dev split to iterate on and a held-out split you look at rarely.

Choosing the scorer

ScorerUse whenWatch out for
Exact match / parsed fieldClassification, extraction, short factual answersNormalization (case, whitespace, number formats) changes the score; test the parser itself
Execution / unit testsCode, SQL, tool calls with checkable effectsWeak tests pass wrong code; sandbox everything
Schema / constraint checksJSON output, length limits, required sectionsValid format says nothing about correct content
LLM judge with rubricOpen-ended text, groundedness, tone, agent trajectoriesCalibrate against humans first; pin the judge version
Human reviewCalibrating judges, high-stakes launches, new task typesSlow and expensive; annotators drift too, so re-measure agreement

Overlap metrics like BLEU and ROUGE reward wording that matches the reference and correlate poorly with quality on open-ended generation. Avoid them except as smoke tests.

MLE angle · close the loop

Every production failure you find (a bad trace, an escalation, a user complaint) should become an eval item within a day, tagged with the slice it came from. After a few months the eval set is a record of everything that has gone wrong, and the regression suite blocks those failures from returning.

Serving metrics and capacity

Module 08 defined the latency metrics: TTFT (queue + prefill until the first token), TPOT (average gap between output tokens after the first), ITL (each individual gap; watch its p99), end-to-end latency \(\approx \text{TTFT} + (n_{\text{out}} - 1)\cdot\text{TPOT}\), and throughput (tokens per second across all requests). Revisit 08 · Latency metrics if those are hazy. In production, one more number ties them together.

$$\htmlClass{t1}{\text{goodput}} = \frac{\big|\{\, r : \htmlClass{t2}{\text{TTFT}_r} \le \htmlClass{t3}{T_{\text{TTFT}}} \,\land\, \htmlClass{t4}{\text{TPOT}_r} \le \htmlClass{t5}{T_{\text{TPOT}}} \,\}\big|}{\htmlClass{t6}{\Delta t}}$$
goodput
requests per second that met every latency target (term popularized by DistServe, Zhong et al., 2024)
\(\text{TTFT}_r\)
time to first token of request \(r\)
\(T_{\text{TTFT}}\)
TTFT target, e.g. 1 s
\(\text{TPOT}_r\)
time per output token of request \(r\)
\(T_{\text{TPOT}}\)
TPOT target, e.g. 40 ms (~25 tokens/s, faster than people read)
\(\Delta t\)
length of the measurement window

In wordsThroughput counts every token. Goodput counts only requests that were fast enough to be useful. Push concurrency too high and throughput keeps climbing while goodput falls off a cliff.

Why it mattersThis is the number to maximize when tuning batch size and scheduler settings. vllm bench serve --goodput ttft:1000 tpot:40 reports it directly.

Definition · Little's law

In any stable system, the average number of requests in flight equals arrival rate × average time in the system: \(L = \lambda W\). At 10 requests/s with a 12-second average response, 120 requests are in flight at once. That's your batch size (summed across replicas), and each one holds KV cache memory (Module 08).

Capacity planning

A first-order model is enough to size a deployment before you benchmark it. Treat each GPU (or each tensor-parallel replica) as a pool of GPU-seconds that prefill and decode both draw from. Prefill is compute-bound and fast per token. Decode is bandwidth-bound, and its aggregate throughput grows with batch size, but bigger batches make each step slower. The latency target caps how big the batch can get.

$$\htmlClass{t1}{G} = \left\lceil \frac{\htmlClass{t2}{\lambda}\left(\dfrac{\htmlClass{t3}{n_{\text{in}}}}{\htmlClass{t4}{R_{\text{pre}}}} + \dfrac{\htmlClass{t5}{n_{\text{out}}}}{\htmlClass{t6}{R_{\text{dec}}}}\right)}{\htmlClass{t7}{u}} \right\rceil, \qquad \htmlClass{t6}{R_{\text{dec}}} = R_{\max}\left(1 - \frac{t_{\min}}{T_{\text{TPOT}}}\right)$$
\(G\)
number of GPUs (or replicas) to provision
\(\lambda\)
peak request rate, requests per second
\(n_{\text{in}}\)
average prompt tokens per request (after prefix-cache hits)
\(R_{\text{pre}}\)
prefill throughput per GPU, tokens/s
\(n_{\text{out}}\)
average output tokens per request
\(R_{\text{dec}}\)
decode throughput per GPU at the batch size that still meets the TPOT target. Modelled from the saturated throughput \(R_{\max}\) and the single-stream step time \(t_{\min}\)
\(u\)
target utilization (0.6–0.8): headroom for bursts, uneven load balancing, and a replica failing

In wordsEach request costs some GPU-seconds of prefill plus some of decode. Multiply by the request rate to get GPUs kept busy, divide by how busy you're willing to run them, and round up. The decode term assumes a step takes \(t_{\min} + B/R_{\max}\) seconds at batch \(B\), so a looser TPOT target allows bigger batches and more tokens per GPU.

Why it mattersIt tells you which knob matters. Long prompts with short answers (RAG, classification) are prefill-heavy, so prefix caching and prompt trimming are the big wins. Long answers (chat, reasoning models) are decode-heavy, so quantization, speculative decoding, and the TPOT target matter most.

Pitfall · planning for the average

Traffic has daily peaks, often several times the daily average, and output lengths are long-tailed: reasoning models can produce 10× the median on some requests. Size for the peak hour, use p90 lengths rather than means for KV-cache memory, and check that the batch the formula implies actually fits in memory (KV bytes per token × context × batch, Module 08). This model ignores memory, so treat its answer as a lower bound.

Cost and caching

API pricing

Hosted APIs bill per token, with separate prices for input and output, and output usually costs several times more than input. Most providers now discount input tokens that hit a prompt cache (the KV-cache reuse from Module 08, sold back to you).

$$\htmlClass{t1}{C_{\text{req}}} = (\htmlClass{t2}{n_{\text{in}}} - \htmlClass{t3}{h})\,\htmlClass{t4}{p_{\text{in}}} + \htmlClass{t3}{h}\,\htmlClass{t5}{\rho}\,\htmlClass{t4}{p_{\text{in}}} + \htmlClass{t6}{n_{\text{out}}}\,\htmlClass{t7}{p_{\text{out}}}$$
\(C_{\text{req}}\)
dollars per request
\(n_{\text{in}}\)
input tokens (system prompt + tools + history + user message)
\(h\)
input tokens served from the provider's prompt cache
\(p_{\text{in}}\)
price per input token (list prices are per 1M; divide by \(10^6\))
\(\rho\)
cached-token price multiplier. Varies by provider and model, roughly 0.1–0.5. Some providers also charge extra to write the cache
\(n_{\text{out}}\)
output tokens, including hidden reasoning tokens for reasoning models
\(p_{\text{out}}\)
price per output token

In wordsPay full price for new input, a fraction for cached input, and the (higher) output price for everything generated. Worked example at illustrative prices of $3 / $15 per 1M tokens and \(\rho = 0.1\): an agent turn with 20K input tokens, 18K of them cached, and 500 output tokens costs $0.006 + $0.0054 + $0.0075 ≈ $0.019. Without the cache it costs $0.0675, 3.6× more.

Why it mattersAgents re-send the whole conversation every turn, so input usually dominates cost. Cache hits require a byte-identical prefix: put stable content (system prompt, tool definitions) first and anything that changes (timestamps, user IDs) last.

Self-hosting

A GPU costs the same per hour whether it's busy or idle. The cost per token therefore depends entirely on how much traffic you keep it busy with.

$$\htmlClass{t1}{c_{\text{1M}}} = \frac{\htmlClass{t2}{G}\,\htmlClass{t3}{P_{\text{GPU}}}}{3600\,\htmlClass{t4}{\Theta}} \times 10^6, \qquad \htmlClass{t5}{T^{*}} = \frac{\htmlClass{t6}{F}}{\htmlClass{t7}{\bar p_{\text{API}}}}$$
\(c_{\text{1M}}\)
dollars per million tokens served
\(G\)
GPUs running (you pay for all of them, all hours)
\(P_{\text{GPU}}\)
price per GPU-hour (cloud rental or amortized purchase + power)
\(\Theta\)
tokens per second actually served across the fleet, averaged over the day including quiet hours
\(T^{*}\)
monthly token volume above which self-hosting is cheaper
\(F\)
fixed monthly cost of the minimum fleet plus the engineering time to run it
\(\bar p_{\text{API}}\)
API price per token, blended across your input/output/cached mix

In wordsSelf-hosting is a fixed cost; the API is a variable cost. Below the break-even volume you're paying for idle GPUs. Above it, each extra token is nearly free until you need another GPU.

Why it mattersThe comparison is only fair at equal quality. An open 8B model you can host is not interchangeable with a frontier API model. Run both through your task eval first; the cheaper option often loses on the slices that matter.

Caching layers

Three different caches get called "caching" in LLM systems. They save different amounts and fail in different ways.

Pitfall · semantic caches answer the wrong question

"How do I cancel my order?" and "How do I un-cancel my order?" can land at cosine similarity above 0.9 with many embedding models, because the embedding mostly encodes topic and small words like "un" barely move it. A semantic cache will happily return the cancellation instructions. Other failures: answers that depend on the user (account balance, permissions) leaking across users, answers that depend on time (prices, stock), and answers that were wrong the first time getting replayed forever. Treat the cache as a classifier. Label a few hundred query pairs as same answer or different answer, pick the similarity threshold from measured precision, scope cache keys by user and permission, and set a TTL.

Observability

Once deployed, the system needs the same treatment as any production service, plus some LLM-specific signals. The core unit is a trace: one user request, with every model call, retrieval, and tool call inside it as nested spans. OpenTelemetry has (still-evolving) semantic conventions for generative-AI spans, and most LLM tracing tools follow them.

Record per callWhy you'll need it
Prompt template version, model ID, sampling paramsAttribute a regression to the change that caused it
Full prompt and completion (redacted, with a retention limit)Debug individual failures; mine new eval items
Input, cached, output, and reasoning token countsCost dashboards per feature, per customer, per prompt version
TTFT, TPOT, end-to-end latency, queue timePercentile dashboards and SLO alerts
Tool calls, retrieved doc IDs, errors, retriesFind which step of an agent or RAG pipeline failed
Guardrail decisions, judge scores on sampled traffic, user feedbackQuality monitoring between offline eval runs

Latency percentiles

Alert on percentiles, never on averages. And the tail compounds. If a task makes \(m\) independent calls, the chance that none of them exceeds the p99 is \(0.99^m\): 90% for 10 calls, 61% for 50. Agents feel slower than their per-call latency suggests.

Drift

The model didn't change, but the inputs did: a new customer with a different document format, a product launch that changes what users ask about, a different language mix. Watch input statistics (length, language, intent classifier output, embedding cluster shares) and output statistics (refusal rate, length, tool-call rate, sampled judge scores) against a reference window. The population stability index is a simple per-feature drift score:

$$\htmlClass{t1}{\text{PSI}} = \sum_{\htmlClass{t2}{j}} (\htmlClass{t3}{a_j} - \htmlClass{t4}{e_j}) \,\ln\frac{\htmlClass{t3}{a_j}}{\htmlClass{t4}{e_j}}$$
PSI
drift score for one feature; 0 = identical distributions
\(j\)
bins of the feature (length buckets, intent classes, topic clusters)
\(a_j\)
fraction of current traffic in bin \(j\)
\(e_j\)
fraction of the reference window (e.g. the period your eval set was sampled from) in bin \(j\)

In wordsA symmetric KL divergence (Module 03) between this week's histogram and the reference histogram. Industry folklore reads below 0.1 as stable, 0.1–0.25 as worth a look, and above 0.25 as a real shift. Those thresholds are conventions, not statistics.

Why it mattersDrift tells you when your eval set has stopped representing traffic. When a slice grows, sample new eval items from it.

Capturing feedback

Explicit feedback (thumbs, ratings) is sparse and skewed toward unhappy or very happy users. Implicit signals are denser: the user regenerated, edited the draft heavily, copied the answer, abandoned the session, escalated to a human, or re-asked the same question. Log them against the trace ID so a bad outcome can be traced back to the exact prompt, retrieval, and model version. Then sample the bad ones into the eval set.

Online evaluation, A/B tests, and guardrails

Offline evals decide what's worth shipping. Online tests decide whether it actually helped. The ladder, from least to most exposure:

  1. Shadow traffic. Run the new version on copies of real requests and log its outputs without showing them to anyone. Catches crashes, latency, cost, and format problems on the real input distribution.
  2. Canary. Serve 1–5% of traffic and watch guardrail metrics closely, with automatic rollback.
  3. A/B test. Randomize users (not requests, or one person sees both versions in one session) between control and treatment, at a split sized to reach the needed sample in a reasonable time.
Primary metric

The one thing you're trying to move

Task completion rate, resolution without escalation, accepted-suggestion rate. Choose it before launch and compute the sample size it needs.

Guardrail metrics

Things that must not get worse

p95 latency, error rate, cost per request, safety-flag rate, complaint rate. A win on the primary metric that breaks a guardrail doesn't ship.

Minimum detectable effect (MDE) is the sample-size formula solved the other way: given the traffic you can get, what's the smallest true effect you'd reliably detect? \(\text{MDE} \approx 2.8\,\sqrt{2\sigma^2 / n}\) per arm at 5% significance and 80% power. For a 30% completion rate (\(\sigma^2 = 0.21\)) and 5,000 users per arm, that's about 2.6 points. If the change you're testing plausibly moves the metric by 1 point, this test can't see it. Run it longer, pick a more sensitive metric, or skip the test and rely on offline evidence.

Pitfall · peeking

Checking the p-value every day and stopping the first time it dips below 0.05 inflates the false-positive rate far above 5%. Fix the duration in advance, or use a sequential testing method designed for continuous monitoring. Also watch for novelty effects (users try the new thing because it's new) and sample-ratio mismatch: if a 50/50 split delivers 50.8/49.2 on large traffic, the assignment is broken and the result is untrustworthy.

Guardrails and safety checks in production

Guardrails are checks that run on every request, outside the model, and can block, rewrite, or escalate:

WhereCheckTypical implementation
InputPolicy violations, prompt injection, PII in promptsSmall classifiers (e.g. Llama Guard, Inan et al., 2023), regexes for structured PII, injection heuristics on retrieved content
OutputSchema validity, unsupported claims, toxic content, leaked secrets or PIIJSON schema validation with retry, groundedness judge on sampled or high-risk traffic, pattern scanners
ActionsAgent tool calls with side effectsAllow-lists, argument validation, human confirmation for irreversible actions (Module 12)
Before releaseJailbreaks and known attacksRed-team regression suite run like any other eval; grows with every incident

A guardrail is a classifier, so evaluate it as one: precision and recall on a labelled set. Each check also adds latency and blocks some legitimate requests. A filter with 2% false positives on a million daily requests refuses 20,000 good ones. Put the guardrail's block rate on the dashboard next to the thing it protects.

1. pass@k, the numerically stable way


import numpy as np
from math import comb

def pass_at_k(n: int, c: int, k: int) -> float:
    """Unbiased pass@k (Chen et al., 2021): n samples, c correct, k attempts."""
    if n - c < k:                       # every size-k subset contains a correct sample
        return 1.0
    # 1 - C(n-c, k) / C(n, k)  ==  1 - prod_{i=n-c+1}^{n} (1 - k / i)
    return 1.0 - float(np.prod(1.0 - k / np.arange(n - c + 1, n + 1)))

# per-problem estimates, then average over problems
per_problem = [(200, 12), (200, 0), (200, 200), (200, 1), (200, 57)]   # (n, c)
for k in (1, 10, 100):
    print(f"pass@{k:<3d} = {np.mean([pass_at_k(n, c, k) for n, c in per_problem]):.3f}")

# sanity checks: matches the binomial form, and pass@1 is just c/n
assert abs(pass_at_k(20, 3, 5) - (1 - comb(17, 5) / comb(20, 5))) < 1e-12
assert abs(pass_at_k(200, 12, 1) - 12 / 200) < 1e-12

2. Paired bootstrap CI for two models on the same items


import numpy as np

def paired_bootstrap(a, b, n_boot=10_000, seed=0, chunk=1_000):
    """a, b: per-item scores for models A and B on the SAME items (0/1 or graded)."""
    a, b = np.asarray(a, float), np.asarray(b, float)
    assert a.shape == b.shape
    d = b - a                                    # keep each item's pair together
    rng = np.random.default_rng(seed)
    boots = []
    for _ in range(n_boot // chunk):             # chunked so n_boot x n never sits in memory
        idx = rng.integers(0, len(d), size=(chunk, len(d)))
        boots.append(d[idx].mean(axis=1))
    boots = np.concatenate(boots)
    lo, hi = np.percentile(boots, [2.5, 97.5])
    return {"diff": d.mean(), "ci95": (lo, hi), "p_b_not_better": (boots <= 0).mean(),
            "se_paired": d.std(ddof=1) / np.sqrt(len(d)),
            "se_unpaired": np.sqrt(a.var(ddof=1) / len(a) + b.var(ddof=1) / len(b))}

# simulate two correlated models on 500 items
rng = np.random.default_rng(1)
difficulty = rng.random(500)
a = (difficulty < 0.82).astype(int)
b = ((difficulty < 0.85) | (rng.random(500) < 0.02)).astype(int)
print(paired_bootstrap(a, b))

3. A tiny eval harness: dataset → model → scorer → report


import hashlib, json, time
import numpy as np
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")   # vLLM or any OpenAI-compatible server
PROMPTS = {"v3": "Classify the support ticket into one of: billing, shipping, returns, other. Reply with the label only."}

def load_dataset(path):
    raw = open(path, "rb").read()
    rows = [json.loads(line) for line in raw.decode().splitlines() if line.strip()]
    return rows, hashlib.sha256(raw).hexdigest()[:12]          # content hash = dataset version

def run_model(row, model, prompt_version):
    t0 = time.perf_counter()
    resp = client.chat.completions.create(
        model=model, temperature=0, max_tokens=16,
        messages=[{"role": "system", "content": PROMPTS[prompt_version]},
                  {"role": "user", "content": row["input"]}])
    return {"output": resp.choices[0].message.content or "",
            "latency_s": time.perf_counter() - t0,
            "tokens_in": resp.usage.prompt_tokens, "tokens_out": resp.usage.completion_tokens}

def score(row, out):                                            # swap in unit tests or a judge per task
    return float(out["output"].strip().lower() == row["expected"].lower())

def report(results):
    slices = {}
    for r in results:
        slices.setdefault("ALL", []).append(r["score"])
        slices.setdefault(r["slice"], []).append(r["score"])
    for name, xs in sorted(slices.items()):
        p, n = float(np.mean(xs)), len(xs)
        print(f"{name:18s} n={n:5d}  acc={p:.3f} ± {1.96 * np.sqrt(p * (1 - p) / n):.3f}")

if __name__ == "__main__":
    rows, ds_hash = load_dataset("tickets_golden_v2.jsonl")    # {"id","input","expected","slice"} per line
    meta = {"dataset": ds_hash, "model": "Qwen/Qwen2.5-7B-Instruct", "prompt": "v3", "scorer": "exact-v1"}
    results = []
    with open(f"run-{ds_hash}-{meta['prompt']}-{int(time.time())}.jsonl", "w") as f:
        for row in rows:
            out = run_model(row, meta["model"], meta["prompt"])
            rec = {**meta, "id": row["id"], "slice": row["slice"], **out, "score": score(row, out)}
            results.append(rec)
            f.write(json.dumps(rec) + "\n")                    # one row per (item, run): diffable later
    report(results)

Lab exit criteria

You're done when you have: (1) a golden set of at least 300 items from a real task, with slice tags and a content hash; (2) a harness run for two prompt or model variants, with per-slice accuracy ± 95% CI and a paired bootstrap CI on the difference; (3) a judge calibrated against 100 of your own labels, with its kappa and confusion matrix; (4) a vllm bench serve sweep showing throughput and goodput against request rate, and a GPU count from the capacity formula that you can check against the sweep's knee.

A model scores 80% on a 100-item eval. What is the approximate 95% confidence interval?

  1. 80% ± 0.8 points
  2. 80% ± 7.8 points
  3. 80% ± 4 points
  4. 80% ± 16 points
SE = √(0.8 × 0.2 / 100) = 0.04. The 95% CI is ± 1.96 × 0.04 ≈ ± 0.078, i.e. [72%, 88%]. ± 4 points is one standard error, not a 95% interval. A prompt change that moves this eval from 80 to 84 is well inside the noise.

Model P has pass@1 = 0.40 and pass@10 = 0.45. Model Q has pass@1 = 0.30 and pass@10 = 0.75. Your product runs the unit tests on 10 samples and shows the first passing one. Which is better, and why?

  1. P, because pass@1 is the standard metric
  2. P, because its samples are more consistent
  3. They're equivalent: the averages are similar
  4. Q, because with a verifier choosing among 10 samples, what matters is how many problems have some correct sample
P is reliably right on ~40% of problems and almost never right on the rest. Q is right sometimes on many more problems. With a verifier, Q solves 75% of tasks vs P's 45%. Without a verifier (one shot, shown directly to a user), P would win.

Your pairwise LLM judge prefers the answer shown first 62% of the time, even on pairs where both answers are identical. What's the standard mitigation?

  1. Judge every pair in both orders and count a win only when both orders agree; otherwise record a tie
  2. Always put the baseline model's answer first
  3. Switch to a 1–10 scale
  4. Lower the judge's temperature to 0
Position bias is systematic, so temperature doesn't remove it, and fixing the order just bakes the bias in favour of whichever slot you chose. Swapping and requiring consistency cancels it, and the rate of inconsistent verdicts tells you how often the judge is effectively guessing.

Peak load is 20 requests/s, each with 2,000 input tokens and 250 output tokens. Per GPU: prefill 20,000 tok/s, decode 4,000 tok/s at your TPOT target. You plan for 70% utilization. How many GPUs?

  1. 2
  2. 4
  3. 5
  4. 8
GPU-seconds per request = 2000/20000 + 250/4000 = 0.100 + 0.0625 = 0.1625. Busy GPUs = 20 × 0.1625 = 3.25. Divided by 0.7 = 4.64, rounded up to 5. Four would run at 81%, leaving little headroom for bursts or a replica failure. Note that prefill is 62% of the GPU time here: prefix caching would be the first optimization to try.

A request has TTFT = 300 ms and TPOT = 30 ms and produces 401 output tokens. Roughly how long until the last token arrives?

  1. 0.33 s
  2. 9.0 s
  3. 12.0 s
  4. 12.3 s
E2E ≈ TTFT + (n_out − 1) × TPOT = 0.3 + 400 × 0.030 = 12.3 s. For long outputs TPOT dominates, and shaving 100 ms off TTFT barely changes total latency. For a chat UI that streams, though, TTFT is what the user notices first.

Models A and B are run on the same 500 items: 82% vs 85%. Two separate 95% CIs overlap. Why can a paired bootstrap still show B is better?

  1. The bootstrap always produces narrower intervals
  2. The models get mostly the same items right and wrong, so shared difficulty cancels in the per-item difference and only the disagreements add variance
  3. The paired test uses a lower confidence level
  4. Overlapping intervals never indicate anything
Var(B − A) = Var(A) + Var(B) − 2 Cov(A, B). Positive covariance (both stumble on the same hard items) shrinks the variance of the difference. The unpaired comparison ignores that covariance and is far too conservative. Overlapping CIs aren't a valid test of a difference even for independent samples.

You want to add a semantic cache (embedding similarity ≥ 0.92 returns the stored answer) in front of a support bot. What should you do before enabling it?

  1. Nothing: cosine 0.92 means the questions are equivalent
  2. Raise the threshold to 0.99 so it can't make mistakes
  3. Label a few hundred query pairs as same or different answer, measure false-hit precision at candidate thresholds, and scope keys by user/permissions with a TTL
  4. Only cache answers that users gave a thumbs-up
Similarity measures topic closeness, not answer equivalence ("cancel" vs "un-cancel"). A very high threshold reduces false hits but can still produce them, and it kills the hit rate. The only way to know is to measure the cache as a classifier. Thumbs-up answers can still be personalized or go stale.
