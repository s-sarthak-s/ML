Inside an inference engine

Once you can picture that loop, every engine flag becomes a lever you can reason about instead of a superstition.

Anatomy of an engine

"Inference engine" sounds like one thing. It's really five or six cooperating parts, usually split across several operating-system processes. Module 08's techniques (continuous batching, paged KV, prefix caching) each live in a specific box below, and most engine bugs and tuning problems come down to one box waiting for another.

Following one request

  1. API server. An OpenAI-compatible endpoint (/v1/chat/completions) validates the request, applies the model's chat template (Module 10), and tokenizes. Images or audio get preprocessed here too.
  2. Request queue. The token ids cross a process boundary (vLLM uses ZeroMQ sockets) into the engine core's waiting queue.
  3. Scheduler. Every step it decides which requests run and how many of their tokens to compute, under a per-step token budget and a cap on concurrent sequences.
  4. KV cache manager. It owns the block allocator. The scheduler asks it for slots before admitting work; it answers yes, no, or "yes, and the first 1,200 tokens are already cached".
  5. Model runner. On each GPU it turns the scheduler's plan into tensors, launches the forward pass (replaying a captured CUDA graph when the batch shape allows), and hands logits to the sampler.
  6. Update and stream. Sampled ids go back to the engine core, which appends them, checks stop conditions, and frees finished requests' blocks. The new ids flow to the API process, which detokenizes incrementally and pushes server-sent events to the client.

Why several processes? Because the Python parts compete for one interpreter lock. Tokenizing a 100K-token prompt, JSON-encoding streamed chunks for 500 clients, and running the scheduler all need CPU time. If they share a thread, the GPU waits while Python serializes JSON. Splitting them lets the engine core keep feeding the GPU while the API process deals with HTTP.

$$\htmlClass{t1}{t_{\text{step}}} = \htmlClass{t2}{t_{\text{sched}}} + \htmlClass{t3}{t_{\text{prep}}} + \htmlClass{t4}{t_{\text{GPU}}} + \htmlClass{t5}{t_{\text{post}}}, \qquad \htmlClass{t6}{U_{\text{GPU}}} = \frac{\htmlClass{t4}{t_{\text{GPU}}}}{\htmlClass{t1}{t_{\text{step}}}}$$
\(t_{\text{step}}\)
wall-clock time of one engine iteration: what a streaming user sees as inter-token latency
\(t_{\text{sched}}\)
CPU time to pick requests, allocate blocks, look up prefix hashes
\(t_{\text{prep}}\)
building input tensors (ids, positions, block tables) and copying them to the GPU
\(t_{\text{GPU}}\)
the forward pass and sampling kernels themselves
\(t_{\text{post}}\)
appending tokens, stop checks, sending outputs to the API process
\(U_{\text{GPU}}\)
fraction of each step the GPU is actually busy

In wordsA step is GPU work sandwiched between CPU bookkeeping. If the bookkeeping runs in series with the GPU, the GPU idles for that long every step.

Why it mattersFor a small model the GPU part can be only a few milliseconds. Illustratively, 3 ms of GPU work plus 2 ms of serial Python gives \(U_{\text{GPU}} = 60\%\). That's why engines capture decode steps as CUDA graphs (one launch instead of hundreds, Module 18), and why SGLang's overlap scheduler and vLLM's async scheduling prepare step \(k{+}1\) on the CPU while the GPU runs step \(k\).

The step loop in detail

Everything an engine does happens inside one loop. Read this simplified version slowly; the rest of the module zooms into its lines.


while True:
    waiting.extend(inbox.drain())                     # newly tokenized requests from the API process

    # 1. SCHEDULE under a token budget (--max-num-batched-tokens) and a seq cap (--max-num-seqs)
    budget, plan = max_num_batched_tokens, []
    for req in list(running):                         # running requests first: decodes and unfinished prefills
        n = min(req.num_tokens_to_compute, budget)    # 1 for a decode, a chunk for a long prefill
        while not kv.allocate_slots(req, n):          # needs a new block and none are free
            victim = running.pop()                    # lowest priority / latest arrival
            kv.free(victim); waiting.appendleft(victim)   # preempt: recompute it later
            if victim is req: break
        if req in running:
            plan.append((req, n)); budget -= n
    while waiting and budget > 0 and len(running) < max_num_seqs:
        req = waiting[0]
        cached = kv.get_computed_blocks(req)          # prefix-cache hit: skip these tokens
        n = min(req.prompt_len - cached, budget)
        if not kv.allocate_slots(req, n): break       # no memory: stop admitting
        running.append(waiting.popleft()); plan.append((req, n)); budget -= n

    # 2. PREPARE one flattened ("ragged") batch: no padding between requests
    ids, positions, slot_mapping, block_tables, query_start_loc, logits_idx = prepare(plan)

    # 3. FORWARD (CUDA graph replay if the batch is decode-only and a graph of that size exists)
    hidden = model(ids, positions, kv_cache, attn_metadata)
    logits = lm_head(hidden[logits_idx])              # only each request's LAST scheduled token

    # 4. SAMPLE: penalties, grammar bitmask, temperature/top-p, speculative verification
    tokens = sampler(logits, sampling_params, grammar_bitmask)

    # 5. UPDATE: append, check stops, free finished blocks (they stay hashed for prefix reuse)
    for (req, n), tok in zip(plan, tokens):
        if req.still_prefilling: continue             # mid-prompt chunk: its sampled token is thrown away
        req.append(tok)
        if req.is_finished(): running.remove(req); kv.free(req)

    # 6. STREAM new token ids to the API process for detokenization
    outbox.send(new_tokens)
$$\htmlClass{t1}{N} = \sum_{i} \htmlClass{t2}{q_i}, \qquad \htmlClass{t3}{\text{slot}}(i, \htmlClass{t4}{p}) = \htmlClass{t5}{\text{BT}_i}\!\left[\left\lfloor \frac{\htmlClass{t4}{p}}{\htmlClass{t6}{B_s}} \right\rfloor\right] \cdot \htmlClass{t6}{B_s} + \left(\htmlClass{t4}{p} \bmod \htmlClass{t6}{B_s}\right)$$
\(N\)
tokens in this step's flattened batch; must be at most the token budget
\(q_i\)
tokens scheduled for request \(i\): 1 for a decode, up to thousands for a prefill chunk
slot
physical index in the KV cache where this token's K and V are written
\(p\)
the token's position within its own sequence
\(\text{BT}_i\)
request \(i\)'s block table: logical block number → physical block id
\(B_s\)
block size in tokens (16 by default in vLLM on CUDA)

In wordsFind which of the request's blocks the position falls in, look up where that block physically lives, and add the offset inside the block.

Why it mattersRequest A at position 812 with block size 16 is in logical block 50 at offset 12. If \(\text{BT}_A[50] = 7\), its slot is \(7 \cdot 16 + 12 = 124\). The attention kernel never sees "sequences" as contiguous tensors, only slots and tables, which is what lets requests of any length share one batch.

Think first: the step processed 8 tokens. Why compute the LM head on only 3 of them?
The LM head is a \(d \times V\) matmul: 4096 × 128,256 for Llama 3, about 1 GFLOP per token, and its output is a 128,256-wide row of logits. Only the last scheduled token of each request produces a token anyone will use. For a 2,000-token prefill chunk, computing every row would produce 1,999 × 128,256 extra logits, about 1 GB in fp32, only to throw them away. Engines gather the hidden states at logits_idx first, then apply the head. (Requests that ask for prompt log-probabilities are the exception.)

The flattened layout is the second idea from the Orca paper (Yu et al., 2022), called selective batching. The matmuls in QKV projections, the MLP, and the LM head don't care which request a row belongs to, so they run on all \(N\) rows together. Only attention needs to know request boundaries, and varlen attention kernels (FlashAttention's varlen API, FlashInfer) take query_start_loc and the block tables to handle that.

Continuous batching, mechanically

Module 08 showed the picture: static batching holds every slot until the longest request in its batch ends, while continuous (iteration-level) batching refills a slot the moment it frees. Here's the arithmetic behind the picture, then a simulator with real arrivals.

$$\htmlClass{t1}{U_{\text{static}}} = \frac{\sum_{i=1}^{\htmlClass{t3}{B}} \htmlClass{t2}{L_i}}{\htmlClass{t3}{B} \cdot \max_i \htmlClass{t2}{L_i}}, \qquad \mathbb{E}\!\left[\max_i \htmlClass{t2}{L_i}\right] = \htmlClass{t4}{\mu} \cdot \htmlClass{t5}{H_B} \quad \text{(exponential lengths)}$$
\(U_{\text{static}}\)
fraction of slot-steps that produce a useful token
\(L_i\)
output length of request \(i\) in the batch
\(B\)
batch size (slots)
\(\mu\)
mean output length
\(H_B\)
harmonic number \(1 + \tfrac12 + \dots + \tfrac1B\); \(H_8 \approx 2.72\)

In wordsEvery slot is held for as long as the longest request runs. Useful work is the sum of lengths; paid-for work is the batch size times the maximum.

Why it mattersWith 8 slots and exponentially distributed output lengths, the longest is expected to be 2.72 times the mean, so utilization is about \(1/2.72 \approx 37\%\). The bigger the batch and the heavier the tail, the worse it gets. Continuous batching keeps utilization near 100% whenever requests are queued.

What the scheduler is really choosing each iteration is the running set. Its rules, in vLLM's V1 scheduler and most others: running requests are served first (in arrival or priority order), each gets its next token or prefill chunk if the budget and KV memory allow, and waiting requests are admitted only from what's left. A request is never admitted unless the KV manager can give it blocks for the tokens scheduled now. Blocks for future tokens are allocated as the sequence grows, which is exactly why preemption exists.

Pitfall · "more slots" isn't free

Raising --max-num-seqs admits more concurrent requests, but every one of them keeps growing its KV cache. Admit too many and the engine runs out of blocks mid-generation and starts preempting, which is far worse for latency than queueing those requests would have been. The cap and the KV pool have to be sized together.

Token budgets and chunked prefill

Continuous batching admits a new request by running its prefill in some step. A 16K-token prompt makes that step take hundreds of milliseconds, and every user streaming in the same batch sees their next token stall for that long. This prefill-decode interference is the main source of inter-token latency (ITL) spikes in a busy server.

Chunked prefill with stall-free scheduling (Sarathi-Serve, Agrawal et al., 2024) fixes it with a per-step token budget. Each step first schedules one token for every running decode, then fills the rest of the budget with a slice of a waiting prompt. Long prompts take several steps, and no step is much longer than any other. The idea works because decode steps are memory-bound (roofline): the GPU reads all the weights anyway, so a few hundred extra prefill tokens ride along almost free.

$$\htmlClass{t1}{t_{\text{step}}} \approx \htmlClass{t2}{a} + \htmlClass{t3}{b} \cdot \htmlClass{t4}{N_{\text{tok}}} + \htmlClass{t5}{c} \cdot \htmlClass{t6}{C_{\text{KV}}}$$
\(t_{\text{step}}\)
duration of one forward pass
\(a\)
fixed cost: reading all weights once plus launch overhead (≈ 6 ms for an 8B bf16 model on an H100-class GPU)
\(b\)
marginal compute per token, about \(2N_{\text{params}}\) FLOPs ÷ achieved FLOP/s (≈ 0.033 ms)
\(N_{\text{tok}}\)
tokens in the step: decodes plus prefill-chunk tokens
\(c\)
cost per cached token read by decode attention (128 KiB ÷ ~3 TB/s ≈ 0.044 µs for Llama-3-8B)
\(C_{\text{KV}}\)
total context tokens the decodes attend over this step

In wordsA step costs a fixed amount just to stream the weights, plus a bit per token computed, plus a bit per cached token read.

Why it mattersThe true curve is flat and then rises (the roofline knee). A linear fit is a decent first-order planning tool, and it's what the widgets here use. The constants are illustrative; fit your own by timing steps at a few batch sizes. Prefill chunks also pay attention compute that grows with how far into the prompt they are, which the widget includes.

$$\htmlClass{t1}{\text{TTFT}} \approx \htmlClass{t2}{t_{\text{queue}}} + \left\lceil \frac{\htmlClass{t3}{P}}{\htmlClass{t4}{\beta} - \htmlClass{t5}{D}} \right\rceil \cdot \htmlClass{t6}{t_{\text{step}}}(\htmlClass{t4}{\beta}), \qquad \htmlClass{t7}{\text{ITL}_{\max}} \approx \htmlClass{t6}{t_{\text{step}}}(\htmlClass{t4}{\beta})$$
TTFT
time to first token of the long request
\(t_{\text{queue}}\)
time before the scheduler admits it at all
\(P\)
prompt tokens still to prefill (after any prefix-cache hit)
\(\beta\)
token budget per step (--max-num-batched-tokens)
\(D\)
running decodes, each taking one token of the budget
\(t_{\text{step}}(\beta)\)
duration of a full-budget step, from the linear model
\(\text{ITL}_{\max}\)
worst gap a streaming user sees while the prefill runs

In wordsThe prompt is eaten in chunks of whatever budget the decodes leave over. Every step is roughly full-budget, so the budget sets both how fast the prompt finishes and how long each streaming user waits per token.

Why it matters\(\beta = 2048\), \(D = 48\), \(P = 16{,}000\): 8 chunks of 2,000 tokens, each step ≈ 6 + 0.033 × 2048 ≈ 74 ms, so TTFT ≈ 0.6 s and nobody's ITL exceeds about 74 ms. Unchunked, the same prompt runs in one ≈ 0.6 s step (more with attention), and all 48 users freeze for it. A bigger budget finishes prompts sooner but makes every step slower: that's the dial.

Think first: why not make the budget tiny, say 256 tokens, and get perfect ITL?
Three costs. TTFT for long prompts grows because each step contributes only \(\beta - D\) prompt tokens, and with 128 running decodes and a 256 budget, that's 128 tokens per step. Each chunk also re-reads the full weights (the fixed cost \(a\)) for little work, so prefill efficiency drops. And every chunk's attention has to read the K and V of all earlier chunks. Small budgets suit latency-critical chat; large ones suit throughput-heavy batch jobs. Typical values run from about 2K to 16K tokens, depending on the model and the SLO.
Engine specifics

vLLM's V1 engine enables chunked prefill by default and treats --max-num-batched-tokens as the per-step budget; its default depends on version and hardware, so read it from the startup log. SGLang exposes --chunked-prefill-size. llama.cpp's server splits prompts by -b (logical batch) and -ub (physical micro-batch). Older engines without chunking had to set the budget at least as large as the maximum model length, so one long prompt could fill a whole step.

The KV cache memory manager

PagedAttention made KV memory look like an operating system's virtual memory. The block manager is the code that plays the kernel: it hands out fixed-size blocks, keeps a block table per request, tracks reference counts, and keeps a free list.

The data structures

  • Block pool. At startup the engine carves the KV region into \(N_{\text{blocks}}\) blocks of \(B_s\) tokens each, across all layers. Nothing is allocated per request beyond this.
  • Block table per request, a list of physical block ids. It's what the attention kernel walks.
  • Reference counts. A block shared by two sequences has count 2 and is freed only when both release it.
  • Free queue. vLLM V1 keeps free blocks in a queue ordered so that blocks freed longest ago are reused first, and prefix-cache hash entries are dropped when their block is reused. That ordering is what makes eviction approximately LRU.
  • Copy-on-write. Parallel samples and beam search share prompt blocks. When a sequence must write into a block someone else still references, the manager copies that block first. Only the partly filled last block ever needs copying.
$$\htmlClass{t1}{T_{\max}} = \frac{\htmlClass{t2}{M_{\text{GPU}}} \cdot \htmlClass{t3}{u} - \htmlClass{t4}{W} - \htmlClass{t5}{A}}{\htmlClass{t6}{m_{\text{kv}}}}, \qquad \htmlClass{t6}{m_{\text{kv}}} = 2 \cdot \htmlClass{t7}{L \cdot n_{\text{kv}} \cdot d_h \cdot s}$$
\(T_{\max}\)
total tokens of KV the engine can hold across all running requests
\(M_{\text{GPU}}\)

\(u\)
fraction the engine may use (--gpu-memory-utilization, e.g. 0.90)
\(W\)

\(A\)

\(m_{\text{kv}}\)
KV bytes per token: K and V, every layer
\(L, n_{\text{kv}}, d_h, s\)

In wordsWhatever memory is left after weights and workspace becomes KV blocks. Divide by the per-token cost to get the token capacity.

Why it mattersAn 80 GB GPU at \(u = 0.9\) running Llama-3.1-8B in bf16: 72 − 16 − ~4 ≈ 52 GB of KV at 128 KiB per token ≈ 397K tokens. That's about 190 concurrent 2K-token conversations, or 12 at 32K. Switch the KV cache to fp8 and both numbers double.

$$\mathbb{E}[\htmlClass{t1}{w}] \approx \frac{\htmlClass{t2}{B_s} - 1}{2}, \qquad \htmlClass{t3}{f_{\text{waste}}} \approx \frac{\htmlClass{t2}{B_s} - 1}{2\,\htmlClass{t4}{\bar{L}}}, \qquad \htmlClass{t5}{S_{\max}} = \left\lfloor \frac{\htmlClass{t6}{N_{\text{blocks}}}}{\lceil \htmlClass{t4}{\bar{L}} / \htmlClass{t2}{B_s} \rceil} \right\rfloor$$
\(w\)
empty token slots in a sequence's last, partly filled block
\(B_s\)
block size in tokens
\(f_{\text{waste}}\)
fraction of KV memory lost to partly filled blocks
\(\bar{L}\)
average sequence length (prompt plus output so far)
\(S_{\max}\)
maximum number of sequences that fit at once
\(N_{\text{blocks}}\)
blocks in the pool, \(T_{\max} / B_s\)

In wordsIf sequence lengths are spread evenly, the last block is half full on average. Waste is a fixed handful of tokens per sequence, so it matters only when sequences are short.

Why it mattersAt \(B_s = 16\), waste is 7.5 tokens per sequence: 0.4% of a 2K-token conversation. At \(B_s = 128\) it's 63.5 tokens, about 3%. Bigger blocks mean fewer table entries and more efficient kernel memory access but coarser prefix-cache matching (only full blocks are hashed). That's the real tradeoff behind --block-size.

MLE angle · read the startup log before anything else

vLLM logs the KV cache size in tokens and the maximum concurrency at --max-model-len. SGLang logs max_total_num_tokens. Compare that to the widget's prediction: a big mismatch usually means a different activation reserve (raised by a large --max-num-batched-tokens), another process holding GPU memory, or a model whose layers don't all use full attention. Newer engines handle sliding-window and hybrid-attention models with separate KV groups, so capacity per token isn't one number for those.

Preemption under memory pressure

The scheduler admits requests based on the blocks they need now. Their outputs keep growing, one block every \(B_s\) tokens. Eventually a running request needs a new block and the free queue is empty. Something has to give: the scheduler preempts a victim, usually the lowest-priority or most recently admitted running request, frees its blocks, and puts it back at the front of the waiting queue.

There are two ways to bring a preempted request back:

  • Swap. Copy its KV blocks to CPU memory over PCIe and copy them back when there's room. Costs link bandwidth and pinned host memory, no GPU compute.
  • Recompute. Throw the KV away. On resume, treat prompt plus generated-so-far as a new prompt and prefill it again. Costs GPU compute, which other requests could have used. With prefix caching on, part of it may still be cached if those freed blocks haven't been reused yet.
$$\htmlClass{t1}{t_{\text{swap}}} = \frac{2\, \htmlClass{t2}{T}\, \htmlClass{t3}{m_{\text{kv}}}}{\htmlClass{t4}{BW_{\text{link}}}}, \qquad \htmlClass{t5}{t_{\text{recompute}}} \approx \frac{2\htmlClass{t6}{N}\htmlClass{t2}{T} + 2 L d\, \htmlClass{t2}{T}^2}{\htmlClass{t7}{F_{\text{eff}}}}$$
\(t_{\text{swap}}\)
time to move the KV out and back in (the 2 is the round trip)
\(T\)
tokens in the preempted sequence
\(m_{\text{kv}}\)
KV bytes per token
\(BW_{\text{link}}\)
effective GPU↔CPU bandwidth; far below the PCIe peak when copying many small blocks
\(t_{\text{recompute}}\)
time to prefill the sequence again (matmuls plus causal attention, from Module 08)
\(N\)
model parameters
\(F_{\text{eff}}\)
achieved FLOP/s during prefill

In wordsSwapping scales with the bytes of KV. Recomputing scales with the FLOPs to rebuild them, which grow faster than linearly for long sequences.

Why it mattersFor a GQA model, KV is small relative to the compute that produced it: 8K tokens of Llama-3-8B is 1 GiB to move (≈ 86 ms round trip at 25 GB/s) versus ≈ 0.37 s to recompute at 400 TFLOP/s. On paper, swapping wins. The PagedAttention paper found the two comparable at typical block sizes because small-block copies use PCIe poorly, and vLLM's V1 engine preempts by recomputation: it's simpler, needs no pinned host memory, and works with prefix caching.

What preemption does to latency

The victim's user sees a long gap mid-stream: its tokens stop until it's readmitted and re-prefilled, often hundreds of milliseconds to seconds. Everyone else pays too, because the recompute prefill takes budget away from their decodes. And preemption tends to cascade: the readmitted request grows again and triggers the next one. A server that preempts regularly is overcommitted, and the fix is admission control (lower --max-num-seqs, a shorter --max-model-len, fp8 KV, or more GPUs), not a cleverer preemption mode.

Scheduling policies and fairness

  • FCFS (first come, first served) is the default nearly everywhere. Simple and predictable, but one client flooding the server delays everyone behind it.
  • Priority. vLLM's --scheduling-policy priority lets each request carry a priority. Lower-priority requests wait and are preempted first. Useful for mixing interactive and batch traffic on one deployment.
  • Cache-aware ordering. SGLang's lpm policy (longest prefix match, set with --schedule-policy; the default has differed between versions) admits the waiting requests with the most cached tokens first, which raises the hit rate but can starve requests with unique prompts under load.
  • Fair share. Sheng et al. (2024) proposed the Virtual Token Counter: track tokens served per client and admit from whoever has received the least, a token-weighted version of fair queueing. Per-tenant fairness is often enforced one layer up, in the gateway (Module 21).

Prefix caching and RadixAttention

Module 08 covered what prefix caching buys. Here's how the two main designs find a match, and how their eviction behaves under a real workload.

Hashed full blocks (vLLM)

Each full block gets a hash of its tokens chained with the hash of the block before it, plus any extra keys that change the KV (a LoRA adapter id, a multimodal input's hash, a cache salt). Because the hash is chained, block \(k\)'s hash identifies the entire prefix up to and including block \(k\). A new request hashes its prompt block by block and walks the table until the first miss. Partly filled blocks are never shared.

A radix tree of token sequences (SGLang)

RadixAttention (Zheng et al., 2024) stores cached sequences in a radix tree: each edge is a run of tokens, each node points at the KV for that run. Matching is a walk from the root, at token granularity. Each node keeps a reference count (how many running requests use it) and a last-access time. Eviction removes the least recently used leaf with no references, so shared trunks like a system prompt survive while one-off branches go first.

$$\htmlClass{t1}{h_r^{\text{radix}}} = \htmlClass{t2}{\ell_r}, \qquad \htmlClass{t3}{h_r^{\text{block}}} = \htmlClass{t4}{B_s} \left\lfloor \frac{\htmlClass{t2}{\ell_r}}{\htmlClass{t4}{B_s}} \right\rfloor, \qquad \htmlClass{t5}{H} = \frac{\sum_r \htmlClass{t1}{h_r}}{\sum_r \htmlClass{t6}{P_r}}$$
\(h_r\)
prompt tokens of request \(r\) served from cache
\(\ell_r\)
length of the longest prefix of \(r\)'s prompt still resident in the cache
\(h_r^{\text{block}}\)
same, when only full blocks can be matched
\(B_s\)
block size
\(H\)
token hit rate: the fraction of prompt tokens not prefilled
\(P_r\)
prompt length of request \(r\)

In wordsA radix tree reuses the exact shared length. Block hashing rounds it down to a whole number of blocks, losing at most \(B_s - 1\) tokens per request.

Why it mattersThe rounding is small next to the thing that really decides \(H\): whether the prefix is still resident. Prefill time saved is \(H\) times the prompt tokens, so TTFT for a mostly cached 20K-token agent prompt drops by close to \(1/(1-H)\).

Think first: drop the cache to 16K tokens with users interleaved, then switch to one session at a time. Why does the hit rate recover with the same capacity?
Interleaved traffic cycles through all 16 users before any of them returns. Their combined histories exceed 16K tokens, so LRU evicts each user's history shortly before that user comes back, the textbook worst case for LRU on a cyclic access pattern. Only the system prompt, which every request touches, stays resident, and the hit rate falls toward the system prompt's share of each prompt (about 65% here, down from 94%). One session at a time keeps the active user's chain hot, so it recovers. What matters is capacity relative to the working set of conversations that are active at once, not total traffic.
Pitfall · prompts that look identical but tokenize differently

Multi-turn chat resends the previous assistant reply as text. If the chat template rewrites it (strips reasoning, normalizes whitespace) or the text re-tokenizes differently from the tokens originally generated, the match ends there and the rest of the history is prefilled again. Check the hit rate your engine reports (vLLM and SGLang both export prefix-cache metrics) instead of assuming a hit.

MLE angle · the cache is per replica

Prefix caching only helps if the follow-up request reaches the replica holding the prefix. Round-robin load balancing across 8 replicas gives each conversation about a 1-in-8 chance of returning to the right one. KV-aware or session-affinity routing (Module 21) is what turns an engine feature into a fleet-level hit rate.

Speculative decoding inside engines

Module 08 derived the acceptance rule and the expected speedup. Inside an engine, the question is different: where do drafts come from, how are they verified in the same ragged batch as everyone else, and what happens at batch 128 instead of batch 1?

Draft sources

  • Separate draft model. A small model from the same family (same tokenizer). It needs its own weights and its own KV cache, managed alongside the target's.
  • EAGLE (Li et al., 2024). A light head, roughly one transformer layer, that drafts autoregressively from the target model's own hidden states instead of from tokens. Features are easier to predict than tokens, so acceptance is high for a tiny cost. EAGLE-2 builds draft trees dynamically from the head's confidence; EAGLE-3 uses features from several layers.
  • Medusa (Cai et al., 2024). Several extra heads on the last hidden state, each predicting the token \(k\) steps ahead. Their top candidates combine into a tree of continuations.
  • N-gram / prompt lookup. Find the last few generated tokens earlier in the context and propose whatever followed them there. No model at all. Very effective when outputs copy from inputs (code edits, RAG answers that quote, summaries), useless for open-ended writing.

Verification with tree attention

Tree-shaped drafts (Medusa, EAGLE-2) propose several branches at once. The target verifies all of them in one forward pass by flattening the tree into a sequence and using an attention mask in which each draft token sees the context plus its own ancestors only.

$$\htmlClass{t1}{S(B)} = \frac{\htmlClass{t2}{\mathbb{E}[\tau]} \cdot \htmlClass{t3}{t}(B)}{\htmlClass{t3}{t}\big(B(\htmlClass{t4}{\gamma}+1)\big) + \htmlClass{t4}{\gamma}\, \htmlClass{t5}{t_{\text{draft}}}(B)}, \qquad \htmlClass{t2}{\mathbb{E}[\tau]} = \frac{1 - \htmlClass{t6}{\alpha}^{\htmlClass{t4}{\gamma}+1}}{1 - \htmlClass{t6}{\alpha}}$$
\(S(B)\)
speedup in tokens per second over plain decoding at the same batch size
\(\mathbb{E}[\tau]\)
expected tokens produced per sequence per verification step
\(t(\cdot)\)
step time for that many tokens, from the linear cost model
\(\gamma\)
draft tokens per sequence per step
\(t_{\text{draft}}\)
time for one drafting step across the batch
\(\alpha\)
per-token acceptance rate

In wordsYou get \(\mathbb{E}[\tau]\) tokens for the price of one step that is \(\gamma+1\) times wider, plus the drafting. At batch 1 the wide step costs almost the same as a narrow one. At large batch, widening it by 5× costs real compute.

Why it mattersWith the illustrative cost model, \(\alpha = 0.75\), \(\gamma = 4\) and a cheap EAGLE-style draft: about 2.6× at batch 1, about 1.6× at batch 128 with 2K-token contexts. Shorter contexts make the break-even batch arrive sooner, because KV reads (shared across the \(\gamma+1\) verified tokens) are what keep large-batch decode memory-bound. The MagicDec paper (2024) made this long-context argument in detail.

Engine bookkeeping you'll notice

Draft tokens count toward the step's token budget, so speculation competes with prefill chunks. Each request needs KV slots for its drafts before verification. And acceptance is workload-specific: measure it (vLLM logs draft acceptance metrics) on your own traffic before keeping it on. For heavily loaded throughput-oriented deployments, the right setting is often "off".

Structured outputs in the engine

When a request asks for JSON matching a schema, the engine guarantees it by masking: before sampling, every token that would make the output invalid gets its logit set to \(-\infty\). Module 12 covers why agents depend on this. The engine's problem is speed: Llama 3 has 128,256 tokens, and the allowed set depends on the grammar state, which changes after every token.

  • Compile once. The JSON schema or regex is compiled to an automaton (a finite-state machine for regular languages; a pushdown automaton when nesting needs a stack). Outlines (Willard & Louf, 2023) precomputes, for each FSM state, which vocabulary tokens are valid, turning the per-step work into a lookup.
  • Split the vocabulary. XGrammar (Dong et al., 2024) handles full context-free grammars by noting that most tokens' validity depends only on the current grammar position, so it can be precomputed; only a small set of "context-dependent" tokens needs checking at runtime against the automaton's stack.
  • Overlap with the GPU. The mask for step \(t\) depends on the token sampled at step \(t-1\), not on step \(t\)'s logits. So the CPU can compute it while the GPU runs step \(t\)'s forward pass, and apply it just before sampling.
$$\htmlClass{t1}{z'_i} = \htmlClass{t2}{z_i} + \log \htmlClass{t3}{m_i(s)}, \qquad \htmlClass{t4}{t^{\text{serial}}} = \htmlClass{t5}{t_{\text{fwd}}} + \htmlClass{t6}{t_{\text{mask}}}, \qquad \htmlClass{t7}{t^{\text{overlap}}} = \max\!\left(\htmlClass{t5}{t_{\text{fwd}}},\, \htmlClass{t6}{t_{\text{mask}}}\right)$$
\(z'_i\)
logit after masking
\(z_i\)
the model's logit for token \(i\)
\(m_i(s)\)
1 if token \(i\) is allowed in grammar state \(s\), else 0, so \(\log 0 = -\infty\) removes it
\(t^{\text{serial}}\)
step time when the mask is computed after the forward pass
\(t_{\text{fwd}}\)
forward-pass time
\(t_{\text{mask}}\)
CPU time to compute the mask for the whole batch
\(t^{\text{overlap}}\)
step time when the mask is computed during the forward pass

In wordsDisallowed tokens get probability exactly zero. If the mask is ready by the time the logits are, it costs nothing.

Why it mattersA decode step for a mid-size model takes roughly 10–30 ms. A grammar engine that needs 5 ms per sequence on one CPU core can't keep up with a batch of 64 constrained requests, no matter how it's overlapped. Mask speed per sequence, and how many cores compute masks, decide whether structured output is free or a bottleneck.

Pitfall · first-request compile time and forced tokenization

Compiling a big schema can take noticeable time on first use; engines cache compiled grammars, so a schema that changes on every request never benefits. Masks can also force the model into token sequences it rarely produces (splitting a word it would normally emit as one token), which can lower quality. A common pattern is to let the model reason in free text first and constrain only the final answer. In vLLM the backend is selectable (XGrammar and llguidance among them); llama.cpp uses its own GBNF grammars.

Multi-LoRA serving

A team with 50 fine-tuned variants of one base model (Module 10's LoRA) doesn't want 50 deployments. Since a LoRA adapter is only a low-rank update \(\Delta W = BA\), one engine can keep the base weights once and apply a different adapter to each request in the same batch: \(y = xW + x A_i B_i\) for request \(i\)'s adapter.

The hard part is the second term: a batch of 128 tokens might use 20 different adapters, which makes many tiny, mismatched matmuls. Punica (Chen et al., 2023) introduced the SGMV kernel (segmented gather matrix-vector multiplication): sort the batch's rows by adapter, then run one kernel that applies each segment's \(A_i\) (shrink, \(d \to r\)) and \(B_i\) (expand, \(r \to d\)). S-LoRA (Sheng et al., 2023) added a unified memory pool that pages adapter weights and KV cache together, so thousands of adapters can live in CPU memory with only the active ones loaded on the GPU.

$$\htmlClass{t1}{M_{\text{adapter}}} = \htmlClass{t2}{r} \cdot \htmlClass{t3}{L} \cdot \sum_{\htmlClass{t4}{m}} \left(\htmlClass{t5}{d_{\text{in}}^{(m)}} + \htmlClass{t6}{d_{\text{out}}^{(m)}}\right) \cdot \htmlClass{t7}{s}$$
\(M_{\text{adapter}}\)
bytes for one adapter
\(r\)
LoRA rank
\(L\)
layers
\(m\)
adapted modules per layer (q, k, v, o, gate, up, down)
\(d_{\text{in}}^{(m)}\)
input width of module \(m\) (the \(A\) matrix is \(d_{\text{in}} \times r\))
\(d_{\text{out}}^{(m)}\)
output width (the \(B\) matrix is \(r \times d_{\text{out}}\))
\(s\)
bytes per element (2 for bf16)

In wordsEach adapted matrix adds two thin matrices whose combined size is the rank times the sum of its two widths.

Why it mattersLlama-3-8B, rank 16, all seven projections: per layer \(16 \times (8192 + 5120 + 5120 + 8192 + 3 \times 18432) = 1{,}310{,}720\) parameters, times 32 layers ≈ 42M parameters ≈ 84 MB in bf16. About 1% of the base model, so dozens of adapters fit next to the KV cache. FLOPs are similarly small, but the skinny matmuls are memory-bound, so real overhead runs higher than the FLOP ratio suggests.

When not to bother

If one adapter carries nearly all traffic, merge it into the base weights (\(W' = W + BA\)) and serve that: zero overhead. Multi-LoRA pays off when traffic spreads across many adapters. Also note that the prefix cache is keyed by adapter: the same system prompt under two adapters produces different KV, so it's cached twice.

How to choose

A tuning playbook

  1. Fix the workload and the target first. A recorded or synthetic request mix with realistic prompt and output lengths, a fixed arrival rate or concurrency, and a stated SLO such as "p95 TTFT under 1 s, p95 ITL under 50 ms". Without an SLO there's no "better", only "different".
  2. Measure the baseline with the engine defaults: throughput, p50/p95/p99 TTFT and ITL, and the engine's own metrics (queue length, KV usage, preemptions, prefix hit rate).
  3. Read the startup log and check KV capacity against the formula. If concurrency at your real sequence lengths is too low, fix memory first (fp8 KV, shorter max length, quantized weights, more GPUs).
  4. Change one knob at a time and re-run the identical workload. Sweep it across a range rather than trying one value.
  5. Locate the knee. Throughput rises with load until the GPU is compute-bound or KV is full; past that, latency climbs while throughput stays flat. Run just below the knee with headroom for bursts.
  6. Re-check after every model, engine-version, or traffic change. Defaults change between releases.
MLE angle · the three metrics that explain most incidents

Requests waiting (the queue is growing: you're over capacity or KV-bound), KV cache usage near 100% (memory is the limit), and the preemption counter rising (you've overcommitted). vLLM exports these on /metrics as Prometheus gauges and counters; exact names vary by version, so grep for num_requests_waiting, cache_usage, and preemptions. Alert on the trend, not single spikes.

Build a mini engine, then drive real ones

1. A toy continuous-batching server

About 120 lines over a small Hugging Face model. It does the real thing at toy scale: requests arrive over HTTP at any time, the engine thread admits them between steps, decodes all running sequences in one batched forward pass, and retires finished ones immediately. Each sequence keeps its own KV tensors; every step they're left-padded into one batch and split back out afterwards. That copy is exactly the overhead PagedAttention removes, and seeing it makes the block-table design obvious.


# Continuous batching over a small HF model. Run:  python mini_engine.py
import json, queue, threading, time
import torch
import torch.nn.functional as F
from http.server import ThreadingHTTPServer, BaseHTTPRequestHandler
from transformers import AutoModelForCausalLM, AutoTokenizer, DynamicCache

MODEL = "HuggingFaceTB/SmolLM2-360M-Instruct"   # plain Llama architecture, no sliding window
MAX_RUNNING = 8                                  # like --max-num-seqs
dev = "cuda" if torch.cuda.is_available() else "cpu"
tok = AutoTokenizer.from_pretrained(MODEL)
model = AutoModelForCausalLM.from_pretrained(MODEL).to(dev).eval()
EOS = tok.eos_token_id

def to_layers(cache):
    """Cache object -> list of (K, V), each (batch, kv_heads, seq, head_dim)."""
    if hasattr(cache, "layers"):                 # transformers >= 4.56
        return [(l.keys, l.values) for l in cache.layers]
    if hasattr(cache, "key_cache"):              # older DynamicCache
        return list(zip(cache.key_cache, cache.value_cache))
    return list(cache)                           # legacy tuple of tuples

def from_layers(layers):
    cache = DynamicCache()
    for i, (k, v) in enumerate(layers):
        cache.update(k, v, i)
    return cache

class Seq:
    def __init__(self, prompt, max_new):
        text = tok.apply_chat_template([{"role": "user", "content": prompt}],
                                       tokenize=False, add_generation_prompt=True)
        self.ids = tok(text, add_special_tokens=False).input_ids
        self.out, self.kv, self.max_new = [], None, max_new
        self.done = threading.Event()
        self.t_arrive, self.t_first, self.t_done = time.perf_counter(), None, None

    @property
    def cache_len(self):                         # tokens with stored K/V (newest token not yet)
        return len(self.ids) + len(self.out) - 1

    @property
    def finished(self):
        return bool(self.out) and (self.out[-1] == EOS or len(self.out) >= self.max_new)

    def append(self, token):
        if not self.out:
            self.t_first = time.perf_counter()
        self.out.append(token)

waiting, running = queue.Queue(), []

@torch.inference_mode()
def prefill(s):                                  # one request at a time; real engines chunk and batch this
    out = model(input_ids=torch.tensor([s.ids], device=dev), use_cache=True)
    s.kv = to_layers(out.past_key_values)
    s.append(int(out.logits[0, -1].argmax()))
    return s

@torch.inference_mode()
def decode(batch):                               # ONE forward pass for every running sequence
    M = max(s.cache_len for s in batch)
    layers = []
    for li in range(len(batch[0].kv)):           # left-pad each sequence's K/V to length M
        ks = [F.pad(s.kv[li][0], (0, 0, M - s.cache_len, 0)) for s in batch]
        vs = [F.pad(s.kv[li][1], (0, 0, M - s.cache_len, 0)) for s in batch]
        layers.append((torch.cat(ks), torch.cat(vs)))
    mask = torch.zeros(len(batch), M + 1, dtype=torch.long, device=dev)
    for i, s in enumerate(batch):
        mask[i, M - s.cache_len:] = 1            # real past tokens + the new one
    out = model(input_ids=torch.tensor([[s.out[-1]] for s in batch], device=dev),
                attention_mask=mask,
                position_ids=torch.tensor([[s.cache_len] for s in batch], device=dev),
                past_key_values=from_layers(layers), use_cache=True)
    new, nxt = to_layers(out.past_key_values), out.logits[:, -1].argmax(-1).tolist()
    for i, s in enumerate(batch):                # split back out, dropping the padding
        L = s.cache_len + 1
        s.kv = [(k[i:i + 1, :, -L:], v[i:i + 1, :, -L:]) for k, v in new]
        s.append(nxt[i])

def engine_loop():
    while True:
        if not running:                          # idle: block until a request arrives
            running.append(prefill(waiting.get()))
        while len(running) < MAX_RUNNING and not waiting.empty():
            running.append(prefill(waiting.get()))   # iteration-level admission
        live = [s for s in running if not s.finished]
        if live:
            decode(live)
        for s in [s for s in running if s.finished]: # retire immediately, free the slot
            running.remove(s)
            s.kv, s.t_done = None, time.perf_counter()
            s.done.set()

class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        body = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        s = Seq(body["prompt"], int(body.get("max_tokens", 64)))
        waiting.put(s)
        s.done.wait()
        data = json.dumps({"text": tok.decode(s.out, skip_special_tokens=True),
                           "tokens": len(s.out),
                           "ttft_s": round(s.t_first - s.t_arrive, 3),
                           "e2e_s": round(s.t_done - s.t_arrive, 3)}).encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def log_message(self, *args):
        pass

if __name__ == "__main__":
    threading.Thread(target=engine_loop, daemon=True).start()
    print("listening on http://127.0.0.1:8001")
    ThreadingHTTPServer(("127.0.0.1", 8001), Handler).serve_forever()

The prompt fills 62 full blocks plus one block holding 8 tokens: 63 blocks, all shared with reference count 4. Each sample's first write lands in that partly filled block. The first three writers each get a private copy and the last one writes in place, so 63 + 3 = 66. Without sharing it would be 4 × 63 = 252.

Your server runs 200 concurrent requests with short contexts and is already close to compute-bound. You enable EAGLE speculation with 4 draft tokens. What is the most likely result?

  1. Roughly the 2–3× speedup seen at batch 1
  2. No change, because speculative decoding is lossless
  3. Throughput falls and latency may rise: each step now computes about 5× the tokens, and rejected drafts waste that compute
  4. Requests fail because the KV cache doubles
Verification is nearly free only while the step is memory-bound. At high batch with short contexts, widening every sequence to γ + 1 tokens costs real FLOPs, and every rejected draft is compute other requests could have used. Lossless refers to the output distribution, not to speed.
