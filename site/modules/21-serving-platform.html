The serving platform

An engine like vLLM or SGLang turns a GPU into a fast token factory. Whether users ever see that speed depends on everything wrapped around it: the gateway that admits requests, the router that picks a replica, the autoscaler that decides how many replicas exist, the minutes it takes a new one to load 140 GB of weights, and the dashboards that tell you any of this is going wrong. This module is about that wrapper.

The full stack

Module 19 followed one request through an engine. In production, that engine is one box out of six or seven, and the request has already crossed three network hops before it gets there. Here's the whole path, with the parts that run per request (the data plane) separated from the parts that run every few seconds or minutes to keep the fleet in shape (the control plane).

Data plane

Per request, milliseconds matter

Gateway, router, engines. Must be stateless where possible, horizontally scalable, and keep working on cached config if the control plane disappears. Every component here adds latency to every request, so it should do as little as possible.

Control plane

Per minute, correctness matters

Autoscaler, orchestrator (usually Kubernetes), rollout controller, quota and tenant config. Reads metrics, writes desired state. A slow control plane delays scale-up; a broken one should freeze the fleet in place, never tear it down.

The platform's own overhead is small next to the engine's. That's why most serving work is about queueing and GPU time, not about the proxy.

Why it mattersWhen TTFT regresses, the first question is which term grew. Queue time is the usual culprit, and it's a capacity or routing problem, not an engine problem. Instrument each term separately (observability) or you'll tune the wrong thing.

Streaming APIs and cancellation

Nearly every LLM API streams. A 500-token answer at 40 ms per token takes 20 seconds to finish, but the first words show up in under a second. The de facto wire format is the OpenAI-compatible chat completions API over Server-Sent Events (SSE): a plain HTTP response with Content-Type: text/event-stream that stays open while the server writes one data: line per chunk.


curl -N http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "chat", "stream": true, "stream_options": {"include_usage": true},
       "messages": [{"role": "user", "content": "Say hi"}]}'

data: {"id":"chatcmpl-7f3","object":"chat.completion.chunk","model":"chat","choices":[{"index":0,"delta":{"role":"assistant","content":""},"finish_reason":null}]}

data: {"id":"chatcmpl-7f3","object":"chat.completion.chunk","model":"chat","choices":[{"index":0,"delta":{"content":"Hi"},"finish_reason":null}]}

data: {"id":"chatcmpl-7f3","object":"chat.completion.chunk","model":"chat","choices":[{"index":0,"delta":{"content":" there!"},"finish_reason":"stop"}]}

data: {"id":"chatcmpl-7f3","object":"chat.completion.chunk","model":"chat","choices":[],"usage":{"prompt_tokens":9,"completion_tokens":3,"total_tokens":12}}

data: [DONE]

Each event is data: <json> followed by a blank line. The text arrives in choices[0].delta.content, the reason the stream ended in finish_reason, token counts in a final usage chunk if you asked for it with stream_options, and the sentinel [DONE] closes the stream. One chunk can carry more than one token, so counting chunks is only an approximation of counting tokens.

Cancellation frees GPU memory

A request that nobody is reading still holds KV cache and still takes a slot in every decode step. For Llama-3-8B, KV is about 128 KB per token in fp16 (Module 08), so a zombie stream with 8K tokens of context pins 1 GiB of GPU memory. Users abandon requests all the time: they hit stop, close the tab, or the client's own timeout fires and it retries. Without cancellation, a retry doubles the work and the original keeps running.

Current versions of vLLM and SGLang abort a request when the HTTP connection to them closes. The platform's job is to make sure that close propagates: the gateway and router must tie the upstream request's lifetime to the downstream connection, not let it run to completion in the background.

A single "request timeout" is the wrong tool for a stream that can legitimately run for minutes. Use separate limits:

Pitfall · proxies that buffer or time out streams

Two classic production bugs. First, a proxy buffers the response, so the client sees nothing until the whole answer is done and TTFT looks like end-to-end latency. In NGINX, turn off proxy_buffering for these routes (or send X-Accel-Buffering: no). Second, an idle timeout at a load balancer (60 seconds by default on AWS's Application Load Balancer, for example) kills streams that pause, for example a reasoning model whose hidden thinking tokens aren't forwarded. Raise the idle timeout for LLM routes, or have the server send SSE comment lines (: keep-alive) as heartbeats.


import asyncio, httpx
from openai import AsyncOpenAI

client = AsyncOpenAI(
    base_url="http://localhost:8000/v1", api_key="none",
    timeout=httpx.Timeout(connect=5.0, read=60.0, write=10.0, pool=5.0),  # read = max gap between chunks
    max_retries=0,                       # retries are a platform decision, see the reliability section
)

async def ask(prompt: str, deadline_s: float = 120.0) -> str:
    out = []
    async def consume():
        stream = await client.chat.completions.create(
            model="chat", stream=True, max_tokens=800,
            messages=[{"role": "user", "content": prompt}])
        try:
            async for chunk in stream:
                if chunk.choices and chunk.choices[0].delta.content:
                    out.append(chunk.choices[0].delta.content)
        finally:
            await stream.close()          # closes the HTTP connection, so the server aborts the sequence
    await asyncio.wait_for(consume(), timeout=deadline_s)   # total deadline; cancels consume() on expiry
    return "".join(out)

Load balancing for LLMs

Classic web load balancing assumes requests cost about the same, so spreading them evenly spreads work evenly. LLM requests break that assumption badly. One request has a 50-token prompt and stops after 5 tokens; the next has a 60K-token prompt and writes 3,000 tokens. In GPU time they differ by three orders of magnitude or more, and the router can see only half of it up front: the prompt length is known, the output length isn't.

Connections are not requests

A Kubernetes Service (kube-proxy) balances connections at layer 4. HTTP clients keep connections alive and reuse them, so a client with a pooled connection can pin all its traffic to one pod. LLM traffic needs a layer-7 balancer that picks a backend per request, and for streams the connection stays open as long as the answer takes, which makes per-connection balancing even more lopsided.

Prefix affinity matters because prefix caching is per replica. Module 19 showed an engine skipping prefill for a cached prefix; that only helps if the next request with that prefix lands on the same replica. Spread a hot 10K-token system prompt across all replicas and every replica stores its own copy, wasting KV memory the fleet could have used for other prefixes.

$$\htmlClass{t1}{C_{\text{eff}}} = \frac{\htmlClass{t2}{N}\cdot \htmlClass{t3}{C}}{\htmlClass{t4}{\bar k}}, \qquad \htmlClass{t5}{P_{\text{hit}}^{\text{random}}} \approx \frac{1}{\htmlClass{t2}{N}} \;\text{ for a session's next turn}$$
\(C_{\text{eff}}\)
distinct prefix tokens the whole fleet can keep cached
\(N\)
number of replicas
\(C\)
KV capacity per replica left over for cached prefixes, in tokens
\(\bar k\)
average number of replicas holding a copy of each cached prefix: up to \(N\) under round-robin for hot prefixes, close to 1 under affinity
\(P_{\text{hit}}^{\text{random}}\)
chance a conversation's follow-up lands on the replica that holds its history, if routing ignores the cache

In wordsDuplicated prefixes divide your fleet's cache by the duplication factor. With 8 replicas and cache-blind routing, a multi-turn chat finds its own history on the right replica about one time in eight.

Why it mattersAgents resend a growing context every turn. At 1-in-8 hits, each turn re-prefills the whole history; at near-100% hits, each turn prefills only the new message. That's often a 5–10× difference in prefill work for long agent sessions (rule of thumb; it depends on how fast contexts grow).

Affinity without hot spots

Strict hashing (replica = hash(prefix) mod N) breaks when one prefix is popular: every request carrying it lands on one replica. Consistent hashing with bounded loads (Mirrokni, Thorup & Zadimoghaddam, 2016) fixes this. Hash as usual, but if the chosen replica already carries more than \((1+\varepsilon)\) times the average load, walk the hash ring to the next replica. Hot prefixes then occupy two or three replicas instead of melting one. A related trick for metric-driven routing is the power of two choices (Mitzenmacher, 2001): sample two replicas at random and pick the less loaded. It avoids the herd that forms when every router sends to the single "least loaded" replica based on the same stale scrape.

Current open-source routers combine these signals. The Kubernetes Gateway API Inference Extension defines an endpoint picker that scores model servers on queue length, KV utilization, and loaded LoRA adapters; llm-d builds a prefix-cache-aware scheduler on top of it; NVIDIA Dynamo's router estimates KV overlap per worker; SGLang ships a cache-aware router that keeps an approximate radix tree per worker. These projects move fast, so treat the details as examples and check current docs.

Router-side cache state is a guess

The router doesn't see engine evictions directly. It either keeps its own approximate model of what each replica holds (and drifts), or subscribes to engine KV events (more accurate, more plumbing). Either way, check the hit rate the engines themselves report. A router that believes it's achieving 90% hits while the engines report 40% is evicting faster than it thinks.

Queueing theory you need

Three results explain most capacity surprises. You don't need the derivations, but you do need the shapes. The first one, Little's law, was introduced in Module 13; here it does more work.

$$\htmlClass{t1}{L} = \htmlClass{t2}{\lambda}\,\htmlClass{t3}{W}$$
\(L\)
average number of requests in the system (queued + running)
\(\lambda\)
average arrival rate (requests per second)
\(W\)
average time each request spends in the system

In wordsIn-flight work equals arrival rate times time-in-system. It holds for any stable system, regardless of arrival pattern or scheduling.

Why it mattersAt 40 requests/s with an 8-second average response, 320 requests are in flight. If each replica runs at most 64 sequences (--max-num-seqs), you need at least 5 replicas just to hold them, and every one of those 320 sequences holds KV memory. It also works in reverse: measure \(L\) (running + waiting) and \(\lambda\) from metrics and you get \(W\) for free, which is a good sanity check on your latency histograms.

$$\htmlClass{t1}{\rho} = \frac{\htmlClass{t2}{\lambda}}{\htmlClass{t3}{c}\,\htmlClass{t4}{\mu}}$$
\(\rho\)
utilization: fraction of capacity in use. Must stay below 1 or the queue grows without bound
\(\lambda\)
arrival rate
\(c\)
number of servers (replicas, or batch slots)
\(\mu\)
service rate per server: requests per second one server completes, \(1/\tau\) for mean service time \(\tau\)

In words\(\rho = 0.7\) means the fleet is busy 70% of the time on average. The remaining 30% is the slack that absorbs bursts, and the next formula shows how quickly latency grows as that slack shrinks.

$$\htmlClass{t1}{W} = \frac{1}{\htmlClass{t2}{\mu} - \htmlClass{t3}{\lambda}} = \frac{\htmlClass{t4}{\tau}}{1 - \htmlClass{t5}{\rho}}$$
\(W\)
mean time in system (wait + service) for one server with Poisson arrivals and exponential service times
\(\mu\)
service rate
\(\lambda\)
arrival rate
\(\tau\)
mean service time, \(1/\mu\)
\(\rho\)
utilization \(\lambda/\mu\)

In wordsLatency is the service time divided by the spare capacity. With \(\tau = 2\) s: at 50% utilization \(W = 4\) s, at 80% it's 10 s, at 90% it's 20 s, at 95% it's 40 s. Every halving of the spare capacity doubles the wait.

Why it mattersThis is the reason for headroom. The curve is flat for a long time and then turns vertical. The last 10% of utilization costs more latency than the first 80% combined. An LLM server isn't an M/M/1 queue (it batches, and its service rate changes with batch size), so read this for the shape, not the numbers.

$$\htmlClass{t1}{W_q} \approx \frac{\htmlClass{t2}{\rho}}{1-\htmlClass{t2}{\rho}}\cdot\frac{\htmlClass{t3}{c_a^2} + \htmlClass{t4}{c_s^2}}{2}\cdot \htmlClass{t5}{\tau}$$
\(W_q\)
mean time waiting in queue, before service starts
\(\rho\)
utilization
\(c_a^2\)
squared coefficient of variation of inter-arrival times (1 for Poisson, larger for bursty traffic)
\(c_s^2\)
squared coefficient of variation of service times. LLM requests with long-tailed output lengths often have \(c_s\) of 1–3
\(\tau\)
mean service time

In wordsQueueing delay is utilization pressure times variability times service time. Kingman's approximation (1961) covers general single-server queues; with Poisson arrivals (\(c_a^2=1\)) it's the exact Pollaczek–Khinchine result for M/G/1.

Why it mattersMixed request lengths raise \(c_s\), and the wait grows with \(c_s^2\). A workload where some requests generate 10× the median output queues far worse than its average suggests. That's an argument for separating short interactive traffic from long batch traffic, and for chunked prefill, which breaks giant prompts into pieces that don't block everyone else.

The headroom rule

Plan to run at 60–80% of the capacity you measured at your latency target during the peak hour (a rule of thumb, not a law). The headroom absorbs bursts, uneven routing, a replica failing or restarting, and the minutes it takes the autoscaler to react. Pooling helps too: one shared queue in front of \(c\) servers waits far less than \(c\) separate queues at the same utilization, which is the queueing argument for load-aware routing over static assignment.

Where LLM servers differ from textbook queues

An engine is a batch server. Its throughput rises with batch size until compute, KV memory, or your ITL target caps it, and each request's speed falls as the batch grows. So "capacity" isn't a fixed \(\mu\): it's the throughput at the largest batch that still meets your SLO. Measure that by load testing (below) and plug it in as \(c\mu\). The queue also forms in two places: at the router (waiting for a replica) and inside the engine (waiting for KV blocks, visible as num_requests_waiting).

Autoscaling

Traffic follows the sun, product launches, and batch jobs someone forgot to tell you about. Autoscaling adds replicas when demand rises and removes them when it falls. The hard parts are choosing a signal that actually measures load, and living with the minutes it takes a new replica to become useful.

Scale-to-zero

Running zero replicas when idle saves real money for dev environments, rarely used fine-tunes, and batch pipelines. The price is that the first request after idle waits for a full cold start, often minutes for a large model. That's acceptable when the caller is a batch job and unacceptable for a chat UI. Middle grounds: keep one small replica warm, scale to zero only outside business hours, serve rarely used LoRA adapters on a shared base model so they never need their own replica (Module 19), or hold requests at the gateway while a replica boots and return 503 with Retry-After if it takes too long.

Pitfall · scaling down kills streams

When the autoscaler removes a replica, Kubernetes sends SIGTERM. If the pod exits immediately, every in-flight stream on it dies mid-sentence. Scale down slowly (long stabilization windows), mark the pod unready first so the router stops sending new requests, and give it a termination grace period long enough to finish its longest legitimate stream (see the Deployment in the Kubernetes section).

Cold starts

A web service container starts in seconds. An LLM replica can take ten minutes, and almost all of that time is spent moving bytes. Break it down and each part has a different fix.

  1. Node provisioning. If no GPU node has room, the cluster autoscaler requests a VM from the cloud. Minutes, and sometimes the provider has no capacity at all for that GPU type in that zone.
  2. Container image pull. Serving images bundle CUDA, PyTorch, and the engine, often 5–10 GB or more. Pulling and decompressing layers is frequently slower than the raw network.
  3. Weight download. 16 GB for an 8B model in bf16, 140 GB for a 70B. From object storage, Hugging Face, or a model registry.
  4. Load into GPU memory. Read from local disk or page cache, deserialize, copy over PCIe, possibly shard across tensor-parallel GPUs.
  5. Warmup. torch.compile, CUDA graph capture for each batch size, KV cache allocation, a first dummy request. Tens of seconds to a few minutes.
$$\htmlClass{t1}{t_{\text{cold}}} = \htmlClass{t2}{t_{\text{node}}} + \htmlClass{t3}{t_{\text{image}}} + \frac{\htmlClass{t4}{W}}{\htmlClass{t5}{BW_{\text{storage}}}} + \frac{\htmlClass{t4}{W}}{\htmlClass{t6}{BW_{\text{load}}}} + \htmlClass{t7}{t_{\text{warmup}}}$$
\(t_{\text{cold}}\)

\(t_{\text{node}}\)

\(t_{\text{image}}\)
pulling and unpacking the container image: 0 if cached on the node
\(W\)

\(BW_{\text{storage}}\)

\(BW_{\text{load}}\)

\(t_{\text{warmup}}\)

In wordsGet a machine, get the software, get the weights, put them on the GPU, warm up. Written as a sum because that's what a naive startup does; streaming loaders overlap the two weight terms so the slower one dominates.

Why it mattersWorked example (illustrative bandwidths): a 70B bf16 model, \(W = 140\) GB, on a fresh node. 240 s node + 40 s image + 140/1.5 ≈ 93 s download + 140/8 ≈ 18 s load + 60 s warmup ≈ 450 s, about 7.5 minutes. Requests keep arriving the whole time: at 5 req/s, that's over 2,000 requests needing somewhere else to go.

Kubernetes and GPU scheduling

Most self-hosted LLM fleets run on Kubernetes. It doesn't know what a GPU is out of the box. A vendor device plugin (NVIDIA's, AMD's) runs on each GPU node and advertises GPUs as an extended resource such as nvidia.com/gpu: 8. Pods request whole units of it in their resource limits, and the scheduler places them only on nodes with enough free units. The NVIDIA GPU Operator packages the driver, container toolkit, device plugin, and DCGM exporter together.

Placing GPU pods

  • Node pools, taints, and tolerations. Taint GPU nodes (for example nvidia.com/gpu=present:NoSchedule) so ordinary pods don't eat expensive capacity, and add a matching toleration to model servers. Label nodes by GPU type and select on it.
  • Topology. Tensor parallelism across GPUs without NVLink, or across nodes, is much slower. Request a whole 8-GPU node for TP=8, or 4 GPUs for TP=4, and let the device plugin's topology awareness pick NVLink-connected GPUs where it supports that.
  • Shared memory. PyTorch and NCCL use /dev/shm for inter-process communication; the container default (64 MB) breaks tensor-parallel startup. Mount a memory-backed emptyDir.
  • Newer APIs. Dynamic Resource Allocation (DRA) is Kubernetes' more expressive API for devices (requesting GPUs by attributes, sharing, partitions), and has been graduating through recent releases. Expect GPU scheduling to move toward it.

Multi-tenancy, fairness, and security

A shared fleet serves many teams or customers. Without limits, one tenant's batch job of 10,000 long prompts fills every queue and everyone else's TTFT goes to minutes. Multi-tenancy has three layers: quotas (how much each tenant may send), priority (who goes first when there's a queue), and isolation (what one tenant can learn about or do to another).

Rate limiting with a token bucket

The standard limiter is a bucket that holds up to \(b\) tokens and refills at \(r\) tokens per second. Each request removes its cost; if the bucket doesn't have enough, the request is rejected (HTTP 429) or queued. For LLMs, "tokens" can be literal: limit tokens per minute rather than requests per minute, because one request can cost 1,000× another.

$$\htmlClass{t1}{B(t)} = \min\!\big(\htmlClass{t2}{b},\; \htmlClass{t1}{B(t_0)} + \htmlClass{t3}{r}\,(t - t_0)\big), \qquad \text{admit if } \htmlClass{t1}{B(t)} \ge \htmlClass{t4}{c}, \qquad \htmlClass{t5}{A(T)} \le \htmlClass{t2}{b} + \htmlClass{t3}{r}\,T$$
\(B(t)\)
tokens in the bucket at time \(t\) (refilled lazily since the last check at \(t_0\))
\(b\)
burst size: bucket capacity, the most a tenant can send at once after being idle
\(r\)
refill rate: the sustained rate the tenant is entitled to
\(c\)
cost of this request, e.g. prompt tokens + max_tokens, reconciled after it finishes
\(A(T)\)
total cost admitted over any window of length \(T\)

In wordsIdle time banks credit up to a cap. Over any window, a tenant can never get more than one full bucket plus the refill rate times the window.

Why it matters\(r = 2{,}000\) tokens/s (120K tokens per minute) with \(b = 60{,}000\): an idle tenant can fire a 60K-token burst instantly, but sustained traffic is held to 2K tokens/s. The bound \(b + rT\) is what you use to prove the fleet can honour every tenant's quota at once: sum the \(r\)'s and compare against capacity.


import time
from dataclasses import dataclass, field

@dataclass
class Bucket:
    rate: float                 # tokens refilled per second (r)
    burst: float                # capacity (b)
    level: float = field(default=None)
    t_last: float = field(default_factory=time.monotonic)

    def __post_init__(self):
        if self.level is None:
            self.level = self.burst

    def _refill(self):
        now = time.monotonic()
        self.level = min(self.burst, self.level + self.rate * (now - self.t_last))
        self.t_last = now

    def try_take(self, cost: float) -> tuple[bool, float]:
        """Returns (admitted, seconds_until_enough). Caller sends 429 + Retry-After if not admitted."""
        self._refill()
        if self.level >= cost:
            self.level -= cost
            return True, 0.0
        return False, (cost - self.level) / self.rate

    def refund(self, amount: float):
        """Return unused reservation (e.g. max_tokens reserved but generation stopped early)."""
        self._refill()
        self.level = min(self.burst, self.level + amount)

buckets = {"team-search": Bucket(rate=2000, burst=60000), "team-batch": Bucket(rate=500, burst=5000)}

def admit(tenant: str, prompt_tokens: int, max_tokens: int):
    reserved = prompt_tokens + max_tokens
    ok, wait = buckets[tenant].try_take(reserved)
    return ok, wait, reserved

def on_finish(tenant: str, reserved: int, prompt_tokens: int, completion_tokens: int):
    buckets[tenant].refund(reserved - prompt_tokens - completion_tokens)

A single process works for one gateway. With several gateway replicas, keep buckets in a shared store (Redis with an atomic script is the usual approach) or give each gateway \(1/n\) of every tenant's rate and accept some unfairness.

Priority, fairness, and noisy neighbours

  • Priority classes. Interactive traffic first, batch traffic fills the gaps. Some engines accept a per-request priority (vLLM has a --scheduling-policy priority mode), and the router can hold batch requests back when interactive queues grow. Batch work tolerates hours of latency, which makes it the perfect filler for idle GPUs at night.
  • Fair sharing inside the engine. First-come-first-served lets one tenant who sends 500 requests at once delay everyone. Sheng et al. (2024) proposed the Virtual Token Counter, which tracks tokens served per tenant and always schedules the tenant that has received the least service, weighting input and output tokens by their cost.
  • Noisy neighbours. A tenant with 100K-token prompts monopolizes prefill and spikes everyone's ITL. Chunked prefill (Module 19) bounds the damage per step; per-tenant concurrency caps and separate pools for long-context traffic bound it further.
  • LoRA per tenant. Customer-specific fine-tunes as LoRA adapters on a shared base model (Module 19) let hundreds of tenants share one fleet. The router should prefer replicas that already have the tenant's adapter loaded.

Isolation between tenants

Shared prefix caches create a timing side channel: if tenant A's request is fast because its prefix is cached, A learns that someone recently sent that prefix. vLLM supports a per-request cache_salt so that only requests with the same salt share cached blocks; salt per tenant (or per user, for sensitive data). Beyond caches, enforce per-tenant auth at the gateway, cap prompt length and max_tokens there (an unbounded max_tokens is a denial-of-service vector), and never echo one tenant's data into another's logs or metrics.

Handling prompts and data

Prompts contain whatever users paste: credentials, medical details, customer records. Decide retention up front, encrypt logs at rest, restrict who can read raw prompts, and keep them out of metric labels entirely. Details are in the observability section.

Protecting weights

Fine-tuned weights represent training data and compute, and sometimes they memorized sensitive data. Keep them in private storage with credentials scoped to the serving pods, encrypt at rest, and log access. For the highest-sensitivity cases, GPUs from the H100 generation onward support confidential-computing modes that encrypt traffic between the CPU's trusted environment and the GPU; it's a specialized setup with performance and tooling costs.

Supply chain

A replica should start from exactly the bytes you tested. Pin container images by digest (image@sha256:…) rather than by tag, since tags move. Pin model revisions to a commit hash, mirror them into your own storage, and serve offline (HF_HUB_OFFLINE=1) so nothing new is pulled at startup. Record the SHA-256 of every weight file when you publish it and check it before loading. Sign images and model artifacts (Sigstore's cosign is one option) and keep a bill of materials for the serving image.

The file format matters too. Pickle-based checkpoints (.bin, .pt) can execute arbitrary code when loaded; safetensors can't. trust_remote_code=True is the same risk by another name, because it runs Python from the model repository. Review that code, pin it, or avoid it.

Capacity planning and cost

A GPU costs the same per hour whether it's busy or idle. Cost per token is therefore a utilization problem as much as a hardware problem. Module 13 covered the API-versus-self-host break-even; here we size a real fleet against a daily traffic curve.

$$\htmlClass{t1}{c_{\text{1M}}} = \frac{\htmlClass{t2}{P_{\text{hr}}}}{\htmlClass{t3}{X}\times 3600}\times 10^6, \qquad \htmlClass{t3}{X} = \htmlClass{t4}{G_{\text{rep}}}\cdot \htmlClass{t5}{u}$$
\(c_{\text{1M}}\)

\(P_{\text{hr}}\)

\(X\)

Why it mattersAt an illustrative $3/hr and 2,500 tok/s at SLO, a fully busy replica costs 3 ÷ (2,500 × 3,600) × 10⁶ ≈ $0.33 per 1M tokens. Run it at 40% average utilization and it's $0.83. Utilization moves cost as much as the choice of GPU, and diurnal traffic caps it: a fleet sized for a peak that's 3× the daily average can't average much above 33% unless it scales down at night or fills the gaps with batch work.

Reliability engineering

GPUs fail more often than CPUs (memory errors, falling off the bus, NCCL hangs), and engines have bugs. Reliability for LLM serving is mostly ordinary distributed-systems practice, adjusted for requests that hold GPU memory for seconds or minutes while they run.

Health checks: liveness vs readiness

Retries, idempotency, and backoff

Retry only what's safe and useful. Connection failures and 429/503 responses before any token was streamed are retryable on another replica, honouring Retry-After. A stream that fails halfway is not transparently retryable: a fresh request generates different text, so the client would see a duplicated or spliced answer. Surface the error, or resume by sending the partial answer back as context if the product supports it. For requests with side effects (tool calls that send email, charge cards), use an idempotency key so a retry doesn't repeat the action.

Space retries with exponential backoff plus random jitter. "Full jitter" waits a uniformly random time between 0 and \(\min(\text{cap}, \text{base}\cdot 2^n)\) before attempt \(n\) (Brooker, 2015), which keeps clients that failed together from retrying together.

$$\htmlClass{t1}{\mathbb{E}[\text{attempts}]} = \frac{1 - \htmlClass{t2}{p}^{\,\htmlClass{t3}{R}+1}}{1 - \htmlClass{t2}{p}}, \qquad \htmlClass{t4}{M_{\text{worst}}} = (1 + \htmlClass{t3}{R})^{\htmlClass{t5}{k}}$$
\(\mathbb{E}[\text{attempts}]\)
expected attempts per request at one layer
\(p\)
probability an attempt fails
\(R\)
maximum retries per layer
\(M_{\text{worst}}\)
worst-case multiplication of load on the bottom layer
\(k\)
number of layers that each retry independently (client, gateway, router...)

In wordsWhen failures are rare, retries cost almost nothing. When everything fails, every layer multiplies the load: three layers with 2 retries each send up to 27 attempts to the engine for one user request.

Why it mattersOverload causes failures; retries then add load, causing more failures. That feedback loop turns a brief overload into an outage. Retry at one layer only (usually the one closest to the client that can pick a different replica), and use a retry budget: retries may add at most about 10% to the request rate, beyond which they're dropped.

Rollouts, draining, and failover

Model rollouts deserve more caution than code rollouts because a new model can be fast, error-free, and worse. Gate promotion on the online quality signals from Module 13 (judge scores on sampled traffic, user feedback, refusal rate), not just on latency and 5xx. Shadow traffic, where the new version gets a copy of requests and its answers are logged but not returned, lets you compare quality before any user sees it.

$$\htmlClass{t1}{A_{\text{serial}}} = \prod_{\htmlClass{t2}{i}} \htmlClass{t3}{a_i}, \qquad \htmlClass{t4}{A_{\text{redundant}}} = 1 - (1 - \htmlClass{t5}{a})^{\htmlClass{t6}{k}}$$
\(A_{\text{serial}}\)
availability of a chain where every component must work
\(i\)
index over components in the request path
\(a_i\)
availability of component \(i\)
\(A_{\text{redundant}}\)
availability with \(k\) independent copies, any one of which suffices
\(a\)
availability of one copy (e.g. one region)
\(k\)
number of independent copies

In wordsChains multiply down; redundancy multiplies the failure probability down. Gateway 99.95% × router 99.95% × engine pool 99.5% ≈ 99.4%. Two independent regions at 99.5% each give 1 − 0.005² ≈ 99.998% on paper.

Why it mattersThe redundant formula assumes failures are independent and failover is instant. Neither holds in practice: regions share software bugs, bad config pushes, and upstream dependencies, and failover takes time. Treat the result as an upper bound. The second region also needs spare capacity for the failed region's traffic, which for GPUs is expensive and may not exist on demand.

Fallbacks

When the primary model is overloaded or down, a degraded answer usually beats an error. Options, roughly in order of quality: route to the same model in another region, to a smaller or quantized model with more headroom, to a hosted API, to a cached answer for common queries (with the semantic-cache caveats from Module 13), or to a clear "try again shortly" message. Decide the ladder ahead of time, test it regularly, and tag degraded responses in telemetry so they're visible in quality metrics.

Averaging each replica's p95 doesn't give the fleet's p95. Aggregate the histogram buckets first (sum by (le)), then take the quantile, as above. Tracing across the platform

Use OpenTelemetry for spans and propagate context through every hop, including the engine (vLLM can export OpenTelemetry traces when configured with an OTLP endpoint). Record token counts, cached tokens, model and adapter, tenant, and the replica that served the request as span attributes. Sample: tracing every token of every request is expensive; keep all errors and slow requests, and a fraction of the rest.

Logging prompts safely

  • Redact before storage: run a PII and secrets detector at the gateway and replace matches with typed placeholders.
  • Separate the stores: metadata (lengths, latencies, IDs) can live long and be widely readable; raw prompts and completions get short retention and narrow access.
  • Never put prompt text, user IDs, or other unbounded values in metric labels. Besides the privacy problem, every distinct label value creates a new time series and will take down Prometheus.
  • Respect tenant contracts: some customers require zero retention, which means the platform must be able to turn content logging off per tenant.

Dashboards and alerts

One dashboard per model pool with the RED metrics (rate, errors, duration) plus saturation (queue, KV, preemptions), and a fleet view with GPU health. Page on SLO burn rate and on hard failures (all replicas unready, error rate spike). Ticket on slow burns, rising preemptions, falling prefix hit rate, and GPU XID errors. Don't page on GPU utilization.

Benchmarking and load testing

Every number in the capacity formulas (goodput per replica, the latency knee, the headroom you need) comes from a load test. Most load tests in the wild measure the wrong thing. The usual mistakes follow.

Closed loop

N users, each waits for a reply before sending again

Concurrency is fixed, so arrival rate falls automatically when the server slows down. The test can never overload the server, and it hides queueing. Fine for measuring "throughput at concurrency N"; misleading for latency under real traffic.

Open loop

Requests arrive on a schedule, regardless of replies

Usually Poisson arrivals at rate \(\lambda\). When the server slows, requests pile up exactly as they would in production. This is the only way to see the latency explosion near capacity.

$$\Pr[\htmlClass{t1}{\Delta t} \gt t] = e^{-\htmlClass{t2}{\lambda} t}, \qquad \htmlClass{t1}{\Delta t} = -\frac{\ln \htmlClass{t3}{U}}{\htmlClass{t2}{\lambda}}, \quad \htmlClass{t3}{U} \sim \text{Uniform}(0,1)$$
\(\Delta t\)
gap between consecutive arrivals, exponentially distributed with mean \(1/\lambda\)
\(\lambda\)
target arrival rate, requests per second
\(U\)
a uniform random number; the inverse-CDF trick turns it into an exponential gap

In wordsIndependent users produce arrivals with no memory: the time to the next one doesn't depend on how long you've waited. Draw each gap as minus log of a uniform, divided by the rate.

Why it mattersPoisson traffic is bursty in a specific way. At \(\lambda = 5\) req/s, the mean gap is 200 ms, but about 9.5% of gaps are under 20 ms (\(1 - e^{-0.1}\)). Evenly spaced test traffic hides those bursts and makes the server look better than it is. Real traffic is often burstier still; vllm bench serve --burstiness uses a gamma distribution where values below 1 are burstier than Poisson.

The rest of the methodology

  • Realistic lengths. Sample prompt and output lengths from production logs, not a fixed 512 in / 128 out. Long tails dominate the queueing (the \(c_s^2\) term above). Enforce output length with max_tokens plus ignore_eos where the engine supports it, or the model will stop early and flatter your numbers.
  • Realistic prefixes. If production shares system prompts, so should the test, or prefix caching gets no credit. If production doesn't, randomize prompts, or prefix caching gets too much.
  • Warmup. Discard the first minute or so: compilation, cache population, and connection setup distort it.
  • Coordinated omission (Gil Tene's term). If the load generator waits for a slow response before sending the next request, the requests that would have arrived during the stall are never sent, so they never record their terrible latency. Open-loop generation fixes most of it; also measure latency from the scheduled send time, so a load generator that falls behind its own schedule still records the delay.
  • Enough samples for the percentile. A p99 from 200 requests rests on the 2 slowest; use thousands of requests per rate, and report several runs.
  • Measure at SLO. Sweep the arrival rate upward. At each step record throughput, p50/p95/p99 TTFT and ITL. The capacity of the system is the highest rate at which the SLO percentiles still hold, not the highest rate it survived.

Built-in tools are good for engine comparisons. For your own workload, a small custom load generator is worth writing, because you control the prompt mix, the prefix sharing, and exactly what gets measured.


import asyncio, csv, math, random, sys, time
import numpy as np
from openai import AsyncOpenAI

BASE_URL = sys.argv[1] if len(sys.argv) > 1 else "http://localhost:9000/v1"
client = AsyncOpenAI(base_url=BASE_URL, api_key="none", max_retries=0, timeout=300)
MODEL = "chat"
rnd = random.Random(0)

# 16 shared "system prompts" (~1,500 tokens each) with Zipf-like popularity, like a multi-app fleet
SYSTEMS = [f"You are assistant #{k} for product line {k}. " + "Follow the style guide strictly. " * 220
           for k in range(16)]
WEIGHTS = [1 / (k + 1) for k in range(16)]

def sample_request():
    system = rnd.choices(SYSTEMS, weights=WEIGHTS)[0]
    user = f"Ticket {rnd.randrange(10**9)}: summarize the issue and propose a fix. " * rnd.randint(1, 20)
    max_tokens = int(min(1024, rnd.lognormvariate(math.log(150), 0.8)))   # long-tailed outputs
    return system, user, max(16, max_tokens)

async def one_request(t_sched: float, results: list):
    system, user, max_tokens = sample_request()
    first, stamps, ok = None, [], True
    try:
        stream = await client.chat.completions.create(
            model=MODEL, stream=True, max_tokens=max_tokens, temperature=0.7,
            messages=[{"role": "system", "content": system}, {"role": "user", "content": user}],
            extra_body={"ignore_eos": True},            # vLLM: generate exactly max_tokens
        )
        async for chunk in stream:
            if chunk.choices and chunk.choices[0].delta.content:
                now = time.perf_counter()
                first = first or now
                stamps.append(now)
    except Exception:
        ok = False
    end = time.perf_counter()
    itl = np.diff(stamps) if len(stamps) > 1 else np.array([np.nan])
    results.append({
        "t_sched": t_sched, "ok": ok,
        "ttft": (first - t_sched) if first else np.nan,          # from the SCHEDULED time: no coordinated omission
        "itl_p95": float(np.nanpercentile(itl, 95)), "n_chunks": len(stamps), "e2e": end - t_sched,
    })

async def run_rate(rate: float, duration: float = 180.0, warmup: float = 30.0):
    results, tasks = [], []
    t0 = time.perf_counter()
    t_next = t0
    while t_next - t0 < duration:
        delay = t_next - time.perf_counter()
        if delay > 0:
            await asyncio.sleep(delay)
        tasks.append(asyncio.create_task(one_request(t_next, results)))   # fire and forget: open loop
        t_next += -math.log(1.0 - rnd.random()) / rate                     # Poisson inter-arrival
    await asyncio.gather(*tasks)
    keep = [r for r in results if r["t_sched"] - t0 >= warmup]
    good = [r for r in keep if r["ok"]]
    ttft = np.array([r["ttft"] for r in good]); itl = np.array([r["itl_p95"] for r in good])
    meets = np.mean((ttft <= 1.0) & (itl <= 0.05)) if len(good) else 0.0
    span = duration - warmup
    return {"rate": rate, "n": len(keep), "errors": len(keep) - len(good),
            "chunks_per_s": sum(r["n_chunks"] for r in good) / span,
            "ttft_p50": np.nanpercentile(ttft, 50), "ttft_p95": np.nanpercentile(ttft, 95),
            "ttft_p99": np.nanpercentile(ttft, 99), "itl_p95_median": np.nanmedian(itl),
            "slo_attainment": meets, "goodput_rps": meets * len(good) / span}

async def main():
    rows = []
    for rate in [1, 2, 4, 6, 8, 10, 12, 16]:
        row = await run_rate(rate)
        print({k: round(v, 3) if isinstance(v, float) else v for k, v in row.items()}, flush=True)
        rows.append(row)
    with open("sweep.csv", "w", newline="") as f:
        w = csv.DictWriter(f, fieldnames=rows[0].keys()); w.writeheader(); w.writerows(rows)

asyncio.run(main())
Make sure the load generator isn't the bottleneck

One Python process can drive a few hundred concurrent streams before its own event loop starts adding latency. Check client CPU during the run, compare a run at low rate against server-side TTFT metrics (they should agree within milliseconds), and split the load across processes or machines for big sweeps.

2. A router with three policies


import hashlib, itertools, json, os
import httpx
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse

BACKENDS = os.environ.get("BACKENDS", "http://localhost:8001,http://localhost:8002").split(",")
POLICY = os.environ.get("POLICY", "rr")          # rr | least | prefix
PREFIX_CHARS = int(os.environ.get("PREFIX_CHARS", "2000"))
EPS = 0.25                                       # bounded load: at most (1+EPS) x average in-flight

app = FastAPI()
client = httpx.AsyncClient(timeout=httpx.Timeout(None, connect=5.0))
rr = itertools.cycle(range(len(BACKENDS)))
inflight = [0] * len(BACKENDS)

def prefix_key(body: dict) -> int:
    text = json.dumps(body.get("messages", []), sort_keys=True)[:PREFIX_CHARS]
    return int.from_bytes(hashlib.sha256(text.encode()).digest()[:8], "big")

def pick(body: dict) -> int:
    n = len(BACKENDS)
    if POLICY == "least":
        return min(range(n), key=lambda i: inflight[i])
    if POLICY == "prefix":
        start = prefix_key(body) % n
        cap = (1 + EPS) * (sum(inflight) + 1) / n
        for step in range(n):                    # walk the ring until a replica is under the cap
            i = (start + step) % n
            if inflight[i] + 1 <= cap or step == n - 1:
                return i
    return next(rr)

@app.post("/v1/chat/completions")
async def chat(req: Request):
    body = await req.json()
    i = pick(body)
    inflight[i] += 1
    try:
        upstream = await client.send(
            client.build_request("POST", BACKENDS[i] + "/v1/chat/completions", json=body), stream=True)
    except Exception:
        inflight[i] -= 1
        raise

    async def relay():
        try:
            async for chunk in upstream.aiter_raw():
                yield chunk
        finally:                                 # runs on normal end AND on client disconnect
            await upstream.aclose()              # closing upstream makes the engine abort the sequence
            inflight[i] -= 1

    return StreamingResponse(relay(), status_code=upstream.status_code,
                             media_type=upstream.headers.get("content-type"),
                             headers={"x-backend": str(i)})

# run:  POLICY=prefix uvicorn router:app --port 9000

The prefix key hashes the first 2,000 characters of the serialized messages. With long system prompts that's effectively "which system prompt", so requests sharing one go to the same replica. With short system prompts it starts including user text and degrades toward session affinity. Try a few values of PREFIX_CHARS, and think about why hashing token blocks (as engines do) would be more precise.

Little's law: \(L = \lambda W = 30 \times 10 = 300\) requests in flight. 300 / 48 = 6.25, so at least 7 replicas, before any headroom. With 70% target utilization you'd want 10.

A replica's utilization goes from 80% to 90%. Using the M/M/1 model as intuition, what happens to mean time in system?

  1. It roughly doubles
  2. It rises by about 12%
  3. It stays the same until 100%
  4. It rises by 10 percentage points
\(W = \tau/(1-\rho)\): at 0.8 it's \(5\tau\), at 0.9 it's \(10\tau\). Halving the spare capacity doubles the wait, which is why the last stretch of utilization is so expensive in latency.

You autoscale on GPU utilization with a 70% target. Under moderate traffic, what most likely happens?

  1. The fleet stays right-sized
  2. The fleet scales to zero

The standard GPU utilization metric is the fraction of time any kernel is running. Decode launches kernels continuously, so it saturates long before the GPU is out of capacity. Scale on in-flight requests or queue depth instead.

A closed-loop load test with 32 concurrent users reports p99 TTFT of 0.8 s. Production at the same average throughput sees p99 TTFT of 6 s. What's the most likely explanation?

  1. Production uses a different tokenizer
  2. The test machine had a faster GPU
  3. The closed loop throttled its own arrivals when the server slowed, hiding queueing; real traffic is open-loop and bursty
  4. p99 can't be measured with 32 users
In a closed loop, a slow response delays the next request, so the queue never grows and the slow periods are under-sampled (coordinated omission). Open-loop Poisson arrivals keep coming during stalls, as real users do.

The client SDK, the gateway, and the router each retry failed requests up to 2 times. During an overload where nearly every attempt fails, how many attempts can one user request generate at the engine?

  2. 27
  3. 9
  4. 3
Each layer makes up to 3 attempts, and they nest: \((1+2)^3 = 27\). That multiplication is how retries turn overload into an outage. Retry at one layer, with a budget.
